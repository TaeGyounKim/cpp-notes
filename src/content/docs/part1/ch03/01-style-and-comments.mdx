- 문법이 아니라 습관에 관한 장. 정답이 하나가 아니고, 팀마다 규칙이 다름. 여러 방식을 알아 두면 낯선 코드를 만나도 당황하지 않음

## 왜 스타일이 중요한가

- 급하게 짠 코드와 잘 다듬은 코드는 둘 다 동작함. 다듬는 데는 시간이 더 듦. 그 시간이 아깝지 않은 이유는?
- 미리 생각해 볼 것: 1년 뒤에 새로 온 사람이 이 코드를 넘겨받는다면
  - 문서도 없고 몇 화면씩 이어지는 함수뿐이라면 그 사람은 어떻게 익힐까
  - 그 "새로 온 사람"은 1년 뒤의 나일 수도 있음. 그때의 나는 지금의 생각을 기억하지 못함
- 잘 쓴 코드는 읽고 이해하기 쉬워서 이런 문제를 미리 막음

## 주석을 쓰는 이유

- 여기서 문서화란 소스 파일 안의 주석을 말함
- **주석** (comment): 코드를 쓸 때 머릿속에 있던 것 가운데, 코드만 봐서는 알 수 없는 것을 적어 두는 곳 <CppRef path="cpp/comment" />

### 이유 1: 쓰는 법을 알리려고

- 함수가 무엇을 하는지는 원래 이름, 반환 타입, 매개변수의 이름과 타입만 보고 알 수 있어야 함
- 그래도 코드로는 표현할 수 없는 것이 있음. 이런 것은 주석으로만 알릴 수 있음

| 코드로 표현할 수 없는 것 | 뜻 |
| --- | --- |
| **사전 조건** (precondition) | 함수를 부르기 전에 부르는 쪽이 지켜야 하는 조건 |
| **사후 조건** (postcondition) | 함수가 끝났을 때 함수가 보장하는 조건 |
| 던지는 예외 | 어떤 상황에서 어떤 예외가 던져지는지 |
| 반환값의 뜻 | 타입만으로는 그 값이 무엇을 나타내는지 알 수 없을 때 |
| 뜻밖의 매개변수 | 예: 왜 `const` 참조가 아니라 그냥 참조로 받는지 |

- 주석을 달지 말지의 기준: 이름과 타입만으로 알 수 없는 **쓸모 있는 정보**가 있을 때만
  - 이름이 이미 말해 주는 것을 되풀이하는 주석은 쓰지 않음. `// 기록을 저장한다` + `saveRecord()`
- 일부 회사의 규칙: 밖으로 공개된 함수에는 모두 정해진 형식의 주석을 달 것. 경험이 적은 사람도 빠뜨리지 않게 하려는 것
- 더 나은 길: 주석 대신 타입으로 말하기
  - 반환 타입이 `int`면 "이 정수는 저장된 기록의 번호"라는 주석이 필요함
  - 반환 타입을 `RecordId` 같은 전용 타입으로 바꾸면 주석이 필요 없음
- 공개 주석에는 **동작**을 적고 **구현**은 적지 말 것
  - 적을 것: 입력, 출력, 오류 상황과 그 처리, 쓰임새, 성능 보장
  - 적지 말 것: 안에서 어떤 알고리즘으로 계산하는지. 쓰는 사람에게 필요 없는 정보이고, 가장 흔한 실수

- 볼 것: `withdraw`의 주석은 이름과 타입으로 알 수 없는 것만 적음. 인수의 조건, 던지는 예외, 실패했을 때 잔액이 그대로라는 보장

### 이유 2: 복잡한 코드를 설명하려고

- 실무의 코드에는 알고리즘이 복잡하거나, 보기만 해서는 의도를 알기 어려운 부분이 있음
- 그런 곳에 적을 것
  - 어떤 알고리즘인지와 큰 흐름
  - 헷갈릴 만한 줄이 왜 그렇게 쓰였는지
  - **불변식** (invariant): 그 코드가 실행되는 동안 항상 참이어야 하는 조건. 반복문에 대한 것은 반복 불변식(loop invariant)

<RunCode client:load code={algorithmCode} />

- 볼 것
  - 함수 위의 주석: 쓰는 법(정렬되어 있어야 한다는 사전 조건, 반환값의 뜻)
  - 함수 안의 주석: 구간을 어떻게 줄여 가는지, 반복 불변식, `low + (high - low) / 2`라고 쓴 이유
  - 주석을 지우고 읽어 보면 차이를 알 수 있음

### 이유 3: 코드 밖의 정보를 남기려고 (옛 방식)

- 오래된 코드에서 보게 되는 주석: 작성자, 작성일, 변경 내역, 관련 버그 번호 같은 **메타 정보**

```cpp
// 2001-04-13 | REQ #005: 값을 정규화하지 않도록 변경
// 작성자: kim
// 버그 #142 때문에 추가 - lee 110428
```

- 지금은 쓰지 않음. 새 코드에 넣지 말 것
  - 이유: 버전 관리 시스템이 이 일을 더 정확하게 해 줌. 누가 언제 무엇을 왜 바꿨는지가 변경 하나하나에 기록됨
  - 변경은 요청이나 버그 수정 단위로 나눠서, 설명을 붙여 커밋할 것
  - 버전 관리: 28장에서 다룸
- 저작권 표시: 회사에 따라 모든 파일의 맨 위에 넣도록 정해 둔 곳이 있음. 표시하지 않아도 저작권은 생기지만 회사 규칙이면 따름

## 주석의 방식

### 줄마다 주석 달기

- 문서화가 모자라는 것을 막으려고 모든 줄에 주석을 다는 방식
- 큰 규모에서는 번잡하고 지루하며 대부분 쓸모가 없음
- 가장 나쁜 예: 코드를 그대로 말로 옮긴 주석

```cpp
if (result % 2 == 0) {   // result를 2로 나눈 나머지가 0이면
```

- 조금 나은 주석: **왜** 그 계산을 하는지를 말함

```cpp
if (result % 2 == 0) {   // result가 짝수이면
```

- 가장 나은 방법: 이름 붙은 함수로 바꿈. 주석이 필요 없어지고 다른 곳에서도 쓸 수 있음

```cpp
bool isEven(int value) { return value % 2 == 0; }

if (isEven(result)) {
```

- 줄마다 주석이 정말 필요한 경우도 있음: 코드만으로는 도저히 알 수 없을 때. 예: 외부 문서의 표나 공식에서 온 값과 계산. 이때도 번역이 아니라 "무슨 일이 일어나는지"를 적고, 근거 문서를 가리킬 것

### 파일 머리 주석

- 모든 소스 파일의 맨 위에 넣는 정해진 형식의 주석

| 넣어도 되는 것 | 넣지 말 것 (버전 관리 시스템이 맡는 일) |
| --- | --- |
| 저작권 정보 | 마지막 수정일 |
| 그 파일이나 클래스에 대한 짧은 설명 | 처음 작성한 사람 |
| | 변경 내역 |
| | 관련 기능 번호 |

- 아직 구현하지 않은 기능, 알려진 버그: 예전에는 여기에 적었지만 지금은 버그·기능 추적 시스템에서 관리

### 정해진 형식의 주석

- 주석을 정해진 형식으로 쓰면 도구가 그것을 읽어 문서를 자동으로 만들어 줌
- C++에서 널리 쓰는 도구: Doxygen. 주석에서 HTML 문서, 클래스 관계도 등을 만듦

```cpp
/**
 * 과일 바구니 하나를 나타낸다.
 */
class Basket
{
public:
    /**
     * @param capacity 담을 수 있는 최대 개수. 1 이상이어야 한다.
     * @throws std::invalid_argument capacity가 0일 때
     */
    Basket(std::size_t capacity);

    /**
     * 과일 하나를 담는다.
     * @param weight 과일의 무게(그램).
     * @return 담은 뒤 남은 자리의 개수.
     */
    std::size_t add(double weight);
};
```

- `@param`, `@return`, `@throws`: Doxygen이 알아보는 표시
- 도구를 쓰더라도 쓸모없는 주석은 쓰지 말 것
  - 위 생성자의 주석에는 "Basket의 생성자"라는 설명이 없음. 이름이 이미 말해 주기 때문

### 그때그때 다는 주석

- 대부분의 주석은 필요할 때 코드 중간에 다는 것. 지침

| 지침 | 이유 |
| --- | --- |
| 주석을 달기 전에, 코드를 고쳐서 주석이 필요 없게 만들 수 있는지 먼저 볼 것 | 이름 바꾸기, 순서 바꾸기, 이름 붙은 중간 변수 넣기 |
| 다른 사람이 읽는다고 상상하고, 바로 보이지 않는 미묘한 점을 적을 것 | |
| 이름 머리글자를 적지 말 것 | 버전 관리 시스템이 기록함 |
| 쓰임이 바로 드러나지 않는 API를 쓸 때는 그 문서를 가리킬 것 | |
| 코드를 고치면 주석도 고칠 것 | 틀린 주석이 달린 코드만큼 헷갈리는 것이 없음 |
| 주석으로 함수를 구역별로 나누고 있다면, 함수를 여러 개로 쪼갤 수 있는지 볼 것 | |
| 남을 깎아내리는 말을 쓰지 말 것 | 누가 읽게 될지 알 수 없음 |

## 자기 문서화 코드

- **자기 문서화 코드** (self-documenting code): 주석 없이도 읽으면 뜻이 드러나는 코드
- 가장 좋은 코드는 읽히도록 쓴 코드. 줄마다 주석을 달고 있다면 코드를 고쳐 쓸 때라는 신호
- 방법
  - 함수, 매개변수, 변수, 클래스에 뜻이 드러나는 이름 붙이기
  - 바뀌지 않는 것에 `const` 붙이기
  - 함수 안의 단계를 읽기 좋은 순서로 놓기
  - 계산 중간 결과에 이름 붙은 변수를 두기
  - 코드를 작은 조각으로 나누기 (다음 글)
- C++은 컴퓨터에 일을 시키는 언어이지만, 읽는 사람에게 뜻을 전하는 데에도 쓸 수 있음

- 볼 것: `isLeapYear`라는 이름 덕분에 `main`에는 주석이 거의 필요 없음. 윤년 규칙을 아는 사람이 아니어도 `main`을 읽을 수 있음

## 헷갈리기 쉬운 점

- 주석은 많을수록 좋은 것이 아님
  - 코드가 이미 말하는 것을 되풀이하는 주석은 읽을 것만 늘리고, 코드가 바뀌면 틀린 주석이 됨
- "무엇을"이 아니라 "왜"를 적을 것
  - 무엇을 하는지는 코드에 있음. 왜 그렇게 했는지는 코드에 없음
- 주석이 필요하다고 느껴지는 순간이 코드를 고칠 기회
  - 이름을 바꾸거나 함수로 빼면 주석이 필요 없어지는 경우가 많음
- 공개 함수의 주석과 함수 안의 주석은 읽는 사람이 다름
  - 공개 함수의 주석: 그 함수를 쓰는 사람. 동작만 알면 됨
  - 함수 안의 주석: 그 함수를 고칠 사람. 구현을 알아야 함

## 정리

| 요소 | 핵심 |
| --- | --- |
| 좋은 스타일 | 문서화, 분해, 이름 짓기, 언어 기능의 활용, 서식 |
| 쓰는 법을 알리는 주석 | 사전·사후 조건, 예외, 반환값의 뜻. 동작만 적고 구현은 적지 않음 |
| 복잡한 코드를 설명하는 주석 | 알고리즘의 흐름, 불변식, 헷갈리는 줄의 이유 |
| 메타 정보 주석 | 쓰지 않음. 버전 관리 시스템에 맡김 |
| 정해진 형식의 주석 | Doxygen 같은 도구가 문서를 만들어 줌 |
| 자기 문서화 코드 | 좋은 이름, `const`, 작은 함수로 주석 없이 읽히게 |

- 사전 조건과 사후 조건
- 어떤 상황에서 어떤 예외를 던지는지

<details>
<summary>`// i를 1 올린다` 같은 주석이 나쁜 이유는?</summary>

- 코드를 말로 옮겼을 뿐, 새로운 정보가 없음
- 왜 올리는지를 적거나, 적을 것이 없으면 주석을 지움

</details>

<details>
<summary>작성자와 수정일을 주석으로 남기지 않는 이유는?</summary>

- 버전 관리 시스템이 변경마다 누가, 언제, 왜 바꿨는지를 자동으로 기록함
- 손으로 적은 정보는 빠지거나 틀리기 쉬움

</details>

<details>
<summary>공개 함수의 주석에 내부 알고리즘을 자세히 적으면 안 되는 이유는?</summary>

- 그 주석을 읽는 사람은 함수를 쓰는 사람. 필요한 것은 동작(입력, 출력, 오류)
- 구현을 적어 두면 구현을 바꿀 때마다 주석도 바꿔야 하고, 쓰는 쪽이 구현에 기대게 됨

</details>

<details>
<summary>`if (age >= 19 && !banned && balance > 0)`를 주석 없이 읽히게 고치려면?</summary>

- 조건에 이름을 붙임. 예: `bool canPurchase(...)` 함수로 빼거나 `const bool canPurchase{ ... };` 변수에 담음
- `if (canPurchase)`로 읽히면 주석이 필요 없음

</details>
