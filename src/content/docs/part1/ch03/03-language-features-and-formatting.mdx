## 언어 기능을 스타일 있게 쓰기

- C++은 읽을 수 없는 코드도 얼마든지 쓰게 해 줌

```cpp
int r{ i++ + ++i };
```

- 읽기 어려운 것보다 큰 문제: 이 식의 동작은 표준이 정하지 않음 (**미정의 동작**, undefined behavior)
  - `i++`는 `i`의 값을 쓰면서 `i`를 1 올리는 부수 효과가 있음
  - 그 올림이 문장 안의 어느 시점에 일어나는지를 표준이 정하지 않음. `++i`가 어떤 값의 `i`를 보게 될지 알 수 없음
  - 컴파일러와 플랫폼에 따라 결과가 다를 수 있음
- 평가 순서 <CppRef path="cpp/language/eval_order" />

```cpp
a[i] = ++i;
```

- 이 식은 C++17부터 동작이 정해져 있음 <Badge text="C++17" />
  - 대입에서는 오른쪽을 모두 계산한 뒤에 왼쪽을 계산함. `i`를 먼저 올리고, 올린 값을 `a[i]`의 번호로 씀
  - 그래도 쓰지 말 것. 읽는 사람이 이 규칙을 기억하고 있어야만 읽히는 코드
- 컴파일러의 도움: GCC는 `-Wall` 옵션에서 두 식 모두에 "operation on 'i' may be undefined" 경고를 냄
- 언어의 힘을 좋은 스타일 쪽으로 쓰는 방법 세 가지를 이어서 봄

### 상수를 쓸 것

- **매직 넘버** (magic number): 코드에 설명 없이 박혀 있는 숫자. `2.71828`, `24`, `3600`
  - 읽는 사람은 그 값이 무엇인지, 왜 그 값인지 추측해야 함
- 해결: 바뀌지 않는 값에 이름을 붙임

```cpp
const int HoursPerDay{ 24 };
const int SecondsPerHour{ 3'600 };
```

- 수학 상수는 직접 적지 말고 표준 라이브러리의 것을 씀 <Badge text="C++20" /> <CppRef path="cpp/numeric/constants" />
  - 헤더 `<numbers>`, 네임스페이스 `std::numbers`
  - `pi`, `e`, `sqrt2`, `phi` 등

<RunCode client:load code={constantsCode} />

- 볼 것
  - `badToSeconds`의 `86400`은 계산해 봐야 뜻을 알 수 있음. `HoursPerDay * SecondsPerHour`는 읽으면 앎
  - `3.14159`는 자릿수가 모자란 근삿값. `std::numbers::pi`는 `double`이 담을 수 있는 가장 가까운 값
- 상수의 다른 이점: 값을 바꿔야 할 때 한 곳만 고치면 됨

### 포인터 대신 참조를 쓸 것

- 배경: C에서는 "원본을 넘기는" 방법이 포인터뿐이었음. C++에는 참조가 있고, 많은 경우 포인터를 참조로 바꿀 수 있음
- 참조의 이점

| 이점 | 설명 |
| --- | --- |
| 더 안전함 | 메모리 주소를 직접 다루지 않고, `nullptr`일 수 없음 |
| 더 읽기 좋음 | 보통 변수와 같은 문법. 넘길 때 `&`, 쓸 때 `*`가 필요 없음 |
| 소유 관계가 분명함 | 참조로 받은 객체는 읽거나 바꿀 수 있지만 그 메모리를 해제할 방법은 없음. "해제는 내 일이 아님"이 분명 |

- 해 볼 것: 마지막 줄의 주석을 풀고 실행
  - 결과: 컴파일 오류. 참조에는 `nullptr`을 넘길 수 없음
- 흔한 반론: "호출하는 곳에 `&`가 보이면 그 함수가 객체를 바꾼다는 것을 알 수 있다. 참조는 그게 안 보인다"
  - 틀린 생각. 포인터로 넘겨도 매개변수가 `const T*`면 바꾸지 않음
  - 바꾸는지 아닌지는 매개변수 타입이 정함

| 매개변수 타입 | 객체를 바꿀 수 있는가 |
| --- | --- |
| `T*`, `T&` | 있음 |
| `const T*`, `const T&` | 없음 |

- 결론: 포인터든 참조든 함수의 선언을 봐야 알 수 있음
- 포인터가 여전히 필요한 경우: "없음"을 나타내야 할 때, 가리키는 대상을 바꿔야 할 때 (1장의 [참조](../../ch01/13-references/))
- 포인터와 소유: 요즘 C++에서는 보통 포인터(raw pointer)는 소유하지 않는다는 뜻으로 읽고, 소유는 스마트 포인터로 나타냄. 7장에서 다룸

### 직접 만든 예외를 쓸 것

- C++에서는 예외를 무시하기 쉬움. 문법이 예외 처리를 강제하지 않음
- 예외 없이 오류를 알리는 전통적인 방법: 특별한 값을 돌려줌(`-1`, `nullptr`), 오류 표시 변수를 둠
  - 약점: 부르는 쪽이 검사를 잊으면 오류가 조용히 묻힘
  - 보완: `[[nodiscard]]`를 붙이면 반환값을 버릴 때 컴파일러가 경고함 <Badge text="C++17" /> <CppRef path="cpp/language/attributes/nodiscard" />
- 예외는 더 풍부한 수단. 직접 만든 예외 타입에는 오류에 관한 정보를 원하는 만큼 담을 수 있음
  - 예: 웹 브라우저의 예외라면 오류가 난 페이지 주소, 그때의 네트워크 상태 등

- 볼 것
  - `UnknownServiceError`는 표준 예외 `std::runtime_error`를 물려받아 만든 타입 <CppRef path="cpp/error/runtime_error" />
  - `catch`에서 메시지(`what()`)뿐 아니라 문제가 된 서비스 이름(`getService()`)도 꺼낼 수 있음
- 아직 배우지 않은 문법: 클래스 물려받기(`: public ...`)는 10장, 예외를 자세히 다루는 것은 14장

## 서식

- **서식** (formatting): 들여쓰기, 공백, 중괄호 위치처럼 동작과 상관없는 코드의 겉모양
- 서식 논쟁은 팀을 갈라놓을 만큼 흔하고 격렬함
- 기본 원칙

| 상황 | 할 일 |
| --- | --- |
| 조직에 서식 표준이 있음 | 마음에 들지 않아도 따름. 적어도 다툴 일은 없음 |
| 표준이 없음 | 도입을 제안함. 이름 규칙과 서식이 통일되면 코드가 고르게 되고 읽기 쉬워짐 |
| 저마다 자기 방식대로 쓰고 있음 | 되도록 너그럽게. 취향일 뿐인 것과 협업을 실제로 어렵게 하는 것을 구별 |

- 자동 서식 도구: 정해 둔 규칙대로 코드를 고쳐 줌. 저장할 때나 커밋하기 직전에 돌아가게 설정하는 것이 보통
  - 널리 쓰는 도구: clang-format. 통합 개발 환경에도 대부분 같은 기능이 들어 있음

### 중괄호의 위치

- 가장 자주 다투는 주제: 블록을 여는 중괄호를 어디에 둘 것인가
- 방식 1: 여는 중괄호를 앞 문장과 같은 줄에. 단, 함수와 클래스는 다음 줄에 (이 사이트의 예제가 쓰는 방식)

```cpp
void check(int value)
{
    if (value > 0) {
        std::println("양수");
    } else {
        std::println("양수가 아님");
    }
}
```

- 방식 2: 여는 중괄호를 언제나 새 줄에

```cpp
void check(int value)
{
    if (value > 0)
    {
        std::println("양수");
    }
    else
    {
        std::println("양수가 아님");
    }
}
```

- 방식 3: 중괄호까지 들여쓰기

```cpp
void check(int value)
{
    if (value > 0)
        {
            std::println("양수");
        }
    else
        {
            std::println("양수가 아님");
        }
}
```

- 비교: 방식 1은 세로 공간을 아낌. 방식 2는 블록의 시작과 끝이 같은 열에 놓여 눈에 잘 띔
- 또 하나의 논점: 문장이 하나뿐일 때 중괄호를 생략할 것인가

```cpp
if (value > 0)
    std::println("양수");
else
    std::println("양수가 아님");
```

- 생략하지 않는 쪽의 근거
  - 나중에 문장을 한 줄 더 넣을 때 실수하지 않음. 들여쓰기만 맞춰 넣으면 그 줄은 `if`에 속하지 않음
  - 잘못 만든 C 스타일 매크로가 여러 문장으로 펼쳐질 때의 사고를 막음. 매크로: 11장에서 다룸
- 고르는 기준: 코드를 보기만 해도 어느 블록이 어느 조건에 속하는지 알 수 있는가

### 공백과 괄호

- 한 줄 안의 서식도 방식이 여럿
- 방식 1: 키워드 뒤, 연산자 앞뒤, 쉼표 뒤에 공백. 계산 순서를 드러내는 괄호 (이 사이트의 예제가 쓰는 방식)

```cpp
if (i == 2) {
    j = i + (k / m);
}
```

- 방식 2: `if`를 함수처럼 붙여 쓰고, 뜻에 영향이 없는 괄호는 생략

```cpp
if( i == 2 ) {
    j = i + k / m;
}
```

- 참고: `if`는 함수가 아니라 키워드. 방식 1이 그 차이를 겉모양으로 드러냄

### 공백, 탭, 줄바꿈

- 들여쓰기에 공백을 쓸지 탭을 쓸지는 취향만의 문제가 아님. 팀이 정하지 않으면 실제로 문제가 생김

| 문제 | 설명 |
| --- | --- |
| 화면이 어긋남 | 탭의 폭은 편집기 설정마다 다름. 한 사람은 4칸, 다른 사람은 8칸으로 보면 같은 파일의 정렬이 서로 다르게 보임 |
| 병합이 어려워짐 | 한 사람이 파일 전체의 들여쓰기를 바꾸는 동안 다른 사람이 같은 파일을 고치면, 버전 관리 시스템이 두 변경을 합치지 못할 수 있음 |

- 기억할 것: 탭은 폭이 정해져 있지 않고, 공백은 언제나 한 칸
- 대부분의 편집기는 Tab 키를 눌렀을 때 공백을 넣도록 설정할 수 있음
- 줄바꿈 문자도 플랫폼마다 다름

| 플랫폼 | 줄바꿈 |
| --- | --- |
| Windows | `\r\n` |
| Linux, macOS | `\n` |

- 여러 플랫폼에서 함께 작업한다면 어느 쪽을 쓸지 정해야 함. 편집기 설정이나 버전 관리 시스템의 자동 변환 기능으로 맞춤

## 스타일을 지켜 나가기

- 새 프로젝트를 시작할 때의 다짐: 바뀌지 않는 것에는 전부 `const`, 이름은 전부 분명하게, 중괄호와 탭은 전부 규칙대로
- 이 수준을 끝까지 지키기는 어려움. 이유 두 가지

### const가 무너지는 과정

- 상황: `const` 매개변수를 받는 함수를 쓰는 중. 그 안에서 `const`가 빠진 오래된 함수를 불러야 함
- 오래된 함수를 고칠 수 있으면 고치는 것이 가장 좋음. 다른 회사의 라이브러리라서 고칠 수 없다면?

| 대응 | 결과 |
| --- | --- |
| 내 함수의 `const`를 뗌 | 내 함수를 부르는 함수의 `const`도 떼야 함. 연쇄적으로 번져서 `const`를 쓰지 않는 프로그램이 됨 |
| 그 호출 한 곳에서만 `const_cast`로 `const`를 잠시 뗌 | 나머지 코드의 `const`는 그대로 남음 |

- `const_cast` <CppRef path="cpp/language/const_cast" />
  - 조건: 그 함수가 인수를 바꾸지 않는다는 것이 확실할 때만
  - 정말로 `const`인 객체를 `const_cast`를 거쳐 바꾸면 미정의 동작

### 취향과 표준이 부딪칠 때

- 엄격한 규칙을 강제하기 어려운 팀도 있음
- 현실적인 방법
  - 꼭 통일해야 하는 것(변수 이름 규칙, 탭)과 개인에게 맡겨도 되는 것(공백 넣는 방식, 주석 방식)을 나눔
  - 스타일 위반을 자동으로 고치거나 표시해 주는 도구를 씀. 설정한 규칙대로 자동 서식을 해 주는 개발 환경이라면 규칙을 지키는 데 힘이 들지 않음

## 헷갈리기 쉬운 점

- `a[i] = ++i`는 C++17부터 괜찮으니 써도 된다?
  - 동작이 정해졌을 뿐 읽기 쉬워진 것은 아님. GCC는 C++23 옵션에서도 여전히 경고함. 두 문장으로 나눠 쓸 것
- 호출하는 곳에 `&`가 있으면 그 객체가 바뀐다?
  - 매개변수가 `const T*`면 바뀌지 않음. 참조든 포인터든 선언을 봐야 앎
- 탭 한 번과 공백 네 칸은 같다?
  - 내 편집기에서만 같아 보임. 탭의 폭은 보는 사람의 설정이 정함
- `const_cast`는 `const`를 없애 주는 편리한 도구다?
  - 고칠 수 없는 옛 코드를 부를 때만 쓰는 마지막 수단. 원래 `const`인 객체를 바꾸는 데 쓰면 미정의 동작
- 서식은 사소하니 각자 편한 대로 하면 된다?
  - 한 사람이 쓸 때는 사소함. 여럿이 같은 파일을 고칠 때는 병합 충돌과 읽기 어려움으로 돌아옴

- 3장에서 다룬 것: 문서화, 분해, 이름 짓기, 언어 기능의 활용, 서식
- 어떤 스타일 규칙이 좋은지를 재는 기준: 얼마나 널리 받아들여졌는가, 코드를 얼마나 읽기 쉽게 하는가
- 팀으로 일한다면 스타일은 프로젝트 초기에, 언어와 도구를 정할 때 함께 정할 것
- 익힐 습관
  - 코드를 남에게 내놓기 전에 스타일을 한 번 훑어볼 것
  - 다른 사람의 코드에서 좋은 스타일을 알아보고 쓸모 있는 관례를 받아들일 것
- 한 문장으로: 읽는 사람을 위해 쓸 것. 그 사람은 대개 미래의 나

## 정리

| 요소 | 핵심 |
| --- | --- |
| 읽을 수 없는 식 | 한 식에서 같은 변수를 바꾸면서 또 쓰지 않음 |
| 상수 | 매직 넘버에 이름을 붙임. 수학 상수는 `std::numbers` |
| 참조 | `nullptr`이 될 수 없고, 보통 변수처럼 쓰며, 소유하지 않는다는 뜻이 분명 |
| 직접 만든 예외 | 오류에 관한 정보를 실어 보냄 |
| 중괄호·공백 | 방식은 여럿. 팀이 하나로 통일 |
| 탭과 줄바꿈 | 통일하지 않으면 화면이 어긋나고 병합이 어려워짐 |
| `const_cast` | 고칠 수 없는 옛 함수를 부를 때, 그 호출 한 곳에서만 |

## 복습 질문

<details>
<summary>`int seconds{ days * 86400 };`을 더 읽기 좋게 고치려면?</summary>

- 이름 붙은 상수를 씀
- `const int SecondsPerDay{ 24 * 3'600 };`을 두고 `days * SecondsPerDay`

</details>

<details>
<summary>함수가 객체를 반드시 받아야 할 때, 포인터보다 참조로 받는 것이 나은 이유 두 가지는?</summary>

- `nullptr`을 넘길 수 없으므로 함수 안에서 검사할 필요가 없음
- 넘기는 쪽과 쓰는 쪽 모두 보통 변수와 같은 문법을 씀

</details>

<details>
<summary>`process(&data);`라는 호출만 보고 `data`가 바뀐다고 단정할 수 없는 이유는?</summary>

- 매개변수가 `const Data*`일 수 있음
- 바뀌는지는 함수의 선언(매개변수 타입의 `const` 여부)을 봐야 알 수 있음

</details>

<details>
<summary>문장이 하나뿐인 `if`에도 중괄호를 쓰자는 쪽의 근거는?</summary>

- 나중에 문장을 추가할 때, 들여쓰기만 맞추고 중괄호를 빠뜨리는 실수를 막음
- 여러 문장으로 펼쳐지는 매크로가 들어와도 안전함

</details>

<details>
<summary>팀에서 들여쓰기에 탭과 공백을 섞어 쓰면 생기는 문제는?</summary>

- 탭의 폭이 편집기마다 달라서 정렬이 사람마다 다르게 보임
- 들여쓰기만 바뀐 변경이 섞여서 병합이 어려워짐

</details>

<details>
<summary>`const`가 빠진 외부 라이브러리 함수를 `const` 매개변수로 불러야 할 때의 올바른 대응은?</summary>

- 그 함수가 인수를 바꾸지 않는다는 것을 확인한 뒤, 그 호출에서만 `const_cast`를 씀
- 내 함수의 `const`를 떼지 않음. 떼기 시작하면 부르는 쪽으로 계속 번짐

</details>
