## 분해

- **분해** (decomposition): 코드를 더 작은 조각으로 나누는 일
- 가장 읽기 힘든 코드: 300줄짜리 함수, 여러 겹으로 중첩된 블록
- 원칙: 함수 하나는 한 가지 일만 함. 복잡한 하위 작업은 따로 함수로 뺌
- 판단 기준 (엄밀한 과학이 아님. 어림 규칙)

| 기준 | 설명 |
| --- | --- |
| 설명해 보기 | "먼저 A를 하고, B를 한 다음, C이면 D를 하고 아니면 E를 한다"라고 답하게 되면 A~E가 각각 함수여야 할 가능성이 큼 |
| 길이 | 함수 하나가 한 화면(인쇄하면 한 쪽)을 넘지 않게. 다만 짧아도 나눠야 하는 코드가 있음 |
| 눈을 가늘게 뜨고 보기 | 내용을 읽지 않고 모양만 볼 때, 어느 한 곳이 유난히 빽빽하면 나눌 곳 |

### 리팩터링으로 분해하기

- 코드가 빽빽해지는 두 가지 경로
  - 몰입해서 빠르게 짤 때: 동작은 하지만 보기 좋지 않은 코드가 나옴. 누구에게나 있는 일
  - 시간이 지나면서: 요구 사항이 바뀌고 버그를 고칠 때마다 작은 수정이 덧붙음
- **크러프트** (cruft): 이렇게 조금씩 쌓여서, 깔끔했던 코드를 땜질과 예외 처리의 더미로 만드는 코드
- **리팩터링** (refactoring): 동작은 그대로 두고 코드의 구조를 고치는 일
- 대표적인 리팩터링 기법

| 목적 | 기법 | 하는 일 |
| --- | --- | --- |
| 더 추상화하기 | 데이터 멤버 캡슐화 | 데이터 멤버를 `private`으로 바꾸고 getter·setter로 접근하게 함 |
| | 타입 일반화 | 더 일반적인 타입을 만들어 코드를 더 많이 함께 쓰게 함 |
| 더 논리적인 조각으로 나누기 | 멤버 함수 추출 | 큰 멤버 함수의 일부를 새 멤버 함수로 뺌 |
| | 클래스 추출 | 클래스의 일부 코드를 새 클래스로 옮김 |
| 이름과 위치 바로잡기 | 멤버 함수·데이터 멤버 옮기기 | 더 알맞은 클래스나 소스 파일로 옮김 |
| | 멤버 함수·데이터 멤버 이름 바꾸기 | 목적이 더 잘 드러나는 이름으로 바꿈 |
| | 위로 올리기 (pull up) | 기반 클래스로 옮김 |
| | 아래로 내리기 (push down) | 파생 클래스로 옮김 |

- 기반 클래스와 파생 클래스: 10장에서 다룸
- 리팩터링은 주기적으로 해야 함. 코드를 다시 들여다볼 때마다 분해가 알맞은지 볼 것
- 리팩터링의 전제: 고치다가 생긴 결함을 잡아 줄 테스트가 있어야 함
  - 단위 테스트(unit test)가 특히 잘 맞음. 30장에서 다룸

### 설계로 분해하기

- 처음부터 나눠서 짜는 방법: 함수를 쓸 때 "이 가운데 나중으로 미룰 수 있는 부분은 무엇인가"를 생각함
  - 미룬 부분은 일단 이름만 정해 함수로 부르고, 그 함수는 나중에 채움
  - 모든 기능을 그 자리에서 끝까지 구현하는 것보다 덜 빽빽하고 정돈된 코드가 됨
- 그래도 코드를 쓰기 전에 설계가 먼저. 설계: 4장에서 다룸

## 이름 짓기

### 언어의 규칙

- **식별자** (identifier): 변수, 함수, 타입 등에 붙이는 이름 <CppRef path="cpp/language/identifiers" />

| 규칙 | 예 |
| --- | --- |
| 쓸 수 있는 글자: 대문자, 소문자, 숫자, 밑줄 | `userName2`, `user_name` |
| 영어 알파벳이 아닌 글자도 가능 | `합계` |
| 숫자로 시작할 수 없음 | `9to5`는 오류 |
| 밑줄 두 개가 이어진 이름은 쓰면 안 됨 | `my__name` |
| 밑줄 + 대문자로 시작하는 이름은 쓰면 안 됨 | `_Name` |
| 전역 네임스페이스에서 밑줄로 시작하는 이름은 쓰면 안 됨 | 전역의 `_name` |

- 아래 세 줄: 컴파일러와 표준 라이브러리가 쓰려고 **예약된 이름** (reserved name)
  - 주의: 써도 컴파일 오류나 경고가 나지 않음. 그래도 어느 날 라이브러리 내부의 이름과 부딪칠 수 있으므로 쓰지 않음
- 한글 같은 글자의 이름: 문법상 가능하지만, 편집기·도구·협업 환경에 따라 불편할 수 있어 실무에서는 대개 영어로 지음
- 이 규칙들 말고는 자유. 이름은 오직 사람을 위해 있는 것

### 좋은 이름 고르기

- 가장 좋은 이름: 그 대상의 목적을 정확히 설명하는 이름
- 시험 방법: 다른 사람이 그 이름을 보고 내가 전하려던 뜻을 알아듣는가
- 정해진 법칙은 없고 조직에서 통하는 규칙이 있을 뿐. 그래도 거의 언제나 나쁜 이름은 있음

| 좋은 이름 | 나쁜 이름 | 나쁜 이유 |
| --- | --- | --- |
| `sourceName`, `destinationName` | `thing1`, `thing2` | 너무 일반적. 둘이 구별되지 않음 |
| `m_nameCounter` | `m_NC` | 너무 줄여서 알 수 없음 |
| `calculateTotalPrice()` | `doAction()` | 무엇을 하는지 말하지 않음 |
| `m_typeString` | `typeSTR256` | 읽기 어려움 |
| `g_settings` | `m_boringMeeting` | 내용과 상관없는 농담 |
| `errorMessage` | `string` | 타입만 말하고 뜻을 말하지 않음 |
| `sourceFile`, `destinationFile` | `srcFile`, `dstFile` | 줄임말 |

### 이름 규칙

- 이름을 지을 때마다 창의력이 필요한 것은 아님. 널리 쓰는 관례가 있음

#### 반복 카운터

- 관례: 반복 카운터는 `i`, 안쪽 반복은 `j`
- 중첩 반복문에서 흔한 실수: `j`번째를 써야 할 곳에 `i`번째를 씀
- 2차원 데이터에서는 `row`, `column`처럼 뜻이 있는 이름이 안전

<RunCode client:load code={loopsCode} />

- 볼 것: `table[row][column]`은 틀리게 쓰면 눈에 띔. `table[j][i]`는 틀려도 눈에 띄지 않음

#### 접두사

- 이름 앞에 타입이나 쓰임을 알리는 글자를 붙이는 방식

| 접두사 | 예 | 뜻 | 쓰임 |
| --- | --- | --- | --- |
| `m`, `m_` | `mData`, `m_data` | member | 클래스의 데이터 멤버 |
| `s`, `ms`, `ms_` | `sLookupTable`, `ms_lookupTable` | static | static 변수나 static 데이터 멤버 |
| `k` | `kMaximumLength` | konstant (독일어의 "상수") | 상수. 접두사 없이 쓰는 사람도 있음 |
| `b`, `is` | `bCompleted`, `isCompleted` | Boolean | 참·거짓 값 |

- 접두사에 반대하는 의견도 많음
  - 이유: 코드가 바뀌면 이름도 다 바꿔야 함. 예: static 멤버를 일반 멤버로 바꾸면 그 이름을 쓰는 모든 곳을 고쳐야 함
  - 고치지 않으면 이름이 틀린 정보를 전하게 됨. 정보가 없는 이름보다 나쁨
- 실제로는 고를 수 없는 경우가 많음. 회사나 프로젝트의 규칙을 따름
- 이 사이트의 예제: 데이터 멤버에 `m_`를 붙임

#### 헝가리안 표기법

- **헝가리안 표기법** (Hungarian notation): 한 글자 접두사 대신 더 자세한 접두사로 타입 정보를 담는 방식. Windows 프로그래밍에서 널리 쓰였음

```cpp
char* pszName;   // psz: pointer to string, zero-terminated
```

- 이름의 유래: 고안한 사람(Charles Simonyi)이 헝가리 사람
- 싫어하는 사람이 많은 이유: 코드가 외국어처럼 보임. 타입을 바꾸면 이름도 바꿔야 함
- 이름을 잘 지으면 `m_` 같은 접두사 말고는 덧붙일 정보가 거의 없음. `m_name`이면 충분

#### getter와 setter

- 데이터 멤버 `m_status`에 대한 관례
  - 값을 읽는 함수(getter): `getStatus()`
  - 값을 바꾸는 함수(setter): `setStatus()`. 필요할 때만 둠
  - 참·거짓 멤버는 `get` 대신 `is`: `isRunning()`
- 언어가 정한 것이 아니라 관례. 조직마다 비슷한 규칙을 정해서 씀

#### 대소문자

- 여러 방식이 있고, 어느 것이든 **팀이 하나로 통일해서 쓰는 것**이 중요

| 방식 | 모양 | 흔한 쓰임 |
| --- | --- | --- |
| 소문자와 밑줄 (snake case) | `priority_queue`, `my_queue` | 표준 라이브러리의 모든 이름 |
| 단어마다 대문자 (Pascal case) | `PriorityQueue` | 클래스 이름 |
| 첫 단어만 소문자 (camel case) | `myQueue`, `getStatus` | 변수, 데이터 멤버, 함수 |

- 함수 이름: 대문자로 시작하는 관례도 있고(`GetStatus`) 소문자로 시작하는 관례도 있음(`getStatus`)
- 이 사이트의 예제: 클래스는 대문자로, 함수와 변수는 소문자로 시작. 함수와 클래스가 이름만으로 구별됨

#### 네임스페이스로 나눈 상수

- 문제 상황: 메뉴의 번호를 상수로 둠. 도움말 메뉴의 상수 이름은 `Help`가 자연스러움. 그런데 도움말 버튼의 번호도 `Help`라고 짓고 싶음
- 해결 1: 상수를 네임스페이스로 나눔. `Menu::Help`, `Button::Help`
- 해결 2(권장): 범위 있는 열거형을 씀. `MenuId::Help`, `ButtonId::Help`
  - 이름이 나뉘는 데 더해 타입도 달라져서, 메뉴를 받는 함수에 버튼 번호를 넘기는 실수를 컴파일러가 잡음

## 헷갈리기 쉬운 점

- 분해하면 코드가 짧아진다?
  - 전체 줄 수는 대개 늘어남. 줄어드는 것은 한 번에 머리에 담아야 하는 양
- 예약된 이름을 썼는데 컴파일이 잘 됨
  - `_Name`, `my__name`은 오류도 경고도 없이 컴파일됨. 그래도 규칙 위반이고, 컴파일러나 라이브러리를 바꿨을 때 문제가 드러날 수 있음
- 접두사가 붙은 이름은 정보가 많아서 무조건 좋다?
  - 코드가 바뀌었는데 이름을 고치지 않으면 틀린 정보가 됨. 팀의 규칙에 있는 접두사만 쓸 것
- 리팩터링은 기능을 고치는 일이 아님
  - 동작은 그대로 두고 구조만 바꿈. 기능 변경과 섞으면 무엇 때문에 깨졌는지 알기 어려움

## 정리

| 요소 | 핵심 |
| --- | --- |
| 분해 | 함수 하나는 한 가지 일. 복잡한 하위 작업은 함수로 뺌 |
| 리팩터링 | 동작은 그대로, 구조만 고침. 테스트가 뒷받침해야 함 |
| 이름의 규칙 | 숫자로 시작 불가. 밑줄 두 개, 밑줄+대문자 시작은 예약됨 |
| 좋은 이름 | 목적을 정확히 설명. 줄임말·일반적인 말·농담을 피함 |
| 접두사 | `m_`, `s`, `k`, `is` 등. 팀의 규칙을 따름 |
| getter / setter | `getStatus()`, `setStatus()`, `isRunning()` |
| 같은 이름의 상수 | 네임스페이스보다 `enum class` |

- 나머지 둘은 컴파일되지만 예약된 이름이므로 쓰면 안 됨

</details>

<details>
<summary>`int d;`라는 변수에 "지난 날짜 수"가 담긴다면 더 나은 이름은?</summary>

- `elapsedDays`처럼 무엇을 세는지 드러나는 이름
- 이름이 뜻을 말하면 `// 지난 날짜 수` 같은 주석이 필요 없음

</details>

<details>
<summary>`Menu::Help`(네임스페이스의 `int` 상수)보다 `MenuId::Help`(`enum class`)가 나은 이유는?</summary>

- 타입이 따로 생겨서, 메뉴를 받는 함수에 버튼 값을 넘기면 컴파일 오류가 남
- `int` 상수는 서로 섞어 써도 컴파일러가 알 수 없음

</details>
