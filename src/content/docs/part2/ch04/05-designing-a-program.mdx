- 다루는 것: 4장에서 배운 것을 모아, 작은 프로그램 하나의 설계를 처음부터 끝까지 해 보기
- 이 글에서 배우는 요소: 설계의 다섯 단계, MVC 구조, 하위 시스템 표, 클래스 계층을 둘 곳과 두지 않을 곳, 오류 처리 설계

- 읽는 법: 아직 배우지 않은 개념(클래스 계층, 패턴)이 나옴. 지금은 설계가 어떤 순서로 진행되는지를 보고, 뒤의 장을 공부한 다음 다시 읽으면 더 많이 보임

## 출발점: 요구 사항

- 설계를 시작하기 전에 기능과 성능에 대한 요구 사항이 분명해야 함. 요구 사항 명세로 문서화되어 있는 것이 이상적
- 오목 프로그램의 요구 사항 (실제로는 더 자세하고 더 많음)
  - 프로그램은 기본 오목 규칙을 지원한다
    - 15×15 판, 흑이 먼저 둔다
    - 가로·세로·대각선 가운데 한 방향으로 같은 색 돌 다섯 개를 먼저 이으면 이긴다
  - 프로그램은 사람 두 명이 번갈아 두는 것을 지원한다. 컴퓨터 상대는 제공하지 않는다
  - 프로그램은 텍스트 인터페이스를 제공한다
    - 판과 돌을 글자로 그린다
    - 둘 자리는 행과 열의 번호를 입력해서 정한다
- 요구 사항의 역할: 프로그램이 사용자가 기대하는 대로 동작하도록 설계의 방향을 잡아 줌

## 설계의 단계

- 원칙: 일반적인 것에서 구체적인 것으로 내려감
- 아래 단계가 모든 프로그램에 그대로 들어맞지는 않지만 길잡이가 됨

| 단계 | 정하는 것 |
| --- | --- |
| 1. 하위 시스템으로 나누기 | 큰 덩어리와 그 사이의 인터페이스 |
| 2. 스레드 구조 고르기 | 큰 단위의 스레드 수와 상호 작용 |
| 3. 클래스 계층 정하기 | 하위 시스템마다 어떤 계층을 둘지 |
| 4. 클래스, 자료 구조, 알고리즘, 패턴 정하기 | 하위 시스템마다의 상세 |
| 5. 오류 처리 정하기 | 하위 시스템마다 시스템 오류와 사용자 오류를 다루는 방법 |

- 그림과 표를 알맞게 넣을 것. 그림의 업계 표준은 UML: 클래스 다이어그램, 시퀀스 다이어그램 등 여러 가지 표준 그림을 정의함
- UML 문법을 엄격히 지키는 것보다 **알아보기 쉬운 그림**이 더 중요함

## 1단계: 하위 시스템으로 나누기

- 할 일: 프로그램을 기능에 따라 큰 덩어리로 나누고, 덩어리 사이의 인터페이스와 상호 작용을 정함
- 이 단계에서 신경 쓰지 않는 것: 자료 구조, 알고리즘, 클래스. 지금은 부분들과 그 사이의 관계를 대강 잡는 것이 목적

### MVC로 나누기

- 추천하는 구조: 데이터를 **저장하는 것**과 **보여 주는 것**을 분명히 나눔
- **MVC** (Model-View-Controller): 많은 프로그램이 "데이터, 그 데이터를 보여 주는 화면, 그 데이터를 바꾸는 조작"으로 이루어진다는 점에 착안한 구조

| 구성 요소 | 뜻 | 오목에서는 |
| --- | --- | --- |
| **모델** (model) | 데이터와 그 규칙 | 판에 놓인 돌, 승패 판정 |
| **뷰** (view) | 모델을 보여 주는 한 가지 방법 | 판을 글자로 그리기 |
| **컨트롤러** (controller) | 어떤 사건에 반응해 모델을 바꾸는 코드 | 사용자의 입력을 받아 돌을 놓기 |

- 세 요소는 되먹임 고리를 이룸: 조작 → 컨트롤러가 모델을 바꿈 → 뷰가 바뀜 → 사용자가 보고 다시 조작
- 이 구조의 이점: 요소들이 분명히 나뉘어 있어, 하나를 고칠 때 다른 것을 건드리지 않아도 됨
  - 예: 모델과 규칙에는 손대지 않고 텍스트 화면을 그래픽 화면으로 바꿈. PC용 화면과 휴대폰용 화면을 따로 둠

### 하위 시스템 표

- 표에 적는 것: 하위 시스템의 이름, 개수, 하는 일, 다른 하위 시스템에 **내놓는** 인터페이스, 다른 하위 시스템에서 **가져다 쓰는** 인터페이스

| 하위 시스템 | 개수 | 하는 일 | 내놓는 인터페이스 | 가져다 쓰는 인터페이스 |
| --- | --- | --- | --- | --- |
| Game | 1 | 게임을 시작함. 차례를 돌림. 승자를 알림. 게임을 끝냄 | 게임 진행 | Player의 "차례 진행", Board의 "승리 확인", BoardView의 "그리기" |
| Board | 1 | 놓인 돌을 저장함. 승리와 무승부를 판정함 | 돌 읽기, 돌 놓기, 승리 확인 | 없음 |
| BoardView | 1 | 판을 그림 | 그리기 | Board의 "돌 읽기" |
| Player | 2 | 사용자에게 둘 자리를 묻고 입력을 받음. 돌을 놓음 | 차례 진행 | Board의 "돌 읽기", "돌 놓기" |
| ErrorLogger | 1 | 오류 메시지를 로그 파일에 기록함 | 오류 기록 | 없음 |

- MVC로 보면: Board는 모델, BoardView는 뷰, Player는 컨트롤러
- 이것이 유일한 답은 아님. 설계에는 같은 목표에 이르는 길이 여럿 있고, 더 나은 것과 못한 것이 있지만 똑같이 타당한 해법이 여러 개인 경우도 많음
- 좋은 나누기의 기준: 프로그램의 기본 기능 단위대로 나뉘었는가
  - Player를 Game에 합치지 않은 이유: 논리적으로 다른 것. 차례를 관리하는 일과 한 사람의 입력을 받는 일은 따로 바뀜
- 표만으로는 관계가 잘 보이지 않음. 하위 시스템을 상자로, 호출을 선으로 그린 그림을 함께 두면 좋음. 이 설계의 호출 관계

| 부르는 쪽 | 불리는 쪽 |
| --- | --- |
| Game | Player, Board, BoardView |
| Player | Board |
| BoardView | Board |
| 모두 | ErrorLogger |

- 볼 것: Board는 불리기만 하고, Game·Player·BoardView 가운데 어느 것도 부르지 않음. 모델은 화면도 입력도 모름. 그래서 화면이나 입력 방식을 바꿔도 Board는 그대로

## 2단계: 스레드 구조 고르기

- 이 단계에서 정하는 것: 프로그램의 큰 단위 스레드가 몇 개이고 서로 어떻게 상호 작용하는가
  - 큰 단위 스레드의 예: 화면을 맡는 스레드, 소리를 재생하는 스레드, 네트워크 통신 스레드
  - 아직 정하지 않는 것: 알고리즘 안의 특정 반복문을 어떻게 병렬로 돌릴지. 그러기엔 이름
- 지침

| 지침 | 이유 |
| --- | --- |
| 스레드끼리 공유하는 데이터를 되도록 없앨 것 | 설계가 단순하고 안전해짐 |
| 공유를 피할 수 없으면 잠금 규칙을 설계에 적을 것 | |
| 멀티스레드에 익숙하지 않거나 플랫폼이 지원하지 않으면 단일 스레드로 | |
| 서로 나란히 진행될 수 있는 뚜렷한 작업이 여럿이면 멀티스레드를 고려 | 예: 그래픽 프로그램에서 주된 작업을 하는 스레드와 사용자의 버튼 입력을 기다리는 스레드 |

- 오목 프로그램: 게임의 흐름을 맡는 스레드 하나면 충분
- 멀티스레드 프로그래밍: 27장에서 다룸

## 3단계: 클래스 계층 정하기

- 이 단계에서 정하는 것: 프로그램에 둘 클래스 계층
- **클래스 계층** (class hierarchy): 공통된 것을 담은 기반 클래스와 그것을 물려받아 구체화한 파생 클래스들의 관계. 5장에서 자세히 다룸

### 계층을 두는 곳

- BoardView: 판을 보여 주는 방법이 여럿일 수 있음

| 클래스 | 역할 |
| --- | --- |
| `BoardView` | 추상 기반 클래스. "판을 그릴 수 있다"만 약속 |
| `ConsoleBoardView` | 콘솔에 글자로 그림 |
| `GraphicalBoardView` | 창에 그림으로 그림. 지금은 요구 사항에 없지만 나중에 추가할 자리가 있음 |

- Player: 수를 정하는 방법이 여럿일 수 있음

| 클래스 | 역할 |
| --- | --- |
| `Player` | 추상 기반 클래스. "차례를 진행할 수 있다"만 약속 |
| `ConsolePlayer` | 콘솔에서 좌표를 입력받음 |
| `ScriptedPlayer` | 미리 정해 둔 수를 차례로 둠. 자동 테스트용 |

### 계층을 두지 않는 곳

- 돌: 흑돌과 백돌은 색만 다르고 동작이 같음. 클래스 계층을 둘 이유가 없음
  - `enum class Stone { None, Black, White }`면 충분
- 비교: 장기나 체스처럼 말마다 움직이는 규칙이 다른 게임이라면, 말에 계층을 두는 것이 자연스러움. 공통 기반 클래스 `Piece`와 말 종류별 파생 클래스
- 교훈: 계층은 **동작이 종류마다 다를 때** 둠. 값만 다르면 데이터 멤버나 열거형으로 충분

## 4단계: 클래스, 자료 구조, 알고리즘, 패턴 정하기

- 이 단계: 더 자세한 수준으로 내려가 하위 시스템마다의 상세를 정함. 하위 시스템 하나가 그대로 클래스 하나가 되는 경우도 많음

| 하위 시스템 | 클래스 | 자료 구조 | 알고리즘 | 패턴 |
| --- | --- | --- | --- | --- |
| Game | `Game` | `Board` 하나, `Player` 둘에 대한 참조, `BoardView`에 대한 참조 | 두 플레이어에게 번갈아 차례를 줌 | 의존성 주입 (플레이어와 뷰를 밖에서 받음) |
| Board | `Board` | 15×15 격자. 칸마다 `Stone` 하나. 한 줄로 편 `std::vector<Stone>` | 방금 놓은 자리에서 네 방향으로 이어진 같은 색 돌을 셈 | 없음 |
| BoardView | `BoardView` 추상 기반 클래스, `ConsoleBoardView` | 없음. 그릴 때마다 `Board`에서 읽음 | 격자를 한 줄씩 출력 | 전략 |
| Player | `Player` 추상 기반 클래스, `ConsolePlayer`, `ScriptedPlayer` | 자기 돌의 색 | 입력을 받고, 둘 수 있는 자리인지 확인하고, 돌을 놓음 | 전략 |
| ErrorLogger | `ErrorLogger` | 기록할 메시지의 큐 | 메시지를 모았다가 로그 파일에 씀 | 전략 + 의존성 주입 |

- 알고리즘 선택의 예: 승리 판정
  - 방법 1: 돌을 놓을 때마다 판 전체를 훑어 다섯 개가 이어진 곳을 찾음. 판의 칸 수에 비례하는 일
  - 방법 2: 방금 놓은 돌에서 네 방향만 살핌. 판의 크기와 상관없는 일정한 일
  - 선택: 방법 2. 새로 생길 수 있는 다섯 줄은 반드시 방금 놓은 돌을 지나기 때문
- 표는 클래스들이 무엇인지 알려 주지만, 클래스들이 **어떤 순서로 서로를 부르는지**는 잘 보여 주지 못함. 그런 상호 작용은 UML 시퀀스 다이어그램으로 그림. 한 차례의 흐름을 글로 적으면

| 순서 | 부르는 쪽 → 불리는 쪽 | 호출 |
| --- | --- | --- |
| 1 | Game → Player | 차례 진행 |
| 2 | Player → Board | 그 자리가 비었는지 읽기 |
| 3 | Player → Board | 돌 놓기 |
| 4 | Game → Board | 승리 확인 |
| 5 | Game → BoardView | 그리기 |
| 6 | BoardView → Board | 모든 칸의 돌 읽기 |

- 설계 문서의 이 부분에는 원래 각 클래스의 실제 인터페이스(멤버 함수 목록)까지 적음
- 이 단계를 이끄는 것은 4장의 두 원칙

| 원칙 | 이 단계에서 할 일 |
| --- | --- |
| 추상화 | 인터페이스와 구현을 따로 생각함. 먼저 쓰는 쪽의 눈으로 "이 부품이 무엇을 해 주면 좋은가"를 정하고, 그다음에 자료 구조와 알고리즘을 골라 "어떻게 할 것인가"를 정함 |
| 재사용 | 표준 자료 구조, 알고리즘, 패턴을 익혀 둠. 표준 라이브러리와 회사 안의 코드에 무엇이 있는지 알아 둠 |

## 5단계: 오류 처리 정하기

- 이 단계: 하위 시스템마다 오류를 어떻게 다룰지 정함
- 두 가지 오류를 모두 다뤄야 함

| 종류 | 예 |
| --- | --- |
| **시스템 오류** | 메모리 할당 실패, 파일을 쓸 수 없음, 네트워크 끊김 |
| **사용자 오류** | 잘못된 입력 |

- 하위 시스템이 예외를 쓰는지도 여기서 명시함

| 하위 시스템 | 시스템 오류 | 사용자 오류 |
| --- | --- | --- |
| Game | 예기치 못한 오류가 나면 ErrorLogger로 기록하고, 사용자에게 알린 뒤, 프로그램을 차분히 끝냄 | 해당 없음 (사용자와 직접 닿지 않음) |
| Board | ErrorLogger로 기록하고 예외를 던짐 | 해당 없음. 다만 판 밖의 자리나 이미 돌이 있는 자리에 놓으라는 요청은 예외로 거부함 |
| BoardView | 그리다가 문제가 생기면 ErrorLogger로 기록하고 예외를 던짐 | 해당 없음 |
| Player | ErrorLogger로 기록하고 예외를 던짐 | 입력한 자리가 판 안인지, 비어 있는지 확인함. 아니면 다시 입력받음 |
| ErrorLogger | 기록을 시도하고, 기록조차 할 수 없으면 사용자에게 알림 | 해당 없음 |

- 오류 처리의 일반 원칙: **전부 다룰 것**
  - 가능한 오류 상황을 빠짐없이 생각함. 하나를 빠뜨리면 그것이 버그로 나타남
  - 어떤 것도 "예상 밖의 오류"로 취급하지 말 것. 메모리 할당 실패, 잘못된 입력, 디스크 오류, 네트워크 오류를 모두 예상함
- 사용자 오류와 내부 오류는 다르게 다룸
  - 둘 수 없는 자리를 입력했다고 프로그램이 끝나면 안 됨. 다시 묻는 것이 맞음
- 오류 처리: 14장에서 자세히 다룸

## 헷갈리기 쉬운 점

- 하위 시스템과 클래스는 같은 것이 아님
  - 하위 시스템은 기능의 큰 덩어리. 클래스 하나가 될 수도 있고 여러 클래스의 묶음이 될 수도 있음. 1단계에서는 클래스를 생각하지 않음
- MVC의 컨트롤러는 "전체를 지휘하는 것"이 아님
  - 사용자의 조작을 받아 모델을 바꾸는 부분. 이 설계에서는 Player
- 클래스가 여럿이면 계층을 만들어야 한다?
  - 동작이 종류마다 다를 때만. 흑돌과 백돌처럼 값만 다르면 열거형으로 충분
- 사용자 오류에도 예외를 던지고 프로그램을 끝낸다?
  - 사용자의 실수는 예상해야 하는 정상적인 상황. 알려 주고 다시 입력받음
- 설계는 한 번에 위에서 아래로 끝난다?
  - 4단계를 하다가 1단계의 나누기를 고치게 되는 일이 흔함. 단계는 순서라기보다 길잡이

## 4장을 마치며

- 4장에서 다룬 것
  - 설계는 프로젝트의 첫 단계이고, 코드가 바뀔 때마다 함께 갱신해야 하는 것
  - C++ 설계에서 염두에 둘 것: 객체 지향과 절차적 방식을 모두 지원함, 기능과 표준 라이브러리가 큼, 일반적인 코드를 쓰는 수단이 있음
  - 첫째 원칙, 추상화: 인터페이스와 구현을 나눔
  - 둘째 원칙, 재사용: 코드의 재사용(라이브러리, 프레임워크)과 설계의 재사용(기법, 패턴)
  - 재사용할 때 따질 것: 능력과 한계, 학습 비용, 성능(빅오), 플랫폼, 라이선스, 지원, 프로토타입
- 다음 장: C++의 객체 지향 기능을 설계에 쓰는 방법

## 정리

| 요소 | 핵심 |
| --- | --- |
| 설계의 방향 | 일반적인 것에서 구체적인 것으로 |
| 1단계 | 하위 시스템으로 나누고 인터페이스를 정함 |
| MVC | 모델(데이터), 뷰(보여 주기), 컨트롤러(조작) |

| 4단계 | 클래스, 자료 구조, 알고리즘, 패턴. 추상화와 재사용이 기준 |
| 5단계 | 오류 처리. 전부 다루되 사용자 오류와 시스템 오류를 구별 |
