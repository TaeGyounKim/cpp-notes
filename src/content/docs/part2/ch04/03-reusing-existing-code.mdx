- 다루는 것: 남이 쓴 코드(와 예전에 내가 쓴 코드)를 가져다 쓰는 일
- 이 글에서 배우는 요소: 라이브러리·프레임워크·API의 구별, 재사용의 장단점, 라이브러리를 고르는 지침, 프로토타입, 오픈 소스와 라이선스, 표준 라이브러리
- 경험 많은 C++ 프로그래머는 프로젝트를 맨바닥에서 시작하지 않음. 표준 라이브러리, 오픈 소스 라이브러리, 회사의 코드, 자신의 지난 프로젝트에서 가져다 씀
- 주의: 재사용은 복사해서 붙여넣기가 아님. 정반대로, 코드를 **복제하지 않고** 다시 쓰는 것

## 용어

### 누가 쓴 코드인가

- 내가 예전에 쓴 코드
- 동료가 쓴 코드
- 조직 밖의 제3자가 쓴 코드 (서드파티, third party)

### 어떤 모양의 코드인가

| 모양 | 설명 | 예 |
| --- | --- | --- |
| 낱개 함수나 클래스 | 내 코드나 동료의 코드를 재사용할 때 흔한 형태 | 지난 프로젝트의 날짜 계산 함수 |
| **라이브러리** (library) | 특정한 일을 하거나 특정한 분야를 다루는 코드 모음 | XML 해석, 암호화, 네트워크, 그래픽 |
| **프레임워크** (framework) | 프로그램을 그 위에 얹어 설계하는 코드 모음. 프로그램의 구조를 정해 줌 | 그래픽 사용자 인터페이스를 만드는 Qt |
| 애플리케이션 전체 | 다른 프로그램을 통째로 내 제품에 포함 | 웹 서버를 함께 묶어 배포 |

- 라이브러리와 프레임워크의 차이: 프로그램은 라이브러리를 **가져다 쓰고**, 프레임워크에는 **끼워 맞춰짐**
  - 라이브러리: 필요한 기능을 내가 부름
  - 프레임워크: 전체 뼈대가 이미 있고, 내 코드가 정해진 자리에 들어감
- **API** (application programming interface): 라이브러리나 코드 묶음을 쓰기 위한 인터페이스
  - 라이브러리와 API를 섞어 부르는 일이 많지만 같은 것이 아님. 라이브러리는 구현, API는 그 라이브러리가 밖으로 내놓은 인터페이스
- 이 글의 나머지에서는 줄여서, 재사용할 수 있는 코드를 모두 "라이브러리"라고 부름

## 가져다 쓸 것인가, 직접 쓸 것인가

- 원칙은 쉬움: 재사용할 것. 어려운 것은 구체적인 판단. 언제, 어떤 코드를?
- 언제나 주고받는 것이 있고, 상황에 따라 답이 다름

### 재사용의 장점

| 장점 | 설명 |
| --- | --- |
| 쓸 줄 모르거나 쓸 시간이 없는 코드를 얻음 | 형식화 출력을 직접 구현하고 싶은 사람은 없음. 그래서 `std::format`을 씀 |
| 설계가 단순해짐 | 재사용하는 부분은 설계할 필요가 없음 |
| 대개 디버깅이 필요 없음 | 이미 많이 시험되고 쓰였음 |
| 더 많은 오류 상황을 처리함 | 처음 짜는 코드에서는 드문 오류와 경계 상황을 빠뜨리기 쉬움 |
| 다양한 플랫폼에서 시험되었음 | 여러 하드웨어, 운영 체제, 버전. 내가 갖춰서 시험할 수 있는 범위를 훨씬 넘음 |
| 잘못된 입력을 의심하도록 만들어져 있음 | 맞지 않는 요청에 정해진 방식으로 오류를 알림 |
| 그 분야 전문가가 쓴 코드가 더 안전함 | 보안·암호 코드를 전문가가 아닌 사람이 직접 쓰면 안 됨. 사소해 보이는 실수 하나가 시스템 전체의 보안을 무너뜨림 |
| 계속 개선됨 | 인터페이스와 구현이 잘 나뉜 라이브러리라면, 버전만 올려서 개선을 얻음 |

### 재사용의 단점

| 단점 | 설명 |
| --- | --- |
| 익히는 시간 | 인터페이스와 올바른 사용법을 먼저 이해해야 함. 초반은 느려지지만, 유지할 코드가 줄어 나중에 시간을 아낌 |
| 딱 맞지 않을 수 있음 | 직접 쓴 코드는 원하는 일을 정확히 함. 라이브러리는 그렇지 않을 수 있음 |
| 성능이 맞지 않을 수 있음 | 전반적으로 느리거나, 내 쓰임에서만 느리거나, 성능이 아예 명시되어 있지 않음 |
| 지원 문제 | 버그를 발견해도 소스가 없으면 고칠 수 없음. 개발자가 내 일정에 맞춰 고쳐 주지 않음. 내 제품보다 라이브러리의 지원이 먼저 끝날 수 있음 |
| 라이선스 문제 | 소스 공개 의무, 재배포 비용, 출처 표시 등. 쓰기 전에 꼭 확인 |
| 믿어야 함 | 쓴 사람이 일을 잘했다고 믿고 쓰는 것 |
| 버전을 올릴 때의 위험 | 새 버전이 버그를 들여올 수 있음. 성능 개선이 내 쓰임에서는 악화일 수 있음 |
| 컴파일러를 올릴 때의 제약 | 소스 없이 바이너리만 받은 라이브러리는, 공급자가 새 컴파일러용 바이너리를 내줘야 컴파일러를 올릴 수 있음 |

### 결정하기

- 답이 분명한 경우: 그래픽 사용자 인터페이스를 만든다면 프레임워크를 씀. 창을 그리는 밑바닥 코드를 익히는 데 시간을 쓸 이유가 없음. 몇 년 치의 일을 아낌
- 답이 분명하지 않은 경우: 낯선 라이브러리에서 단순한 자료 구조 하나만 필요함. 며칠이면 직접 쓸 수 있다면, 라이브러리를 익히는 시간이 더 클 수 있음
- 결국 저울질: **직접 쓰는 데 드는 시간** 대 **찾아서 익히는 데 드는 시간**
- 마음은 나중에 바꿀 수 있음. 추상화를 잘 해 두었다면(라이브러리를 내 인터페이스 뒤에 숨겼다면) 바꾸기도 쉬움

## 라이브러리를 고르는 지침

### 무엇을 할 수 있고 무엇을 못 하는지 이해할 것

- 시간을 들여 그 코드를 알아볼 것. 능력만큼 한계도 알아야 함
- 순서
  1. 문서와 공개된 인터페이스(API)부터. 이것으로 충분한 것이 이상적
  2. 인터페이스와 구현이 잘 나뉘어 있지 않다면 소스 코드를 읽어야 할 수도 있음
  3. 써 본 사람에게 물어봄
- 기본으로 알아볼 것
  - 라이브러리라면: 어떤 함수를 제공하는가
  - 프레임워크라면: 내 코드가 어디에 들어가는가. 어떤 클래스를 물려받아야 하는가. 직접 써야 하는 것은 무엇인가
- 고를 때 확인할 것

| 질문 | 이유 |
| --- | --- |
| 멀티스레드 프로그램에서 써도 안전한가 | |
| 쓰는 쪽에 특정한 컴파일러 설정을 요구하는가 | 내 프로젝트에서 받아들일 수 있는 설정인지 |
| 다른 어떤 라이브러리에 의존하는가 | 딸려 오는 것까지 내 프로젝트의 짐이 됨 |

- 쓰기로 했다면 더 자세히 알아볼 것

| 질문 | 설명 |
| --- | --- |
| 초기화와 정리를 위해 불러야 하는 함수는 | |
| 클래스를 물려받아야 한다면 | 어떤 생성자를 부르고 어떤 가상 멤버 함수를 덮어써야 하는가 |
| 함수가 메모리의 포인터를 돌려준다면 | 해제는 누구 책임인가. 라이브러리 책임이라면 언제 해제되는가. 스마트 포인터(7장)로 관리할 수 있는지 확인 |
| 함수가 돌려주는 값은 | 가능한 모든 반환값 |
| 던질 수 있는 예외는 | |
| 오류를 어떻게 다루는가 | 무엇을 검사하고 무엇을 가정하는가. 오류를 어떻게 알리는가 |

- 피할 라이브러리: 오류가 났을 때 스스로 메시지 창을 띄우거나, 콘솔에 출력하거나, 프로그램을 끝내는 것
  - 사용자에게 오류를 어떻게 알릴지는 라이브러리가 아니라 그것을 쓰는 프로그램이 정할 일

### 익히는 비용을 이해할 것

- **학습 비용** (learning cost): 개발자가 그 라이브러리를 쓸 줄 알게 되기까지 드는 시간
- 처음 한 번만 드는 비용이 아님. 팀에 새 사람이 올 때마다 다시 듦
- 지침: 필요한 기능이 잘 알려진 라이브러리에 있다면, 낯설고 덜 알려진 라이브러리보다 그쪽을 씀
  - 특히 표준 라이브러리에 있는 자료 구조와 알고리즘이면 표준 라이브러리의 것을 씀

### 성능을 이해할 것

- 그 라이브러리가 보장하는 성능을 알아야 함. 성능이 중요하지 않은 프로그램이라도, 내 쓰임에서 터무니없이 느리지 않은지는 확인할 것
- 성능을 말하고 문서화하는 공통 언어: 빅오 표기법. 다음 글에서 따로 다룸

### 플랫폼의 제약을 이해할 것

- 쓰기 전에: 어떤 플랫폼에서 동작하는가
- 여러 플랫폼에서 도는 프로그램을 만든다면 라이브러리도 그래야 함. 당연해 보이지만, 여러 플랫폼을 지원한다는 라이브러리도 플랫폼마다 미묘하게 다르게 동작할 수 있음
- 플랫폼에는 운영 체제의 **버전**도 포함됨
  - 지원해야 하는 모든 버전에서 라이브러리가 동작하는지 확인
  - 한 버전에서 된다고 그 앞이나 뒤 버전에서도 된다고 가정할 수 없음

### 라이선스를 이해할 것

- 제3자의 라이브러리에는 라이선스 문제가 따라옴
  - 사용료를 내야 하는 경우
  - 수출 제한 같은 그 밖의 제약
  - 일부 오픈 소스 라이선스: 그것과 함께 링크되는 코드도 소스를 공개하도록 요구함 (아래 "오픈 소스 라이브러리" 절)

:::caution
만든 코드를 배포하거나 판매할 계획이라면, 쓰는 모든 제3자 라이브러리의 라이선스 제약을 확실히 이해해야 한다. 확신이 없으면 지식재산권 전문 법률가에게 묻는다.
:::

### 지원과 도움 받을 곳을 알아 둘 것

- 쓰기 전에 확인: 버그를 어떻게 알리는가. 고쳐지기까지 얼마나 걸리는가. 언제까지 지원되는가
- 사내 라이브러리도 지원 문제가 있음. 다른 부서의 동료에게 버그를 고쳐 달라고 하는 것이 외부 회사에 요청하는 것보다 쉽다는 보장이 없음. 돈을 내는 고객이 아니기 때문에 더 어려울 수도 있음
- 애플리케이션을 통째로 포함한 경우: 고객이 그 부분에서 문제를 겪으면 누구에게 연락해야 하는가. 출시 전에 정해 둘 것
- 도움을 구하는 순서
  1. 라이브러리에 딸린 문서
  2. 널리 쓰이는 라이브러리라면 책
  3. 웹 검색, 커뮤니티와 포럼

:::caution
웹에서 읽은 것을 모두 믿지 말 것. 웹의 글은 책이나 공식 문서 같은 검토를 거치지 않았을 수 있고, 틀린 내용이 있을 수 있다.
:::

### 프로토타입을 만들어 볼 것

- **프로토타입** (prototype): 본 제품을 만들기 전에 무언가를 확인하려고 빠르게 만들어 보는 작은 프로그램
- 새 라이브러리나 프레임워크를 처음 만났을 때 가장 좋은 방법: 직접 써 보는 것
  - 프로그램 설계에 들어가기 전에 해 보면 좋음. 능력과 한계를 손으로 알고 나서 설계하게 됨
  - 성능도 이때 직접 재 볼 수 있음
- 실제 제품과 닮을 필요가 없음. 쓰려는 기능만 시험하는 가짜 프로그램이면 충분
- 예: 도서 대출 프로그램을 설계하기 전에, 표준 라이브러리의 `<chrono>`로 반납일을 계산할 수 있는지 확인 <Badge text="C++20" /> <CppRef path="cpp/chrono/year_month_day" />

- 이 프로토타입으로 알게 된 것
  - 날짜에 날 수를 더하려면 `sys_days`로 바꿔야 함. 문서만 읽어서는 놓치기 쉬운 사용법

:::

## 오픈 소스 라이브러리

- **오픈 소스** (open source): 소스 코드가 공개되어 누구나 볼 수 있는 소프트웨어
- 라이브러리만이 아님. 운영 체제(Linux, Android), 웹 브라우저(Chromium, Firefox)도 오픈 소스

### 두 가지 이름

- 비슷한 것을 가리키는 이름이 둘 있음

| 이름 | 쓰는 쪽 | 강조하는 것 |
| --- | --- | --- |
| **자유 소프트웨어** (free software) | GNU 프로젝트 | 사용자의 자유: 소스를 살펴보고, 고치고, 다시 배포할 자유 |
| **오픈 소스 소프트웨어** (open-source software) | Open Source Initiative | 소스가 공개된 개발 방식의 실용적인 이점 |

- "free"는 무료가 아니라 자유라는 뜻. 자유 소프트웨어도 돈을 받고 팔 수 있음
- 두 이름에 해당하는 라이선스는 대부분 겹침. 다른 것은 주로 강조점
- 이 사이트에서는 뜻이 덜 헷갈리는 "오픈 소스"를 씀. 어느 한쪽의 입장을 지지한다는 뜻은 아님

### 라이선스

- 오픈 소스에도 라이선스가 있고, 종류가 많음. 크게 두 부류

| 부류 | 대표적인 라이선스 | 내 코드에 주는 영향 |
| --- | --- | --- |
| 같은 조건을 요구하는 라이선스 | GNU GPL | GPL 라이브러리를 써서 만든 제품을 배포하려면 그 제품의 소스도 GPL로 공개해야 함 |
| 허용 범위가 넓은 라이선스 | Boost Software License, BSD, MIT, Apache | 소스를 공개하지 않는 제품에도 쓸 수 있음 |

- 같은 라이선스에도 버전이 여럿 있고 조건이 다름
- 허용 범위가 넓은 라이선스에도 의무가 있음
  - 라이선스 전문을 제품에 함께 넣을 것
  - 그 라이브러리를 썼다는 표시를 할 것
- 결론: 소스를 공개하지 않는 제품에 쓰려면 라이선스마다의 세부 조건을 반드시 읽을 것. 승인된 오픈 소스 라이선스의 목록과 전문은 [opensource.org/licenses](https://opensource.org/licenses)에 있음

### 찾기와 쓰기

- 얻는 것
  - 기능: XML 해석, 로그 기록, 기계 학습에 이르기까지 온갖 일을 하는 C++ 라이브러리가 있음
  - 비용: 무료가 의무는 아니지만 실제로는 대부분 무료
  - 수정: 대개는 내 필요에 맞게 고쳐 쓸 수 있음. 라이선스가 허락하는 범위에서
- 찾는 곳: 웹 검색, [GitHub](https://github.com), [Boost](https://www.boost.org)
- 쓸 때의 지침

| 지침 | 설명 |
| --- | --- |
| 받은 만큼 기여할 것 | 대부분 개발자들이 자기 시간을 들여 만듦. 덕을 봤다면 버그 수정이나 개발에 참여하는 것이 좋은 시민의 자세. 회사가 직접적인 수익이 없다고 꺼릴 수 있지만 간접적인 이익(회사 이름의 노출, 평판)이 있음 |
| 급한 버그는 직접 고칠 것 | 주인이 한 명이 아니고 흩어져서 개발하므로 지원이 느릴 수 있음. 기다리는 것보다 직접 고치는 것이 빠를 때가 많음 |
| 고친 것은 되돌려 줄 것 | 수정 사항을 공개 저장소에 보냄. 라이선스에 따라서는 의무 |
| 고치지 못해도 알릴 것 | 발견한 문제를 보고하면 다른 사람이 같은 문제로 시간을 버리지 않음 |

## C++ 표준 라이브러리

- C++ 프로그래머에게 가장 중요한 라이브러리
- 표준의 일부이므로 표준을 따르는 컴파일러에는 반드시 들어 있음. 설치하거나 라이선스를 따질 필요가 없음
- 한 덩어리가 아니라 여러 구성 요소의 모음: 문자열, 컨테이너, 알고리즘, 입출력, 형식화 등. 이미 써 온 것들이고, 언어의 일부라고 여겼을 수도 있음
- 표준 라이브러리 전체: 16~25장에서 다룸

### C 표준 라이브러리

- C++은 대체로 C를 포함하므로 C 표준 라이브러리도 쓸 수 있음

| 종류 | 예 |
| --- | --- |
| 수학 함수 | `abs()`, `sqrt()`, `pow()` |
| 오류 처리 보조 | `assert()`, `errno` |
| 문자 배열을 문자열로 다루기 | `strlen()`, `strcpy()` |
| C 방식 입출력 | `printf()`, `scanf()` |

- 주의: 문자열과 입출력은 C++의 것이 더 나음. C 방식의 문자열 함수와 입출력 함수는 쓸 수 있지만 피하고, C++의 문자열과 형식화([2장](../../../part1/ch02/02-std-string/))와 입출력 스트림(13장)을 쓸 것

### 표준 라이브러리를 쓸 것인가

- 표준 라이브러리의 설계 목표: 기능, 성능, 그리고 구성 요소들이 서로 독립적이면서 조합되는 것
- 쓰면 얻는 것
  - 연결 리스트나 균형 이진 트리의 포인터 오류를 추적하거나, 제대로 정렬되지 않는 정렬 알고리즘을 디버깅하는 일을 거의 하지 않게 됨
  - 대부분의 C++ 개발자가 이미 쓸 줄 앎. 새 팀원의 학습 비용이 낮음
- 결론: 필요한 것이 표준 라이브러리에 있으면 그것을 씀

## 헷갈리기 쉬운 점

- 라이브러리와 프레임워크
  - 라이브러리는 내가 부르는 것, 프레임워크는 내 코드가 끼워 맞춰지는 틀. 프레임워크는 한번 고르면 바꾸기 어려우므로 더 신중하게 고름
- 라이브러리와 API
  - 라이브러리는 구현, API는 그것의 공개된 인터페이스
- 오픈 소스는 마음대로 써도 된다?
  - 오픈 소스에도 라이선스가 있음. GPL 라이브러리를 쓰고 소스를 공개하지 않은 채 배포하면 라이선스 위반
- "free software"는 무료 소프트웨어다?
  - 자유 소프트웨어. 값이 아니라 사용자의 자유에 관한 말
- 프로토타입은 제품의 초안이다?
  - 무언가를 알아내려고 만드는 것이고, 대개 버리는 것. 그대로 키워서 제품으로 만들면 급하게 짠 구조가 발목을 잡음
- 재사용이 언제나 정답이다?
  - 원칙은 재사용이지만 익히는 비용, 라이선스, 지원을 따져야 함. 작은 기능 하나 때문에 큰 의존성을 들이는 것은 손해일 수 있음

## 정리

| 요소 | 핵심 |
| --- | --- |
| 라이브러리 | 특정한 일을 하는 코드 모음. 내가 불러서 씀 |
| 프레임워크 | 프로그램의 구조를 정해 주는 틀. 내 코드가 끼워 맞춰짐 |
| API | 라이브러리의 공개된 인터페이스 |
| 재사용의 저울질 | 직접 쓰는 시간 대 찾아서 익히는 시간 |
| 고르는 지침 | 능력과 한계, 학습 비용, 성능, 플랫폼, 라이선스, 지원 |
| 프로토타입 | 설계 전에 라이브러리를 직접 써 보는 작은 프로그램 |
| 오픈 소스 라이선스 | GPL은 내 소스 공개를 요구. Boost·BSD·MIT·Apache는 비공개 제품에도 가능 |
| 표준 라이브러리 | 가장 먼저 찾아볼 곳 |

- 라이브러리의 능력과 한계를 직접 확인한 뒤에 설계하려고
