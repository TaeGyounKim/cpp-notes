- 다루는 것: C++ 프로그램을 설계할 때 따르는 두 가지 기본 원칙
- 이 글에서 배우는 요소: 추상화(인터페이스와 구현의 분리), 데이터 숨기기, 재사용할 수 있는 코드 쓰기, 설계의 재사용(디자인 패턴)
- 이 두 원칙은 앞으로의 모든 장에서 되풀이해서 나옴. 설계가 좋은지 따질 때 가장 먼저 대어 보는 잣대

## 추상화

- **추상화** (abstraction): 안이 어떻게 되어 있는지 몰라도 쓸 수 있게 만드는 것
- 일상의 예: 엘리베이터
  - 쓰는 법은 누구나 앎: 층 버튼, 열림·닫힘 버튼
  - 안에서 모터와 도르래와 제어 장치가 어떻게 움직이는지는 모름. 몰라도 타는 데 지장이 없음
  - 가능한 이유: 겉의 **인터페이스** (interface)와 속의 **구현** (implementation)이 분명히 나뉘어 있음
  - 구동 방식이 통째로 바뀌어도 버튼이 그대로라면 타는 사람은 달라진 것을 모름

### 추상화가 주는 이득

- 소프트웨어에서도 같음: 속의 구현을 몰라도 코드를 쓸 수 있음
- 함수의 예: `std::sqrt()` <CppRef path="cpp/numeric/math/sqrt" />
  - 제곱근을 어떤 알고리즘으로 구하는지 몰라도 부를 수 있음
  - 라이브러리의 버전이 바뀌면서 구현이 달라져도, 인터페이스가 그대로면 내 코드는 그대로 동작함
- 클래스의 예: `std::vector` <CppRef path="cpp/container/vector" />

```cpp
std::vector<int> values;
values.push_back(33);
values.push_back(44);
```

- 문서에 적힌 인터페이스(`push_back`)만 알면 됨. 메모리를 안에서 어떻게 관리하는지는 몰라도 됨
- `vector`의 구현은 겉으로 보이는 동작과 인터페이스가 그대로인 한 얼마든지 바뀔 수 있음

### 내 설계에 추상화 넣기

- 목표: 나와 다른 프로그래머가 **구현을 모르고도, 구현에 기대지 않고도** 쓸 수 있는 함수와 클래스
- 예: 극장의 좌석 예약 현황. 좌석은 행과 열로 놓여 있음
- 구현을 드러낸 설계: 2차원 배열을 그대로 씀

| 구현을 바꾸기 어려움 | 한 줄로 편 `vector`로 바꾸려면 좌석표를 쓰는 프로그램 전체를 고쳐야 함 |

- 볼 것
  - 쓰는 쪽(`print`, `main`)이 아는 것: `reserve`, `isReserved`, `getRowCount`, `getColumnCount`뿐
  - 속의 구현: 2차원 배열이 아니라 한 줄로 편 `std::vector<bool>`. 쓰는 쪽은 이 사실을 알 수 없고 알 필요도 없음
  - 인터페이스는 어떤 구현도 약속하지 않음. 구현을 바꿔도 인터페이스는 그대로
  - 덤: 구현 쪽에서 범위 검사 같은 기능을 더할 수 있음. `reserve(3, 0)`이 미정의 동작이 아니라 예외가 됨

### 데이터 멤버는 모두 private으로

- 이런 설계는 한 가지 규칙을 엄격히 지킬 때만 가능함

:::caution[규칙]
클래스의 데이터 멤버는 모두 `private`으로 둔다. 밖에서 접근하게 해 줘야 한다면 `public` getter와 setter를 둔다.
:::

- **데이터 숨기기** (data hiding): 데이터 멤버를 모두 `private`으로 두는 것
- 이 규칙이 주는 것

| 이득 | 설명 |
| --- | --- |
| 구현을 바꿀 자유 | `public` 인터페이스를 건드리지 않고 속을 바꿀 수 있음 |
| 끼어들 자리 | 값을 읽거나 쓸 때마다 할 일을 넣을 수 있음. 잘못된 값이 들어오지 않게 검사하기, 값이 바뀌면 알림 보내기 |
| 디버깅 | getter와 setter에 중단점을 걸면, 누가 그 값을 읽고 쓰는지 찾기 쉬움. 디버거: 31장에서 다룸 |

- 객체 지향 설계: 5장. 추상화의 원칙을 더 깊이: 6장. 클래스를 쓰는 문법 전체: 8~10장

## 재사용

- **재사용** (reuse): 이미 있는 것을 다시 쓰는 것. 설계의 둘째 기본 원칙
- 일상의 예: 김치찌개를 끓임
  - 냄비를 직접 만들지 않음. 김치를 그 자리에서 담그지 않고, 두부를 직접 만들지 않음. 있는 것을 가져다 씀
  - 끓이는 방법도 지어내지 않음. 알려진 조리법을 따름
  - 요리에서는 너무 당연한 이야기. 그런데 프로그래밍에서는 당연하지 않음
- 프로그래머가 요리 게임을 만든다면: 냄비부터 두부까지 모든 부품을 직접 짜는 것을 이상하게 여기지 않음
  - 다른 길: 가져다 쓸 코드가 있는지 먼저 찾아봄. 동료가 만든 비슷한 게임의 코드가 있을 수 있고, 그대로는 안 맞아도 조금 고치면 쓸 수 있음
- 재사용은 이미 하고 있는 일
  - `std::println()`으로 처음 출력한 날부터. 화면에 글자를 찍는 코드를 직접 쓰지 않았음
  - 값을 여러 개 담을 때 `std::vector`를 씀. 자료 구조를 직접 만들지 않았음
- 그런데도 있는 코드를 쓰지 않고 바퀴를 다시 발명하는 일이 흔함. 설계할 때 기존 코드를 고려하고, 알맞으면 재사용할 것
- 재사용의 세 갈래

| 방향 | 다루는 곳 |
| --- | --- |
| 남이 쓴 코드를 내가 재사용함 | 다음 글 |
| 내 코드를 재사용할 수 있게 씀 | 이 글, 6장 |
| 코드가 아니라 설계를 재사용함 | 이 글의 마지막 절 |

### 재사용할 수 있는 코드 쓰기

- 내가 쓰는 클래스, 알고리즘, 자료 구조도 재사용할 수 있게 설계함. 나와 동료가 지금 프로젝트에서도, 다음 프로젝트에서도 쓸 수 있게
- 피할 것: 당장의 경우에만 들어맞는 지나치게 특수한 코드
- C++에서 일반적인 코드를 쓰는 수단 가운데 하나: **템플릿** (template) <CppRef path="cpp/language/class_template" />
- 예: 앞의 좌석표는 "행과 열로 놓인 칸"이라는 구조. 같은 구조가 필요한 곳이 많음
  - 오목판: 칸마다 돌
  - 시간표: 칸마다 과목 이름
  - 따로 만들면 `SeatMap`, `GomokuBoard`, `Timetable`에 거의 같은 코드가 세 번 들어감
- 해결: 칸에 담을 타입을 정하지 않은 `Grid` 클래스 템플릿 하나를 만듦. 담을 타입은 쓸 때 정함

<RunCode client:load code={templateCode} />

- 볼 것
  - `template <typename CellType>`: `CellType`은 나중에 채울 타입의 자리
  - `Grid<char>`, `Grid<std::string>`, `Grid<double>`: 같은 코드에서 세 가지 클래스가 만들어짐
  - 바뀐 것은 인터페이스의 타입 하나뿐. `bool`로 못 박는 대신 `CellType`으로 받음
- 템플릿 문법: 12장에서 자세히 다룸. 지금은 "타입을 비워 둔 클래스를 만들 수 있다"는 것만 알면 됨
- 핵심: 코드의 변경은 작지만, 이런 결정은 **설계 단계에서** 내려야 함. 다 짜고 나서 일반화하려면 고칠 곳이 많음
- 재사용을 염두에 둔 설계: 6장에서 자세히 다룸

### 설계를 재사용하기

- C++ 문법을 아는 것과 좋은 C++ 프로그래머가 되는 것은 다른 일
  - 문법은 언어가 할 수 있는 일을 정할 뿐, 각 기능을 **어떻게 써야 하는지**는 말하지 않음
- 조리법의 비유: 요리할 때마다 조리법을 새로 지어내지 않음. 그런데 프로그램을 설계할 때는 알려진 "조리법"을 두고 매번 기법을 새로 발명하는 일이 흔함
- 알려진 조리법에 해당하는 것

| 용어 | 뜻 |
| --- | --- |
| **설계 기법** (design technique) | 언어 기능을 활용하는 정리된 방법 |
| **디자인 패턴** (design pattern) | 되풀이되는 설계 문제를 푸는, 이름이 붙은 해법 |

- 어떤 패턴은 당연한 해법에 이름을 붙인 것이고, 어떤 패턴은 생각해 보지 못한 새로운 해법임
- 설계 기법과 패턴: 32장, 33장에서 다룸

#### 예: 로그를 남기는 서비스

- 상황: 프로그램의 여러 부품이 오류와 진행 상황을 한 곳에 기록해야 함. 기록을 맡는 로거(logger)가 필요
- 원하는 것
  - 여러 부품이 같은 로거를 함께 씀
  - 기록하는 곳을 바꿀 수 있음: 콘솔, 파일, 원격 서버
- 이런 문제에 쓰는 알려진 해법: **전략 패턴** (strategy pattern) + **의존성 주입** (dependency injection)

| 단계 | 하는 일 |
| --- | --- |
| 1. 서비스의 인터페이스를 만듦 | "로그를 남길 수 있다"만 약속하는 `Logger` |
| 2. 인터페이스의 구현을 여럿 만듦 | 콘솔에 쓰는 로거, 메모리에 모으는 로거 등 |
| 3. 부품에 필요한 인터페이스를 밖에서 넣어 줌 | 부품은 `Logger`만 알고, 실제로 어떤 로거인지는 모름 |

<RunCode client:load code={strategyCode} />

- 볼 것
  - `Downloader`의 코드에는 `ConsoleLogger`도 `MemoryLogger`도 나오지 않음. `Logger`만 나옴
  - 로거를 바꿔도 `Downloader`는 한 글자도 고치지 않음
  - 추상화와의 연결: `Downloader`는 `Logger`의 인터페이스에만 기대고 구현에는 기대지 않음
- 아직 배우지 않은 문법: `virtual`, `= 0`, `override`, `: public Logger`. 10장에서 다룸
- 설계 문서에는 이렇게 적음: "로그 서비스는 전략 패턴과 의존성 주입으로 구현한다". 패턴의 이름을 아는 사람끼리는 이 한 줄로 구조가 전달됨
- 패턴을 익혀 둘 이유: 설계 문제를 만났을 때 "이건 그 패턴으로 풀리는 문제"라고 알아볼 수 있어야 쓸 수 있음

## 이전 표준에서는

- 이 글의 클래스와 템플릿은 `std::println`만 빼면 C++11에서도 같은 모양으로 쓸 수 있음

| 이 글에서 쓴 것 | 들어온 표준 | 그 이전에는 |
| --- | --- | --- |
| `override` | C++11 | 적지 않음. 덮어쓴다는 뜻을 컴파일러가 확인해 주지 않음 |
| `std::string_view` | C++17 | `const std::string&` |
| `std::println` | C++23 | `std::cout <<` |

## 헷갈리기 쉬운 점

- 추상화는 "복잡하게 만드는 것"이 아님
  - 쓰는 쪽이 알아야 하는 것을 줄이는 일. 클래스를 하나 더 만드는 수고가 들지만, 쓰는 코드 전체가 단순해짐
- getter와 setter를 다 만들어 두면 데이터 숨기기가 된다?
  - 모든 멤버에 기계적으로 getter·setter를 달면 구현을 그대로 내보이는 것과 다르지 않음. 밖에서 정말 필요한 것만 인터페이스로 냄
  - `SeatMap`에는 `m_reserved`를 통째로 돌려주는 함수가 없음
- 재사용은 복사해서 붙여넣기가 아님
  - 복사하면 같은 코드가 두 벌이 되고, 버그를 고칠 때 두 곳을 다 고쳐야 함. 재사용은 한 벌을 여러 곳에서 쓰는 것
- 일반적일수록 좋은 코드다?
  - 쓰일 일이 없는 일반화는 코드를 어렵게만 만듦. 같은 구조가 실제로 여러 번 필요할 때 일반화함
- 디자인 패턴은 가져다 붙이는 코드 조각이 아님
  - 해법의 구조와 이름. 코드는 상황에 맞게 매번 새로 씀

## 정리

| 요소 | 핵심 |
| --- | --- |
| 추상화 | 인터페이스와 구현을 나눔. 구현을 몰라도 쓸 수 있게 |
| 데이터 숨기기 | 데이터 멤버는 모두 `private`. 필요한 접근만 `public` 함수로 |
| 재사용 | 있는 코드를 찾아 쓰고, 내 코드도 다시 쓸 수 있게 씀 |
| 템플릿 | 타입을 비워 두어 여러 타입에 쓰는 코드 |
| 디자인 패턴 | 되풀이되는 설계 문제의 이름 붙은 해법 |
| 전략 패턴 + 의존성 주입 | 인터페이스를 만들고, 구현을 밖에서 넣어 줌 |
