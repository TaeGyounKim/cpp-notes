- 다루는 것: 코드를 한 줄 쓰기 전에 하는 일. 어떤 자료 구조를 쓸지, 어떤 클래스를 만들지 정하는 것
- 이 글에서 배우는 요소: 요구 사항(기능·비기능), 프로그램 설계, 설계 문서의 구성, 설계가 필요한 이유, C++ 설계에서 염두에 둘 점, 설계가 막혔을 때의 대처
- 4장부터 6장까지는 문법이 아니라 설계를 다룸. 코드는 적고 생각할 거리가 많음
- 흔한 현실: 설계는 소프트웨어 개발에서 가장 오해받고 가장 덜 쓰이는 단계. 계획 없이 코딩하면서 설계하면 복잡하게 꼬인 구조가 되고, 개발·디버깅·유지 보수가 모두 어려워짐
- 직관과 반대되는 사실: 처음에 설계에 시간을 더 쓰면 프로젝트 전체로는 시간이 줄어듦

## 프로그램 설계란

### 먼저 요구 사항

- 새 프로그램이나 새 기능의 첫 단계: **요구 사항 분석** (requirements analysis). 그 프로그램을 필요로 하는 사람들(이해관계자)과 이야기해서 정리함
- 분석의 결과물 두 가지

| 문서 | 담는 것 | 예 |
| --- | --- | --- |
| **기능 요구 사항** (functional requirements) | 무엇을 해야 하는가. 어떻게 하는지는 적지 않음 | "사용자가 도형을 추가·이동·삭제할 수 있다" |
| **비기능 요구 사항** (non-functional requirements) | 완성된 시스템이 어떠해야 하는가 | 보안, 확장 가능성, "도형 1만 개에서도 화면 갱신 0.1초 이내" |

### 그다음 설계

- **프로그램 설계** (program design, software design): 모든 요구 사항을 만족하도록 구현할 구조를 정해 적은 것. 쉽게 말해 "프로그램을 어떻게 짤 것인가"에 대한 계획
- 보통 **설계 문서** (design document)로 씀. 형식은 회사와 프로젝트마다 다르지만 큰 틀은 비슷함

| 부분 | 담는 것 |
| --- | --- |
| 1. 프로그램을 **하위 시스템** (subsystem)으로 크게 나눈 것 | 하위 시스템 사이의 인터페이스와 의존 관계, 데이터의 흐름, 각 하위 시스템의 입력과 출력, 전체 스레드 구조 |
| 2. 하위 시스템 하나하나의 상세 | 클래스로 나눈 것, 클래스 계층, 자료 구조, 알고리즘, 스레드 구조, 오류 처리 방식 |

- 그림과 표: 하위 시스템의 상호 작용과 클래스 계층은 대개 그림으로 그림. 업계 표준 표기법은 UML(Unified Modeling Language)
- 가장 중요한 점: 문서의 형식보다 **설계에 대해 생각하는 과정**이 중요함. 설계의 목적은 프로그램을 쓰기 전에 그 프로그램에 대해 생각하는 것

### 설계는 바뀐다

- 목표: 코딩을 시작하기 전에 설계를 되도록 좋게 만듦. 웬만한 프로그래머라면 따라가며 구현할 수 있는 지도여야 함
- 그래도 코딩을 시작하면 미처 생각하지 못한 문제가 나오고, 설계를 고치게 됨. 피할 수 없는 일
- 개발 방법론은 이런 변경을 받아들이도록 만들어져 있음
  - 예: 애자일(agile) 방법론의 하나인 스크럼(Scrum). 스프린트(sprint)라는 짧은 주기를 되풀이하며 개발하고, 주기마다 설계를 고치고 새 요구 사항을 받아들임
  - 개발 방법론: 28장에서 다룸

## 설계가 왜 중요한가

- 건너뛰고 싶은 마음이 드는 이유
  - 코드가 컴파일되고 실행되는 것만큼 "진척이 있다"는 느낌을 주는 것이 없음
  - 구조는 이미 대충 머릿속에 있는데 굳이 적는 것이 낭비처럼 보임
  - 설계 문서를 쓰는 일은 코딩만큼 재미있지 않음
- 그러나 아주 단순한 프로젝트가 아니라면 거의 틀림없이 문제로 이어짐. 경험이 많고 C++을 깊이 알아도 마찬가지. 설계(생각하기)는 프로그래머의 일에 포함됨

### 팀에게 필요한 이유

- 각자 다른 부분을 맡는 팀: 모두가 따를 설계 문서가 꼭 있어야 함
- 새로 온 사람: 설계 문서로 구조를 빨리 익힘
  - 문서가 없으면 원래의 설계 의도를 알 수 없고, 적혀 있지 않은 설계를 깨는 수정을 하게 됨
- 누가 설계하는가는 회사마다 다름

| 형태 | 설명 |
| --- | --- |
| 역할이 나뉜 곳 | 기능 분석 담당이 요구 사항을, 소프트웨어 아키텍트가 설계를 맡음. 개발자는 구현에 집중 |
| 개발자가 다 하는 곳 | 요구 사항 수집과 설계까지 개발자가 함 |
| 그 사이 | 아키텍트가 큰 구조만 정하고, 작은 설계는 개발자가 함 |

### 계획 없이 만들면 벌어지는 일

- 예: 메모 앱을 설계 없이 만든다고 하자
  - 화면에 메모를 보여 주고 고치는 기능부터 만듦. 메모의 내용은 화면을 그리는 코드 안의 변수에 그대로 둠
  - 한참 뒤에 "저장하기"를 만들려고 보니, 저장할 데이터가 화면 코드 여기저기에 흩어져 있음
  - 선택 1: 화면 코드 곳곳에 저장 코드를 끼워 넣음. 당장은 동작함
  - 선택 2: 데이터를 따로 모으도록 구조를 다시 짬. 이미 만든 것의 절반을 고쳐야 함
- 대개 선택 1을 고르고 "보기 흉하지만 동작한다"고 말함. 문제는 그다음
  - 새로 온 사람이 화면을 하나 추가하면서 저장 코드를 끼워 넣어야 한다는 것을 모름. 그 화면에서 쓴 메모만 저장되지 않는 버그가 생기고, 원인을 찾는 데 몇 주가 걸림
- 설계가 있었다면: "메모 데이터를 맡는 부분"과 "화면을 맡는 부분"을 처음부터 나눴을 것이고, 저장은 데이터를 맡는 부분에 한 번만 들어감

### 설계가 주는 것

- 전체가 어떻게 맞물리는지 보여 줌. 하위 시스템들이 서로 어떤 관계이고 어떻게 함께 요구 사항을 만족시키는지
- 설계가 없을 때 놓치는 것
  - 하위 시스템 사이의 연결
  - 재사용하거나 공유할 수 있는 부분
  - 일을 해내는 가장 단순한 방법
- 큰 그림이 없으면 세부 구현에 파묻혀 전체 구조와 목표를 잃음
- 설계 문서는 프로젝트의 모든 사람이 참조하는 기록이 됨
- 문서를 얼마나 최신으로 유지할 것인가
  - 애자일의 원칙 가운데 하나: "포괄적인 문서보다 동작하는 소프트웨어를"
  - 적어도 큰 부분들이 어떻게 함께 동작하는지에 대한 설계 문서는 최신으로 유지
  - 작은 부분의 문서는 팀이 가치를 따져 결정. 유지하지 않기로 했으면 지우거나 "오래된 문서"라고 표시할 것

### 코딩부터 시작했을 때: 도형 편집기

- 상황: 도형 편집기를 만듦. 전체를 설계하지 않고 가장 쉬운 것부터 코딩하기로 함
- 원이 가장 단순해 보여서 `Circle` 클래스부터 만듦

| `Circle` | |
| --- | --- |
| 데이터 | 위치(`m_x`, `m_y`), 색(`m_color`), 반지름(`m_radius`) |
| 동작 | `move()`, `draw()` |

- 다음으로 쉬운 사각형, `Rectangle` 클래스

| `Rectangle` | |
| --- | --- |
| 데이터 | 위치(`m_x`, `m_y`), 색(`m_color`), 너비와 높이 |
| 동작 | `move()`, `draw()` |

- 이쯤에서 드는 의심: 두 클래스가 닮았음
  - 위치와 색은 완전히 같음. `move()`는 글자 하나 다르지 않음
  - `draw()`는 내용이 다르지만 "그릴 수 있다"는 능력은 둘 다 필요함
  - 삼각형, 선, 글상자를 추가할 때마다 같은 코드를 또 복사하게 됨
- 설계를 먼저 했다면: 도형들이 서로 닮았다는 것을 미리 알았을 것이고, 공통 부분을 한 번만 쓰는 방법을 찾았을 것. 그 방법(객체 지향 설계)은 5장에서 다룸
- 또 하나의 문제: 도형 클래스는 다른 하위 시스템에 기대고 있음
  - `draw()`를 쓰려면 화면이 정해져야 함. 창에 그리는가, 파일로 내보내는가, 둘 다인가
  - 위치를 도형이 알고 있을지, 도형을 담는 캔버스가 관리할지도 캔버스를 어떻게 만들지에 달림
- 핵심: 하위 시스템은 혼자 있지 않고 서로 얽혀 있음. 설계 작업의 대부분은 이 관계를 찾아내고 정하는 일

## C++로 설계할 때 염두에 둘 것

| C++의 특징 | 설계에 주는 영향 |
| --- | --- |
| 객체 지향 기능을 제공함 | 설계에 클래스 계층, 클래스 인터페이스, 객체 사이의 상호 작용이 들어감. C 같은 언어의 절차적 설계와 많이 다름. 5장에서 다룸 |
| 여러 패러다임을 지원함 | 객체 지향 말고 절차적 방식도 쓸 수 있음. 어느 것을 쓸지 고르는 것도 설계의 일부 |
| 일반적이고 재사용할 수 있는 코드를 위한 수단이 많음 | 템플릿을 이용한 제네릭 프로그래밍 등. 6장에서 다룸 |
| 큰 표준 라이브러리가 있음 | 문자열, 형식화, 입출력, 멀티스레딩, 자료 구조와 알고리즘. 직접 만들지 않아도 되는 것이 많음 |
| 디자인 패턴을 적용하기 좋음 | 되풀이되는 문제를 푸는 잘 알려진 방법들을 쓸 수 있음 |

- **패러다임** (paradigm): 프로그램을 짜는 방식에 대한 큰 틀

### 설계가 막혔을 때

- 설계는 버거운 일. 며칠씩 아이디어를 적고 지우기를 되풀이하기도 함
  - 그 끝에 깔끔한 설계가 나오기도 하고, 아무것도 안 나오기도 함. 그래도 낭비가 아님. 잘못된 설계로 구현했다가 다시 만드는 쪽이 훨씬 큰 낭비
- 중요한 것: 실제로 나아가고 있는지 스스로 살필 것. 막혔다면

| 방법 | 설명 |
| --- | --- |
| 도움을 청함 | 동료, 선배, 책, 커뮤니티, 웹 |
| 잠시 다른 일을 함 | 그 결정은 나중에 다시 봄 |
| 결정하고 넘어감 | 이상적이지 않아도 하나를 정해서 써 봄. 틀린 선택은 곧 드러나고, 쓸 만한 선택으로 판명될 수도 있음 |

- 깔끔한 방법이 없는 경우도 있음. 요구 사항을 만족하는 현실적인 방법이 그것뿐이라면 보기 흉한 해법을 받아들여야 할 때가 있음
- 무엇을 정하든 **기록할 것**: 왜 그렇게 정했는지, 그리고 버린 대안과 버린 이유까지. 나중의 나와 다른 사람이 같은 고민을 되풀이하지 않게 됨
- 좋은 설계는 어렵고 연습이 필요함. C++ 코딩보다 C++ 설계가 더 익히기 어렵다고 느껴도 이상한 일이 아님

## 헷갈리기 쉬운 점

- 요구 사항과 설계는 다른 것
  - 요구 사항: 무엇을. 설계: 어떻게
  - "메모를 저장할 수 있다"는 요구 사항. "메모 데이터를 맡는 클래스가 파일로 쓴다"는 설계
- 설계 문서를 쓰는 것이 설계가 아님
  - 목적은 문서가 아니라 생각하기. 형식을 채우느라 생각을 건너뛰면 의미가 없음
- 설계를 먼저 한다는 것은 설계를 바꾸지 않는다는 뜻이 아님
  - 구현하다 보면 고치게 됨. 바꿀 때 문서도 함께 고칠 것
- 애자일이면 설계 문서가 필요 없다?
  - "문서보다 동작하는 소프트웨어"는 문서를 쓰지 말라는 뜻이 아님. 가치가 있는 문서는 유지함

## 정리

| 요소 | 핵심 |
| --- | --- |
| 기능 요구 사항 | 무엇을 해야 하는가 |
| 비기능 요구 사항 | 시스템이 어떠해야 하는가 (보안, 성능, 확장성) |
| 프로그램 설계 | 요구 사항을 만족시킬 구조에 대한 계획 |
| 설계 문서 | 하위 시스템으로 나눈 것 + 하위 시스템별 상세 |
| 설계가 주는 것 | 전체가 맞물리는 모습, 재사용할 부분, 모두가 참조할 기록 |
| 막혔을 때 | 도움 청하기, 잠시 미루기, 결정하고 넘어가기. 결정은 이유와 함께 기록 |

<details>
<summary>도형 편집기 예에서, 코딩부터 시작해서 놓친 것 두 가지는?</summary>

- 도형들의 공통 부분(위치, 색, 이동). 같은 코드를 클래스마다 되풀이해서 씀
- 다른 하위 시스템과의 관계. 화면과 캔버스가 정해지지 않으면 `draw()`와 위치 관리를 제대로 쓸 수 없음

</details>

<details>
<summary>설계 결정을 내릴 때, 고른 것 말고도 기록해 둘 것은?</summary>

- 왜 그렇게 정했는지
- 버린 대안과 버린 이유

</details>

<details>
<summary>설계에 며칠을 썼는데 결론이 나지 않았다. 할 수 있는 일은?</summary>

- 다른 사람에게 묻거나 자료를 찾음
- 그 결정을 잠시 미루고 다른 부분을 봄
- 완벽하지 않아도 하나를 정해 써 보고, 이유를 기록함

</details>
