## 빅오 표기법

- 성능을 말하는 두 가지 방법

| 방법 | 예 | 문제 |
| --- | --- | --- |
| 절대적인 시간 | "0.3초 걸린다" | 어떤 컴퓨터에서? 데이터가 몇 개일 때? |
| 입력 크기에 따른 변화 | "데이터가 두 배가 되면 시간도 두 배" | |

- **빅오 표기법** (big-O notation): 둘째 방법. 입력이 커질 때 알고리즘의 실행 시간이 **어떻게 늘어나는지**를 나타냄
- 입력 크기의 예
  - 정렬 알고리즘: 정렬할 원소의 개수
  - 해시 테이블에서 키 찾기: 테이블에 든 원소의 개수
  - 파일 복사: 파일의 크기
- 적용 범위: 속도가 입력에 달려 있는 알고리즘에만 해당함. 입력이 없거나 실행 시간이 무작위인 알고리즘에는 쓰지 않음. 실제로 관심 있는 알고리즘은 대부분 입력에 달려 있으므로 큰 제약이 아님

### 읽는 법

- 정식으로는: 알고리즘의 실행 시간을 입력 크기의 함수로 나타낸 것. 이 함수를 그 알고리즘의 **복잡도** (complexity)라고 함
- 예: 원소가 두 배가 되면 시간도 두 배가 되는 알고리즘

| 원소 수 | 시간 |
| --- | --- |
| 200 | 1초 |
| 400 | 2초 |
| 800 | 4초 |

- 그래프로 그리면 직선. 그래서 "입력 크기에 대해 선형"이라고 말함
- 빅오로 적으면 **O(n)**
  - O: 빅오 표기법이라는 표시
  - n: 입력 크기
  - 뜻: 걸리는 시간이 n에 비례함

### 흔한 복잡도

- 좋은 것에서 나쁜 것 순서

| 이름 | 표기 | 뜻 | 예 |
| --- | --- | --- | --- |
| 상수 (constant) | O(1) | 입력 크기와 상관없이 일정 | 배열의 원소 하나에 접근 |
| 로그 (logarithmic) | O(log n) | 입력이 두 배가 되어도 한 걸음만 더 | 정렬된 목록에서 이진 탐색 |
| 선형 (linear) | O(n) | 입력에 비례 | 정렬되지 않은 목록에서 찾기 |
| 선형 로그 (linear logarithmic) | O(n&nbsp;log&nbsp;n) | n에 log n을 곱한 만큼 | 병합 정렬 |
| 제곱 (quadratic) | O(n<sup>2</sup>) | 입력의 제곱에 비례 | 선택 정렬 같은 느린 정렬 |
| 지수 (exponential) | O(2<sup>n</sup>) | 입력이 하나 늘 때마다 두 배 | 가능한 모든 부분 집합을 살펴보기 |

- 숫자로 보면 차이가 분명해짐. 아래 코드는 각 복잡도의 알고리즘이 걷는 걸음 수를 실제로 셈

- 볼 것
  - n이 10에서 10000으로 1000배가 될 때
    - O(log n): 3걸음에서 13걸음. 거의 늘지 않음
    - O(n): 1000배
    - O(n<sup>2</sup>): 100만 배. 100에서 1억으로
  - O(n log n)은 O(n)보다 조금 나쁜 정도. O(n<sup>2</sup>)과는 비교가 안 됨
- 해 볼 것: `n` 목록에 `100'000`을 추가하고 실행

### 입력 크기로 말하는 이유

| 이점 | 설명 |
| --- | --- |
| 플랫폼과 무관함 | "이 컴퓨터에서 0.2초"는 다른 컴퓨터에서의 속도에 대해 아무것도 말해 주지 않음. 두 알고리즘을 비교하려 해도 같은 컴퓨터, 같은 부하에서 돌려야 함. 입력 크기의 함수는 어디서나 통함 |
| 모든 입력을 한 번에 다룸 | 초 단위의 시간은 어느 한 입력에 대한 것. 입력 크기의 함수는 가능한 모든 입력을 하나의 식으로 설명함 |

## 표준 라이브러리의 성능 읽기

- C++ 표준 라이브러리는 알고리즘과 자료 구조의 성능을 빅오로 적어 둠. 표준이 요구하는 보장이므로 어느 컴파일러에서나 같음

| 연산 | 문서에 적힌 복잡도 |
| --- | --- |
| `std::vector`의 `[]`로 원소 접근 | 상수 |
| `std::vector`의 `push_back` | 분할 상환 상수. 가끔 재할당이 일어나지만 평균으로는 상수 |
| `std::find` | 선형 |
| `std::binary_search` | 로그 |
| `std::sort` | O(n log n) |
| `std::map`에서 키 찾기 | 로그 |
| `std::unordered_map`에서 키 찾기 | 평균 상수, 최악 선형 |

- cppreference의 각 항목에는 "Complexity" 절이 있음. 예: `std::find` <CppRef path="cpp/algorithm/find" />, `std::binary_search` <CppRef path="cpp/algorithm/binary_search" />, `std::sort` <CppRef path="cpp/algorithm/sort" />
- 문서의 말이 실제와 맞는지 확인하는 코드: 비교 횟수를 직접 셈

<RunCode client:load code={searchCode} />

- 볼 것
  - `std::find`: 비교 횟수가 n과 같음. 선형
  - `std::binary_search`: n이 1000배가 되어도 11번에서 21번으로. 로그
  - 원소 100만 개에서 100만 번 대 21번
- 설계에 주는 뜻: 자주 찾아야 하는 데이터라면 "정렬해 두고 이진 탐색" 또는 "찾기가 빠른 컨테이너"를 고르는 것만으로 성능이 크게 달라짐. 이런 판단은 설계 단계에서 함
- 단, `std::binary_search`는 데이터가 정렬되어 있어야 함. 정렬에는 O(n log n)이 듦. 한 번만 찾을 거라면 정렬하지 않고 `std::find`를 쓰는 쪽이 나음

## 빅오의 한계

- 빅오만으로는 부족하거나 오히려 오해를 부르는 경우가 있음

| 한계 | 설명 |
| --- | --- |
| 원래 얼마나 걸리는지는 말하지 않음 | "데이터가 두 배면 시간도 두 배"는 처음에 얼마나 걸렸는지와 상관없는 말. 잘 늘어나지만 형편없이 짠 알고리즘도 있음. 예: 쓸데없이 디스크에 접근하는 코드. 빅오는 그대로지만 전체 성능은 매우 나쁨 |
| 같은 빅오끼리는 비교할 수 없음 | 둘 다 O(n log n)이라는 정렬 두 가지 가운데 어느 쪽이 빠른지는 직접 재 봐야 앎 |
| 작은 입력에서는 틀릴 수 있음 | 빅오는 입력이 한없이 커질 때의 경향. 입력이 작으면 O(n<sup>2</sup>) 알고리즘이 O(n log n) 알고리즘보다 빠를 수 있음 |

- 셋째 한계를 확인하는 코드: 삽입 정렬(O(n<sup>2</sup>))과 병합 정렬(O(n log n))이 같은 데이터를 정렬하며 하는 일(비교와 이동)의 횟수를 셈

<RunCode client:load code={smallCode} />

- 볼 것
  - n = 8: 삽입 정렬이 더 적게 일함. 42 대 65
  - n = 32부터 뒤집힘
  - n = 2048: 삽입 정렬이 30배 넘게 더 일함
- 결론: 판단하기 전에 내 프로그램이 다룰 입력의 크기를 먼저 생각할 것. 원소가 늘 열 개 안팎이라면 단순한 알고리즘이 더 나을 수 있음
- 참고: 실제 정렬 라이브러리도 이 성질을 이용함. 큰 입력은 빠르게 늘어나지 않는 알고리즘으로 나누고, 조각이 작아지면 삽입 정렬로 마무리하는 구현이 흔함

## 성능을 판단할 때의 지침

### 얼마나 자주 쓰이는 코드인가

- **90/10 규칙**: 대부분의 프로그램에서 실행 시간의 90%는 코드의 10%에서 쓰임
- 쓰려는 라이브러리 코드가 어디에 속하는가

| 속하는 곳 | 할 일 |
| --- | --- |
| 자주 실행되는 10% | 성능 특성을 꼼꼼히 분석함 |
| 나머지 90% | 성능 분석에 시간을 많이 쓰지 않음. 빨라져도 프로그램 전체는 거의 빨라지지 않음 |

- 어디가 그 10%인지 찾는 도구: **프로파일러** (profiler). 29장에서 다룸

### 문서만 믿지 말 것

- 문서에 적힌 성능은 출발점일 뿐
- 그 라이브러리가 **내 쓰임에서** 받아들일 만한 성능을 내는지는 반드시 직접 재서 확인. 앞 글의 프로토타입이 이 일을 하기에 좋은 자리

## 헷갈리기 쉬운 점

- O(1)은 "빠르다"는 뜻이 아님
  - 입력 크기와 상관없이 일정하다는 뜻. 한 번에 1초가 걸려도 O(1)
- 빅오가 좋은 알고리즘이 언제나 더 빠르다?
  - 입력이 충분히 클 때의 이야기. 작은 입력에서는 단순한 알고리즘이 이길 수 있음
- 빅오는 시간을 알려 준다?
  - 시간이 아니라 늘어나는 모양을 알려 줌. 실제 시간은 재 봐야 앎
- `std::binary_search`가 `std::find`보다 빠르니 항상 그것을 쓴다?
  - 정렬된 데이터에서만 올바르게 동작함. 정렬되지 않은 데이터에 쓰면 틀린 답이 나올 수 있음
- 프로그램의 모든 곳을 빠르게 만들어야 한다?
  - 시간이 실제로 쓰이는 10%를 찾아 그곳을 고칠 것. 나머지를 다듬는 것은 코드만 어렵게 만듦

## 정리

| 요소 | 핵심 |
| --- | --- |
| 빅오 표기법 | 입력이 커질 때 실행 시간이 늘어나는 모양 |
| 좋은 순서 | O(1), O(log n), O(n), O(n log n), O(n<sup>2</sup>), O(2<sup>n</sup>) |
| 입력 크기로 말하는 이유 | 플랫폼과 무관하고, 모든 입력을 한 식으로 설명 |
| 빅오의 한계 | 원래 걸리는 시간을 말하지 않음, 같은 빅오끼리 비교 불가, 작은 입력에서는 뒤집힐 수 있음 |
| 90/10 규칙 | 실행 시간의 90%는 코드의 10%에서. 그 10%에 집중 |
| 지침 | 문서를 읽되, 내 쓰임에서 직접 잴 것 |
