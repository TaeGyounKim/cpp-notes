- 다루는 것: 재사용할 수 있는 코드의 둘째 조건, **쓰기 쉬움**
- 이 글에서 배우는 요소: 접근 지정자와 공개 인터페이스, 인터페이스를 쓸 사람과 목적, 쓰기 쉬운 인터페이스를 위한 네 가지 전략(익숙한 방식, 필요한 기능 빠뜨리지 않기, 군더더기 없애기, 문서)
- 아무리 아름답고 효율적인 구현이라도 인터페이스가 형편없으면 그 라이브러리는 쓸모가 없음
- 여러 프로그램에서 쓸 생각이 없는 구성 요소도 좋은 인터페이스가 필요함
  - 언제 재사용될지 모름
  - 처음 한 번 쓸 때도 중요함. 팀으로 일한다면 다른 사람이 내 코드를 씀

## 무엇을 공개할 것인가

- C++에서 클래스의 속성과 멤버 함수에는 접근 수준을 정할 수 있음 <CppRef path="cpp/language/access" />

| 지정자 | 접근할 수 있는 곳 |
| --- | --- |
| `public` | 어떤 코드든 |
| `protected` | 그 클래스 자신과 파생 클래스 |
| `private` | 그 클래스 자신만. 파생 클래스도 접근할 수 없음 |

- 주의: 접근 지정은 **객체 단위가 아니라 클래스 단위**
  - 한 클래스의 멤버 함수는 같은 클래스의 **다른 객체**의 `private` 멤버에도 접근할 수 있음

<RunCode client:load code={accessCode} />

- 볼 것: `hasSameCurrency`가 `other.m_currency`를 읽음. `other`는 다른 객체지만 같은 `Money` 클래스라서 허용됨
- 공개 인터페이스 설계란 결국 **무엇을 `public`으로 할지 고르는 일**
  - 한 번에 끝나는 결정이 아니라 과정으로 볼 것
  - 인터페이스의 주목적은 코드를 쓰기 쉽게 하는 것. 일부 기법은 일반성을 높이는 데도 도움이 됨(다음 글)

## 누가 쓸 것인가

- 공개 인터페이스를 설계하는 첫 단계: 누구를 위해 설계하는지 생각하기
  - 팀의 다른 사람인가? 나 자신인가? 회사 밖의 프로그래머인가? 고객이나 외주 개발자인가?
  - 누가 도움을 청하러 올지 알게 될 뿐 아니라, 설계 목표도 분명해짐

| 쓰는 사람 | 특징 |
| --- | --- |
| 나 자신 | 쓰면서 필요에 따라 바꿀 수 있어 자유로움. 그래도 팀의 역할은 바뀌므로 언젠가 다른 사람이 쓰게 될 가능성이 큼 |
| 회사 안의 다른 프로그래머 | 인터페이스가 그들과의 **계약**이 됨. 예: 데이터 저장 부품을 만든다면 다른 사람들이 그 인터페이스가 특정 연산을 지원한다고 믿고 코드를 씀. 팀이 바라는 것을 모두 알아내야 함. 버전 관리가 필요한가? 어떤 종류의 데이터를 저장하는가? |
| 회사 밖의 고객 | 이상적으로는 고객이 어떤 기능을 노출할지 정하는 데 참여해야 함. 지금 원하는 기능과 앞으로 원할 기능을 함께 생각함. 인터페이스의 용어는 고객이 아는 말이어야 하고, 문서도 그 독자에 맞춰 씀. 내부 농담, 코드명, 개발자 은어는 빼야 함 |

- 회사 안이든 밖이든 인터페이스는 계약
  - 코딩 전에 합의한 인터페이스를 코드가 쓰인 뒤에 바꾸면 쓰는 사람들의 원성을 삼
- 쓰는 사람의 규모가 설계에 들일 시간을 정함
  - 멤버 함수 몇 개짜리를 몇 군데서 몇 사람만 쓴다면, 나중에 바꿔도 괜찮을 수 있음
  - 복잡하거나 많은 사람이 쓸 인터페이스라면 설계에 시간을 더 들이고, 쓰이기 시작한 뒤에는 되도록 바꾸지 않게 함
  - **하이럼의 법칙** (Hyrum's law): 쓰는 사람이 충분히 많으면, 문서에 약속한 것과 상관없이 겉으로 관찰되는 **모든 동작**에 누군가는 기대게 됨. 그래서 많이 쓰이는 인터페이스는 사소한 동작 변화도 누군가의 코드를 깨뜨림

## 무엇을 위한 인터페이스인가

- 코드를 쓰기 전에, 어떤 기능을 노출할지 정하기 전에 인터페이스의 **목적**부터 이해해야 함

### API

- **API**: 제품을 넓히거나 그 기능을 다른 맥락에서 쓰게 하려고 밖으로 내놓은 수단
- 회사 안의 인터페이스가 계약이라면, API는 **돌에 새긴 법**에 가까움. 회사 밖 사람들이 쓰기 시작하면, 그들에게 도움이 되는 새 기능을 더하는 것 말고는 바뀌기를 바라지 않음. 내놓기 전에 계획하고 고객과 논의할 것
- 설계의 핵심 저울질: **쓰기 쉬움 대 유연함**
  - 쓰는 사람은 제품의 내부를 모름. 배우는 과정이 완만해야 함. 너무 어려우면 실패한 API
  - 제품의 모든 기능을 쓰게 하고 싶지만, 제품이 할 수 있는 모든 일을 할 수 있게 하는 API는 너무 복잡해지기 쉬움
- 널리 알려진 격언: **"좋은 API는 흔한 일을 쉽게, 드문 일을 가능하게 만든다"**
  - 대부분의 프로그래머가 하려는 일은 곧바로 할 수 있어야 함
  - 고급 쓰임도 가능해야 함. 흔한 경우를 단순하게 하려고 드문 경우가 복잡해지는 것은 받아들일 만함

### 도구 클래스나 라이브러리

- 프로그램의 다른 곳에서 두루 쓸 기능을 만드는 경우. 예: 로그 기록 클래스
- 인터페이스를 정하기가 비교적 쉬움. 기능의 대부분이나 전부를 노출하되, 구현은 되도록 드러내지 않음
- 일반성이 중요함. 범용이므로 가능한 쓰임새들을 설계에 고려해야 함

### 하위 시스템 인터페이스

- 프로그램의 큰 하위 시스템 둘 사이의 인터페이스. 예: 데이터베이스에 접근하는 부분
- 인터페이스와 구현을 나누는 것이 무엇보다 중요함. 이유

| 이유 | 설명 |
| --- | --- |
| 가짜로 바꿔 끼울 수 있음 (mockability) | 테스트할 때 실제 구현을 같은 인터페이스의 다른 구현으로 바꿈. 데이터베이스 테스트에서 진짜 데이터베이스 대신 접근을 흉내 내는 구현을 씀 |
| 유연함 | 테스트가 아니어도, 바꿔 쓸 수 있는 여러 구현을 둘 수 있음. 예: 한 데이터베이스 제품을 쓰는 구현을 다른 제품을 쓰는 구현으로. 실행 중에 바꿀 수도 있음 |
| 동시에 진행 | 인터페이스를 먼저 끝내 두면, 구현이 끝나기 전에도 다른 프로그래머가 그 인터페이스에 맞춰 코드를 쓰기 시작할 수 있음 |

- 하위 시스템을 맡으면: 먼저 주목적이 무엇인지 생각하고, 그다음 구체적인 쓰임새와 다른 코드에 어떻게 보여야 하는지를 생각함. 구현의 세부 사항에 빠지지 말고 쓰는 쪽의 입장이 되어 볼 것
- 4장의 `Logger`와 전략 패턴이 이 구조

### 구성 요소 인터페이스

- 정의하는 인터페이스의 대부분은 이보다 작음. 내가 쓴 다른 코드 안에서 쓰는 클래스들
- 흔한 함정: 인터페이스가 조금씩 자라다가 다루기 어려워짐
- 내가 쓸 것이라도 남이 쓸 것처럼 생각할 것. 클래스마다 주목적을 생각하고, 그 목적에 보탬이 되지 않는 기능을 노출하는 것을 경계할 것

## 쓰기 쉬운 인터페이스를 설계할 것

- 쉽다는 것이 하찮다는 뜻은 아님. 기능이 허락하는 한 단순하고 직관적이어야 함
- **KISS 원칙** (Keep It Simple, Stupid): 단순하게 유지하라
  - 간단한 자료 구조 하나 쓰려고 소스나 문서를 몇 쪽씩 읽게 하거나, 원하는 기능을 얻으려고 코드를 이리저리 비틀게 하면 안 됨
- 전략 넷

### 전략 1: 익숙한 방식을 따를 것

- 쓰기 쉬운 인터페이스를 만드는 가장 좋은 전략. 사람들은 전에 써 본 것과 비슷한 인터페이스를 더 잘 이해하고, 더 쉽게 받아들이고, 덜 잘못 씀
- 비유: 자동차의 조향 장치
  - 조이스틱, 좌우 버튼 두 개, 가로 레버, 그리고 핸들
  - 가장 쓰기 쉬운 것도, 가장 잘 팔릴 것도 핸들. 사람들이 익숙하기 때문
  - 성능과 안전이 더 뛰어난 장치를 만들었어도 팔기도 가르치기도 어려움
- 혁신은 인터페이스가 아니라 **구현**에서
  - 전기차가 잘 팔리는 이유 하나: 운전하는 인터페이스가 휘발유차와 똑같음
- C++에 적용하면: C++ 프로그래머가 익숙한 관례를 따르는 인터페이스
  - 예: 생성자는 객체를 준비하고, 소멸자는 정리함 (8장)
  - 이미 있는 객체를 "다시 초기화"하고 싶다면, 새로 만든 객체를 대입하는 것이 표준적인 방법
  - 생성자·소멸자 대신 `initialize()`와 `cleanup()`을 부르게 하면, 쓰는 사람은 모두 헷갈리고 부르기를 잊음

  - `Recorder`: 블록이 끝나면 소멸자가 저절로 정리함. 잊을 방법이 없음

#### 연산자 오버로딩

- C++의 **연산자 오버로딩** (operator overloading): 내가 만든 클래스에도 `int`, `double` 같은 기본 타입처럼 표준 연산자(`+`, `-`, `==` 등)가 동작하게 하는 기능 <CppRef path="cpp/language/operators" />
- 쓰기 쉬운 인터페이스를 만드는 데 도움이 됨

<RunCode client:load code={operatorCode} />

- 볼 것
  - `price.add(coupon)`보다 `price + coupon`이 숫자를 다루듯 읽힘
  - 출력도 2장에서 배운 `std::formatter` 특수화로 `{}`에 바로 넘김
- 남용하지 말 것
  - `+`가 빼기를 하거나 `-`가 곱하기를 하게 만들 수도 있음. 직관에 반하는 인터페이스가 됨
  - 그렇다고 모든 연산자가 언제나 수학과 똑같은 일을 해야 하는 것은 아님. `std::string`의 `+`는 이어 붙이기. 문자열에 대해서는 직관적임
- 연산자 오버로딩의 문법: 9장, 15장

### 전략 2: 필요한 기능을 빠뜨리지 말 것

- 앞날을 생각할 것
  - 몇 년 동안 바꾸지 못할 설계인가? 그렇다면 플러그인 구조처럼 넓힐 자리를 남겨 둬야 할 수 있음
  - 사람들이 원래 목적과 다른 데 쓰려 할 조짐이 있는가? 그들과 이야기해서 쓰임새를 이해할 것
  - 그러지 않으면 나중에 다시 쓰거나, 더 나쁘게는 새 기능을 아무렇게나 덧붙여 지저분한 인터페이스가 됨
- 단, 반대쪽 함정: **추측성 일반화** (speculative generality)
  - 앞으로의 쓰임이 불분명한데 "모든 것을 다 하는" 로그 클래스를 설계하지 말 것. 설계, 구현, 공개 인터페이스가 쓸데없이 복잡해짐
- 이 전략의 두 부분

#### 클라이언트가 필요로 할 모든 동작의 인터페이스를 둘 것

- 당연해 보임. 속도계 없는 자동차는 만들지 않음. 분자와 분모를 꺼낼 방법이 없는 분수 클래스도 만들지 않음
- 덜 분명한 동작도 있음. 클라이언트가 내 코드를 어떻게 쓸지 모두 내다봐야 함
  - 예: 게임판 클래스. 오목만 생각해서 "한 칸에 돌 하나"로 정함
  - 나중에 한 칸에 말이 여럿 쌓이는 보드게임을 만들려 하면, 이 게임판은 쓸 수 없음
- 모든 쓰임을 내다보는 것은 불가능에 가까움. 완벽한 인터페이스를 위해 괴로워할 필요는 없음. 생각해 보고 최선을 다하면 됨

#### 구현 안에 기능을 되도록 많이 담을 것

- 구현이 이미 알거나, 설계를 달리하면 알 수 있는 정보를 클라이언트에게 요구하지 말 것
  - 예: 라이브러리가 임시 파일을 써야 한다면, 그 경로를 클라이언트가 정하게 하지 말 것. 클라이언트는 어떤 파일을 쓰든 상관없음. 알맞은 임시 경로는 라이브러리가 알아서 찾음. 표준 라이브러리에도 그 일을 하는 `std::filesystem::temp_directory_path()`가 있음 <Badge text="C++17" /> <CppRef path="cpp/filesystem/temp_directory_path" />
- 결과를 합치는 수고를 클라이언트에게 떠넘기지 말 것
  - 예: 난수의 위쪽 비트와 아래쪽 비트를 따로 계산하는 알고리즘이라면, 합쳐서 하나의 수로 돌려줌

### 전략 3: 군더더기 없는 인터페이스를 내놓을 것

- 기능을 빠뜨리지 않으려다 정반대 끝으로 가는 사람도 있음: 생각할 수 있는 모든 기능을 다 넣음
  - 할 수 없는 일은 없겠지만, 인터페이스가 너무 어수선해서 **어떻게** 하는지 끝내 알아내지 못함
  - 이런 것을 **뚱뚱한 인터페이스** (fat interface)라고 부름
- 불필요한 기능을 넣지 말고 깔끔하고 단순하게 유지할 것
  - 앞의 전략과 부딪쳐 보이지만 아님. 필요한 기능은 넣고, 쓸모없거나 오히려 해로운 인터페이스는 뺌
- 비유: 자동차 계기판
  - 운전은 몇 가지만 다룸: 핸들, 브레이크와 가속 페달, 변속기, 거울, 속도계 등
  - 계기판이 비행기 조종석처럼 다이얼, 레버, 화면, 버튼 수백 개라면 쓸 수 없음
  - 운전은 비행보다 훨씬 쉬우므로 인터페이스도 훨씬 단순할 수 있음. 고도를 보거나 관제탑과 교신하거나 날개를 조종할 필요가 없음
- 뚱뚱한 인터페이스를 피하는 방법
  - 여러 개의 작은 인터페이스로 나눔(다음 글의 인터페이스 분리 원칙)
  - **퍼사드** (facade) 패턴: 뚱뚱한 인터페이스 위에 더 쉬운 인터페이스를 하나 이상 덧씌움

  - `Image`의 세밀한 함수들은 그대로 있음. 고급 사용자는 직접 씀
  - `QuickEdit::autoEnhance()` 하나로 흔한 작업을 끝냄. "흔한 일을 쉽게, 드문 일을 가능하게"
- 라이브러리를 만드는 쪽에서도 작은 라이브러리가 유지하기 쉬움. 모두를 만족시키려 하면 실수할 곳이 늘고, 모든 것이 얽혀 있으면 실수 하나가 라이브러리 전체를 못 쓰게 만들 수 있음
- 솔직히, 군더더기 없는 인터페이스는 말은 쉬워도 실천하기 매우 어려움. 무엇이 필요한지는 결국 주관적인 판단. 잘못 판단하면 클라이언트가 틀림없이 알려 줌

### 전략 4: 문서를 제공할 것

- 인터페이스를 아무리 쉽게 만들어도 쓰는 법을 알려 주는 문서가 필요함. 알려 주지 않고 올바르게 쓰기를 기대할 수는 없음
- 내 라이브러리를 다른 프로그래머가 쓰는 **제품**으로 생각할 것. 제품에는 올바른 사용법을 설명하는 문서가 있어야 함
- 두 가지 형태. 둘 다 제공하도록 노력할 것

| 형태 | 설명 |
| --- | --- |
| 인터페이스 안의 주석 | 헤더나 모듈 파일 안. 많은 공개 API가 이것을 거의 생략함. 그래도 가장 중요한 형태로 볼 만함 |
| 외부 문서 | Unix의 man 페이지, 개발 환경에 딸린 도움말이나 웹 문서 등 |

- 코드만 있는 "맨몸의" 헤더나 모듈을 내놓지 말 것
  - 주석이 외부 문서를 그대로 되풀이하더라도, 친절한 주석이 있는 파일이 코드만 있는 파일보다 덜 부담스러움
  - 아무리 뛰어난 프로그래머도 가끔은 사람의 말로 된 설명을 보고 싶어 함
- 무엇을 어떻게 주석으로 적을지, 주석에서 외부 문서를 만들어 주는 도구: 3장

## 헷갈리기 쉬운 점

- `private` 멤버는 그 객체 자신만 쓸 수 있다?
  - 같은 클래스라면 다른 객체의 `private` 멤버에도 접근할 수 있음. 접근 제어는 클래스 단위
- 쓰기 쉬운 인터페이스는 기능이 적은 인터페이스다?
  - 필요한 기능은 다 있되, 쓸모없는 것이 없는 인터페이스. 흔한 일은 쉽게, 드문 일도 가능하게
- 필요한 기능을 빠뜨리지 말라는 것은 미래의 쓰임까지 전부 미리 만들라는 뜻이다?
  - 아님. 불분명한 미래를 위한 일반화(추측성 일반화)는 오히려 해로움. 생각할 수 있는 범위에서 최선을 다할 뿐
- 연산자 오버로딩은 기본 타입과 똑같은 의미일 때만 써야 한다?
  - 직관에 맞으면 됨. 문자열의 `+`(이어 붙이기)처럼. 직관에 어긋나는 쓰임(`+`가 빼기)이 문제
- 외부 문서가 있으면 헤더의 주석은 필요 없다?
  - 헤더를 여는 사람이 먼저 보는 것은 주석. 되풀이가 되더라도 둘 다 제공하는 것이 좋음

## 정리

| 요소 | 핵심 |
| --- | --- |
| 접근 지정자 | `public`, `protected`, `private`. 클래스 단위 |
| 쓰는 사람 | 나, 팀, 외부 고객. 인터페이스는 계약. 많이 쓰일수록 바꾸기 어려움 |
| 목적 | API, 도구 라이브러리, 하위 시스템, 구성 요소 |
| 좋은 API | 흔한 일은 쉽게, 드문 일은 가능하게 |
| 익숙한 방식 | 생성자·소멸자 같은 관례를 따름. 혁신은 구현에서 |
| 연산자 오버로딩 | 기본 타입처럼 쓰게. 직관에 맞게만 |
| 빠뜨리지 않기 | 필요한 동작은 모두. 구현이 아는 정보는 요구하지 않음 |
| 군더더기 없애기 | 뚱뚱한 인터페이스를 피함. 나누거나 퍼사드로 감쌈 |
| 문서 | 헤더 주석과 외부 문서 둘 다 |

<details>

- 생성자에서 연결을 준비하고 소멸자에서 정리함
- 쓰는 사람이 부르기를 잊을 수 없고, 다른 C++ 클래스와 같은 방식이라 익히기 쉬움

</details>

<details>

- 구현이 알 수 있는 정보를 클라이언트에게 요구함. 쓰는 사람은 알맞은 값을 모르고, 틀린 값을 넣을 수도 있음
- 기본값을 라이브러리가 정하고, 꼭 바꾸고 싶은 사람만 바꾸게 함

</details>
