## 템플릿으로 일반적인 자료 구조와 알고리즘을 쓸 것

- 문제: 정수 배열 코드를 짰는데 실수 배열이 필요해짐. 코드를 통째로 복사해서 `int`를 `double`로 바꿔야 할까?
- **템플릿** (template): 타입을 명세의 **매개변수**로 삼는 C++의 기능 <CppRef path="cpp/language/templates" />
  - 코드 한 벌로 어떤 타입에든 쓰임
  - 자료 구조와 알고리즘 모두 템플릿으로 만들 수 있음
- 가장 친숙한 예: `std::vector`. 정수 벡터는 `std::vector<int>`, 실수 벡터는 `std::vector<double>`
- 템플릿 프로그래밍은 매우 강력한 만큼 아주 복잡해질 수 있음. 다행히 "타입 하나를 매개변수로 받는" 정도의 단순한 쓰임도 충분히 쓸모 있음
  - 템플릿을 직접 쓰는 기법: 12장, 26장. 여기서는 설계의 측면만
- 지침: 되도록 특정 프로그램의 사정을 박아 넣지 말고 일반적으로 설계함
  - 책만 담는 균형 이진 트리를 짜지 말 것. 어떤 타입이든 담게 만들면 서점, 음반 가게, 운영 체제 등 균형 이진 트리가 필요한 어디서든 씀
  - 표준 라이브러리 전체가 이 전략 위에 서 있음
- 단, 일반적인 자료 구조는 만드는 데 시간이 더 듦
  - 요구 조건을 더 많이 생각해야 하고, 여러 타입으로 더 많이 시험해야 함
  - 한 가지 쓰임에만 맞는 자료 구조라면 그 수고가 보상받지 못할 수 있음. 그럴 때는 일반적이지 않은 단순한 구현으로 시작하는 편이 나음

### 템플릿이 다른 방법보다 나은 이유

- 일반적인 자료 구조를 만드는 방법은 템플릿만이 아님

| 방법 | 방식 | 문제 |
| --- | --- | --- |
| `void*` 포인터 | 무엇이든 `void*`로 바꿔 담고, 꺼낼 때 원래 타입으로 되돌림 | **타입 안전하지 않음**. 컨테이너가 담긴 것의 타입을 검사하지 못함. 한 사람은 `int`를 가리키는 포인터를 담았는데 다른 사람이 그것을 다른 타입의 포인터로 바꿔 쓰면, 프로그램은 엉뚱하게 동작함. 오래된 방법이고 권하지 않음 |
| `std::any` <Badge text="C++17" /> | 어떤 타입의 객체든 담을 수 있는 클래스. 담긴 타입을 기억함 | 타입 안전함. 하지만 틀린 타입으로 꺼내는 실수는 **실행할 때**에야 드러남 |
| 공통 기반 클래스 | 특정 클래스를 담도록 만들고, 다형성으로 그 파생 클래스를 모두 담음. Java의 옛 컨테이너는 모든 클래스의 조상인 `Object`를 담았음 | 꺼낼 때 원래 무엇이었는지 기억해서 파생 클래스로 **다운캐스트** (down cast, 계층의 아래쪽 클래스로 바꾸기)해야 함. 타입 안전하지 않음 |
| 템플릿 | 타입을 매개변수로 받아 타입마다 코드를 만듦 | 올바로 쓰면 타입 안전함. 한 인스턴스에는 한 타입만 담기고, 다른 타입을 담으려 하면 **컴파일되지 않음** |

- `std::any` <CppRef path="cpp/utility/any" />: 24장에서 다룸. 내부에서 `void*`를 쓰는 경우도 있지만 담긴 타입을 따로 기억하므로 안전함

- 볼 것
  - 템플릿 `Shelf<std::string>`: 문자열만 담김. 주석을 풀어 `titles.put(42);`를 넣으면 컴파일 오류("cannot convert 'int' to 'const std::string&'")
  - `std::any`: 문자열과 정수를 한 벡터에 담을 수 있음. 대신 틀린 타입으로 꺼내면 `std::bad_any_cast` 예외. 실수가 실행할 때에야 드러남
- 템플릿의 또 다른 장점: 컴파일러가 인스턴스마다 매우 최적화된 코드를 만듦. `void*`나 `std::any`를 쓰는 자료 구조보다 자유 저장소 할당을 피할 수 있어 성능이 더 좋을 수 있음
- 요즘의 Java에는 C++ 템플릿처럼 타입 안전한 제네릭이 있음

### 템플릿의 문제점

| 문제 | 설명 |
| --- | --- |
| 문법이 헷갈림 | 처음 보는 사람에게는 특히 |
| 같은 타입만 담는 자료 구조 | 균형 이진 트리 클래스 템플릿으로 `int` 트리와 `std::string` 트리는 만들 수 있지만, 한 트리에 둘을 섞어 담을 수는 없음. 타입 안전함의 직접적인 결과 |
| 코드 부풀림 (code bloat) | 인스턴스마다 특화된 코드가 생기므로, 조금 느린 일반 코드 한 벌보다 실행 파일이 커짐. 요즘은 대개 큰 문제가 아님 |

### 템플릿인가, 상속인가

| 쓰는 것 | 경우 | 예 |
| --- | --- | --- |
| 템플릿 | 서로 다른 타입에 **같은 기능**을 줄 때. 모든 타입을 똑같이 다룸 | 어떤 타입에든 쓰는 정렬 알고리즘(함수 템플릿), 어떤 타입이든 담는 컨테이너(클래스 템플릿) |
| 상속 | 관련된 타입들에 **다른 동작**을 줄 때 | 원, 사각형, 선을 그리는 프로그램. 각 도형이 `Shape`를 물려받음 |

- 필요하면 템플릿도 특정 타입만 다르게 다룰 수 있음: **템플릿 특수화** (template specialization). 2장에서 `std::formatter`를 특수화했던 것이 그 예. 12장에서 다룸
- 또 하나의 차이: 언제 정해지는가

| | 정해지는 때 | 이름 |
| --- | --- | --- |
| 템플릿 | 컴파일할 때. 관련된 모든 타입을 컴파일할 때 알아야 함 | 컴파일 시간 다형성 |
| 상속(가상 함수) | 실행할 때 | 실행 시간 다형성 |

## 알맞은 검사와 안전장치를 둘 것

- 재사용을 염두에 둔 코드는 **지금의 쓰임**뿐 아니라 여러 쓰임에서 안전해야 함
- 안전한 코드를 설계하는 두 가지 상반된 방식. 가장 좋은 것은 아마 둘을 적절히 섞는 것

### 방식 1: 계약에 의한 설계

- **계약에 의한 설계** (design by contract): 함수나 클래스의 문서를 하나의 **계약**으로 봄. 클라이언트 코드의 책임과 함수·클래스의 책임을 자세히 적음
- 계약의 세 요소 (3장의 주석에서도 나왔음)

| 요소 | 뜻 |
| --- | --- |
| **사전 조건** (precondition) | 함수를 부르기 전에 클라이언트 코드가 지켜야 하는 조건 |
| **사후 조건** (postcondition) | 함수가 끝났을 때 함수가 지켜야 하는 조건 |
| **불변식** (invariant) | 함수가 실행되는 내내 지켜져야 하는 조건 |

- 표준 라이브러리도 자주 씀
  - `std::vector`의 `[]`: 범위를 검사하지 않음. 번호가 올바른지는 클라이언트의 책임 <CppRef path="cpp/container/vector/operator_at" />
  - 즉 "번호가 올바르다"가 `[]`의 사전 조건
  - 이유: 번호가 범위 안이라는 것을 이미 아는 클라이언트 코드의 성능을 위해

### 방식 2: 되도록 안전하게

- 함수와 클래스를 가능한 한 안전하게 설계함. 가장 중요한 것: 코드 안에서 **오류를 검사**하는 것
  - 예: 난수 생성기의 씨앗(seed)이 어떤 범위 안이어야 한다면, 클라이언트가 올바른 값을 줄 거라고 믿지 말 것. 넘어온 값을 확인하고, 틀리면 호출을 거부함
  - `std::vector`에는 `[]` 말고 `at()`도 있음. 범위를 검사하고, 틀린 번호면 예외를 던짐 <CppRef path="cpp/container/vector/at" />
  - 그래서 클라이언트가 고를 수 있음: 검사 없는 `[]`, 검사하는 `at()`
- 비유: 세무사
  - 세무사에게 한 해의 금융 정보를 넘기면 세금 신고서를 채워 줌
  - 하지만 그냥 옮겨 적지 않고 말이 되는지 확인함. 집이 있는데 재산세를 안 적었으면 물어보고, 소득보다 대출 이자가 훨씬 많으면 숫자가 맞는지 확인함
  - 세무사를 쓰는 이유는 서류를 채워 주는 것만이 아니라 이런 **검사와 안전장치** 때문
  - 프로그래밍에서도 구현에 검사와 안전장치를 최대한 둘 수 있음

- 볼 것
  - `operator[]`: 계약 방식. 주석에 사전 조건을 적고 검사하지 않음. 반복문처럼 범위가 보장된 곳에서 씀
  - `at()`: 안전 방식. 사용자 입력처럼 믿을 수 없는 번호에 씀

| --- | --- |

## 확장할 수 있게 설계할 것

- 목표: 클래스를 **물려받아 넓힐 수는 있되, 고칠 필요는 없게**. 구현을 고치지 않고도 동작을 넓힐 수 있어야 함
- **열림/닫힘 원칙** (open/closed principle, OCP): 확장에는 열려 있고, 수정에는 닫혀 있어야 함
- 예: 쇼핑몰의 알림 기능
  - 첫 버전은 메일만 보냄. `EmailChannel`과, 메일들을 보내는 `Notifier`를 만듦
  - 문자 알림을 더하려니 `Notifier`의 보내는 함수를 고쳐야 함. 매개변수에 문자 목록을 하나 더 받고, 반복문도 하나 더

```cpp
void Notifier::notify(const std::vector<EmailChannel>& emails,
                      const std::vector<SmsChannel>& smses,
                      std::string_view message)
{
    for (auto& email : emails) { /* 메일 보내기 */ }
    for (auto& sms : smses) { /* 문자 보내기 */ }
}
```

- 이렇게 고치다 보면 뭔가 잘못되었다는 느낌이 듦. 맞음. 기능을 넓히려고 기존 구현을 고쳐야 하므로 **수정에 닫혀 있지 않음**. 앱 알림을 더할 때 또 고쳐야 함
- 상속을 쓴 설계
  - 공통 기반 클래스 `Channel`에 "보낼 수 있다"만 약속하는 `send()`를 둠
  - 채널마다 `Channel`을 물려받아 `send()`를 구현함
  - `Notifier`는 `Channel`의 목록만 알고, 각 채널에 `send()`를 부름

  - 새 채널을 지원하려면 `Channel`을 물려받는 클래스를 하나 쓰면 끝. 기존 코드를 고치지 않고 넓힘: 확장에 열려 있고 수정에 닫혀 있음

## 헷갈리기 쉬운 점

- 템플릿은 무엇이든 담을 수 있다?
  - 타입 **하나**를 정해서 그 타입만 담음. 여러 타입을 한 컨테이너에 섞어 담는 것은 `std::any`나 공통 기반 클래스의 영역
- `std::any`는 타입 안전하지 않다?
  - 타입 안전함. 틀린 타입으로 꺼내면 예외를 던짐. 다만 그 실수가 컴파일할 때가 아니라 실행할 때 드러남. `void*`와 혼동하지 말 것
- 모든 자료 구조를 처음부터 템플릿으로 만들어야 한다?
  - 일반화에는 비용이 듦. 한 가지 쓰임뿐이라면 단순하게 시작하고, 정말 여러 타입이 필요해질 때 일반화함
- 계약에 의한 설계는 검사를 안 하니 위험하다?
  - 책임이 클라이언트에게 있다고 **문서로 분명히 할 뿐**. 성능이 중요한 곳에서 쓰고, 믿을 수 없는 입력에는 검사하는 함수를 함께 제공함
- 열림/닫힘 원칙은 클래스를 아예 고치지 말라는 뜻이다?
  - 버그를 고치는 것까지 막는 말이 아님. 새 **기능**을 더할 때 기존 코드를 고치지 않아도 되게 설계하라는 뜻

## 정리

| 요소 | 핵심 |
| --- | --- |
| 템플릿 | 타입을 매개변수로. 한 벌의 코드를 모든 타입에. 타입 안전함 |
| 다른 방법 | `void*`는 위험, `std::any`는 실행할 때 검사, 공통 기반 클래스는 다운캐스트가 필요 |
| 템플릿의 문제 | 문법, 같은 타입만 담음, 코드 부풀림 |
| 템플릿 대 상속 | 같은 기능을 여러 타입에 / 다른 동작을 관련된 타입에. 컴파일 시간 / 실행 시간 다형성 |
| 계약에 의한 설계 | 사전 조건, 사후 조건, 불변식을 문서로. 검사는 클라이언트 책임 |
| 안전한 설계 | 넘어온 값을 검사하고 틀리면 거부 |
| 열림/닫힘 원칙 | 새 기능은 파생 클래스로 더하고 기존 코드는 고치지 않음 |

## 복습 질문

<details>
<summary>`void*`로 만든 일반적인 컨테이너가 위험한 이유는?</summary>

- 컨테이너가 담긴 것의 타입을 알지도 검사하지도 못함
- 꺼내는 쪽이 원래 타입을 잘못 짐작해 다른 타입으로 바꿔 쓰면, 컴파일러도 실행 환경도 막지 못하고 프로그램이 엉뚱하게 동작함

</details>

<details>
<summary>"어떤 타입이든 담는 고정 크기 원형 버퍼"와 "종류마다 그리는 방법이 다른 도형"은 각각 템플릿과 상속 가운데 무엇이 맞는가?</summary>

- 원형 버퍼: 템플릿. 모든 타입에 같은 일(넣고 꺼내기)을 함
- 도형: 상속. 관련된 타입들이 서로 다른 동작(그리기)을 함

</details>

<details>
<summary>`std::vector`가 `[]`와 `at()`을 둘 다 제공하는 이유는?</summary>

- `[]`는 검사하지 않아 빠름. 번호가 올바르다는 것을 아는 코드를 위한 계약 방식
- `at()`은 범위를 검사하고 예외를 던짐. 믿을 수 없는 번호를 위한 안전 방식
- 클라이언트가 상황에 맞게 고를 수 있음

</details>

<details>
<summary>보고서 출력 프로그램이 PDF와 HTML을 지원하는데, 엑셀 형식을 더하려면 `ReportPrinter::print()`를 고쳐야 한다. 무엇이 문제이고 어떻게 바꾸는가?</summary>

- 열림/닫힘 원칙을 어김. 기능을 더할 때마다 기존 코드를 고쳐야 함
- 형식마다 공통 기반 클래스(예: `ReportFormat`)를 물려받게 하고, `ReportPrinter`는 기반 클래스의 인터페이스로만 부름. 엑셀은 새 파생 클래스 하나로 더함

</details>

<details>
<summary>계약에 의한 설계의 세 요소는?</summary>

- 사전 조건: 부르기 전에 클라이언트가 지킬 것
- 사후 조건: 끝났을 때 함수가 지킬 것
- 불변식: 실행되는 내내 지켜질 것

</details>
