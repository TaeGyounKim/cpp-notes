## 일반적인 인터페이스를 설계할 것

### 같은 기능을 여러 방법으로 제공할 것

- 모든 "고객"을 만족시키려고, 같은 기능을 여러 방법으로 제공하면 도움이 될 때가 있음
  - 단, 아껴서 쓸 것. 지나치면 어수선한 인터페이스가 됨
- 비유: 자동차 문 열기
  - 요즘 차는 대부분 리모컨 키의 버튼으로 문을 엶
  - 그래도 리모컨 배터리가 다 됐을 때를 위해 물리적인 열쇠로도 열 수 있음
  - 둘은 중복이지만 대부분의 사람이 둘 다 있는 것을 반김
- 인터페이스의 예: 앞 글의 `std::vector`
  - 범위를 검사하는 `at()`과 검사하지 않는 `[]`
  - 번호가 올바르다는 것을 안다면 `[]`로 검사 비용을 아낌
- 이것은 "군더더기 없는 인터페이스" 규칙의 **예외**. 알맞은 경우가 몇 가지 있지만, 대부분은 군더더기 없는 쪽을 따를 것

### 맞춤 설정을 제공할 것

- 인터페이스를 더 유연하게 하려면 **맞춤 설정** (customizability)을 제공함
  - 간단하게는 오류 기록을 켜고 끄게 하는 것
  - 기본 생각: 모든 클라이언트에게 같은 기본 기능을 주되, 조금씩 바꿀 수 있게 함
- 방법 1: 인터페이스로 의존 관계를 뒤집음(아래 SOLID의 D)
  - 구현 하나가 **의존성 주입**. 4장의 로거 예: `Logger` 인터페이스를 정의하고, 로거가 필요한 부품마다 구체적인 구현을 밖에서 넣어 줌
- 방법 2: **콜백** (callback)과 템플릿 매개변수
  - 콜백: 클라이언트가 넘겨준 함수를 라이브러리가 정해진 때에 불러 줌
  - 예: 오류가 나면 클라이언트가 등록한 처리 함수를 부름. 콜백은 19장에서 자세히 다룸

- 볼 것
  - `quiet`: 처리 함수를 등록하지 않음. 실패해도 아무것도 출력하지 않고 `false`만 돌려줌(기본 동작)
  - `verbose`: 람다를 등록해 오류를 세고 출력하게 맞춤. `Uploader`의 코드는 그대로
  - `std::function<void(std::string_view)>`: "문자열 하나를 받고 아무것도 돌려주지 않는 함수"라면 무엇이든 담는 타입 <CppRef path="cpp/utility/functional/function" />
  - 앞 글의 원칙("라이브러리는 출력하지 않는다")도 지킴. 출력할지 말지는 클라이언트가 고름
- 표준 라이브러리는 이 전략을 극단까지 밀고 감: 컨테이너가 쓸 **메모리 할당자**까지 클라이언트가 정할 수 있음
  - 대부분의 컨테이너가 할당자를 템플릿 매개변수로 받음
  - 쓰려면 표준 라이브러리가 요구하는 인터페이스를 지키는 할당자 클래스를 직접 써야 함. 25장에서 다룸

### 일반성과 쓰기 쉬움을 함께 얻기

- 두 목표는 서로 부딪쳐 보일 때가 있음. 일반성을 높이면 인터페이스가 복잡해지기 쉬움
  - 예: 지도 프로그램에서 도시를 담는 그래프 구조가 필요함
  - 일반성을 위해 템플릿으로, 도시뿐 아니라 어떤 타입이든 담는 그래프를 만듦. 다음에 네트워크 시뮬레이터를 만들 때 라우터를 담는 데 다시 씀
  - 하지만 템플릿 때문에 인터페이스가 조금 거추장스러워짐. 템플릿에 익숙하지 않은 클라이언트에게는 특히
- 그래도 둘은 서로를 배제하지 않음. 일반적이면서도 쓰기 쉬운 인터페이스를 설계할 수 있음
- 방법: 인터페이스를 **여럿**으로 나눔
  - **인터페이스 분리 원칙** (interface segregation principle, ISP)
  - 예: 범용 네트워크 라이브러리를 두 얼굴로. 하나는 게임에 쓸모 있는 네트워크 인터페이스, 다른 하나는 웹 브라우징(HTTP)에 쓸모 있는 인터페이스
- 여러 인터페이스는 "흔한 기능은 쉽게, 고급 기능도 가능하게"에도 도움이 됨
  - 지도 예: 도시 이름을 여러 언어로 정하는 인터페이스를 따로 두고, 기본 언어를 정해 둠. 대부분의 클라이언트는 언어를 신경 쓰지 않아도 되고, 원하는 클라이언트만 정함
  - 간단한 형태로는 기본 인수만으로도 이 효과를 낼 수 있음

## 성공적인 추상화를 설계하기

- 좋은 추상화에는 **경험과 반복**이 꼭 필요함
  - 정말 잘 설계된 인터페이스는 수년간 다른 추상화를 쓰고 써 본 데서 나옴
  - 남의 수년간의 경험을 빌릴 수도 있음: 잘 설계된 기존 추상화, 즉 표준 디자인 패턴을 재사용함
- 습관

| 습관 | 설명 |
| --- | --- |
| 무엇이 통했고 무엇이 안 통했는지 기억할 것 | 지난주에 쓴 파일 시스템 API에서 무엇이 아쉬웠나? 동료 대신 내가 네트워크 감싸개를 썼다면 무엇을 다르게 했을까? |
| 계속 고칠 것 | 최고의 인터페이스가 처음 종이에 적은 것인 경우는 드묾 |
| 동료에게 보이고 의견을 구할 것 | 코드 검토를 하는 회사라면, 구현을 시작하기 전에 인터페이스 명세부터 검토함 |
| 코딩이 시작된 뒤에도 추상화를 바꾸기를 두려워하지 말 것 | 다른 프로그래머가 맞춰 고쳐야 하더라도. 좋은 추상화가 길게 보면 모두에게 이롭다는 것을 알게 됨 |
| 설득할 준비와 받아들일 준비를 함께 | 팀이 예전 설계에 문제를 못 느끼거나, 새 방식이 자기 일을 늘린다고 느낄 수 있음. 내 설계를 변호할 준비, 그리고 알맞다면 그들의 생각을 받아들일 준비 |

- 좋은 추상화의 기술적인 조건
  - 공개 인터페이스에는 **안정적이고 바뀌지 않을** 공개 멤버 함수만 있음. 이를 위한 기법 하나: **pimpl 관용구** (private implementation). 9장에서 다룸
  - 클래스 하나짜리 추상화를 경계할 것. 하는 일에 깊이가 있다면 주 인터페이스와 함께할 짝 클래스를 생각함. 예: 데이터를 처리하는 인터페이스라면 결과를 쉽게 보고 해석하게 해 주는 결과 클래스도 함께
  - 속성은 언제나 멤버 함수로 바꿀 것. 바깥 코드가 클래스의 데이터를 직접 만지게 하지 말 것. 부주의하거나 악의적인 프로그래머가 토끼 객체의 키를 음수로 정하게 둘 수는 없음. "키 정하기" 멤버 함수에서 범위를 검사함
- 가장 중요한 것을 다시: **반복**. 설계에 대한 의견을 구하고 응답하고, 필요하면 바꾸고, 실수에서 배울 것

## SOLID 원칙

- 4~6장에서 객체 지향 설계의 기본 원칙을 여럿 봤음. 이것들을 외우기 쉬운 머리글자로 줄여 부르는 것이 **SOLID**

| 글자 | 원칙 | 뜻 | 다룬 곳 |
| --- | --- | --- | --- |
| S | **단일 책임 원칙** (Single Responsibility Principle, SRP) | 구성 요소 하나는 잘 정의된 책임 하나만 가지며, 관계없는 기능을 섞지 않음 | 6장 첫째 글 (배터리와 드론) |
| O | **열림/닫힘 원칙** (Open/Closed Principle, OCP) | 클래스는 확장에 열려 있고 수정에 닫혀 있어야 함. 상속이 한 방법. 템플릿, 함수 오버로딩 등도 있음. 이런 자리를 **맞춤 지점** (customization point)이라고 부름 | 6장 둘째 글 (알림 채널) |
| L | **리스코프 치환 원칙** (Liskov Substitution Principle, LSP) | 객체를 그 하위 타입의 객체로 바꿔 넣을 수 있어야 함. 바꿔 넣어도 동작이 그대로여야 함 | 5장 둘째 글 (스택과 `vector`) |
| I | **인터페이스 분리 원칙** (Interface Segregation Principle, ISP) | 인터페이스를 깔끔하고 단순하게. 넓은 범용 인터페이스 하나보다 잘 정의된 단일 책임의 작은 인터페이스 여럿이 나음 | 이 글 |
| D | **의존 관계 역전 원칙** (Dependency Inversion Principle, DIP) | 인터페이스로 의존 관계를 뒤집음. 높은 수준의 코드가 구체적인 구현이 아니라 인터페이스에 기댐. 의존성 주입이 이를 지원하는 한 방법 | 4장 둘째 글 (로거), 이 글 |

## 헷갈리기 쉬운 점

- 같은 기능을 여러 방법으로 제공하는 것은 좋은 일이다?
  - 예외적으로만. `[]`와 `at()`처럼 분명한 이유가 있을 때. 기본은 군더더기 없는 인터페이스
- 맞춤 설정을 열어 두면 쓰기 어려워진다?
  - 기본 동작을 정해 두면 대부분의 클라이언트는 신경 쓰지 않아도 됨. 바꾸고 싶은 사람만 바꿈
- 의존성 주입과 의존 관계 역전 원칙은 같은 말이다?
  - 의존 관계 역전은 원칙(인터페이스에 기대라), 의존성 주입은 그것을 이루는 방법 가운데 하나(구현을 밖에서 넣어 준다)
- 인터페이스 분리 원칙은 클래스를 잘게 쪼개라는 뜻이다?
  - 쪼개는 것은 **인터페이스**. 구현 클래스는 여러 인터페이스를 함께 구현할 수 있음(복합기)
- SOLID를 모두 지키면 좋은 설계가 된다?
  - 원칙은 판단의 길잡이일 뿐 공식이 아님. 작은 프로그램에 모든 원칙을 기계적으로 적용하면 오히려 복잡해짐

## 6장을 마치며

- 6장에서 다룬 것
  - 재사용의 철학: "한 번 쓰고 여러 번 쓴다". 재사용할 수 있는 코드는 일반적이고 쓰기 쉬워야 함
  - 재사용할 수 있는 코드를 설계하려면 추상화를 쓰고, 코드를 알맞게 구조화하고, 좋은 인터페이스를 설계해야 함
  - 구조화의 전략: 관계없는 개념을 섞지 않기, 템플릿으로 일반적인 자료 구조와 알고리즘 만들기, 알맞은 검사와 안전장치 두기, 확장할 수 있게 설계하기
  - 인터페이스의 여섯 전략: 익숙한 방식 따르기, 필요한 기능 빠뜨리지 않기, 군더더기 없애기, 문서 제공하기, 같은 기능을 여러 방법으로, 맞춤 설정 제공하기
  - 자주 부딪치는 일반성과 쓰기 쉬움을 함께 얻는 법
  - 가장 중요한 설계 원칙을 담은 머리글자 SOLID

## 정리

| 요소 | 핵심 |
| --- | --- |
| 여러 방법 | 분명한 이유가 있을 때만 예외적으로 |
| 맞춤 설정 | 기본 동작은 그대로, 바꾸고 싶은 사람만. 의존성 주입, 콜백, 템플릿 매개변수 |
| 일반성과 쓰기 쉬움 | 인터페이스를 여럿으로 나누고, 흔한 경우에는 기본값을 |
| 좋은 추상화 | 경험과 반복. 안정적인 공개 멤버 함수, 짝 클래스, 속성은 멤버 함수로 |
| SOLID | 단일 책임, 열림/닫힘, 리스코프 치환, 인터페이스 분리, 의존 관계 역전 |

## 복습 질문

<details>
<summary>SOLID의 다섯 글자가 뜻하는 원칙은?</summary>

- S: 단일 책임 원칙
- O: 열림/닫힘 원칙
- L: 리스코프 치환 원칙
- I: 인터페이스 분리 원칙
- D: 의존 관계 역전 원칙

</details>

<details>
<summary>라이브러리가 진행률을 알려 주고 싶다. 콘솔에 출력하는 대신 무엇을 제공하면 좋은가?</summary>

- 진행률이 바뀔 때마다 부를 콜백을 클라이언트가 등록하게 함
- 콘솔에 찍을지, 진행 막대를 그릴지, 무시할지는 클라이언트가 정함

</details>

<details>
<summary>"동물" 인터페이스에 `fly()`, `swim()`, `run()`을 모두 넣었더니, 펭귄 클래스가 `fly()`에서 예외를 던지게 되었다. 어떤 원칙을 어겼고 어떻게 고치는가?</summary>

- 인터페이스 분리 원칙. 쓸 일 없는 멤버 함수를 억지로 구현하게 함
- `Flyer`, `Swimmer`, `Runner`처럼 작은 인터페이스로 나누고, 펭귄은 `Swimmer`와 `Runner`만 구현함
- 리스코프 치환 원칙과도 관련 있음. "동물"을 쓰던 자리에 펭귄을 넣으면 `fly()`의 동작이 달라짐

</details>

<details>
<summary>주문 처리 클래스가 안에서 `MySqlDatabase`를 직접 만들어 쓴다. 의존 관계 역전 원칙을 따르게 바꾸면?</summary>

- `Database` 인터페이스를 정의하고, 주문 처리 클래스는 그 인터페이스에만 기댐
- 실제로 쓸 데이터베이스 구현은 생성자 등으로 밖에서 넣어 줌(의존성 주입). 테스트 때는 가짜 구현을 넣을 수 있음

</details>

<details>
<summary>좋은 추상화를 만드는 데 가장 중요하다고 한 것은?</summary>

- 반복. 의견을 구하고 응답하고, 필요하면 바꾸고, 실수에서 배우기
- 최고의 인터페이스가 처음 적은 것인 경우는 드묾

</details>
