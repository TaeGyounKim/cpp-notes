- 다루는 것: 재사용의 나머지 절반. 4장은 남의 코드를 **가져다 쓰는** 법이었고, 이 장은 내 코드를 **다시 쓸 수 있게 만드는** 법
- 이 글에서 배우는 요소: 재사용을 위한 설계의 이유, 재사용할 수 있는 코드의 두 조건, 클라이언트라는 말, 추상화와 핸들, 코드 구조를 짜는 전략 다섯 가지(관계없는 개념 나누기, 하위 시스템, 클래스 계층과 템플릿 믹스인, 집합, 화면 의존 없애기)
- 잘 설계된 라이브러리는 쓰는 즐거움이 있고, 엉망인 라이브러리는 차라리 직접 짜고 싶게 만듦. 남에게 줄 라이브러리를 만들든 클래스 계층 하나를 정하든, 재사용을 염두에 두고 설계할 것
- 5장의 객체 지향 설계 원칙 위에 쌓는 장

## 재사용의 철학

- 나와 다른 프로그래머가 다시 쓸 수 있는 코드를 설계해야 함
  - 남에게 줄 생각으로 만드는 라이브러리와 프레임워크만이 아님. 프로그램을 위해 설계하는 모든 클래스, 하위 시스템, 구성 요소에 해당함
- 늘 기억할 표어
  - "한 번 쓰고, 여러 번 쓴다"
  - "코드 중복을 피한다"
  - **DRY** (Don't Repeat Yourself): 같은 것을 되풀이하지 말 것
- 이유

| 이유 | 설명 |
| --- | --- |
| 코드는 한 프로그램에서만 쓰이는 일이 드묾 | 어떻게든 다시 쓰이게 됨. 처음부터 그에 맞게 설계할 것 |
| 시간과 돈을 아낌 | 나중의 재사용을 막는 설계는, 비슷한 기능이 필요할 때 나나 동료가 바퀴를 다시 발명하게 만듦 |
| 팀의 다른 사람이 내 코드를 쓸 수 있어야 함 | 혼자 일하는 경우는 드묾. 재사용을 위한 설계는 "협력하는 코딩"이라고도 할 수 있음 |
| 재사용하지 않으면 코드가 중복되고, 중복은 유지 보수의 악몽이 됨 | 중복된 코드에서 버그가 나오면 복사된 모든 곳을 고쳐야 함. 코드를 복사해서 붙이려 할 때마다 도우미 함수나 클래스로 빼는 것을 적어도 한 번은 생각할 것 |
| 가장 덕을 보는 사람은 나 | 경험 많은 프로그래머는 코드를 버리지 않음. 시간이 지나며 자기만의 도구 모음을 키워 감 |

:::caution
회사의 직원으로서 설계하거나 작성한 코드의 지식재산권은 대개 본인이 아니라 회사에 있다. 퇴사할 때 그 설계나 코드의 사본을 가지고 나가는 것은 불법인 경우가 많다. 고객을 위해 일하는 개인 사업자도 마찬가지다.
:::

## 재사용할 수 있는 코드의 두 조건

| 조건 | 뜻 |
| --- | --- |
| 일반적임 | 조금 다른 목적이나 다른 분야에도 쓸 수 있을 만큼. 특정 프로그램의 세부 사항이 박힌 부품은 다른 프로그램에서 다시 쓰기 어려움 |
| 쓰기 쉬움 | 인터페이스나 기능을 이해하는 데 시간이 많이 들지 않음. 다른 프로그래머가 자기 프로그램에 금방 넣을 수 있어야 함 |

- 이 글은 첫째 조건(일반적인 구조)을, 셋째 글은 둘째 조건(쓰기 쉬운 인터페이스)을 주로 다룸
- 라이브러리를 건네는 방법도 설계에 제약을 줌

| 건네는 형태 | 설명 |
| --- | --- |
| 소스 코드 | 받는 쪽이 자기 프로젝트에 소스를 그대로 넣음 |
| 정적 라이브러리 | 컴파일된 코드. 받는 쪽 프로그램에 링크되어 함께 들어감 |
| 동적 라이브러리 | 실행할 때 불러 쓰는 컴파일된 코드. Windows의 `.dll`, Linux의 `.so` |

- 용어
  - **클라이언트** (client): 이 장에서는 내 인터페이스를 쓰는 **프로그래머**. 프로그램을 실행하는 사용자와 헷갈리지 말 것
  - **클라이언트 코드** (client code): 내 인터페이스를 쓰도록 작성된 코드
- 재사용할 수 있는 코드를 설계하는 가장 중요한 전략: 추상화

## 추상화를 쓸 것

- 추상화의 핵심: 인터페이스와 구현을 제대로 나누는 것 (4장)
  - **구현**: 하려는 일을 해내려고 내가 쓰는 코드
  - **인터페이스**: 다른 사람이 내 코드를 쓰는 방법
  - C에서는 라이브러리의 함수들을 선언한 헤더 파일이 인터페이스. 객체 지향에서는 클래스의 공개된 멤버 함수와 속성의 모음이 인터페이스
  - 좋은 인터페이스에는 공개 **멤버 함수**만 있음. 속성(데이터 멤버)은 절대 `public`으로 두지 않고, 필요하면 getter와 setter로 내보냄
- 추상화가 주는 것

| 누가 | 얻는 것 |
| --- | --- |
| 클라이언트 | 구현의 세부 사항을 걱정하지 않음. 속을 몰라도 기능을 씀 |
| 나(라이브러리 작성자) | 인터페이스를 바꾸지 않고 속을 고칠 수 있음. 클라이언트가 쓰는 법을 바꾸지 않아도 개선과 수정을 내놓을 수 있음. 동적 라이브러리라면 클라이언트가 다시 빌드할 필요조차 없을 수 있음 |
| 둘 다 | 어떤 상호 작용을 기대하고 어떤 기능을 지원하는지 인터페이스에 정확히 적을 수 있음(3장의 문서화). 의도하지 않은 방식으로 쓰여 생기는 뜻밖의 동작과 버그를 막음 |

:::caution
인터페이스를 설계할 때 구현의 세부 사항을 클라이언트에게 드러내지 않는다.
:::

### 핸들은 불투명하게

- 어떤 라이브러리는 한 함수가 돌려준 정보를 클라이언트가 보관했다가 다른 함수에 넘기게 함. 이것을 **핸들** (handle)이라고 부르기도 함
  - 호출과 호출 사이에 상태를 기억해야 하는 낱낱의 대상을 가리킬 때 씀
  - 실제 예: 그래픽 라이브러리 OpenGL. 버퍼를 만드는 함수가 버퍼를 가리키는 정수 핸들(`GLuint`)을 돌려주고, 그 버퍼로 무언가를 할 때마다 그 핸들을 넘김
- 핸들이 필요한 설계라면 속을 드러내지 말 것
  - **불투명한** (opaque) 클래스로 만듦. 클라이언트가 데이터 멤버에 직접도, getter·setter로도 닿을 수 없게
  - 클라이언트가 핸들 안의 변수를 만지작거리게 하지 말 것. 나쁜 예: 오류 기록을 켜려면 "불투명하다던" 핸들 구조체의 특정 멤버를 클라이언트가 직접 바꿔야 하는 라이브러리
- 아쉬운 점: C++의 클래스 문법은 좋은 추상화에 썩 친절하지 않음
  - 공개 인터페이스와 비공개(`private`, `protected`) 데이터 멤버를 한 클래스 정의에 함께 적어야 해서, 구현의 일부가 클라이언트 눈에 보임
  - 이를 피해 깔끔한 인터페이스를 내놓는 기법: 9장
- 추상화는 설계 전체를 이끌어야 할 만큼 중요함
  - 결정을 내릴 때마다 물을 것: 이 선택이 추상화의 원칙을 지키는가?
  - 클라이언트의 입장이 되어 볼 것: 인터페이스를 쓰려면 속의 구현을 알아야 하는가?
  - 이 규칙에 예외를 두는 일은 거의 없어야 함
- 추상화로 재사용할 수 있는 코드를 설계할 때 집중할 두 가지
  - 코드를 알맞게 **구조화**함: 어떤 클래스 계층을 쓸까? 템플릿을 쓸까? 하위 시스템을 어떻게 나눌까? (이 글과 다음 글)
  - **인터페이스**를 설계함: 라이브러리의 기능으로 들어가는 "입구" (셋째 글)

## 코드를 재사용하기 좋게 구조화하기

- 재사용은 설계의 처음부터, 모든 수준에서 생각해야 함: 함수 하나, 클래스 하나, 라이브러리와 프레임워크 전체
- 이 글에서는 이 모든 수준을 **구성 요소** (component)라고 부름
- 아래 전략들은 모두 코드를 **일반적으로** 만드는 데 초점이 있음

### 관계없는 개념을 섞지 않을 것

- 구성 요소 하나는 한 가지 일이나 한 무리의 일에 집중해야 함
  - **응집도** (cohesion)가 높다고 함. **단일 책임 원칙** (single responsibility principle, SRP)이라고도 부름. 마지막 글에서 다시 다룸
  - 난수 생성기와 XML 해석기처럼 관계없는 개념을 한데 섞지 말 것
- 재사용할 생각이 없는 코드에서도 이 전략을 기억할 것
  - 프로그램 전체가 그대로 재사용되는 일은 드묾. 그 일부, 하위 시스템이 다른 프로그램에 들어가거나 조금 다르게 고쳐져 쓰임
  - 그러니 논리적으로 다른 기능은 다른 구성 요소로 나눠, 다른 프로그램에서 다시 쓸 수 있게 함. 구성 요소마다 책임이 분명해야 함
- 실제 세계의 설계 원칙인 "따로 떨어진, 바꿔 끼울 수 있는 부품"을 본뜬 것
- 예: 드론
  - `Drone` 클래스에 배터리의 속성과 행동을 몽땅 넣을 수도 있음
  - 그러나 배터리는 드론과 묶여 있지 않은, 떼어 낼 수 있는 부품. 다른 기기에도 들어감
  - 올바른 설계: 배터리만의 기능을 담은 `Battery` 클래스를 두고, `Drone`은 `Battery`를 가짐

### 프로그램을 논리적인 하위 시스템으로 나눌 것

- 하위 시스템은 따로따로 다시 쓸 수 있는, 떨어진 부품으로 설계함
  - **결합도** (coupling)를 낮춘다고 함. 한 부품이 다른 부품에 덜 기댈수록 따로 쓰기 쉬움
- 예: 네트워크 게임
  - 네트워크 부분과 그래픽 사용자 인터페이스 부분을 다른 하위 시스템으로 둠
  - 혼자 하는 게임을 만들 때는 그래픽 부분만, 파일 공유 프로그램을 만들 때는 네트워크 부분만 다시 씀. 한쪽을 쓰려고 다른 쪽까지 끌고 올 필요가 없음
- 하위 시스템마다 추상화의 원칙을 지킬 것
  - 각 하위 시스템을, 일관되고 쓰기 쉬운 인터페이스를 갖춰야 하는 **작은 라이브러리**로 생각함
  - 그 작은 라이브러리를 쓰는 사람이 나뿐이어도, 잘 설계된 인터페이스와 구현의 덕을 봄

### 클래스 계층으로 논리적 개념을 나눌 것

- 하위 시스템뿐 아니라 클래스 수준에서도 관계없는 개념을 섞지 말 것
- 예: 공유 자전거 서비스
  - 자전거 클래스에 대여 로직(대여자, 요금, 반납)을 바로 넣었다고 하자
  - 대여하지 않는 개인 자전거가 필요할 때, 대여 로직은 쓸모없는 짐이 됨. 결제 라이브러리처럼 원래는 필요 없는 것을 링크해야 할 수도 있음
  - 해결 하나: 클래스 계층. "대여용 자전거"를 "자전거"의 파생 클래스로 둠. 대여가 필요 없는 프로그램은 기반 클래스만 쓰고 그 비용을 치르지 않음
- 개념이 둘일 때는 잘 맞지만, 셋 이상이면 복잡해짐
  - 자전거와 킥보드가 있고, 각각 대여용일 수도 아닐 수도 있음
  - 자전거와 킥보드는 탈것(`Vehicle`)의 파생 클래스. 대여용은 각각의 파생 클래스여야 함
  - 한 줄로 이어진 계층으로는 이 둘을 동시에 나눌 수 없음
- 방법: 대여라는 측면을 **믹스인**으로 만듦
  - 5장의 믹스인은 다중 상속으로 만들었음(`FolderIcon`이 `Image`와 `Clickable`을 물려받음)
  - 여기서는 다른 종류의 믹스인이 더 잘 맞음: **클래스 템플릿**으로 만드는 믹스인

```cpp
template <typename T>
class Rentable : public T
{
    // 대여에 필요한 모든 것
};

Rentable<Bicycle> shareBike;
Rentable<Scooter> shareScooter;
```

- 읽는 법
  - `class Derived : public Base {};`: `Derived`가 `Base`를 물려받는다는 뜻 (10장)
  - `Rentable<T>`는 `T` 자리에 들어온 클래스를 물려받는 클래스 템플릿 (12장)
  - `Rentable<Bicycle>`: 컴파일러가 `T`를 `Bicycle`로 바꿔 `Bicycle`을 물려받는 클래스를 만듦. `Rentable<Scooter>`도 같은 방식

  - 대여 코드는 `Rentable`에 한 번만 있음. 자전거와 킥보드 모두에 붙음
  - `myBike`는 그냥 `Bicycle`. 대여 기능도 그 비용도 없음
  - `Rentable<Bicycle>`은 원래 기능(`getWheelCount`)과 대여 기능(`rentTo`)을 모두 가짐
  - `this->getId()`의 `this->`: 템플릿 안에서 물려받는 클래스의 멤버를 부를 때 필요함. 이유는 12장
- 이 해법에는 클래스가 넷 필요함(`Vehicle`, `Bicycle`, `Scooter`, `Rentable`). 그래도 기능을 깔끔하게 나누는 값어치가 있음
- 믹스인의 더 자세한 기법: 32장
- 관계없는 개념을 섞지 않는 것은 설계의 **모든 수준**에 해당함
  - 멤버 함수 수준에서도: 함수 하나가 논리적으로 관계없는 일을 여럿 하면 안 됨. 값을 바꾸는 일(set)과 값을 살펴보는 일(get)을 한 함수에 섞지 말 것

### 집합으로 논리적 개념을 나눌 것

- 집합(has-a): 객체가 다른 객체를 담아 기능의 일부를 맡김 (5장). 고를 수 있다면 is-a보다 has-a
- 예: 조직도 프로그램을 만듦
  - 조직도를 담기에는 트리 자료 구조가 딱 맞음
  - 트리 코드를 `OrgChart` 클래스 안에 바로 넣지 말고, 따로 `Tree` 클래스를 만듦. `OrgChart`는 `Tree`를 가짐
  - 그러면 `Tree`를 다른 프로그램(파일 탐색기의 폴더 구조, 댓글의 답글 구조)에서 쉽게 다시 씀
- 위 드론 예의 `Battery`도 같은 전략

### 사용자 인터페이스 의존을 없앨 것

- 데이터를 다루는 라이브러리라면, 데이터 처리와 사용자 인터페이스를 떼어 놓아야 함
  - 라이브러리가 어떤 사용자 인터페이스에서 쓰일지 가정하지 말 것
  - 표준 콘솔 입출력(`std::println`, `std::cin`)을 라이브러리 안에서 쓰지 말 것. 그래픽 프로그램에서 쓰이면 말이 안 됨. Windows의 그래픽 프로그램에는 대개 콘솔이 아예 없음
  - 그래픽 프로그램에서만 쓰일 거라 생각해도, 메시지 창 같은 알림을 띄우지 말 것. 사용자에게 무엇을 어떻게 보여 줄지는 클라이언트 코드가 정할 일
- 이런 의존이 주는 피해
  - 재사용하기 나쁨
  - 클라이언트 코드가 오류에 알맞게 대응하지 못함. 예: 조용히 처리하고 넘어가고 싶어도 그럴 수 없음

## 헷갈리기 쉬운 점

- 클라이언트는 프로그램의 사용자다?
  - 이 장의 클라이언트는 내 인터페이스를 쓰는 **프로그래머**. 사용자는 완성된 프로그램을 실행하는 사람
- 재사용할 수 있는 코드는 일반적이기만 하면 된다?
  - 쓰기 쉬워야 함. 너무 일반적이어서 쓰는 법을 익히기 어려우면 아무도 다시 쓰지 않음
- 응집도와 결합도
  - 응집도는 **한 구성 요소 안**이 얼마나 한 가지에 집중하는가(높을수록 좋음). 결합도는 **구성 요소 사이**가 얼마나 서로 기대는가(낮을수록 좋음)
- 라이브러리 함수가 오류를 친절하게 출력해 주면 좋다?
  - 출력 방식을 라이브러리가 정해 버리면, 콘솔이 없는 프로그램이나 오류를 조용히 처리하려는 프로그램에서 쓸 수 없음. 오류는 돌려주고, 알리는 것은 부르는 쪽이 함
- 템플릿 믹스인과 5장의 믹스인은 다른 개념이다?
  - "능력 하나를 덧붙인다"는 생각은 같음. 만드는 문법이 다를 뿐(다중 상속 대 템플릿). 템플릿 쪽은 어떤 기반 클래스에든 붙일 수 있고, 원래 계층을 건드리지 않음

## 정리

| 요소 | 핵심 |
| --- | --- |
| 재사용의 철학 | 한 번 쓰고 여러 번 씀. DRY. 복사하고 싶을 때 함수나 클래스로 뺌 |
| 두 조건 | 일반적일 것, 쓰기 쉬울 것 |
| 추상화 | 인터페이스에는 공개 멤버 함수만. 구현을 드러내지 않음. 핸들은 불투명하게 |
| 높은 응집도 | 구성 요소 하나는 한 가지 일. 떼어 낼 수 있는 부품은 따로 클래스로 |
| 낮은 결합도 | 하위 시스템을 서로 기대지 않게. 각각을 작은 라이브러리처럼 |
| 계층과 템플릿 믹스인 | 서로 독립된 개념(탈것의 종류, 대여)을 따로 나눔 |
| 화면 의존 없애기 | 라이브러리는 출력하지 않고 결과와 오류를 돌려줌 |
