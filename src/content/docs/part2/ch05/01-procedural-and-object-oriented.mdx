## 절차적으로 생각하기

- **절차적 언어** (procedural language): 코드를 작은 조각(프로시저, 함수)으로 나누고, 조각마다 한 가지 일을 하게 하는 언어. 대표: C
- 함수는 컴퓨터를 위한 것이 아님. 코드가 전부 `main()`에 있든 이름 붙은 조각으로 나뉘어 있든 컴퓨터는 상관하지 않음. 쓰는 사람과 읽는 사람을 위한 추상화
- 절차적 사고의 출발점이 되는 질문: **"이 프로그램은 무엇을 하는가?"**
  - 이 질문에 말로 답하면 절차적으로 생각한 것
- 예: 도서관 대출 프로그램
  - 답: "먼저 책 목록을 불러온다. 다음에 빌리려는 책을 찾는다. 빌릴 수 있으면 대출 처리한다. 끝으로 현황을 출력한다"
  - 이 답이 그대로 함수가 됨: `loadBooks()`, `findBook()`, `checkOut()`, `printStatus()`

- 절차적 방식이 잘 맞는 경우: 프로그램이 정해진 단계를 차례로 밟을 때
- 한계

| 한계 | 설명 |
| --- | --- |
| 일이 한 줄로 흐르지 않는 프로그램 | 요즘의 큰 프로그램에서는 사용자가 아무 때나 아무 명령을 내림. 정해진 순서가 없음 |
| 데이터에 대해 말하지 않음 | "책을 찾는다"고 했을 뿐, 책이 무엇으로 이루어지는지는 다루지 않았음 |
| 데이터를 지킬 수 없음 | 예제의 마지막 줄: 어떤 코드든 `isOnLoan`을 직접 바꿀 수 있음. 대출 규칙이 `checkOut()` 안에 있어도 그것을 건너뛰는 것을 막지 못함 |

- 용어 주의: C에서 프로시저를 "함수"라고 부르지만, C는 함수형 언어(functional language)가 아님. 함수형은 절차적과 다른, Lisp 같은 언어가 쓰는 전혀 다른 방식의 추상화
- 지금까지 절차적으로 생각해 왔다 해도 문제없음. 객체 지향은 소프트웨어를 생각하는 또 하나의, 더 유연한 방법일 뿐

## 객체 지향으로 생각하기

- **객체 지향 프로그래밍** (object-oriented programming, OOP)의 출발점이 되는 질문: **"어떤 실제 대상들을 본뜨고 있는가?"**
- 생각의 단위가 다름
  - 절차적: 프로그램을 **할 일**로 나눔
  - 객체 지향: 프로그램을 **대상의 모형**으로 나눔
- 처음에는 막연하지만, 대상을 네 가지 관점으로 보면 분명해짐: 클래스, 구성 요소, 속성, 행동

### 클래스와 객체

- 자전거를 생각해 보면 두 가지 이야기를 할 수 있음

| 이야기 | 예 | 용어 |
| --- | --- | --- |
| 자전거라는 것 일반 | "자전거는 바퀴가 둘이고 페달을 밟아 움직이는 탈것이다" | 클래스 |
| 어느 한 자전거 | "지금 현관에 세워 둔 내 파란 자전거" | 객체 |

- **클래스** (class): 어떤 부류의 대상을 그 부류이게 하는 것을 묶어 정의한 것 <CppRef path="cpp/language/classes" />
- **객체** (object): 클래스의 **인스턴스** (instance). 같은 클래스의 다른 인스턴스와 구별되는 특징을 지닌 낱낱의 것
  - 내 자전거는 자전거 클래스에 속함. 그러므로 바퀴가 둘이고 페달로 움직인다는 것을 앎
  - 거기에 더해 "파란색, 21단"이라는 그 자전거만의 값이 있음
- 도서관 예에서: "책"은 클래스. 책이 무엇으로 이루어지는지에 대한 정의. "서가 3번 칸에 꽂힌 그 한 권"은 객체
- C의 눈으로 보면: 클래스와 객체는 타입과 변수의 관계와 같음

### 구성 요소

- 복잡한 대상은 더 작은 부품으로 이루어짐
  - 자전거: 프레임, 바퀴, 브레이크, 변속기
  - 바퀴: 타이어, 림, 바큇살
- **구성 요소** (component): 본질은 클래스와 같음. 더 작고 더 구체적일 뿐
- 대상을 더 작은 구성 요소로 나눠 생각하는 능력은 객체 지향의 기본. 절차적 프로그래밍에서 복잡한 일을 작은 함수로 나누는 것과 같은 역할
- 좋은 객체 지향 프로그램의 `Bicycle` 클래스는 자전거의 모든 것을 직접 기술하지 않음. 그러면 클래스가 거대해짐. 대신 더 작고 다루기 쉬운 구성 요소들을 거느림

### 속성

- **속성** (property): 객체를 다른 객체와 구별해 주는 특징. "이 객체는 무엇이 다른가?"에 대한 답
- 같은 클래스의 객체는 모두 같은 속성을 가짐. 값이 다를 뿐
  - 모든 자전거에는 색과 기어 단수가 있음. 내 자전거는 파란색 21단, 다른 자전거는 빨간색 7단
- 속성은 두 수준에서 생각할 수 있음

| 수준 | 뜻 | 예 |
| --- | --- | --- |
| 클래스 속성 | 그 클래스의 모든 객체가 함께 지니는 것 | 자전거는 바퀴가 둘 |
| 객체 속성 | 모든 객체에 있지만 값이 저마다 다른 것 | 색, 기어 단수 |

- 도서관 예에서 책의 객체 속성: 제목, 저자, 쪽수, 대출 중인지 여부

### 행동

- **행동** (behavior): 두 질문 가운데 하나에 대한 답
  - "이 객체는 무엇을 하는가?"
  - "이 객체에 무엇을 할 수 있는가?"
- 자전거: 스스로 하는 일은 별로 없지만 자전거에 할 수 있는 일은 있음. 타기, 브레이크 잡기, 기어 바꾸기
- 도서관 예에서: 절차적으로 생각할 때 "대출 처리"는 프로그램의 기능 가운데 하나였음. 객체 지향으로 생각하면 **책이 스스로 대출될 수 있음**. 대출은 책 객체의 행동이 됨
- 객체 지향 프로그래밍에서는 기능을 하는 코드의 대부분이 함수에서 클래스 안으로 옮겨감
  - 얻는 것: 코드를 그것이 다루는 데이터에 붙여 두는 훨씬 풍부한 수단
  - C++에서 행동은 클래스의 **멤버 함수** (member function)로 구현함

### 다시 설계해 보기

- 도서관 대출 프로그램을 네 관점으로 다시 설계

| 클래스 | 구성 요소 | 속성 | 행동 |
| --- | --- | --- | --- |

### 전부 클래스에 넣어야 하는 것은 아님

- C++은 여러 패러다임을 지원하는 언어. 모든 것을 클래스 안에 넣도록 강제하는 언어(예: Java)와 다름
- 객체 지향이 맞는 곳에 클래스를 쓰고, 어떤 기능은 독립 함수로 두는 것은 전혀 잘못이 아님
- 표준 라이브러리도 그렇게 되어 있음. 알고리즘은 모두 클래스의 멤버가 아니라 독립 함수 <Badge text="C++20" /> <CppRef path="cpp/algorithm/ranges/sort" />

## 클래스로 가득한 세계에서

- 절차적 사고에서 객체 지향으로 넘어온 프로그래머가 흔히 겪는 일: 속성과 행동을 클래스로 묶는다는 발상에 눈이 뜨임. 하던 프로그램의 일부를 클래스로 다시 쓰거나, 전부 버리고 처음부터 객체 지향으로 다시 짜고 싶어짐
- 클래스를 쓰는 두 가지 태도

| 태도 | 방식 | 평가 |
| --- | --- | --- |
| 클래스는 유용한 도구 | 데이터와 기능을 묶기 좋은 곳에만 클래스를 씀. "클래스처럼 느껴지는" 부분, 즉 따로 떼어 실제 세계의 말로 설명할 수 있는 부분 | 잘못된 것이 없음 |
| 모든 것이 클래스 | 실제 대상(책, 자전거)뿐 아니라 추상적인 개념(정렬기, 실행 취소)까지 전부 클래스로 만듦 | |

- 알맞은 지점은 대개 두 극단 사이의 어딘가. 처음에는 절차적 프로그램에 클래스 몇 개를 끼워 넣거나, 반대로 `int` 하나까지 클래스로 감싸게 됨. 경험이 쌓이면서 균형점을 찾음

### 지나친 클래스화

- 창의적인 객체 지향 설계와 "사소한 것까지 전부 클래스로 만들어 팀원을 괴롭히는 것" 사이는 종이 한 장 차이
- 예: 4장에서 설계한 오목 게임. 판을 나타내는 `Board`가 있고, 그 구성 요소로 돌을 나타내는 `Stone` 클래스를 둔다고 하자
- 멈추고 따져 볼 것: 돌에 클래스가 필요한가? `Stone` 클래스를 표로 적어 보면

| 클래스 | 구성 요소 | 속성 | 행동 |
| --- | --- | --- | --- |
| `Stone` | 없음 | 흑 또는 백 | 없음 |

- 표가 휑함. 온전한 클래스로 삼기에는 너무 잘다는 강한 신호
  - 열거형 `enum class Stone { None, Black, White }`면 충분함. 4장의 설계가 고른 방법
- 반론도 있음: 지금은 빈약해도 클래스로 해 두면 나중에 넓히기 쉬움. 예: "마지막에 놓인 돌인가", "몇 번째 수인가" 같은 속성을 더할 때
- 또 다른 길: 돌 대신 **칸의 상태**로 생각함. 칸은 비었거나, 흑이거나, 백. 추상 기반 클래스 `CellState`와 파생 클래스 셋을 두면 나중에 속성을 더할 자리가 생김
- 정답은 없음. 중요한 것은 설계할 때 이런 점을 **따져 보는 것**
- 기준: 클래스는 프로그래머가 코드를 다루기 쉽게 하려고 있는 것. "더 객체 지향적으로 보이려고"가 유일한 이유라면 잘못된 것

### 지나치게 일반적인 클래스

- 클래스가 아니어야 할 것을 클래스로 만드는 것보다 더 곤란한 것: 너무 일반적인 클래스
- 먼저, 추상적인 클래스 자체는 문제가 아님. 많은 프로그램에 "애플리케이션 클래스"가 있음. 애플리케이션은 손에 잡히는 대상이 아니지만 속성과 행동이 있으므로 클래스로 나타낼 만함
- **지나치게 일반적인 클래스**: 특정한 무엇도 나타내지 않는 클래스. 유연하고 재사용할 수 있게 만들려다 헷갈리는 것을 만들어 버린 경우
- 예: 문서 편집기. 문서 안에 글 문단, 그림, 표가 들어감
  - 지나치게 일반적인 접근: 이것들을 전부 "요소"로 보고, 모든 종류를 감당하는 클래스 하나를 만듦
  - 속성 `data`: 종류에 따라 글자들, 그림의 픽셀, 표의 칸들이 들어감
  - 행동 `handle()`: 종류에 따라 글을 줄 맞춰 놓거나, 그림을 그리거나, 표의 칸 너비를 계산함
- 너무 일반적이라는 단서는 **이름**에 있음
  - `data`: 그 자체로는 아무 뜻이 없는 말. 서로 아주 다른 세 가지 쓰임을 한 클래스에 욱여넣었기 때문에 이런 일반적인 말을 쓸 수밖에 없었음
  - `handle`: 종류마다 전혀 다른 일을 함
- 그렇다고 `Element` 클래스가 없어야 한다는 뜻은 아님. 있어야 함. 다만 담는 것이 달라야 함

| 클래스 | 담는 것 | 담지 않는 것 |
| --- | --- | --- |
| `Element` | 모든 요소에 공통인 속성: 문서 안의 위치, 차지하는 크기 | 글을 배치하는 코드, 그림을 그리는 코드 |
| `Paragraph`, `Picture`, `Table` | 그 종류에만 있는 속성과 기능 | |

- `Paragraph`, `Picture`, `Table`은 `Element`와 어떤 식으로든 관계가 있음. 클래스 사이의 관계를 어떻게 나타내는가: 다음 글에서 다룸

## 이전 표준에서는

| 이 글에서 쓴 것 | 들어온 표준 | 그 이전에는 |
| --- | --- | --- |
| `std::ranges::sort`와 멤버 함수를 기준으로 정렬 | C++20 | `std::sort(begin, end, 비교 람다)` |
| `std::println` | C++23 | `std::cout <<` |

- 클래스, 멤버 함수, `private`은 처음 표준(C++98)부터 있음

## 헷갈리기 쉬운 점

- 클래스와 객체
  - 클래스는 정의(자전거라는 것), 객체는 그 정의대로 만들어진 낱낱의 것(내 자전거). 타입과 변수의 관계
- 속성의 값이 다르다고 클래스가 다른 것이 아님
  - 파란 자전거와 빨간 자전거는 같은 클래스의 두 객체. 색이라는 속성의 값이 다를 뿐
- 클래스를 쓰면 객체 지향이다?
  - 구조체에 `public` 데이터만 담고 모든 일을 밖의 함수가 한다면 생각의 방식은 여전히 절차적. 객체 지향의 핵심은 데이터와 그것을 다루는 행동을 한데 묶는 것
- 객체 지향이 절차적 방식보다 언제나 낫다?
  - 정해진 단계를 차례로 밟는 작은 프로그램은 절차적으로 짜는 것이 더 단순함. C++에서는 둘을 섞어 쓰는 것이 자연스러움
- 클래스가 많을수록 객체 지향적인 좋은 설계다?
  - 속성 하나뿐이고 행동이 없는 클래스는 대개 변수나 열거형으로 충분함
- 클래스 하나로 여러 종류를 다 처리하면 재사용이 잘된다?
  - `data`, `handle` 같은 뜻 없는 이름이 나오기 시작하면 너무 일반적이라는 신호. 공통인 것만 한 클래스에 두고 종류별 기능은 종류별 클래스로

## 정리

| 요소 | 핵심 |
| --- | --- |
| 절차적 사고 | "이 프로그램은 무엇을 하는가?" 할 일을 함수로 나눔 |
| 객체 지향 사고 | "어떤 대상들을 본뜨는가?" 대상을 클래스로 나눔 |
| 클래스 / 객체 | 정의 / 그 정의의 인스턴스 |
| 구성 요소 | 큰 대상을 이루는 더 작은 클래스 |
| 속성 | 객체를 구별하는 특징. C++에서는 데이터 멤버 |
| 행동 | 객체가 하는 일, 객체에 할 수 있는 일. C++에서는 멤버 함수 |
| 지나친 클래스화 | 속성 하나, 행동 없음이면 클래스가 필요한지 의심 |
| 지나치게 일반적인 클래스 | `data`, `handle` 같은 이름이 단서. 공통부와 종류별 클래스로 나눔 |

<summary>절차적 사고와 객체 지향 사고가 각각 출발점으로 삼는 질문은?</summary>

- 절차적: "이 프로그램은 무엇을 하는가?"
- 객체 지향: "어떤 실제 대상들을 본뜨고 있는가?"

</details>

<details>
<summary>음악 재생 앱에서 "노래"를 클래스로 본다면 속성과 행동의 예는?</summary>

- 속성: 제목, 가수, 길이, 재생 횟수
- 행동: 재생하기, 멈추기, 즐겨찾기에 추가하기

</details>

<details>
<summary>절차적 예제에서는 `books[0].isOnLoan = true;`가 되고, 객체 지향 예제에서는 같은 일을 할 수 없는 이유는?</summary>

- 객체 지향 예제에서는 대출 상태가 `private` 데이터 멤버
- 상태를 바꾸는 길이 `checkOut()` 멤버 함수뿐이라, 대출 규칙을 건너뛸 수 없음

</details>

<details>
<summary>어떤 클래스의 속성이 값 하나뿐이고 행동이 없다. 무엇을 의심해야 하는가?</summary>

- 지나친 클래스화. 변수나 열거형으로 충분한지 따져 봄
- 다만 나중에 속성이나 행동이 늘 것이 분명하다면 클래스로 두는 선택도 타당함

</details>

<details>
<summary>클래스의 멤버 이름이 `data`, `process()`, `handle()`처럼 뜻 없는 말뿐이라면 무엇의 신호인가?</summary>

- 서로 다른 여러 쓰임을 한 클래스에 욱여넣은, 지나치게 일반적인 클래스
- 공통인 속성만 한 클래스에 남기고, 종류마다 다른 기능은 종류별 클래스로 나눔

</details>
