## 계층

- 클래스 A가 B의 기반 클래스이듯, B가 다시 C의 기반 클래스일 수 있음
- **클래스 계층** (class hierarchy): 이렇게 여러 단계로 이어진 is-a 관계의 모음

### 공통 부모 끌어올리기

- 예: 스마트 홈 앱. 처음에는 모든 기기를 `Device` 하나에서 바로 파생시킴
  - `Light`(조명), `Fan`(선풍기), `DoorLock`(문 잠금장치)
- 파생 클래스를 하나씩 만들다 보면 서로 비슷한 것들이 보임
  - 조명은 밝기를, 선풍기는 풍량을 0~100 단계로 조절함. 값을 범위 안에 묶는 코드가 똑같음
  - 이럴 때 둘 사이에 **공통 부모**를 하나 둘 것을 생각함: `AdjustableDevice`
- 그렇게 정리한 계층

| 단계 | 클래스 | 맡는 것 |
| --- | --- | --- |
| 1 | `Device` | 이름, 상태 보고 |
| 2 | `AdjustableDevice` | 0~100 단계 조절과 범위 검사 |
| 3 | `Light`, `Fan` | 단계를 무엇이라고 부르는가(밝기, 풍량) |
| 2 | `DoorLock` | 잠그기. 단계 조절이 없으므로 `Device`에서 바로 내려옴 |

- 볼 것

  - `using Device::Device;`: 기반 클래스의 생성자를 그대로 물려받는 문법. 10장에서 다룸

### 실제 세계의 분류와 기능상의 관계

- 가전제품을 잘 아는 사람이 이 계층을 보면 어색하다고 할 수 있음. 조명과 선풍기는 제품 분류로는 전혀 다른 범주
- 그러나 이것이 중요한 점: 코드에서는 **실제 세계의 관계**와 **기능을 함께 쓰는 관계** 사이에서 균형을 잡아야 함
  - 실제 세계에서 가까운 두 대상도 기능을 함께 쓰지 않으면 코드에서는 관계가 없을 수 있음(앞 글의 not-a)
  - 기기를 "조명 기기"와 "냉난방 기기"로 나눌 수도 있음. 하지만 그렇게 나눠도 기반 클래스로 모을 공통 기능이 생기지 않음
- 계층을 짜는 방법은 하나가 아님
  - 위 설계는 주로 "어떻게 조절하는가"로 나눔
  - 전력 사용량이나 설치 위치를 기준으로 나눈다면 전혀 다른 계층이 됨
  - 결국 중요한 것은 **클래스들이 어떻게 쓰일 것인가**. 쓰임새가 계층의 설계를 정함

### 좋은 계층의 조건

| 조건 | 뜻 |
| --- | --- |
| 기능상 의미 있는 관계로 묶음 | 분류표가 아니라 함께 쓰는 기능을 기준으로 |
| 공통 기능을 기반 클래스로 모아 코드를 재사용함 | 같은 코드가 파생 클래스마다 되풀이되지 않음 |
| 부모의 기능을 대부분 바꾸는 파생 클래스가 없음 | 예외: 부모가 추상 기반 클래스인 경우 |

## 다중 상속

- 지금까지의 예는 모두 상속의 사슬이 하나. 클래스마다 바로 위의 부모가 많아야 하나였음
- **다중 상속** (multiple inheritance): 한 클래스가 기반 클래스를 둘 이상 가지는 것 <CppRef path="cpp/language/derived_class" />
- 예 1: 동물을 세 갈래로 분류함
  - 크기에 따른 계층, 먹이에 따른 계층, 움직이는 방식에 따른 계층
  - 각 동물은 세 계층에서 하나씩 물려받음. 코끼리는 "큰 동물"이면서 "초식 동물"이면서 "걷는 동물"
- 예 2: 사용자 인터페이스의 그림 버튼
  - 누를 수 있는 그림은 그림이면서 버튼으로 보임
  - 구현: `Image`와 `Button`을 둘 다 물려받음
- C++은 다중 상속을 직접 지원함. Java 같은 언어는 아예 없앴음(추상 기반 클래스에 해당하는 인터페이스를 여럿 물려받는 것만 허용)
- 쓸모 있는 경우도 있지만, 많은 프로그래머가 꺼림. 비판하는 쪽의 근거 셋

### 문제 1: 그림으로 그리기 어려움

- 계층이 여럿이고 선이 서로 엇갈리면, 단순한 클래스 다이어그램도 금세 복잡해짐
- 클래스 계층은 코드 사이의 관계를 이해하기 쉽게 하려고 있는 것인데, 다중 상속에서는 서로 아무 관계 없는 부모 여럿이 한 클래스에 코드를 보탬
- 한 객체에 그렇게 많은 클래스가 코드를 보태면, 무슨 일이 일어나는지 정말로 따라갈 수 있는가?

### 문제 2: 깔끔한 계층을 망침

- 동물 예에서 다중 상속으로 바꾸면 `Animal` 기반 클래스의 의미가 약해짐. 동물을 설명하는 코드가 세 계층으로 흩어지기 때문
- 처음에는 세 계층이 깔끔해도 금세 엉킬 수 있음
  - 예: "뛰는 동물"이 모두 같은 방식으로 움직일 뿐 아니라 먹이도 같다는 것을 알게 됨
  - 계층이 따로 나뉘어 있으니, 움직임과 먹이라는 두 개념을 잇는 방법은 파생 클래스를 또 하나 만드는 것뿐

  - 고치려면 `save.Image::draw()`처럼 어느 쪽인지 밝혀야 함. 그림 버튼이라면 사실 "그림을 그리고 테두리도 그리는" 자기만의 `draw()`가 필요함
- 두 기반 클래스가 **같은 기반 클래스**를 물려받았다면? (다이아몬드 모양)

```cpp
struct Widget { int x{ 0 }; };
struct Image : Widget {};
struct Button : Widget {};
struct ImageButton : Image, Button {};

ImageButton b;
b.x;   // 컴파일 오류: 'x'가 모호함
```

- `ImageButton` 안에 `Widget`이 **둘** 들어 있음. `Image`를 거쳐 온 것과 `Button`을 거쳐 온 것
  - 위치 `x`가 둘이 되어, 어느 쪽을 말하는지 모호해짐
  - 하나로 합치는 방법(가상 상속)이 있지만 그만큼 더 복잡해짐. 10장에서 다룸
- 이런 관계는 쓰는 사람에게도 읽는 사람에게도 코드로 구조를 짜기 어려움

### 피할 수 있으면 피한다

- 다른 언어들이 다중 상속을 빼 버릴 수 있었던 이유: 대개 피할 수 있기 때문
- 프로젝트의 설계를 내가 정할 수 있다면, 계층을 다시 생각해서 다중 상속을 쓰지 않는 길을 찾을 수 있는 경우가 많음
  - 예: 그림 버튼은 "버튼이 그림을 가진다"(has-a)로 설계할 수 있음

## 믹스인 클래스

- **믹스인 클래스** (mixin class): 클래스 사이의 또 다른 관계
  - C++에서 만드는 방법 하나는 문법상 다중 상속과 똑같음. 그러나 설계에서 뜻하는 바가 전혀 다름
- 믹스인 클래스가 답하는 질문: **"이 클래스는 그 밖에 무엇을 할 수 있는가?"**
  - 답은 흔히 "~할 수 있는"으로 끝남. 영어로는 `-able`
  - 예: `Clickable`(누를 수 있는), `Draggable`(끌 수 있는), `Printable`(출력할 수 있는)
- 온전한 is-a 관계를 맺지 않고 기능을 덧붙이는 방법. "~와 기능을 함께 나눈다"(shares-with) 관계라고 생각할 수 있음
- 예: 사용자 인터페이스
  - "그림 버튼은 그림이면서 버튼이다" 대신 "그림 버튼은 **누를 수 있는** 그림이다"
  - 바탕 화면의 폴더 아이콘은 **누를 수 있고 끌 수 있는** 그림
  - 개발자들은 이런 형용사를 즐겨 지어냄

### 다중 상속과 무엇이 다른가

- 코드의 차이보다 **클래스를 어떻게 생각하는가**의 차이

| | 다중 상속의 기반 클래스 | 믹스인 클래스 |
| --- | --- | --- |
| 묻는 질문 | "이것은 무엇인가?" | "이것은 그 밖에 무엇을 할 수 있는가?" |
| 범위 | 그 자체로 온전한 개념. 큰 계층을 이루기도 함 | 행동 한두 개. 예: `Clickable`은 누름에 관한 것만 |
| 계층 | 여러 단계로 깊어질 수 있음 | 큰 계층을 이루는 일이 드묾 |
| 결과 | 기능이 서로 뒤섞이기 쉬움 | 기능이 서로 섞여 들 일이 없음 |

- 그래서 믹스인은 다중 상속보다 이해하기 쉬움. 범위가 매우 좁기 때문
- 믹스인을 만드는 더 발전된 기법(템플릿을 이용하는 방법 등): 32장

## 헷갈리기 쉬운 점

- 실제 세계의 분류대로 계층을 짜야 한다?
  - 기능을 함께 쓰는 관계대로 짬. 조명과 선풍기가 같은 부모를 둔 것은 "단계 조절"이라는 기능 때문
- 계층은 깊을수록 정교한 설계다?
  - 단계마다 모아 둔 공통 기능이 있어야 의미가 있음. 자기만의 것이 없는 중간 클래스는 없애는 편이 나음
- 다중 상속에서 두 부모에 같은 이름의 함수가 있으면 나중에 적은 쪽이 쓰인다?
  - 어느 쪽도 고르지 않음. 모호하다는 컴파일 오류가 남
- 다이아몬드 모양에서 공통 조상은 하나만 들어 있다?
  - 기본으로는 갈래마다 하나씩, 둘이 들어 있음. 하나로 합치려면 따로 문법(가상 상속)이 필요함
- 믹스인과 다중 상속은 문법이 같으니 같은 것이다?
  - 문법은 같아도 설계의 뜻이 다름. 믹스인은 "무엇인가"가 아니라 "무엇을 더 할 수 있는가"를 덧붙이는 작은 클래스

## 5장을 마치며

- 5장에서 다룬 것
  - 절차적 사고와 객체 지향 사고: 할 일로 나누는가, 대상으로 나누는가
  - 클래스, 객체, 구성 요소, 속성, 행동
  - 지나친 클래스화와 지나치게 일반적인 클래스
  - 클래스 사이의 관계: has-a(집합, 합성), is-a(상속), not-a
  - 다형성, 리스코프 치환 원칙
  - 계층, 다중 상속, 믹스인
- 이 개념들은 C++에만 해당하지 않음. 객체 지향 언어라면 거의 어디에나 들어맞음
- 클래스 사이의 관계를 공부해야 하는 이유
  - 잘 이어진 클래스는 코드 재사용을 돕고 군더더기를 줄임
  - 팀으로 일하게 됨. 의미 있게 이어진 클래스는 읽기 쉽고 유지하기 쉬움
- 프로그램을 설계할 때 이 장의 "클래스 사이의 관계"를 참고 자료처럼 다시 펼쳐 봐도 좋음
- 다음 장: 재사용을 염두에 두고 코드를 설계하는 방법

## 정리

| 요소 | 핵심 |
| --- | --- |
| 클래스 계층 | 여러 단계로 이어진 is-a 관계 |
| 공통 부모 | 파생 클래스들에 같은 코드가 보이면 그 사이에 둠 |
| 좋은 계층 | 기능상의 관계, 공통 기능의 재사용, 부모의 기능을 대부분 바꾸는 자식이 없음 |
| 다중 상속 | 기반 클래스가 둘 이상. 그리기 어렵고, 계층을 망치고, 모호성이 생김 |
| 모호성 | 두 부모의 같은 이름은 컴파일 오류. `Base::name`으로 밝힘 |
| 믹스인 | "~할 수 있는" 능력 하나를 덧붙이는 작은 클래스 |

- 두 클래스 사이에 공통 부모(예: `RetryingSender`)를 두고 재시도 코드를 그곳으로 옮김
- 앞으로 만들 다른 발송 클래스도 그 기능을 그대로 얻음

</details>

<details>
<summary>좋은 객체 지향 계층의 세 조건은?</summary>

- 기능상 의미 있는 관계로 묶음
- 공통 기능을 기반 클래스로 모아 재사용함
- 부모의 기능을 대부분 바꾸는 파생 클래스가 없음 (추상 기반 클래스는 예외)

</details>

<details>
<summary>두 기반 클래스에 모두 `save()`가 있는 클래스의 객체에서 `obj.save()`를 부르면?</summary>

- 모호하다는 컴파일 오류
- `obj.First::save()`처럼 어느 쪽인지 밝히거나, 파생 클래스에 자기만의 `save()`를 둠

</details>

<details>
<summary>다중 상속을 비판하는 근거 세 가지는?</summary>

- 다이어그램으로 그리기 어렵고 관계를 따라가기 어려움
- 한 개념이 여러 계층으로 흩어져 깔끔한 계층을 망침
- 같은 이름의 멤버나 공통 조상 때문에 구현이 복잡해짐

</details>

<details>
<summary>게임의 여러 객체(상자, 문, 상인 캐릭터)에 "말을 걸 수 있다"는 능력을 주고 싶다. 공통 기반 클래스와 믹스인 가운데 어느 쪽이 맞는가?</summary>

- 믹스인(`Talkable` 같은)
- 상자, 문, 캐릭터는 그 밖에 공통점이 없고 이미 다른 계층에 속해 있음. 기존 계층을 깨지 않고 능력 하나만 덧붙이면 됨

</details>
