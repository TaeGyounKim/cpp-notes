- 다루는 것: 서로 닮았거나 어떤 식으로든 이어져 있는 클래스들의 관계를 설계하는 법
- 이 글에서 배우는 요소: has-a 관계(집합, 합성), is-a 관계(상속), 상속으로 기반 클래스와 달라지는 네 가지 방법, 다형성, has-a와 is-a 사이에서 고르기, 리스코프 치환 원칙, 관계가 없어야 할 곳(not-a)
- 객체 지향 언어는 클래스 사이의 관계를 나타내는 수단을 여럿 줌. 어려운 부분은 수단이 아니라 **실제로 어떤 관계인지 알아내는 것**
- 클래스 사이의 관계는 크게 둘: **has-a** (가진다)와 **is-a** (~의 한 종류이다)
- 문법(상속, `virtual`)은 10장에서 자세히 다룸. 여기서는 설계의 눈으로 봄

## has-a 관계

- **has-a 관계**: "A는 B를 가진다" 또는 "A는 B를 담고 있다". 한 클래스를 다른 클래스의 일부로 볼 수 있는 관계
- 앞 글의 구성 요소가 대개 has-a 관계. 더 작은 클래스들로 이루어진 클래스를 말하기 때문
- 일상의 예: 축구팀과 선수. 팀은 선수를 가짐
- 사용자 인터페이스의 예: 창과 버튼. 버튼과 창은 분명히 다른 클래스지만 관계가 있음. 버튼이 창 안에 있으므로 "창은 버튼을 가진다"
  - 화면의 요소들은 클래스로 옮기기 좋아서, 클래스 관계를 떠올릴 때 사용자 인터페이스를 생각해 보면 도움이 됨

### 집합과 합성

- has-a 관계는 두 가지로 나뉨. 기준은 **가진 쪽이 사라질 때 가진 것도 사라지는가**

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| **집합** (aggregation) | 가진 쪽이 사라져도 구성 요소는 계속 살아 있음 | 팀이 해체돼도 선수는 남아 다른 팀으로 감 |
| **합성** (composition) | 가진 쪽이 사라지면 구성 요소도 함께 사라짐 | 창을 닫으면 그 안의 버튼도 사라짐 |

- C++에서 흔히 나타내는 방법
  - 합성: 구성 요소를 **데이터 멤버로 직접** 둠. 가진 객체가 소멸할 때 데이터 멤버도 함께 소멸함
  - 집합: 구성 요소를 **가리키기만** 함(참조나 포인터). 구성 요소의 수명은 다른 곳에서 관리함

- 볼 것
  - 합성: 창의 블록이 끝나자 창이 사라지고, 버튼 둘이 뒤따라 사라짐. 데이터 멤버는 선언의 반대 순서로 소멸해서 "취소"가 먼저
  - 집합: 팀의 블록이 끝나도 팀만 사라짐. 선수는 `main`이 끝날 때 사라짐
- 포인터로 가리킬 때는 가리키는 대상이 먼저 사라지지 않게 해야 함. 소유와 수명을 다루는 방법은 7장에서 다룸

## is-a 관계 (상속)

- **is-a 관계**: "A는 B의 한 종류이다". 객체 지향 프로그래밍의 너무나 기본적인 개념이라 부르는 이름이 많음: 파생, 서브클래싱, 확장, **상속** (inheritance)
- 클래스가 "실제 세계에는 속성과 행동을 지닌 대상들이 있다"를 본뜬다면, 상속은 "그 대상들은 계층을 이루는 경향이 있다"를 본뜸
- 예: 앞 글의 문서 편집기
  - 문단은 요소이다. 그림은 요소이다. 표는 요소이다
  - 이 말만으로도 관계가 정해짐. 그리고 셋 모두에 공통인 것이 있음: 문서 안의 위치, 그려질 수 있다는 것
  - 공통인 것을 `Element` 클래스에 담고, `Paragraph`, `Picture`, `Table`은 `Element`의 **파생 클래스** (derived class)가 됨. `Element`는 **기반 클래스** (base class) <CppRef path="cpp/language/derived_class" />
  - 문단은 요소의 모든 특징에 더해, 문단을 문단이게 하는 특징을 지님
- 사용자 인터페이스의 예: 버튼에도 종류가 있음. 체크 상자는 버튼의 한 종류. 버튼이 "누르면 무언가를 하는 요소"라면, 체크 상자는 거기에 "체크되었는가"라는 상태를 더함
- is-a 관계를 맺을 때의 목표 하나: **공통 기능을 기반 클래스로 모으는 것**
  - 파생 클래스들에 비슷하거나 똑같은 코드가 있다면 그 코드를 기반 클래스로 옮길 수 있는지 볼 것
  - 그러면 고칠 일이 생겨도 한 곳만 고치면 되고, 앞으로 만들 파생 클래스도 그 기능을 공짜로 얻음

### 기반 클래스와 달라지는 방법

- 파생 클래스가 기반 클래스(부모 클래스, 슈퍼클래스라고도 함)와 달라지는 방법은 여럿이고, 하나의 파생 클래스가 여러 방법을 함께 씀
- 알아보는 법: "A는 ~한 B이다"라는 문장을 채워 봄

| 방법 | 문장 | 문서 편집기에서 |
| --- | --- | --- |
| 기능 더하기 | "그림은 크기를 바꿀 수 있는 요소이다" | `Picture`에만 `scale()`이 있음 |
| 기능 바꾸기 | "문단은 글자를 줄 맞춰 그리는 요소이다" | `Element`의 `draw()`를 `Paragraph`가 자기 방식으로 다시 정의함 (**재정의**, override) |
| 속성 더하기 | "그림은 너비와 높이가 있는 요소이다" | `Picture`에만 `m_width`, `m_height`가 있음 |
| 속성 바꾸기 | | 거의 쓰지 않음. 아래 설명 |

- 볼 것
  - `Picture`는 `scale()`이라는 기능과 `m_width`, `m_height`라는 속성을 더함
  - `Paragraph`와 `Picture`는 `draw()`를 바꿈. `getTop()`은 바꾸지 않고 그대로 물려받아 씀
  - 마지막 줄의 `Element`는 바꾸지 않은 기본 `draw()`를 씀
- 기능을 바꿀 때의 경고: 기반 클래스의 기능을 **전부** 바꾸고 있다면 애초에 상속이 맞지 않았다는 신호일 수 있음
  - 예외: 기반 클래스가 **추상 기반 클래스** (abstract base class)인 경우. 일부 멤버 함수에 구현이 없고, 파생 클래스가 그것을 반드시 구현해야 하는 클래스. 추상 기반 클래스로는 객체를 만들 수 없음. 10장에서 다룸

#### 속성 바꾸기는 거의 쓰지 않음

- C++에서는 기반 클래스에 있는 데이터 멤버와 이름이 같은 데이터 멤버를 파생 클래스에 또 선언할 수 있음
- 그러나 이것은 속성을 **바꾸는** 것이 아님. 이름이 같은 속성이 **하나 더 생기고**, 기반 클래스의 것을 가림(**이름 가리기**, hiding)

  - `Picture` 객체 안에 `width`가 둘 있음. 크기가 4바이트에서 8바이트로 늘어난 이유
  - `Picture`의 이름으로 부르면 640, 기반 클래스의 멤버 함수 안에서는 100. 같은 객체가 보는 쪽에 따라 다른 값을 가짐
- 헷갈리지 말 것: "속성을 바꾸는 것"과 "파생 클래스마다 속성의 **값**이 다른 것"은 다름
  - 모든 요소에 위치가 있음. 문단의 위치는 0, 그림의 위치는 30. 이것은 같은 속성에 값이 다를 뿐, 속성을 바꾼 것이 아님
- 이름 가리기의 자세한 동작: 10장

### 다형성

- **다형성** (polymorphism): 정해진 속성과 멤버 함수를 지키는 객체들을 서로 바꿔 가며 쓸 수 있다는 개념 <CppRef path="cpp/language/virtual" />
- 클래스 정의는 객체와 그 객체를 쓰는 코드 사이의 **계약**과 같음
  - `Paragraph` 객체라면 `Paragraph` 클래스의 속성과 멤버 함수를 반드시 지원함
  - 문단은 요소이므로, 모든 `Paragraph` 객체는 `Element` 클래스의 속성과 멤버 함수도 지원함
- 위 예제의 마지막 반복문이 다형성
  - 문서의 모든 요소를 돌면서 하나씩 그리라고 함
  - 모든 요소가 `Element`의 일원이므로 모두 그릴 줄 앎. 몇몇은 `draw()`를 자기 방식으로 바꿨지만, 그게 핵심
  - 반복문은 요소에게 "그려라"라고만 할 뿐, 그것이 어떤 종류인지 알지도 신경 쓰지도 않음. 각자 자기가 아는 방식으로 그림
- 다형성은 상속이 주는 것을 제대로 활용하는 부분. 새로운 종류의 요소(`Table`)를 더해도 반복문은 한 글자도 고치지 않음

## has-a와 is-a 사이의 가는 선

- 실제 세계에서는 구별이 쉬움. 아무도 "문단은 요소를 가진다"라고 하지 않음. 문단은 요소이다
- 코드에서는 분명하지 않을 때가 있음
- 예: 스택(stack)을 만들려고 함
  - **스택**: 맨 위에만 넣고(push) 맨 위에서만 꺼내는(pop) 자료 구조
  - 값을 담는 일은 `std::vector`가 이미 잘함. 그것을 활용하고 싶음
  - 스택은 `vector`의 한 종류인가(is-a), 아니면 `vector`를 가지는가(has-a)?

- is-a로 만든 `StackIsA`
  - `push`, `pop`, `top`을 더했으니 스택처럼 쓸 수 있음
  - 문제: `vector`의 공개 멤버 함수가 **전부 딸려 옴**. `insert`로 맨 아래에 끼워 넣고, `[]`로 가운데 값을 바꿀 수 있음. 스택의 규칙이 깨지는데 컴파일러는 막지 않음
  - 실행 결과의 `[99, 0, 2, 3]`: 스택이라면 있을 수 없는 상태
- has-a로 만든 `StackHasA`
  - `vector`를 데이터 멤버로 가짐. 밖에 내놓는 것은 스택다운 연산뿐
  - 속을 `std::deque`나 직접 만든 배열로 바꿔도 쓰는 쪽은 그대로
- 두 쪽의 근거를 표로

| | is-a | has-a |
| --- | --- | --- |
| 찬성 | 근본적으로 같은 추상(값을 순서대로 담음)에 특징이 다를 뿐. 기반 클래스의 기능을 그대로 물려받아 코드가 적음 | 필요한 멤버 함수만 골라 둘 수 있음. 기반 클래스에 무엇이 있는지 신경 쓰지 않아도 됨. 겉의 인터페이스를 바꾸지 않고 구현을 바꿀 수 있음 |
| 반대 | 스택은 정의상 맨 위만 건드리는 자료 구조. 아무 데나 넣을 수 있는 것을 스택이라 부를 수 없음. 맞지 않거나 원치 않는 속성과 멤버 함수가 새어 나옴 | 어떤 의미에서는 바퀴를 다시 발명함. 필요한 연산마다 감싸는 함수를 직접 써야 함. 기반 클래스의 다른 기능이 쓸모 있었을 수도 있음 |

- 이 경우 is-a에 반대하는 근거가 매우 강함
- 실제 표준 라이브러리의 `std::stack`도 has-a로 되어 있음. 다른 컨테이너를 감싸서 스택의 인터페이스만 내놓는 **컨테이너 어댑터** (container adaptor) <CppRef path="cpp/container/stack" />

### 리스코프 치환 원칙

- has-a와 is-a 사이에서 고를 때 도움이 되는 원칙
- **리스코프 치환 원칙** (Liskov substitution principle, LSP): 기반 클래스를 쓰던 곳에 파생 클래스를 대신 넣어도 **동작이 바뀌지 않아야** 함
- 스택에 적용하면
  - `std::vector`를 받아 "맨 앞에 값을 끼워 넣는" 코드가 있다고 하자
  - is-a라면 그 코드에 스택을 넘길 수 있음. 넘기면 스택의 규칙이 깨짐
  - 즉 `vector`를 쓰던 곳에 스택을 그대로 넣을 수 없음. 그러므로 is-a가 아니라 has-a여야 함
- 다른 설계도 가능함: 둘이 같은 기반 클래스를 물려받게 하는 등. 하나의 설계 문제에는 여러 해법이 있음
- 결론

:::caution[권장]
두 관계 가운데 고를 수 있다면 is-a보다 has-a를 택한다.
:::

- 이유를 한 줄로: has-a는 밖에 내놓을 인터페이스를 내가 정하고, is-a는 기반 클래스의 인터페이스를 전부 떠안음

## not-a 관계

- 클래스들이 어떤 관계인지 따지다 보면, **관계가 정말 있기는 한지**도 따져야 함
- 객체 지향 설계에 대한 열정이 쓸데없는 기반 클래스·파생 클래스 관계를 잔뜩 만드는 것으로 번지지 않게 할 것
- 흔한 함정: 실제 세계에서는 분명히 관계가 있지만 코드에서는 아무 관계가 없는 것

| 실제 세계의 분류 | 코드에서 관계로 만들 이유가 있는가 |
| --- | --- |
| 음악 장르: 음악 → 록 → 블루스 록 | 대개 없음. 장르마다 동작이 다르지 않음. 곡의 "장르"라는 속성 값으로 충분 |
| 회사 조직: 대표 → 개발 부문장 → 팀장 → 개발자 | 대개 없음. 직급이 달라도 다루는 방식이 같다면 "직급" 속성과 "상사"를 가리키는 관계(has-a)로 충분 |

- 객체 지향 계층이 본떠야 하는 것은 **기능상의 관계**. 분류표나 조직도처럼 겉보기 관계를 그대로 옮기면 안 됨
- 쓸데없는 상속을 피하는 가장 좋은 방법: 설계를 먼저 그려 볼 것
  - 클래스와 파생 클래스마다 둘 속성과 멤버 함수를 적어 봄
  - 다시 생각해야 하는 경우
    - 어떤 클래스에 **자기만의** 속성이나 멤버 함수가 하나도 없음
    - 기반 클래스의 속성과 멤버 함수를 파생 클래스가 **전부** 바꿈 (추상 기반 클래스는 예외)

## 헷갈리기 쉬운 점

- 집합과 합성
  - 차이는 "가진 것의 수명이 가진 쪽에 묶여 있는가". 창과 버튼은 합성, 팀과 선수는 집합
- 파생 클래스에 같은 이름의 데이터 멤버를 두면 속성이 바뀐다?
  - 바뀌지 않음. 하나가 더 생기고 기반 클래스의 것이 가려질 뿐. 기반 클래스의 코드는 여전히 자기 것을 봄
- 파생 클래스마다 속성의 값이 다르면 속성을 바꾼 것이다?
  - 같은 속성에 값이 다를 뿐. 문단과 그림의 위치가 다른 것은 속성 바꾸기가 아님
- 코드를 재사용하려면 상속해야 한다?
  - has-a로도 재사용함. `StackHasA`는 `vector`를 물려받지 않고도 `vector`의 기능을 다시 씀. 상속은 "한 종류이다"가 참일 때만
- 실제 세계에서 "A는 B의 한 종류"이면 코드에서도 상속이다?
  - 기능이 다르지 않으면 상속할 이유가 없음. 장르, 직급은 대개 속성 값으로 충분
- 리스코프 치환 원칙은 "파생 클래스를 기반 클래스 자리에 넣으면 컴파일된다"는 뜻이다?
  - `public`으로 물려받았다면 컴파일은 늘 됨. 원칙이 묻는 것은 넣었을 때 **동작이 그대로인가**

## 정리

| 요소 | 핵심 |
| --- | --- |
| has-a | A는 B를 가진다. 구성 요소의 관계 |
| 합성 / 집합 | 함께 사라짐(데이터 멤버) / 따로 삶(참조·포인터) |
| is-a | A는 B의 한 종류이다. 상속 |
| 달라지는 방법 | 기능 더하기, 기능 바꾸기(재정의), 속성 더하기. 속성 바꾸기는 사실상 이름 가리기 |
| 다형성 | 종류를 묻지 않고 기반 클래스의 인터페이스로 부름. 각자 자기 방식으로 동작 |
| 고르는 기준 | 고를 수 있으면 has-a. 리스코프 치환 원칙으로 확인 |
| not-a | 실제 세계의 분류를 그대로 계층으로 옮기지 않음. 기능상의 관계만 |

## 복습 질문

<details>
<summary>자동차와 엔진, 주차장과 자동차는 각각 합성인가 집합인가?</summary>

- 자동차와 엔진: 대개 합성. 자동차를 폐차하면 엔진도 함께 사라진다고 봄
- 주차장과 자동차: 집합. 주차장이 문을 닫아도 자동차는 남음

</details>

<details>
<summary>"알림 메시지"를 기반 클래스로 두고 "이메일 알림", "문자 알림"을 파생 클래스로 둔다. 다형성을 쓰면 어떤 코드가 가능해지는가?</summary>

- 알림들을 한 목록에 담고, 종류를 묻지 않고 하나씩 "보내라"라고 부르는 코드
- 새 알림 종류를 더해도 그 반복문은 고치지 않음

</details>

<details>
<summary>파생 클래스에 기반 클래스와 같은 이름의 데이터 멤버 `count`를 선언했다. 기반 클래스의 멤버 함수가 `count`를 읽으면 어느 값을 보는가?</summary>

- 기반 클래스의 `count`
- 파생 클래스의 것은 별개의 데이터 멤버이고, 기반 클래스의 것을 가릴 뿐 바꾸지 않음

</details>

<details>
<summary>"읽기 전용 목록"을 `std::vector`를 물려받아 만들면 안 되는 이유를 리스코프 치환 원칙으로 설명하면?</summary>

- `vector`를 받아 값을 고치는 코드에 읽기 전용 목록을 넘기면 값이 바뀌어 버림
- `vector`를 쓰던 자리에 넣었을 때 "읽기 전용"이라는 동작이 지켜지지 않으므로 is-a가 아님. `vector`를 가지는(has-a) 쪽으로 설계함

</details>

<details>
<summary>쇼핑몰에서 상품을 "의류 → 상의 → 티셔츠"로 분류한다. 이 분류대로 클래스 계층을 만들어야 하는가?</summary>

- 분류마다 동작(가격 계산, 배송 방법 등)이 실제로 다르지 않다면 아님
- 대개는 "분류"라는 속성 값으로 충분함. 계층은 기능상의 관계가 있을 때만

</details>
