- 다루는 것: 어떤 이름을 어디서 정의하고 어디서 쓸 수 있는지를 정하는 **링크** (linkage)
- 이 글에서 배우는 요소: 번역 단위와 링커, 네 가지 링크, 내부 링크, 이름 없는 네임스페이스, `static`, `extern`

:::note
링크는 여러 소스 파일 사이의 이야기라 이 글의 여러 파일 예는 정적 코드 블록으로 보인다. 결과와 오류 메시지는 로컬 GCC로 실제로 링크해 확인한 것이다. 페이지 안 예제는 한 파일 안에서 볼 수 있는 부분만 보인다.
:::

## 번역 단위와 링커

- 1장: C++ 소스 파일은 먼저 **전처리기**가 전처리기 지시자를 모두 처리함. 그 결과가 **번역 단위** (translation unit)
- 번역 단위는 저마다 따로 컴파일되어 **목적 파일**이 됨
  - 기계어 코드가 들어 있지만, 다른 곳의 함수 등을 가리키는 참조는 아직 풀리지 않음
- 마지막 단계의 **링커** (linker)가 목적 파일들을 하나로 묶어 실행 파일을 만들면서 그 참조를 풀어 줌
- 실제로는 단계가 더 있지만 이 글에서는 이 정도면 충분함

## 네 가지 링크

- 번역 단위 안의 이름(함수, 전역 변수 등)은 링크를 가지거나 가지지 않음. 링크는 그 이름을 어디서 정의할 수 있고 어디서 쓸 수 있는지를 정함 <CppRef path="cpp/language/storage_duration" />

| 링크 | 쓸 수 있는 곳 |
| --- | --- |
| 링크 없음 (no linkage) | 그 이름이 정의된 범위 안에서만 (예: 지역 변수) |
| 외부 링크 (external linkage) | 어느 번역 단위에서든 |
| 내부 링크 (internal linkage, 정적 링크라고도 함) | 지금 번역 단위 안에서만 |
| 모듈 링크 (module linkage) | 같은 모듈의 어느 번역 단위에서든 |

## 내부 링크

- 함수와 전역 변수는 기본적으로 **외부 링크**
- 예: 파일 두 개

```cpp
// main.cpp
void report();          // 선언만. 정의는 다른 파일에

int main()
{
    report();
}
```

```cpp
// other.cpp
#include <cstdio>

void report();
void report() { std::printf("report\n"); }
```

- 같은 함수의 원형을 여러 파일에 쓰는 것은 문법상 괜찮음
  - 헤더 파일에 원형을 두고 여러 소스 파일이 `#include`하면 전처리기가 바로 이 일을 해 줌. 원형 하나를 관리하기 쉬웠던 것이 헤더를 쓰던 이유
  - 지금은 C++이 모듈을 지원하므로 헤더보다 모듈을 권함
- 두 파일 모두 오류 없이 컴파일되고 링크도 됨. `report()`가 외부 링크라서 `main()`이 다른 파일에서 부를 수 있음

### 이름 없는 네임스페이스

- `other.cpp`의 `report()`를 **이름 없는 네임스페이스**로 감싸면 내부 링크가 됨 <CppRef path="cpp/language/namespace" />

```cpp
// other.cpp
#include <cstdio>

namespace
{
    void report() { std::printf("report\n"); }
}
```

- 이름 없는 네임스페이스 안의 것은 내부 링크. 같은 번역 단위에서는 선언 뒤 어디서든 쓸 수 있지만, 다른 번역 단위에서는 쓸 수 없음
- 이제 두 파일은 각자 컴파일은 되지만 **링크가 실패함**: ``undefined reference to `report()'``

### static

- 이름 없는 네임스페이스 대신 선언 앞에 `static`을 붙여도 내부 링크가 됨
  - 함수 이름이 처음 나오는 곳 앞에 한 번만 있으면 되고, 정의에서 다시 적을 필요는 없음

```cpp
static void report();
void report() { std::printf("report\n"); }
```

- 이름 없는 네임스페이스를 쓴 것과 뜻이 완전히 같음(GCC 결과도 같은 링크 오류)

:::caution
번역 단위 안에서만 필요한 도우미는 이름 없는 네임스페이스로 감싸 내부 링크를 준다. 이 용도로 `static`을 쓰는 것은 권하지 않는다.
:::

## extern

- 관련 키워드 `extern`은 `static`의 반대, 즉 뒤에 오는 이름에 외부 링크를 주는 것처럼 보이고, 실제로 그렇게 쓰일 때도 있음 <CppRef path="cpp/language/storage_duration" />
  - 예: `const` 전역 변수와 `typedef`는 기본이 **내부 링크**. `extern`으로 외부 링크를 줄 수 있음
- 복잡한 점: 이름을 `extern`으로 지정하면 컴파일러는 그것을 **정의가 아니라 선언**으로 다룸
  - 변수라면 공간을 잡지 않음. `extern` 없는 정의를 따로 둬야 함

```cpp
// other.cpp
extern int g_count;     // 선언
int g_count{ 3 };       // 정의
```

- `extern` 선언에서 초기화하면 선언이자 정의가 됨: `extern int g_count{ 3 };`
  - 하지만 이 경우 `extern`은 별 쓸모가 없음. `g_count`는 어차피 기본이 외부 링크

### 진짜 쓰임: 다른 파일의 변수 쓰기

```cpp
// main.cpp
#include <cstdio>
extern int g_count;     // 다른 파일에 정의된 변수를 쓰겠다는 선언

int main()
{
    std::printf("%d\n", g_count);   // 3
}
```

- `main()`에서 `g_count`를 쓰려면 컴파일러가 선언을 알아야 함
- `extern` 없이 `int g_count;`라고 쓰면 정의가 되어 공간을 또 잡음. 전역 범위에 `g_count`가 둘이 되어 링크가 실패함: ``multiple definition of `g_count'``
- `const` 전역 변수는 기본이 내부 링크라 다른 파일에서 `extern const int k_limit;`로 써도 링크 실패(``undefined reference to `k_limit'``). 정의하는 쪽도 `extern const int k_limit{ 10 };`으로 외부 링크를 줘야 함

:::caution
전역 변수는 쓰지 않는 것이 좋다. 헷갈리고 실수를 부르며, 큰 프로그램일수록 더 그렇다. 쓴다면 신중하게. 예외는 전역 상수다. 같은 상수를 여기저기서 정의하지 말고, 한 곳에서 정의해 모든 곳에서 쓴다.
:::

## 헷갈리기 쉬운 점

- 함수는 기본이 내부 링크다?
  - 함수와 전역 변수는 기본이 외부 링크. `const` 전역과 `typedef`는 기본이 내부 링크
- 이름 없는 네임스페이스와 `static`은 다르게 동작한다?
  - 내부 링크라는 뜻은 같음. 새 코드에는 이름 없는 네임스페이스를 권함
- `extern int x;`가 `x`를 만든다?
  - 선언일 뿐 공간을 잡지 않음. 정의가 어딘가에 따로 있어야 함
- 컴파일이 되면 링크도 된다?
  - 각 파일은 따로 컴파일되므로, 정의가 없거나 둘이면 링크 단계에서야 오류가 남

## 정리

| 요소 | 핵심 |
| --- | --- |
| 번역 단위 | 전처리를 마친 소스 파일 하나. 따로 컴파일됨 |
| 링커 | 목적 파일을 묶고 다른 파일을 가리키는 참조를 풂 |
| 외부 링크 | 어느 번역 단위에서든. 함수·전역 변수의 기본 |
| 내부 링크 | 그 번역 단위에서만. 이름 없는 네임스페이스(권장) 또는 `static` |
| 모듈 링크 | 같은 모듈 안에서 |
| `extern` | 선언으로 만듦. 다른 파일의 전역 변수를 쓸 때 |
| 링크 오류 | 정의 없음: `undefined reference`, 정의 둘: `multiple definition` |
