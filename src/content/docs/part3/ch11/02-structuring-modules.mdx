## 하위 모듈

- 표준에 "하위 모듈"이라는 개념이 따로 있지는 않음. 그러나 모듈 이름에 점을 쓸 수 있으므로 원하는 계층으로 구조를 만들 수 있음
- 예: 앞 글의 `Weather` 네임스페이스에 `Sensor`와 `Station`이 함께 있던 모듈을, `weather.sensor`와 `weather.station` 두 하위 모듈로 나눔

```cpp
// weather.sensor.cppm
export module weather.sensor;
export namespace Weather { class Sensor { /* ... */ }; }
```

```cpp
// weather.station.cppm
export module weather.station;
export namespace Weather { class Station { /* ... */ }; }
```

- 그리고 `weather` 모듈이 두 하위 모듈을 가져와 곧바로 다시 내보냄: `export import`

```cpp
// weather.cppm
export module weather;
export import weather.sensor;    // 가져와서 다시 내보냄
export import weather.station;
```

- 하위 모듈의 멤버 함수 구현도 그 하위 모듈의 구현 파일에 둘 수 있음: `module weather.sensor;`로 시작하는 `.cpp` 파일
- 장점: 사용하는 쪽이 전부를 한꺼번에 가져올 수도, 필요한 부분만 가져올 수도 있음

```cpp
import weather;          // 전부
import weather.sensor;   // Sensor만
```

- 한꺼번에 가져오는 편이 편함. 특히 거의 바뀌지 않는 안정된 모듈에서
- 자주 바뀌는 모듈은 필요한 것만 가져오면 빌드 시간을 줄일 수 있음. 예: `weather.station`의 인터페이스가 바뀌면 그것을 가져온 파일만 다시 컴파일됨

## 모듈 파티션

- 모듈을 나누는 다른 방법: **파티션** (partition) <CppRef path="cpp/language/modules" />
- 하위 모듈과의 차이
  - 하위 모듈은 구조가 **사용하는 쪽에 드러남**. 원하는 하위 모듈만 골라 가져올 수 있음
  - 파티션은 모듈을 **안에서** 나누는 수단. 사용하는 쪽에 드러나지 않음
- 모듈 인터페이스 파티션 파일에서 선언한 파티션은 모두, 직접이든 간접이든, **기본 모듈 인터페이스 파일**에서 내보내야 함
  - 기본 모듈 인터페이스 파일은 모듈마다 하나뿐. `export module 이름;` 선언이 있는 인터페이스 파일
- 이름: 모듈 이름과 파티션 이름을 콜론으로 이어 씀. 파티션 이름은 올바른 식별자면 됨

```cpp
// weather-sensor.cppm
export module weather:sensor;              // 파티션
export namespace Weather
{
    class Sensor
    {
    public:
        Sensor();
        double read() const;
    };
}
```

```cpp
// weather-station.cppm
export module weather:station;
import :sensor;                            // 같은 모듈의 다른 파티션
export namespace Weather { class Station { /* Sensor를 씀 */ }; }
```

```cpp
// weather.cppm: 기본 모듈 인터페이스
export module weather;
export import :sensor;                     // 파티션을 가져와 내보냄
export import :station;
```

- 파티션을 가져올 때는 콜론으로 시작하는 파티션 이름만: `import :sensor;`
  - `import weather:sensor;`는 잘못: 파티션은 모듈 안에서만 가져올 수 있으므로 모듈 이름을 앞에 붙이는 것은 불필요하고 허용되지 않음(GCC: `expected ';' before ':' token`)
- 사용하는 쪽은 모듈 전체를 가져옴: `import weather;`

:::note
파티션은 모듈을 안에서 나누는 것이라 모듈 밖에서는 보이지 않는다. 사용하는 쪽은 특정 파티션만 가져올 수 없고 모듈 전체를 가져와야 한다. 일부만 골라 가져오게 하려면 파티션 대신 하위 모듈을 쓴다.
:::

### 파티션의 구현은 어디에

- 같은 파티션 이름을 가진 파일은 **하나만** 있을 수 있음
  - 그래서 `module weather:sensor;`로 시작하는 구현 파일을 따로 두는 것은 잘못
- 파티션의 구현은 모듈의 구현 파일(`module weather;`)에 둠

```cpp
// weather.cpp
module weather;            // weather:sensor가 아님!
Weather::Sensor::Sensor() {}
double Weather::Sensor::read() const { /* ... */ }
```

:::caution
여러 파일이 같은 파티션 이름을 가질 수 없다. 같은 이름의 인터페이스 파티션 파일이 둘 있으면 안 되고, 인터페이스 파티션 파일의 선언을 같은 파티션 이름의 구현 파일에서 구현할 수도 없다. 구현은 모듈의 구현 파일에 둔다.
:::

### 파티션은 모듈을 암묵적으로 가져오지 않음

- 앞 글: `module 이름;` 선언은 `import 이름;`을 암묵적으로 포함함. **파티션은 그렇지 않음**
  - `weather:station` 파티션은 `import weather;`를 암묵적으로 하지 않음
  - 명시적으로 `import weather;`를 넣을 수도 없음. `weather` 인터페이스는 `import :station;`을 하고, `weather:station`은 `import weather;`를 하는 **순환 의존**이 되기 때문
- 해결: `weather:station`이 필요로 하는 기능을 `weather` 인터페이스 파일에서 또 다른 파티션으로 옮기고, 두 파일이 모두 그 파티션을 가져옴

## 구현 파티션

- 파티션은 인터페이스 파티션 파일 말고 **모듈 구현 파티션 파일**(보통 `.cpp`)에서도 선언할 수 있음: **구현 파티션** (내부 파티션이라고도 함)
  - 구현 파티션은 내보낼 수 없음. 인터페이스 파티션은 반드시 내보내야 하는 것과 반대
- 쓰임새: 모듈의 함수들을 구현하는 데 필요하지만 내보내면 안 되는 도우미 함수

```cpp
// weather-details.cpp
module weather:details;              // 구현 파티션
double calibrate(double value) { return value - 0.4; }
```

```cpp
// weather.cpp
module weather;
import :details;                     // 도우미를 가져옴
double Weather::Sensor::read() const { return calibrate(22.0); }
```

- 여러 구현 파일이 그 도우미를 쓸 때 의미가 있음

## private 모듈 조각

- 기본 모듈 인터페이스 파일은 **private 모듈 조각** (private module fragment)을 가질 수 있음. 다음 줄로 시작함

```cpp
module :private;
```

- 이 줄 뒤에 정의한 것은 내보내지지 않고, 모듈을 쓰는 쪽에 보이지 않음
- 9장의 pimpl 관용구는 인터페이스 파일과 구현 파일 두 개가 필요했음. private 모듈 조각을 쓰면 **파일 하나로** 같은 분리를 할 수 있음

```cpp
module;
#include <memory>
export module adder;

export class Adder
{
public:
    Adder();
    ~Adder();
    int add(int a, int b) const;
private:
    class Impl;
    std::unique_ptr<Impl> m_impl;
};

module :private;     // 여기부터는 쓰는 쪽에 보이지 않음

class Adder::Impl
{
public:
    int add(int a, int b) const { return a + b; }
};

Adder::Adder() : m_impl{ std::make_unique<Impl>() } {}
Adder::~Adder() = default;
int Adder::add(int a, int b) const { return m_impl->add(a, b); }
```

- 정말 숨겨지는지: `Adder`에 `Impl*`를 돌려주는 `public` 함수가 있다면
  - 쓰는 쪽에서 그 포인터를 `auto`로 받아 담아 두는 것은 됨. 불완전한 타입의 포인터일 뿐
  - 그러나 그 포인터로 `add()`를 부르면 오류. `Adder::Impl`은 private 모듈 조각 안에 있어 쓰는 쪽에서 정의를 볼 수 없음
- `module :private;` 줄을 지우면 그 호출도 됨
  - `Impl`을 명시적으로 내보내지 않았는데도? `Adder`를 내보냈고 `Impl`이 `Adder` 안에서 선언되었으므로 **암묵적으로** 내보내짐

## 헤더 유닛

- 모듈은 `import sensor;`처럼 가져옴
- 기존 코드의 `sensor.h`는 제대로 된 모듈 `sensor.cppm`으로 바꿔 쓰는 것이 원칙. 그러나 바꿀 수 없을 때도 있음
  - 모듈을 아직 지원하지 않는 컴파일러에서도 쓸 수 있어야 함
  - 고칠 수 없는 외부 라이브러리의 헤더
- 그럴 때 헤더 파일을 직접 가져올 수 있음

```cpp
import "sensor.h";            // 상대·절대 경로도 됨
import "include/sensor.h";
import <sensor.h>;            // 시스템 포함 디렉터리에서 찾음
```

- 헤더의 모든 것이 암묵적으로 내보내짐. 헤더에서 정의한 **매크로도 보임**
  - 진짜 모듈(직접 만든 모듈, `std`, `std.compat`)은 매크로를 밖에 보이지 않는 것과 다름
- `#include` 대신 `import`로 헤더를 가져오면 빌드가 빨라짐. 헤더가 암묵적으로 모듈로 바뀌어 한 번만 컴파일되기 때문
  - 컴파일러마다 다른 "미리 컴파일된 헤더" 기능 대신 쓸 수 있는 표준 방법
- 헤더 파일을 가져올 때마다 컴파일러가 헤더 내용을 내보내는 모듈을 만듦: **헤더 유닛** (header unit)
  - 만드는 절차는 컴파일러마다 다름. 예: GCC는 다음 명령으로 `<vector>`의 헤더 유닛을 먼저 만든 뒤 `import <vector>;`를 씀

```sh
g++ -std=c++23 -fmodules -x c++-system-header vector
```


:::note
헤더 유닛을 가져오면 그 안의 전처리기 정의를 쓸 수 있다. 그러나 헤더 유닛을 `export import`해도 전처리기 정의는 더 내보내지지 않는다. 그 정의가 필요한 코드는 헤더 유닛을 직접 가져와야 한다.
:::

## 표준 라이브러리 헤더 가져오기

- `<iostream>`, `<vector>`, `<string>` 같은 C++ 헤더는 모두 **가져올 수 있는 헤더**: `import <vector>;`
- C++23부터는 `import std;` 하나로 표준 라이브러리 전체를 가져오는 편이 더 편함
- C++ 표준 헤더는 `.h` 확장자가 없고(`<vector>`), 모두 `std` 네임스페이스(또는 그 하위)에 정의함

### C 헤더

- C 표준 라이브러리 헤더는 `.h`로 끝나고(`<stdio.h>`) 네임스페이스를 쓰지 않음
- C++에서는 C 기능을 두 가지 헤더로 제공함
  - 권장: `.h` 없이 앞에 `c`를 붙인 판. 예: `<cstdio>`. 모두 `std` 네임스페이스에 둠
  - C 스타일 판: `<stdio.h>`. 네임스페이스를 쓰지 않음. C++과 C에서 동시에 유효해야 하는 코드가 아니면 쓰지 않음
- C++23 전까지 `<이름.h>` 형태의 C 헤더는 폐기 예정이었음. C++23부터 폐기 예정은 아니지만 여전히 권하지 않음 <Badge text="C++23" />
- 엄밀히는 옛 판이 `std`에도 넣을 수 있고, 새 판이 전역 네임스페이스에도 넣을 수 있음. 표준이 정한 동작이 아니므로 기대지 말 것
- `import std;`로는 `<cmath>`의 수학 함수 같은 C 함수도 `std` 안에 들어옴(`std::sqrt()`). `import std.compat;`라면 전역에도(`::sqrt()`)
- `std`, `std.compat`을 쓸 수 없다면: C 헤더는 `import`로 가져올 수 있다는 보장이 없음. 안전하게 `#include <cxyz>`

### 매크로가 필요할 때

- 진짜 모듈(`std`, `std.compat`)을 가져오면 모듈 안에서 정의한 C 스타일 매크로는 보이지 않음
- C 표준 라이브러리의 매크로를 쓸 때 중요함. 다행히 많지 않음
  - 예: `<cassert>`의 `assert()` 매크로(31장)
  - `std`로는 `assert()`가 보이지 않고, `<cassert>`는 C 헤더라 가져올 수 있다는 보장이 없음. 그래서 `#include <cassert>`

:::note
가져올 수 있는 헤더라면 `import`하는 편을 권한다. 가져올 수 없을 때만 `#include`한다. 예를 들어 헤더 내용이 전처리기 `#define`에 따라 달라지는 경우다(다음 글).
:::

- 모듈 인터페이스 파일이나 구현 파일에서 `#include`가 필요하면 **전역 모듈 조각**에 둠
  - 이름 없는 모듈 선언 `module;`로 시작하고, 이름 있는 모듈 선언보다 앞에 있어야 함
  - 전역 모듈 조각에는 `#include`, `#define` 같은 전처리기 지시자만 올 수 있음
  - 이름 있는 모듈 선언 앞에 올 수 있는 것은 전역 모듈 조각과 주석뿐

```cpp
module;                  // 전역 모듈 조각 시작
#include <cassert>       // 기존 헤더 포함
export module sensor;    // 이름 있는 모듈 선언
import std;
export class Sensor { /* ... */ };
```

:::caution
모듈 인터페이스 파일과 구현 파일의 `#include` 지시자는 모두 전역 모듈 조각에 둔다.
:::

## 헷갈리기 쉬운 점

- 하위 모듈과 파티션은 같은 것이다?
  - 하위 모듈은 사용하는 쪽에 드러나 골라 가져올 수 있음. 파티션은 모듈 안의 구조일 뿐
- 사용하는 쪽도 `import weather:sensor;`로 파티션만 가져올 수 있다?
  - 불가. 모듈 안에서 `import :sensor;`로만
- 파티션의 구현은 같은 파티션 이름의 구현 파일에 둔다?
  - 같은 파티션 이름의 파일은 하나뿐이어야 함. 모듈의 구현 파일에 둠
- `import "sensor.h";`는 `#include`와 똑같다?
  - 내용은 같지만 헤더 유닛으로 한 번만 컴파일되어 빠름. 매크로도 보임
- `import std;`로 `assert()`를 쓸 수 있다?
  - 모듈은 매크로를 내보내지 않음. `#include <cassert>`

## 정리

| 요소 | 핵심 |
| --- | --- |
| 하위 모듈 | `weather.sensor`처럼 점으로 이름을 나눔. 골라 가져올 수 있음 |
| `export import` | 가져온 모듈을 다시 내보냄 |
| 파티션 | `weather:sensor`. 모듈 안의 구조. 기본 인터페이스가 내보내야 함 |
| 파티션 가져오기 | 모듈 안에서 `import :sensor;` |
| 구현 파티션 | 내보내지 않는 도우미 모음 |
| private 모듈 조각 | `module :private;` 뒤는 숨겨짐. 파일 하나로 pimpl |
| 헤더 유닛 | `import "x.h";`, `import <vector>;`. 매크로도 보임 |
| C 헤더 | `<cstdio>` 권장. 매크로가 필요하면 `#include`를 전역 모듈 조각에 |

## 복습 질문

<details>
<summary>모듈의 일부만 골라 가져오게 하고 싶다면 하위 모듈과 파티션 가운데 무엇을 쓰는가?</summary>

- 하위 모듈. 파티션은 밖에서 골라 가져올 수 없음

</details>

<details>
<summary>`weather` 모듈의 파티션 `weather:station`에서 `import weather;`를 쓸 수 없는 이유는?</summary>

- 기본 인터페이스가 `import :station;`을 하므로 순환 의존이 됨
- 공통으로 필요한 것을 다른 파티션으로 빼서 둘 다 가져오게 함

</details>

<details>
<summary>모듈 인터페이스 파일에서 `assert()`를 쓰려면 어떻게 하는가?</summary>

- 파일 맨 앞의 전역 모듈 조각(`module;` 뒤, `export module ...;` 앞)에 `#include <cassert>`를 둠

</details>
