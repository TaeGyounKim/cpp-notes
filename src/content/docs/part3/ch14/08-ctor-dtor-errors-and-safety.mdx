- 다루는 것: 생성자와 소멸자에서의 오류 처리, 그리고 함수가 예외에 대해 무엇을 약속하는가
- 이 글에서 배우는 요소: 생성자에서 던지기, 완전히 만들어진 하위 객체, 함수 try 블록, 소멸자와 `noexcept`, `std::uncaught_exceptions()`, 예외 안전성 보장

## 생성자에서의 오류

- 예외를 알기 전에는 생성자의 오류 처리가 골칫거리
  - 생성자가 객체를 제대로 만들지 못하면? 생성자는 값을 돌려주지 않으므로 반환 코드를 쓸 수 없음
  - 예외 없이 할 수 있는 최선: 객체에 "제대로 만들어지지 않음" 표시를 두고 `isValid()` 같은 멤버로 확인하게 함. 만든 뒤 확인하는 것을 쓰는 쪽이 잊지 않기를 바랄 뿐
- 예외는 훨씬 나은 해법. 값을 돌려줄 수 없는 생성자에서도 예외는 던질 수 있음
  - 단, 전역 객체의 생성자에서는 던지지 않음. 전역 객체는 `main()`이 시작하기 전에 만들어져 그 예외를 잡을 수 없음

### 소멸자가 불리지 않는다

- 큰 문제: 예외가 생성자 밖으로 나가면 그 객체의 **소멸자는 절대 불리지 않음**
  - 객체가 다 만들어지지 않았으므로 소멸할 것도 없다는 논리
- 그래서 예외가 생성자를 떠나기 전에, 생성자에서 확보한 자원과 할당한 메모리를 직접 정리해야 함

:::caution
예외가 생성자를 떠나면 그 객체의 소멸자는 불리지 않는다.
:::

### 날 포인터로 할 때의 정리

- 예: `T`의 2차원 배열을 날 포인터 `T**`로 가진 `Matrix<T>`(실제 코드라면 `std::vector` 같은 컨테이너를 쓸 것. 문제를 보이려고 일부러 날 포인터를 씀)

```cpp
template <typename T>
Matrix<T>::Matrix(std::size_t rows, std::size_t cols)
{
    m_data = new T*[rows]{};   // 모두 nullptr로 초기화
    m_rows = rows;             // 위 할당이 성공한 뒤에야 정함
    m_cols = cols;
    try {
        for (std::size_t i{ 0 }; i < rows; ++i) {
            m_data[i] = new T[cols];
        }
    } catch (...) {
        cleanup();                                   // 지금까지 할당한 것을 해제
        std::throw_with_nested(std::bad_alloc{});    // 원래 예외를 품어 다시 던짐
    }
}

template <typename T>
void Matrix<T>::cleanup()
{
    for (std::size_t i{ 0 }; i < m_rows; ++i) { delete[] m_data[i]; }
    delete[] m_data;
    m_data = nullptr;
    m_rows = m_cols = 0;
}

template <typename T>
Matrix<T>::~Matrix() { cleanup(); }
```

- 첫 `new`는 `try`로 감싸지 않음. 실패해도 아직 해제할 것이 없음
- 그다음 `new`가 실패하면 이미 할당한 것을 모두 해제해야 함
  - `T`의 생성자가 무슨 예외를 던질지 모르므로 `catch (...)`로 모두 잡고, 잡은 예외를 `bad_alloc` 안에 품어(4편) 다시 던짐
- 첫 배열을 `{}`로 영 초기화해 모든 원소가 `nullptr`. `nullptr`에 `delete[]`를 해도 괜찮으므로 `cleanup()`이 단순해짐
- `m_rows`, `m_cols`는 생성자 초기화 목록이 아니라 첫 할당이 성공한 **뒤에** 정함

### 완전히 만들어진 하위 객체는 정리된다

- 상속이 섞이면? 기반 클래스 생성자가 파생 클래스 생성자보다 먼저 실행됨. 파생 클래스 생성자가 던지면, 이미 다 만들어진 기반 클래스의 소멸자는 실행됨
- 멤버도 마찬가지

:::note
C++은 완전히 만들어진 모든 **하위 객체** (subobject, 기반 클래스 부분과 멤버)의 소멸자 실행을 보장한다. 예외 없이 끝난 생성자에 대응하는 소멸자는 반드시 실행된다. 그래서 멤버를 `std::vector`나 `std::unique_ptr` 같은 RAII 객체로 두면 위와 같은 수동 정리가 필요 없다.
:::

## 함수 try 블록

- 생성자 **초기화 목록**에서 던진 예외는 어떻게 잡는가? 생성자 본문의 `try`로는 잡을 수 없음
- **함수 try 블록** (function-try-block): 초기화 목록과 본문 전체를 감싸는 `try` <CppRef path="cpp/language/function-try-block" />
  - 오래전부터 있었지만 경험 많은 프로그래머도 잘 모르는 기능

```cpp
MyClass::MyClass()
try
    : /* 생성자 초기화 목록 */
{
    /* 생성자 본문 */
}
catch (const std::exception& e)
{
    /* ... */
}
```

- `try`는 초기화 목록 바로 앞에, `catch`는 생성자 본문의 닫는 중괄호 **뒤**(본문 밖)에 옴
- 생성자의 함수 try 블록 규칙

| 규칙 | 내용 |
| --- | --- |
| 잡는 범위 | 초기화 목록이나 본문에서 직접·간접으로 던진 모든 예외 |
| 다시 던지기 | `catch`는 지금 예외를 다시 던지거나 새 예외를 던져야 함. 아무것도 하지 않으면 런타임이 **자동으로** 다시 던짐 |
| 인수 | 생성자에 넘긴 인수에 접근할 수 있음 |
| 정리 순서 | `catch`가 실행되기 **전에** 이미 다 만들어진 기반 클래스와 멤버는 모두 소멸됨 |
| 멤버 접근 | 객체인 데이터 멤버는 이미 소멸했으므로 접근하지 않음. 날 포인터 같은 클래스가 아닌 멤버는, 예외 전에 초기화되었다면 접근 가능. 그런 "날" 자원은 `catch`에서 해제해야 함 |
| `return` | 생성자의 함수 try 블록 `catch`에서는 쓸 수 없음 |

- 그래서 쓸모 있는 경우가 한정됨
  - 초기화 목록에서 난 예외를 다른 예외로 바꿀 때
  - 로그를 남길 때
  - 예외 전에 초기화 목록에서 할당한 날 자원을 해제할 때

```cpp
class Panel
{
public:
    Panel()
    try : m_data{ new int[42]{} }, m_gauge{ 42 }   // Gauge 생성자가 던짐
    {
    }
    catch (const std::exception& e)
    {
        delete[] m_data;   // 날 자원 정리
        m_data = nullptr;
        std::println(std::cerr, "함수 try 블록이 잡음: {}", e.what());
        // 던지지 않으면 잡은 예외가 자동으로 다시 던져짐
    }

private:
    int* m_data{ nullptr };
    Gauge m_gauge;
};
```

- 이 코드는 실수하기 쉬워 권하지 않음. `m_data`를 `std::vector`나 `std::unique_ptr`로 바꾸고 함수 try 블록을 없애는 것이 올바른 해법
- 함수 try 블록은 보통 함수에도 쓸 수 있지만, 함수 본문 안의 `try`/`catch`로 쉽게 바꿀 수 있어 쓸 이유가 없음
  - 보통 함수에서는 `catch`가 예외를 다시 던지지 않아도 되고, 런타임이 자동으로 다시 던지지도 않음. `return`도 쓸 수 있음

:::caution
함수 try 블록은 피한다. 대개 데이터 멤버로 날 자원이 있을 때만 필요한데, 날 자원은 `std::vector`나 `std::unique_ptr` 같은 RAII 클래스로 피할 수 있다.
:::

## 소멸자에서의 오류

- 소멸자에서 생기는 오류는 소멸자 안에서 모두 처리함. 소멸자 밖으로 예외를 내보내지 않음. 이유는 넷
  1. 쓰는 쪽이 할 수 있는 일이 없음. 소멸자는 직접 부르는 것이 아니라 자동으로 불림. 예외를 받아도 합리적으로 대응할 방법이 없음
  2. 소멸자는 객체의 메모리와 자원을 해제할 **단 한 번의 기회**. 예외로 일찍 빠져나가면 다시 돌아가 해제할 수 없음
  3. 소멸자는 암시적으로 **`noexcept`** <Badge text="C++11" />. `noexcept(false)`로 명시했거나 `noexcept(false)` 소멸자를 가진 하위 객체가 있을 때만 예외. `noexcept` 소멸자에서 던지면 `std::terminate()`가 불려 프로그램이 끝남(GCC는 `-Wterminate` 경고)
  4. 소멸자는 다른 예외를 처리하는 **스택 풀기 도중**에도 실행될 수 있음. 그때 소멸자가 예외를 던지면 `std::terminate()`가 불림
- 소멸자가 정상 종료나 `delete` 때문에 불렸는지, 스택 풀기 때문에 불렸는지 알아낼 수는 있음
  - `<exception>`의 `std::uncaught_exceptions()` <Badge text="C++17" />: 던져졌지만 아직 맞는 `catch`에 닿지 않은 예외의 수. 0보다 크면 스택 풀기 중 <CppRef path="cpp/error/uncaught_exception" />
  - 올바르게 쓰기 복잡하고 지저분하므로 피함
  - C++17 이전의 단수형 `uncaught_exception()`은 `bool`을 돌려줬음. C++17에서 권장하지 않게 되었고 C++20에서 제거됨

:::caution
소멸자 밖으로 예외가 빠져나가지 않게 조심한다.
:::

## 예외 안전성 보장

- 작성한 코드가 예외가 났을 때 무엇을 약속하는지 단계로 나타낼 수 있음. 쓰는 쪽이 무엇을 기대할지 알 수 있음 <CppRef path="cpp/language/exceptions" />

| 보장 | 예외가 나면 |
| --- | --- |
| 던지지 않음 (nothrow 또는 nofail) | 함수는 절대 예외를 던지지 않음 |
| 강한 보장 (strong) | 관련된 모든 객체가 함수를 부르기 전 상태로 되돌아감. 예: 복사 후 맞바꾸기(9장) |
| 기본 보장 (basic) | 관련된 모든 객체가 유효한 상태로 남고 자원이 새지 않음. 다만 부르기 전과 다른 상태일 수 있음 |
| 보장 없음 | 프로그램이 어떤 잘못된 상태든 될 수 있음. 자원 누수, 메모리 손상 등 |

:::tip
예외를 던질 수 있는 함수라면 적어도 기본 보장은 제공한다.
:::

## 헷갈리기 쉬운 점

- 생성자에서 예외가 나도 소멸자가 정리해 준다?
  - 그 객체의 소멸자는 불리지 않음. 이미 다 만들어진 기반 클래스와 멤버의 소멸자만 불림
- 함수 try 블록의 `catch`에서 예외를 삼키면 객체가 만들어진다?
  - 런타임이 자동으로 다시 던짐. 객체는 만들어지지 않음
- 함수 try 블록의 `catch`에서 멤버 객체를 써도 된다?
  - 이미 소멸함. 쓰지 않음
- 소멸자에서 던진 예외는 바깥 `try`가 잡는다?
  - 소멸자는 기본 `noexcept`라 `terminate()`. 스택 풀기 중이어도 `terminate()`
- 강한 보장은 "예외를 던지지 않음"이다?
  - 던질 수는 있지만 던지면 부르기 전 상태로 되돌린다는 약속

## 정리

| 요소 | 핵심 |
| --- | --- |
| 생성자에서 던지기 | 가능. 그 객체의 소멸자는 불리지 않음. 날 자원은 던지기 전에 정리 |
| 하위 객체 | 완전히 만들어진 기반 클래스·멤버의 소멸자는 실행됨. 그래서 RAII 멤버 |
| 함수 try 블록 | 초기화 목록의 예외를 잡음. `catch`가 끝나면 자동으로 다시 던짐. 되도록 피함 |
| 소멸자 | 예외를 내보내지 않음. 기본 `noexcept`. 어기면 `terminate()` |
| `uncaught_exceptions()` | 스택 풀기 중인지 알 수 있음. 쓰기 까다로움 |
| 예외 안전성 | 던지지 않음 > 강한 > 기본 > 없음. 최소 기본 보장 |

<details>
<summary>`push_back()`이 강한 보장을 제공한다는 것은 무슨 뜻인가?</summary>

- `push_back()` 도중 예외가 나면(예: 메모리 재할당 실패) 벡터는 부르기 전과 똑같은 상태로 남음. 원소가 반쯤 추가되거나 기존 원소가 망가지지 않음
- 단, 원소 타입이 복사할 수 없고 이동 생성자가 예외를 던질 수 있는 경우에는 기본 보장만 함

</details>

## 14장을 마치며

- C++ 프로그램의 오류 처리 문제를 다루고, 오류 처리 계획을 세워 설계하고 코딩해야 함을 강조함
