## 오류와 예외적인 상황

- 홀로 동작하는 프로그램은 없음. 운영체제, 네트워크, 파일 시스템, 서드파티 라이브러리, 사용자 입력 같은 바깥에 기대어 동작함
  - 파일을 열 수 없거나, 네트워크가 끊기거나, 사용자가 잘못된 값을 넣을 수 있음
- 이런 잠재적인 문제를 통틀어 **예외적인 상황** (exceptional situation)이라 함. 완벽하게 짠 프로그램도 오류와 예외적인 상황을 만남
- 그래서 전문적인 프로그램은 반드시 오류 처리 기능을 갖춰야 함
- 언어마다 접근이 다름
  - C: 오류 처리를 위한 언어 기능이 거의 없음. 함수의 반환값 등 임시방편에 기댐
  - Java: **예외** (exception)라는 언어 기능을 오류 처리에 쓰도록 강제함
  - C++: 그 사이. 예외를 언어로 지원하지만 쓰라고 강제하지는 않음
- 그래도 C++에서 예외를 완전히 무시할 수는 없음. 메모리 할당 같은 기본 기능과 표준 라이브러리의 여러 클래스가 기본으로 예외를 씀

## 예외란

- 코드의 한 부분이 정상적인 실행 경로를 거치지 않고 다른 부분에 "예외적인" 상황이나 오류를 알리는 수단 <CppRef path="cpp/language/exceptions" />
  - 오류를 만난 코드가 예외를 **던지고** (throw)
  - 그것을 처리하는 코드가 예외를 **잡음** (catch)
- 예외는 익숙한 "한 줄씩 차례로 실행" 규칙을 따르지 않음
  - 예외를 던지면 프로그램은 즉시 차례 실행을 멈추고 **예외 처리기** (exception handler)로 건너뜀
  - 처리기는 같은 함수의 바로 다음 줄일 수도, 호출 스택을 여러 단계 올라간 곳일 수도 있음
  - 야구에 빗대면, 외야수(던진 코드)가 공을 내야로 던지고 가장 가까운 내야수(가장 가까운 처리기)가 받는 셈
- 예: `main()`에 처리기가 있고, `main()`이 `total()`을, `total()`이 `check()`를 부르고, `check()`가 예외를 던짐
  - 처리기가 예외를 잡으면 `check()`와 `total()`의 스택 프레임은 사라지고 `main()`만 남음

- C#, Java 등 대부분의 현대 언어가 예외를 지원함. C에서 왔다면 새롭겠지만 익숙해지면 되돌아가고 싶지 않을 것

## C++에서 예외가 좋은 이유

### C 스타일 오류 처리의 문제

- 실행 시간 오류는 피할 수 없지만, 대부분의 C와 C++ 프로그램의 오류 처리는 지저분하고 임시방편임
- C의 사실상 표준(많은 C++ 프로그램이 물려받음): 정수 **반환 코드**와 **`errno`** 매크로 <CppRef path="cpp/error/errno" />
  - `errno`는 스레드마다 따로 있는 정수 변수처럼 동작함. 함수가 이것으로 호출한 쪽에 오류를 알림
- 문제 1: 일관성이 없음
  - 어떤 함수는 성공이면 0, 오류면 -1을 돌려주고 `errno`에 오류 코드를 넣음
  - 어떤 함수는 성공이면 0, 오류면 0이 아닌 값(그 값이 곧 오류 코드)을 돌려주고 `errno`는 안 씀
  - 또 어떤 함수는 반대로 실패에 0을 돌려줌(0이 거짓이므로)
  - 비슷한 함수는 비슷하게 동작하리라 가정하기 쉬운데 그렇지 않아 문제가 생김. 같은 운영체제 안의 두 동기화 라이브러리에서 이름도 비슷한 세마포어 초기화 함수가 오류를 서로 다르게 알리는 일도 있었음
- 문제 2: 함수의 반환 타입은 하나뿐
  - 결과와 오류를 둘 다 돌려주려면 다른 수단이 필요함
  - `std::pair`나 `std::tuple`, 직접 만든 구조체, C++23의 `std::expected`(결과 또는 오류를 담음, 24장), 참조 매개변수, `nullptr` 같은 특별한 값
  - 어느 방법이든 호출한 쪽이 오류를 명시적으로 확인하고, 직접 처리하지 않으면 다시 위로 넘겨야 함. 그러다 오류의 중요한 정보를 잃기 쉬움

:::danger
C의 `setjmp()`/`longjmp()`는 C++에서 올바르게 쓸 수 없다. 스택에 있는 객체의 소멸자를 건너뛰기 때문이다. C 프로그램에서도 피하는 것이 좋으므로 이 사이트에서는 다루지 않는다.
:::

### 예외의 장점

- 예외는 더 쉽고, 일관되고, 안전한 오류 처리 수단
- 반환 코드는 확인하는 것을 **잊을 수 있음**
  - `[[nodiscard]]`(1장)로 반환값을 무시하지 못하게 할 수 있지만 완벽하지 않음
  - 예외는 잊거나 무시할 수 없음. 잡지 않으면 프로그램이 끝남
- 정수 반환 코드에는 **정보가 부족함**
  - 예외로는 오류를 찾은 코드에서 처리하는 코드로 원하는 만큼 정보를 넘길 수 있음
  - 예외로 오류가 아닌 정보를 전달할 수도 있지만, 많은 개발자가 이를 예외의 남용으로 봄
- 예외는 호출 스택의 **여러 단계를 건너뛸** 수 있음
  - 여러 단계 아래에서 생긴 오류를 중간 함수에 오류 처리 코드 없이 처리할 수 있음
  - 반환 코드라면 각 단계가 아래 단계의 뒷정리를 하고 오류 코드를 명시적으로 위로 넘겨야 함

### 성능

- 예전 일부 컴파일러에서는 예외 처리기가 있는 함수마다 약간의 비용이 들었음
- 대부분의 현대 컴파일러는 예외를 **던지지 않는** 경우의 비용이 거의 또는 전혀 없고, 실제로 던질 때만 약간의 비용이 듦
- 이 균형은 나쁘지 않음. 예외는 함수에서 값을 돌려주는 것 같은 **정상 흐름 제어에 쓰지 않고**, 디스크의 파일을 읽다 실패하는 것처럼 정상적으로는 잘 일어나지 않는 예외적인 일에만 씀
- 그러므로 오류가 없는 경우에는 반환 코드로 구현한 것보다 예외를 쓴 코드가 오히려 빠름

### 강제하지 않음

- Java는 예외 처리를 강제함. 던질 수 있는 예외 목록을 밝히지 않은 함수는 예외를 던질 수 없음
- C++은 정반대. 함수는 어떤 예외든 던질 수 있음. 예외를 던지지 않는다고 `noexcept`(2편)로 밝힌 경우만 예외

- 볼 것

  - 예외가 나면 `try` 블록의 나머지 줄은 실행되지 않음

## 권하는 방법

- 오류 처리에는 예외를 권함. 예외가 주는 구조와 형식이 단점보다 큼
- 표준 라이브러리, Boost 같은 널리 쓰는 라이브러리가 예외를 쓰므로 어차피 처리할 준비가 되어 있어야 함
- 그래서 이 장의 나머지는 예외를 다룸

## 헷갈리기 쉬운 점

- 예외는 던진 함수 안에서만 잡을 수 있다?
  - 호출 스택을 거슬러 올라가 가장 가까운 처리기가 잡음
- 예외가 나도 함수의 남은 줄은 실행된다?
  - 정상 흐름이 즉시 멈춤. 처리기까지 건너뜀
- 예외는 언제나 느리다?
  - 현대 컴파일러에서는 던지지 않는 경우 비용이 거의 없음. 던질 때만 비용이 듦
- 예외로 함수의 결과를 돌려줘도 된다?
  - 정상 흐름 제어에 쓰지 않음. 예외적인 상황에만

## 정리

| 요소 | 핵심 |
| --- | --- |
| 예외적인 상황 | 바깥 요인으로 생기는 피할 수 없는 문제 |
| 예외 | 던지고(`throw`) 잡는(`catch`) 수단. 호출 스택을 거슬러 올라감 |
| 반환 코드·`errno` | 일관성 없음, 잊기 쉬움, 정보 부족, 단계마다 넘겨야 함 |
| 예외의 장점 | 무시할 수 없음, 정보를 담음, 단계를 건너뜀 |
| 성능 | 던지지 않으면 비용이 거의 없음. 예외적인 일에만 |
| C++의 태도 | 지원하되 강제하지 않음. 함수는 무엇이든 던질 수 있음(`noexcept` 제외) |
