## 스마트 포인터

- 왜 필요한가
  - 동적 메모리를 많이 쓰고 포인터를 객체들 사이에 많이 넘기면, 각 포인터를 **딱 한 번, 알맞은 때** `delete`하기를 기억하기 어려움
  - 틀렸을 때의 대가가 큼: 두 번 풀거나 해제된 메모리를 쓰면 메모리 손상이나 치명적 오류, 풀기를 잊으면 누수
- **스마트 포인터** (smart pointer): 동적으로 잡은 자원(메모리 등)을 쥐고 있다가, 범위를 벗어나거나 `reset`될 때 그 자원을 **저절로** 풀어 주는 객체
  - 누수를 피하는 권장 방법
  - 함수 안의 지역 변수로도, 클래스의 데이터 멤버로도 쓰고, 함수 인수로 소유권을 넘기는 데도 씀
- C++이 스마트 포인터를 만들기 좋은 이유
  - 템플릿(12장)으로 어떤 포인터 타입에든 쓰는 타입 안전한 스마트 포인터 클래스를 만들 수 있음
  - 연산자 오버로딩(15장)으로 `*`, `->`, `[]`를 오버로딩해서, 보통 포인터처럼 쓸 수 있음
- 표준 라이브러리의 두 스마트 포인터. 헤더 `<memory>`

| 종류 | 소유 방식 | 자원을 푸는 때 |
| --- | --- | --- |
| `std::unique_ptr` | **단독 소유**: 자원의 주인이 하나뿐 | 그 `unique_ptr`가 사라지거나 `reset`될 때 |
| `std::shared_ptr` | **공동 소유**: 여럿이 같은 자원을 가리킴 | 그 자원을 가리키는 **마지막** `shared_ptr`가 사라지거나 `reset`될 때 (다음 글) |

:::tip
기본으로 쓸 스마트 포인터는 `unique_ptr`이다. 자원을 정말로 나눠 가져야 할 때만 `shared_ptr`을 쓴다.
:::

:::caution
자원을 할당한 결과를 맨 포인터에 담지 않는다. 어떤 방법으로 자원을 잡든, 그 포인터를 곧바로 `unique_ptr`이나 `shared_ptr` 같은 스마트 포인터, 또는 다른 RAII 클래스에 담는다.
:::

- **RAII** (Resource Acquisition Is Initialization, 자원 획득은 초기화): 어떤 자원의 소유권을 맡아 알맞은 때에 풀어 주는 클래스를 만드는 설계 기법. 스마트 포인터가 그 대표. 32장에서 다룸

## unique_ptr

- `std::unique_ptr` <CppRef path="cpp/memory/unique_ptr" />: 자원을 **홀로** 소유하는 스마트 포인터. 자신이 사라지거나 `reset`되면 자원을 저절로 풂
- 큰 장점: `return`이 실행되든 예외가 던져지든 자원이 **언제나** 풀림
  - `return`이 여러 군데인 함수에서 `return`마다 해제 코드를 넣을 필요가 없음
- 규칙: 주인이 하나인 동적 자원은 언제나 `unique_ptr`에 담음

### 맨 포인터는 왜 위험한가

- 누가 봐도 새는 코드: `new`만 하고 `delete`가 없음
- 덜 분명한 경우: `delete`를 제대로 적었는데도 샐 수 있음

```cpp
void couldLeak()
{
    Photo* photo{ new Photo{} };
    photo->upload();   // 여기서 예외가 나면
    delete photo;      // 이 줄은 실행되지 않음
}
```

- 볼 것

  - `withUniquePtr`: 예외가 나도 `photo`가 범위를 벗어나며 소멸자가 객체를 지움. 개수가 늘지 않음
  - `delete`를 한 줄도 적지 않았음

### 만들기: make_unique

- `std::make_unique<T>(인수...)` <Badge text="C++14" /> <CppRef path="cpp/memory/unique_ptr/make_unique" />: `T`를 자유 저장소에 만들고 그것을 가진 `unique_ptr`를 돌려줌
  - 생성자에 넘길 인수를 그대로 넘김
  - `auto`와 함께 쓰면 타입을 한 번만 적음. **권장하는 방법**

```cpp
auto song{ std::make_unique<Song>("Intro") };

// 생성자를 직접 부르는 방법. Song을 두 번 적어야 함
std::unique_ptr<Song> same{ new Song{ "Intro" } };
```

- 템플릿 인수 `<Song>`: `unique_ptr`는 어떤 타입의 메모리든 가리킬 수 있는 클래스 템플릿이고, `make_unique`는 함수 템플릿. 꺾쇠 안에 가리킬 타입을 적음. 템플릿의 자세한 내용은 12장이지만 스마트 포인터를 쓰는 데는 몰라도 됨
- 클래스 템플릿 인수 추론(CTAD)은 `unique_ptr`에 쓸 수 없음. `std::unique_ptr p{ new int{ 1 } };`는 컴파일 오류("class template argument deduction failed"). 타입을 생략할 수 없음
- 초기화 방식
  - `make_unique`는 **값 초기화**: 기본 타입은 0, 객체는 기본 생성자
  - 어차피 곧 덮어쓸 값이라 초기화가 아깝다면 `std::make_unique_for_overwrite<T>()` <Badge text="C++20" />: 기본 초기화. 기본 타입은 초기화되지 않음(아무 값), 객체는 여전히 기본 생성자
- C++17 이전에는 `make_unique`가 **안전성** 때문에도 필요했음
  - `f(std::unique_ptr<A>{ new A{} }, std::unique_ptr<B>{ new B{} });` 같은 호출에서, 컴파일러가 두 `new`를 먼저 하고 `unique_ptr`를 나중에 만들 수 있었음. 그사이 예외가 나면 누수
  - C++17부터 함수 인수의 평가 순서 규칙이 강화되어 이 문제는 없어짐. 그래도 읽기 쉬우므로 `make_unique`를 씀

:::tip
`unique_ptr`는 언제나 `make_unique()`로 만든다.
:::

### 쓰기

- 새 문법을 거의 배우지 않아도 됨. 보통 포인터처럼 `*`와 `->`로 역참조함

| 멤버 / 연산 | 하는 일 |
| --- | --- |
| `p->member`, `(*p).member` | 보통 포인터처럼 접근 |
| `p.get()` | 맨 포인터를 꺼냄. 소유권은 그대로. 맨 포인터를 받는 함수에 넘길 때 |
| `p.reset()` | 가진 자원을 풀고 `nullptr`이 됨 |
| `p.reset(new T{...})` | 가진 자원을 풀고 새 자원을 가짐 |
| `p.release()` | 소유를 **포기**하고 맨 포인터를 돌려줌. `p`는 `nullptr`. 이제 그 자원을 푸는 것은 내 책임 |
| `if (p)`, `p == nullptr` | 무언가를 가지고 있는지 검사 |

<RunCode client:load code={opsCode} />

- 볼 것
  - `[+]`와 `[-]`가 정확히 짝을 이룸. `delete`는 `release()` 뒤의 한 번뿐
  - `reset(new Song{ "Verse" })`: 새것을 만든 뒤(`[+] Verse`) 옛것을 지움(`[-] Intro`)
  - `show(song.get())`: 소유하지 않고 잠깐 쓰기만 하는 함수는 맨 포인터(또는 참조)로 받음. 요즘 C++에서 맨 포인터는 "소유하지 않음"이라는 뜻
  - `Verse`는 `main`이 끝나며 `playlist`가 사라질 때 지워짐

### 소유권 넘기기: 복사는 안 되고 이동은 됨

- `unique_ptr`는 단독 소유이므로 **복사할 수 없음**
  - 복사하면 주인이 둘이 되어, 둘 다 사라질 때 같은 객체를 두 번 지우게 됨
  - `auto b{ a };`는 컴파일 오류: `use of deleted function 'std::unique_ptr<…>::unique_ptr(const std::unique_ptr<…>&)'`. 복사 생성자를 일부러 지워 둔 것
- 대신 **이동**할 수 있음: `std::move()` <CppRef path="cpp/utility/move" />로 소유권을 다른 `unique_ptr`에 넘김
  - 넘겨준 쪽은 `nullptr`이 됨. 주인은 여전히 하나
  - 이동 의미론의 자세한 내용: 9장. 지금은 "`std::move`로 소유권을 넘긴다"만 알면 됨

  - 마지막 단계: `delete`를 한 번도 적지 않았지만 남은 메모리가 없음

### C 스타일 배열

- `unique_ptr`는 동적으로 잡은 C 스타일 배열도 담을 수 있음

```cpp
auto values{ std::make_unique<int[]>(10) };   // 타입은 unique_ptr<int[]>
values[1] = 123;                              // [] 로 원소에 접근
```

- `make_unique`는 원소를 모두 값 초기화함(기본 타입은 0). `std::vector`와 같음
- `make_unique_for_overwrite<int[]>(n)`은 기본 초기화(기본 타입은 초기화 안 됨). 초기화되지 않은 데이터는 되도록 피하므로 신중하게
- 소멸할 때 `delete[]`를 알맞게 불러 줌
- 그래도 C 스타일 배열보다는 `std::array`나 `std::vector`를 권함

### 사용자 정의 삭제자

- 기본으로 `unique_ptr`는 표준 `new`와 `delete`로 메모리를 다룸
- 다른 해제 함수를 쓰게 할 수 있음. 제3자 C 라이브러리를 쓸 때 유용함
  - 예: 여는 함수와 닫는 함수를 반드시 짝으로 불러야 하는 C API
- 문법이 좀 투박함: 삭제자의 **타입**을 둘째 템플릿 인수로 적어야 함

```cpp
std::unique_ptr<Connection, decltype(&close_connection)> connection{
    open_connection(7), close_connection
};
```

- `decltype(&close_connection)`: `close_connection` 함수를 가리키는 포인터의 타입. "포인터 하나를 받고 `void`를 돌려주는 함수"의 포인터 <CppRef path="cpp/language/decltype" />
- 메모리만이 아니라 다른 자원에도 쓸 수 있음: 파일, 네트워크 소켓 등. 범위를 벗어나면 저절로 닫힘
- `shared_ptr`의 사용자 정의 삭제자는 더 쉬움(다음 글)

## 헷갈리기 쉬운 점

- `get()`으로 꺼낸 포인터를 `delete`해도 된다?
  - 안 됨. 소유권은 여전히 `unique_ptr`에 있음. 나중에 `unique_ptr`가 또 지워 두 번 지우기가 됨
- `release()`는 메모리를 푼다?
  - 풀지 않음. 소유를 포기하고 맨 포인터를 돌려줄 뿐. 푸는 것은 받은 쪽의 책임. 푸는 것은 `reset()`
- `std::move(a)`를 하면 객체가 옮겨진다?
  - 객체는 그 자리에 있고, 그것을 가진 주인(포인터)만 바뀜. 이동한 뒤 `a`는 `nullptr`
- `unique_ptr`를 함수에 넘기려면 복사해야 한다?
  - 소유권을 넘기려면 `std::move`, 잠깐 쓰게만 하려면 `get()`이나 `*p`(참조)로 넘김
- 스마트 포인터를 쓰면 `new`를 쓰는 곳이 없어진다?
  - `make_unique`를 쓰면 대부분 없어짐. `reset(new ...)`처럼 남는 곳도 있지만, 결과를 곧바로 스마트 포인터에 담는 한 안전함

## 정리

| 요소 | 핵심 |
| --- | --- |
| 스마트 포인터 | 범위를 벗어나거나 `reset`되면 자원을 저절로 푸는 객체 (RAII) |
| `unique_ptr` | 단독 소유. 기본 선택 |
| 만들기 | `auto p{ std::make_unique<T>(인수) };` |
| 쓰기 | `->`, `*`, `get()`, `reset()`, `release()` |
| 넘기기 | 복사 불가, `std::move`로 이동. 넘긴 쪽은 `nullptr` |
| 배열 | `make_unique<T[]>(n)`. 그래도 `vector` 권장 |
| 사용자 정의 삭제자 | `unique_ptr<T, decltype(&함수)>{ 자원, 함수 }` |

- 소유권은 `unique_ptr`에 남고, 함수는 잠깐 빌려 씀

<details>
<summary>C 라이브러리의 `FILE*`을 `fclose`로 저절로 닫히게 하려면?</summary>

- 닫는 함수를 하나 만들어 삭제자로 줌: `void closeFile(FILE* file) { std::fclose(file); }`
- `std::unique_ptr<FILE, decltype(&closeFile)> file{ std::fopen("a.txt", "r"), closeFile };`
- 범위를 벗어나면 `delete` 대신 `closeFile`이 불림
- `&std::fclose`를 바로 쓰지 않는 이유: 표준 라이브러리 함수의 주소를 얻는 것은 표준이 동작을 보장하지 않음(C++20부터 명시)
