## 포인터 다루기

- 포인터가 나쁜 평판을 얻은 이유: 쉽게 잘못 쓸 수 있음
- 포인터는 그저 메모리 주소. 이론상 주소를 손으로 바꿀 수도 있음

```cpp
char* scaryPointer{ (char*)7 };   // 주소 7을 가리키는 포인터
```

- 주소 7은 아무 의미 없는 값이거나 프로그램의 다른 곳이 쓰는 메모리일 것
- `new`나 스택처럼 나를 위해 떼어 둔 곳이 아닌 메모리를 쓰기 시작하면, 언젠가 객체의 메모리나 자유 저장소를 관리하는 메모리를 망가뜨림
- 망가짐이 드러나는 모습

| 모습 | 설명 |
| --- | --- |
| 틀린 결과 | 데이터가 망가져서 |
| 하드웨어 예외 | 없는 메모리에 접근하거나 보호된 메모리에 쓰려 해서 |
| 프로그램 강제 종료 | 운영 체제나 런타임 라이브러리가 끝냄. 이것이 그나마 **운이 좋은** 경우 |
| 조용히 틀린 결과 | 운이 나쁘면 아무 오류 없이 결과만 틀림 |

### 포인터를 머릿속에 그리는 두 방법

| 관점 | 포인터는 | 역참조 `*` | 주소 연산자 `&` |
| --- | --- | --- | --- |
| **주소** 관점 | 메모리의 위치에 해당하는 숫자. 신비한 통로가 아님 | 포인터가 가리키는 주소로 **건너뜀** | 그 위치의 주소 숫자를 얻음. 포인터에 담을 수 있음 |
| **화살표** 관점 | "저기를 봐!"라고 알려 주는 간접 단계 | 화살표를 꼬리에서 머리까지 **따라감** | 그 위치를 머리로 하는 새 화살표를 만듦. 꼬리를 포인터에 담을 수 있음 |

- 주소 관점은 뒤에 나올 포인터 산술을 이해하기 쉽게 함
- 화살표 관점은 여러 단계의 포인터를 데이터로 가는 길의 단계들로 보게 함. 이 사이트의 시각화가 이 관점
- 그림의 주소는 설명을 위해 지어낸 값. 실제 주소는 하드웨어와 운영 체제에 따라 완전히 다름

### 포인터 형변환

- 포인터는 그저 주소이므로 타입이 약한 편. XML 문서를 가리키는 포인터와 정수를 가리키는 포인터는 크기가 같음
- C 스타일 형변환으로는 어떤 포인터 타입이든 다른 포인터 타입으로 쉽게 바꿀 수 있음

```cpp
Document* documentPtr{ getDocument() };
char* myCharPtr{ (char*)documentPtr };                 // 컴파일됨. 위험
char* other{ static_cast<char*>(documentPtr) };        // 컴파일 오류
```

- C 스타일 형변환의 결과를 쓰면 실행 중에 치명적인 오류가 날 수 있음
- `static_cast`는 조금 더 안전함. 관계없는 타입의 포인터 사이에서는 형변환을 거부함 <CppRef path="cpp/language/static_cast" />
  - GCC: "invalid 'static_cast' from type 'Document*' to type 'char*'"
- 형변환의 종류: 10장에서 자세히 다룸

## 배열과 포인터의 이중성

- 이미 본 겹침: 자유 저장소의 배열은 0번 원소를 가리키는 포인터로 다룸. 스택의 배열은 `[]`가 붙은 변수로 다룸
- 겹침은 여기서 끝나지 않음. 포인터와 배열은 얽힌 관계

### 배열은 포인터로 바뀜

- 스택의 배열도 포인터 문법으로 다룰 수 있음
- 배열의 주소는 곧 0번 원소의 주소. 배열 변수의 이름을 통째로 쓰면, 컴파일러는 그것을 0번 원소의 주소로 봄
- **배열의 붕괴** (array decay): 배열이 0번 원소를 가리키는 포인터로 바뀌는 것 <CppRef path="cpp/language/array" />

```cpp
int values[10]{};
int* ptr{ values };   // 0번 원소의 주소
ptr[4] = 5;           // 포인터로 배열에 접근
```

### 배열을 함수에 넘기기

- 배열을 받는 함수는 포인터로 받음
  - 부르는 쪽이 크기를 **따로** 넘겨야 함. 포인터는 크기에 대해 아무것도 알려 주지 않음. 이것도 표준 컨테이너를 써야 할 이유
- 넘기는 세 방법: 자유 저장소 배열의 포인터, 스택 배열의 이름 그대로, 스택 배열의 0번 원소 주소(`&values[0]`)
- 함수 매개변수를 배열 문법으로 적어도 실제로는 포인터

```cpp
void doubleAll(int* values, std::size_t size);
void doubleAll(int values[], std::size_t size);
void doubleAll(int values[2], std::size_t size);   // 2는 무시됨
```

- 세 선언은 **모두 같음**. 대괄호 안의 수는 그냥 무시됨
- 그래서 배열을 넘기면 복사본이 아니라 **원래 배열**이 바뀜. 참조로 넘기는 것처럼 동작함
  - 이유: 효율. 원소를 복사하는 데는 시간과 메모리가 듦. 언제나 포인터를 넘기면 복사 코드가 필요 없음
- 크기를 아는 스택 배열을 "참조로" 넘기는 방법도 있음. 문법이 낯섦. 자유 저장소의 배열에는 쓸 수 없음

```cpp
void doubleFour(int (&values)[4]);   // 원소 4개짜리 스택 배열만 받음

template <std::size_t N>
void printAll(const int (&values)[N]);   // 크기 N을 컴파일러가 알아냄
```

- 함수 템플릿: 12장에서 다룸

- 볼 것
  - `main`에서 `sizeof(scores)`는 16(int 4개). 함수 안에서 `sizeof(values)`는 8(포인터 하나). 배열이 포인터로 바뀌어 크기 정보가 사라짐
  - 컴파일러도 이 실수를 경고함: "'sizeof' on array function parameter 'values' will return size of 'int*'"
  - `doubleAll`을 두 번 불러서 원래 배열이 4배가 됨(`5, 8, 9, 11` → `20, 32, 36, 44`). 복사본이 아니라 원본이 바뀐다는 증거
  - `printAll`은 배열의 참조로 받아 원소 개수 4를 앎. 자유 저장소 배열(포인터)을 넘기면 컴파일 오류
  - `std::size()` <Badge text="C++17" /> <CppRef path="cpp/iterator/size" />: 배열의 원소 개수

:::tip
C 스타일 배열을 함수에 직접 넘기는 대신, 매개변수를 `std::span`으로 받는 것을 권한다. `span`은 배열을 가리키는 포인터와 그 크기를 함께 감싼다(<Badge text="C++20" />, 18장).
:::

### 모든 포인터가 배열은 아님

- 배열을 포인터 자리에 넘길 수 있으니 포인터와 배열이 같다고 생각하기 쉬움. 그러나 미묘하고 중요한 차이가 있음
- 포인터 자체만으로는 의미가 없음. 아무 메모리를 가리킬 수도, 객체 하나를 가리킬 수도, 배열을 가리킬 수도 있음

```cpp
int* ptr{ new int };   // 올바른 포인터. 그러나 배열이 아님
ptr[0];                // 문법상 가능하지만 스타일이 의심스럽고 얻는 것도 없음
ptr[1];                // 무엇이 있는지 알 수 없음. 버그를 부름
```

:::caution
배열은 저절로 포인터로 바뀌지만, 모든 포인터가 배열인 것은 아니다.
:::

## 저수준 메모리 연산

- C++이 C보다 나은 큰 장점: 메모리를 덜 걱정해도 됨
  - 객체로 코딩하면 각 클래스가 자기 메모리를 제대로 관리하는지만 신경 쓰면 됨
  - 생성과 소멸을 통해 컴파일러가 언제 메모리를 관리할지 알려 줌
  - 메모리 관리를 클래스 안에 숨기면 쓰기 쉬움이 크게 달라짐. 표준 라이브러리 클래스들이 보여 주는 대로
- 그래도 어떤 프로그램이나 오래된 코드에서는 더 낮은 수준에서 메모리를 다뤄야 함. 오래된 코드, 효율, 디버깅, 호기심. 무엇 때문이든 바이트를 다루는 기법을 알아 두면 도움이 됨

### 포인터 산술

- **포인터 산술** (pointer arithmetic): 포인터에 정수를 더하거나 빼서 주소를 옮기는 것 <CppRef path="cpp/language/operator_arithmetic" />
- 컴파일러는 포인터의 **타입**을 보고 계산함
  - `int*`에 1을 더하면 `int` 하나의 크기만큼 뒤로 감. 1바이트가 아님
- 배열에 가장 쓸모 있음. 같은 타입의 데이터가 메모리에 이어져 있기 때문

```cpp
values[2] = 33;
*(values + 2) = 33;   // 같은 뜻: "int 두 개 뒤"의 칸에 씀
```

- 원소에 접근하는 다른 문법으로서는 매력이 없음. 진짜 힘은 `values + 2`도 여전히 `int*`라서 **더 작은 배열**을 나타낼 수 있다는 데 있음
- 빼기: 같은 타입의 포인터끼리 빼면 그 사이의 **원소 개수**가 나옴. 바이트 수가 아님

<RunCode client:load code={arithmeticCode} />

- 볼 것
  - `last - p`는 4(원소). 바이트로 바꿔 빼면 16
  - `sum(p + 2, 3)`: 배열의 뒷부분을 그 자체로 작은 배열처럼 함수에 넘김
  - `wchar_t`: 유니코드 문자를 담는 문자 타입. 보통 `char`보다 큼. 이 예제가 도는 Linux에서는 4바이트, Windows에서는 2바이트. 그래도 `wide + 7`은 언제나 **7글자** 뒤. 넓은 문자열은 21장에서 다룸
- 요즘 코드에서는 같은 일을 `std::string_view::substr()`이나 `std::span::subspan()`으로 더 안전하게 함

### 직접 메모리 관리

- 99%의 경우(100%라고 하는 사람도 있음) C++의 내장 할당 기능으로 충분함
  - 뒤에서 `new`와 `delete`가 다 해 줌: 알맞은 크기로 나눠 주고, 쓸 수 있는 영역의 목록을 관리하고, 지우면 목록에 되돌림
- 자원이 극도로 빠듯하거나 공유 메모리를 다루는 등 아주 특별한 상황이라면 직접 관리가 선택지가 될 수 있음
  - 생각만큼 무섭지 않음: 클래스가 큰 메모리 덩어리를 잡아 두고, 필요할 때 조각을 나눠 주는 것
- 나은 점: 부가 비용을 줄일 수 있음
  - `new`로 메모리를 잡으면 얼마나 잡았는지 기록하는 작은 공간이 더 듦. 그래야 `delete`가 알맞은 양을 돌려줌
  - 대부분의 객체에는 이 비용이 무시할 만함. 그러나 작은 객체가 엄청나게 많으면 영향이 있음
  - 직접 관리하면 객체 크기를 미리 알 수 있어 객체마다의 부가 비용을 피할 수 있음
- 직접 관리하려면 `new`와 `delete` 연산자를 오버로딩해야 함. 15장에서 다룸

### 가비지 컬렉션

- **가비지 컬렉션** (garbage collection): 아무도 참조하지 않는 객체를 런타임 라이브러리가 어느 시점에 저절로 치우는 방식. 프로그래머는 메모리를 거의 직접 풀지 않음
- C#이나 Java와 달리 C++ 언어에는 들어 있지 않음

| 코드 | 메모리 관리 |
| --- | --- |
| 요즘 C++ | 스마트 포인터. 특히 `std::shared_ptr`은 가비지 컬렉션과 매우 비슷함: 어떤 자원을 가리키는 마지막 `shared_ptr`이 사라지는 순간 자원도 사라짐 (이 장의 여섯째 글) |
| 오래된 코드 | 객체 단위로 `new`와 `delete` |

- 진짜 가비지 컬렉션을 C++에서 구현하는 것은 가능하지만 쉽지 않고, 메모리 해제의 짐을 덜면 새로운 골칫거리가 생김
  - 한 방식: **표시하고 쓸기** (mark and sweep). 수집기가 주기적으로 프로그램의 모든 포인터를 살펴 그것이 가리키는 메모리에 "사용 중"을 표시하고, 표시되지 않은 메모리를 풂. 잘못 구현하면 `delete`보다 더 실수하기 쉬움
- 완벽한 구현이 있다 해도 모든 프로그램에 맞지는 않음. 단점

| 단점 | 설명 |
| --- | --- |
| 멈춤 | 수집기가 돌 때 프로그램이 응답하지 않을 수 있음 |
| 소멸 시점을 알 수 없음 | 객체가 수집될 때까지 소멸되지 않으므로, 범위를 벗어나도 소멸자가 바로 실행되지 않음. 파일 닫기나 잠금 풀기처럼 소멸자가 하는 정리가 언제 될지 모름 |

- 가비지 컬렉션을 직접 만드는 것은 매우 어렵고, 틀리기 쉽고, 느리기 쉬움. 꼭 필요하다면 이미 있는 전문 라이브러리를 찾아 재사용할 것(4장)

### 객체 풀

- 비유
  - 가비지 컬렉션: 소풍에 일회용 접시를 사 와서, 쓴 접시를 마당에 두면 누군가 언젠가 치워 버리는 것
  - **객체 풀** (object pool): 재활용. 적당한 수의 접시를 사 와서, 쓰고 나면 씻어 다시 씀
- 잘 맞는 상황: 같은 타입의 객체를 오랫동안 많이 쓰고, 객체를 만들 때마다 비용이 드는 경우
- 성능을 위한 객체 풀: 29장

## 헷갈리기 쉬운 점

- 함수 매개변수 `int values[10]`은 원소 10개짜리 배열이다?
  - 그냥 `int*`. 10은 무시됨. 함수 안의 `sizeof(values)`는 포인터의 크기
- 배열을 함수에 넘기면 복사된다?
  - 0번 원소의 주소가 넘어감. 함수가 바꾸면 원래 배열이 바뀜
- `p + 1`은 주소에 1을 더한다?
  - 가리키는 타입 하나만큼 더함. `int*`라면 보통 4바이트, `double*`라면 8바이트 뒤
- 포인터끼리 빼면 바이트 수가 나온다?
  - 원소 개수가 나옴. 두 포인터는 같은 배열 안을 가리켜야 함
- 포인터와 배열은 같은 것이다?
  - 배열은 포인터로 바뀔 수 있지만, 포인터는 배열이 아닐 수 있음. 포인터만 봐서는 크기도, 배열인지도 알 수 없음
- `shared_ptr`가 있으니 C++에도 가비지 컬렉션이 있다?
  - 비슷한 효과지만 다름. `shared_ptr`은 마지막 소유자가 사라지는 **바로 그 순간** 자원을 풂. 가비지 컬렉션은 언제 풀지 정해져 있지 않음

## 정리

| 요소 | 핵심 |
| --- | --- |
| 포인터를 보는 관점 | 주소(숫자) 또는 화살표. `*`는 건너뜀/따라감, `&`는 주소를 얻음/화살표를 만듦 |
| 포인터 형변환 | C 스타일은 무엇이든 허용해 위험. `static_cast`는 관계없는 타입을 거부 |
| 배열의 붕괴 | 배열 이름은 0번 원소의 포인터로 바뀜. 크기 정보가 사라짐 |
| 배열 매개변수 | 실제로는 포인터. 크기는 따로 넘기거나 `std::span` |
| 포인터 산술 | 타입의 크기 단위로 이동. 빼면 원소 개수 |
| 직접 메모리 관리 | 아주 특별한 경우에만. `new`/`delete` 오버로딩 |
| 가비지 컬렉션 | C++에는 없음. 스마트 포인터가 비슷한 역할 |
| 객체 풀 | 같은 타입의 객체를 재활용 |

## 복습 질문

<details>
<summary>`void f(int a[5])` 안에서 `sizeof(a)`는 무엇의 크기인가?</summary>

- `int*`의 크기. 매개변수의 배열은 포인터로 바뀌고 5는 무시됨
- 64비트 환경에서 보통 8

</details>

<details>
<summary>`double* p{ arr };`에서 `p + 3`은 `p`보다 몇 바이트 뒤인가? (`double`이 8바이트일 때)</summary>

- 24바이트
- 포인터 산술은 가리키는 타입의 크기 단위로 움직임: 3 × 8

</details>

<details>
<summary>`int x[]{ 1, 2, 3 }; int* a{ &x[0] }; int* b{ &x[2] };`일 때 `b - a`는?</summary>

- 2
- 바이트 수(8)가 아니라 그 사이의 원소 개수

</details>

<details>
<summary>`static_cast<char*>(documentPtr)`가 컴파일되지 않고 `(char*)documentPtr`은 컴파일되는 이유와, 무엇을 써야 하는가?</summary>

- `static_cast`는 관계없는 타입의 포인터 사이 변환을 거부함. C 스타일 형변환은 무엇이든 허용함
- 컴파일러가 막아 주는 `static_cast`를 씀. 정말로 바이트로 다뤄야 하는 드문 경우에만 `reinterpret_cast`를 의도를 밝혀 씀

</details>

<details>
<summary>가비지 컬렉션의 단점 두 가지는?</summary>

- 수집기가 도는 동안 프로그램이 멈추거나 느려질 수 있음
- 소멸자가 언제 실행될지 알 수 없어, 파일 닫기 같은 정리가 늦어짐

</details>
