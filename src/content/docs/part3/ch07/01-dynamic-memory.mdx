## 왜 메모리를 알아야 하는가

- `std::vector`, `std::string` 같은 현대적인 도구를 쓰면 C++은 안전한 언어
  - 길과 차선과 신호등이 갖춰진 셈: C++ Core Guidelines(코딩 지침), 코드의 올바름을 분석해 주는 정적 분석 도구 등
- 그래도 C++은 **길 밖으로 달리는 것**도 허락함. 그 대표가 메모리를 손으로 잡고 돌려주는 **수동 메모리 관리**
  - 실수하기 특히 쉬운 영역
  - 그런 코드를 실제로 만나게 되므로, 메모리가 뒤에서 어떻게 동작하는지 알아야 함
- 그러나 요즘 코드에서는 저수준 메모리 연산을 되도록 피함

| 피할 것 | 대신 쓸 것 |
| --- | --- |
| 동적으로 할당한 C 스타일 배열 | `std::vector` 같은 표준 라이브러리 컨테이너. 메모리를 알아서 관리함 |
| 소유권을 가진 맨 포인터 (raw pointer) | 스마트 포인터 `std::unique_ptr`, `std::shared_ptr`. 필요 없어지면 자원을 저절로 돌려줌 (이 장의 다섯째, 여섯째 글) |
| `new`/`new[]`, `delete`/`delete[]`를 직접 부르기 | 위의 것들 |

- 목표: 코드에 메모리 할당 함수를 직접 부르는 곳이 없게 하기. 늘 가능하지는 않고, 기존 코드에는 대개 있음

:::caution
요즘 C++ 코드에서는 저수준 메모리 연산을 되도록 피하고, 소유권이 걸린 곳에 맨 포인터를 쓰지 말고, 오래된 C 방식의 구문과 함수를 피한다. 대신 `std::string`, `std::vector`, 스마트 포인터처럼 메모리를 스스로 관리하는 안전한 C++ 도구를 쓴다.
:::

## 메모리를 그림으로 보기

- 동적 메모리는 머릿속에 그림이 있으면 훨씬 이해하기 쉬움
- 이 사이트의 그림에서
  - 메모리 한 칸은 **상자**. 옆에 이름(변수 이름)과 타입, 주소가 붙음
  - 상자 안은 그 메모리의 현재 값. 초기화하지 않아 값을 알 수 없으면 `?`
  - 포인터는 가리키는 칸으로 향하는 **화살표**

| 영역 | 무엇이 놓이는가 | 사라지는 때 |
| --- | --- | --- |
| **스택** (stack) | 함수 안의 지역 변수. **자동 변수** (automatic variable)라고도 함 | 그 변수를 선언한 범위를 벗어날 때 저절로 |
| **자유 저장소** (free store) | `new`로 잡은 메모리. **동적 메모리** (dynamic memory) | `delete`로 돌려줄 때만 |

- 자유 저장소는 흔히 **힙** (heap)이라고도 부름. 아래 그림의 오른쪽 "힙" 칸이 자유 저장소
- 주의: 포인터도 그냥 변수. 스택에 있을 수도 있고 자유 저장소에 있을 수도 있음. 잊기 쉬운 사실
  - 동적 메모리 자체는 언제나 자유 저장소에 있음
- 아래 그림은 한 함수 안에서 일어나는 일을 단계별로 보여 줌. 마지막 단계에서 무엇이 남는지 볼 것

  - 5단계: `int**`는 "int를 가리키는 포인터"를 가리키는 포인터. 스택의 `handle` → 자유 저장소의 포인터 → 자유 저장소의 `int`

## 메모리를 잡고 돌려주기

### new와 delete

- **`new`** <CppRef path="cpp/language/new" />: 필요한 타입을 주면 그만한 공간을 자유 저장소에 잡고, 그곳을 가리키는 포인터를 돌려줌
  - 그 포인터를 변수에 담아 두는 것은 내 몫
- **`delete`** <CppRef path="cpp/language/delete" />: `new`로 잡은 메모리의 포인터를 주면, 그 메모리를 돌려줘서 프로그램의 다른 곳이 다시 쓸 수 있게 함

```cpp
int* ptr{ new int };
delete ptr;
ptr = nullptr;
```

- 규칙: 메모리를 `new`로 잡고 그 포인터를 스마트 포인터가 아닌 맨 포인터에 담는 코드 한 줄마다, 같은 메모리를 `delete`로 돌려주는 코드 한 줄이 짝으로 있어야 함
- 돌려준 뒤에는 포인터를 `nullptr`로 비우는 것을 권함
  - 이미 돌려준 메모리를 실수로 쓰지 않게 됨
  - `nullptr`에 `delete`를 해도 됨. 아무 일도 일어나지 않음

### 메모리 누수

- `new`가 돌려준 값을 버리거나, 그 포인터를 담은 변수가 범위를 벗어나면, 그 메모리에 닿을 방법이 없어짐
- **메모리 누수** (memory leak): 스택에서 직접으로도 간접으로도 닿을 수 없는 자유 저장소의 메모리. 프로그램이 끝날 때까지 돌려받지 못함
- 컴퓨터의 메모리가 무한하지 않은 한, 객체의 메모리를 언제 돌려줘도 되는지 컴파일러에게 알려 줘야 함

<RunCode client:load code={leakCode} />

- 볼 것
  - `careful`: `new` 하나에 `delete` 하나. 세 번 불러도 남은 객체 0
  - `leaky`: 돌려받은 주소를 버림. 부를 때마다 하나씩 쌓임
  - 실제 프로그램에서는 이런 누수가 오래 돌수록 메모리를 계속 먹어 들어감. 누수를 찾는 도구는 이 장의 넷째 글에서 다룸

### malloc은 왜 안 되는가

- C 프로그래머라면 `malloc()`이 익숙함. 주어진 바이트 수만큼 메모리를 잡는 함수. C++에도 있지만 피해야 함
- `new`가 `malloc()`보다 나은 가장 큰 이유: `new`는 메모리만 잡는 것이 아니라 **객체를 만듦**

| | 하는 일 |
| --- | --- |
| `malloc()` | 정해진 크기의 메모리만 떼어 둠. 객체에 대해서는 모르고 관심도 없음. 생성자를 부르지 않음 |
| `new` | 알맞은 크기의 메모리를 잡고, 알맞은 생성자를 불러 객체를 만듦 |
| `free()` | 메모리만 돌려줌. 소멸자를 부르지 않음 |
| `delete` | 소멸자를 불러 객체를 제대로 정리한 뒤 메모리를 돌려줌 |

<RunCode client:load code={newVsMallocCode} />

- 볼 것
  - `new`/`delete` 쪽에서는 생성자와 소멸자의 출력이 보임
  - `malloc`/`free` 쪽에서는 아무 출력이 없음. `m_seat`라는 `std::string`이 만들어지지 않았으므로, 그 메모리를 `Ticket`으로 여기고 쓰면 정의되지 않은 동작

:::caution
C++에서는 `malloc()`과 `free()`를 쓰지 않는다.
:::

### 할당이 실패하면

- 많은 프로그래머가 `new`는 언제나 성공한다고 가정하고 코드를 씀
  - 실패한다면 메모리가 바닥났다는 뜻이고, 그때 프로그램이 할 수 있는 일이 분명하지 않기 때문
- 기본 동작: `new`가 실패하면(요청한 만큼의 메모리가 없으면) **예외**를 던짐. `std::bad_alloc` <CppRef path="cpp/memory/new/bad_alloc" />
  - 잡지 않으면 프로그램이 끝남. 많은 프로그램에서 이것으로 충분함
- 예외를 던지지 않는 `new`도 있음: 실패하면 `nullptr`을 돌려줌. C의 `malloc()`과 비슷한 동작

```cpp
int* ptr{ new (std::nothrow) int };
```

- 문법이 조금 이상함: `nothrow`를 `new`에 인수처럼 적음. 실제로 인수임
- 권하지 않는 이유: 결과가 `nullptr`일 때 무엇을 할지는 예외 버전과 똑같이 막막함. 게다가 컴파일러가 검사를 요구하지 않으므로 검사를 빠뜨려 다른 버그로 이어지기 쉬움. 표준 버전의 `new`를 쓸 것

- 볼 것: 감당할 수 없는 크기를 요청하자 기본 `new`는 예외를, `nothrow` 버전은 `nullptr`을 돌려줌

## 헷갈리기 쉬운 점

- 포인터는 자유 저장소에 있다?
  - 포인터 변수 자체는 대개 스택에 있음. 자유 저장소에 있는 것은 포인터가 **가리키는** 동적 메모리. 포인터의 포인터라면 포인터도 자유 저장소에 있을 수 있음
- `delete`를 하면 포인터가 `nullptr`이 된다?
  - 메모리만 돌려줄 뿐, 포인터에 든 주소는 그대로. 그래서 직접 `nullptr`로 비우는 것을 권함
- `new int`는 0으로 초기화된다?
  - 초기화하지 않음. 값을 알 수 없음. 0이 필요하면 `new int{}`처럼 중괄호를 붙임
- 함수가 끝나면 그 안에서 `new`로 잡은 메모리도 돌려준다?
  - 돌려주는 것은 스택의 변수뿐. 자유 저장소의 메모리는 `delete`하기 전까지 남음. 포인터를 잃으면 누수
- `malloc`으로 잡고 `delete`로 돌려줘도 된다?
  - 안 됨. `malloc`에는 `free`, `new`에는 `delete`. 섞으면 정의되지 않은 동작

## 정리

| 요소 | 핵심 |
| --- | --- |
| 스택 | 지역 변수. 범위를 벗어나면 저절로 사라짐 |
| 자유 저장소 | `new`로 잡은 메모리. `delete`해야 사라짐 |
| `new` / `delete` | 객체를 만들고 메모리를 잡음 / 소멸자를 부르고 메모리를 돌려줌. 짝을 맞출 것 |
| 메모리 누수 | 닿을 길이 없어진 자유 저장소의 메모리 |
| `malloc` / `free` | 생성자·소멸자를 부르지 않음. C++에서는 쓰지 않음 |
| 할당 실패 | 기본 `new`는 `std::bad_alloc`을 던짐. `nothrow` 버전은 `nullptr` |
| 요즘 C++ | 컨테이너와 스마트 포인터를 쓰고, `new`/`delete`를 직접 부르지 않음 |

<details>
<summary>다음 함수의 문제는? `void f() { int* p{ new int }; *p = 1; }`</summary>

- `delete`가 없음. 함수가 끝나면 `p`는 사라지고 자유 저장소의 칸에 닿을 길이 없어져 메모리 누수
- `delete p;`를 넣거나, 처음부터 지역 변수 `int value{ 1 };`나 스마트 포인터를 씀

</details>

<details>
<summary>`std::string`을 데이터 멤버로 가진 클래스를 `malloc`으로 잡으면 무엇이 문제인가?</summary>

- 생성자가 불리지 않아 `std::string` 멤버가 만들어지지 않음. 그 객체를 쓰면 정의되지 않은 동작
- `free`도 소멸자를 부르지 않아 정리가 되지 않음

</details>

<details>
<summary>`new (std::nothrow)`보다 기본 `new`를 권하는 이유는?</summary>

- `nothrow` 버전은 실패를 `nullptr`로 알리는데, 컴파일러가 검사를 요구하지 않아 빠뜨리기 쉬움
- 기본 `new`는 예외를 던져, 처리하지 않으면 실패가 묻히지 않음

</details>

<details>
<summary>`delete ptr;` 다음 줄에 `ptr = nullptr;`를 적는 이유는?</summary>

- `delete`는 메모리만 돌려주고 `ptr`의 주소는 그대로 남김. 그 주소로 다시 접근하면 정의되지 않은 동작
- `nullptr`로 비워 두면 실수로 쓰는 것을 막기 쉽고, 한 번 더 `delete`해도 안전함

</details>
