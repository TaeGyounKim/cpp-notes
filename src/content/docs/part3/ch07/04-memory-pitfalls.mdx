## 실수를 찾아 주는 도구: AddressSanitizer

- **AddressSanitizer** (ASan): 컴파일러가 메모리 접근마다 검사 코드를 끼워 넣어, 실행 중에 메모리 실수를 잡아내는 도구
  - GCC와 Clang에서는 `-fsanitize=address` 옵션으로 켬. `-g`를 함께 주면 소스의 줄 번호까지 알려 줌
  - Visual C++도 `/fsanitize=address`로 지원함
  - 실수를 발견하면 프로그램을 멈추고, 어떤 종류의 실수인지와 어느 줄에서 일어났는지 출력함
- 출력은 길지만 볼 곳은 정해져 있음

| 줄 | 알려 주는 것 |
| --- | --- |
| `ERROR: AddressSanitizer: ...` | 실수의 종류 |
| `#… in main /app/example.cpp:10` | 실수가 일어난 곳(파일과 줄 번호) |
| `allocated by` / `freed by` | 그 메모리를 잡은 곳 / 돌려준 곳 |
| `SUMMARY:` | 한 줄 요약 |

- 검사 때문에 느려지고 메모리를 더 씀. 개발하고 시험할 때 켜고, 출시 빌드에서는 끔

## 버퍼를 모자라게 잡기와 범위 밖 접근

### 모자라게 잡기

- **버퍼** (buffer): 데이터를 담으려고 잡아 둔 메모리 덩어리
- C 스타일 문자열에서 특히 흔한 실수: 끝의 `'\0'`(널 문자)을 담을 한 칸을 빠뜨림 (2장의 [C 스타일 문자열](../../../part1/ch02/01-c-strings-and-literals/))
- 또 다른 원인: "이 정도면 충분하겠지" 하고 최대 크기를 정해 버리는 것
- C의 기본 문자열 함수(`strcpy`, `strcat` 등)는 크기를 지키지 않음. 버퍼 끝을 지나 아무 메모리에나 신나게 씀 <CppRef path="cpp/string/byte/strcpy" />

<RunCode client:load code={overflowCode} flags="-std=c++23 -Wall -Wextra -fsanitize=address -g" />

- 볼 것
  - `ERROR: AddressSanitizer: heap-buffer-overflow`: 자유 저장소 버퍼를 넘어섬
  - `example.cpp:10`: `strcpy`를 부른 줄. `allocated by ... example.cpp:9`: 모자라게 잡은 줄
  - 같은 코드를 `-fsanitize=address` 없이 실행하면 `Hello`가 멀쩡히 출력되고 종료 코드도 0. 실수가 **조용히 지나감**. 그래서 위험함

### 고치는 방법

- 예: 네트워크에서 데이터를 조금씩 받아 하나의 문자열에 이어 붙임. 고정 크기 `char` 배열에 `strcat`으로 붙이면 언젠가 넘침
- 고치는 방법, 좋은 순서대로

| 순위 | 방법 |
| --- | --- |
| 1 | C++ 문자열(`std::string`)을 씀. 이어 붙일 때 필요한 메모리를 알아서 관리함 |
| 2 | 버퍼를 자유 저장소에 잡고, 자리가 모자라면 지금 내용과 새 조각을 담을 만큼 큰 버퍼를 새로 잡아 옮긴 뒤 옛 버퍼를 지움 |
| 3 | 데이터를 받는 함수가 최대 개수(`'\0'` 포함)를 받아 그 이상은 넘기지 않게 하고, 버퍼의 남은 자리와 현재 위치를 따로 관리함 |

### 범위 밖 접근과 버퍼 오버플로

- 버퍼를 모자라게 잡으면 대개 **범위 밖 접근**으로 이어짐: 버퍼가 실제보다 크다고 생각하고 그 밖에 씀
- 중요한 메모리가 덮어써지는 것은 시간문제이고, 결국 프로그램이 죽음. 객체의 메모리가 갑자기 덮어써진다고 상상해 볼 것
- `'\0'`을 잃어버린 C 스타일 문자열도 같은 문제를 일으킴

```cpp
void fillWithX(char* text)
{
    for (int i{ 0 }; text[i] != '\0'; ++i) {
        text[i] = 'X';   // '\0'이 없으면 문자열 뒤의 메모리까지 계속 덮어씀
    }
}
```

- **버퍼 오버플로** (buffer overflow): 배열의 끝을 지나 메모리에 쓰는 버그
  - 바이러스나 웜 같은 악성 코드가 이 버그를 많이 이용해 왔음. 메모리 일부를 덮어쓸 수 있다는 점을 악용해 실행 중인 프로그램에 코드를 집어넣음

:::caution
아무 보호도 해 주지 않는 C 스타일 문자열과 배열을 피한다. 메모리를 모두 알아서 관리하는 `std::string`, `std::vector` 같은 현대적이고 안전한 도구를 쓴다.
:::

## 메모리 누수

- 요즘 C++에서는 메모리 누수가 없음. 모든 메모리 관리를 `std::vector`, `std::string` 같은 상위 클래스가 맡기 때문
  - 길 밖으로 나가 메모리를 손으로 잡고 돌려줄 때만 누수가 생김
- 누수는 찾고 고치기 괴로움
  - 프로그램이 드디어 동작하고 결과도 맞아 보임
  - 그런데 오래 돌릴수록 메모리를 점점 더 먹음. 누수가 있다는 뜻
- **누수**: 메모리를 잡고 돌려주는 것을 잊은 것. 조심하면 쉽게 피할 수 있을 것 같지만 그렇지 않음
  - 클래스마다 `new`에 맞는 `delete`가 다 있어도 누수가 생길 수 있음

<RunCode client:load code={leakCode} flags="-std=c++23 -Wall -Wextra -fsanitize=address -g" />

- 무슨 일이 일어났나
  - `Sensor` 클래스는 제대로 짜였음. 생성자에서 잡고 소멸자에서 돌려줌
  - `replace()`가 부르는 쪽의 포인터를 새 객체로 바꿔 버림. 첫째 `Sensor`를 지우지 않았음
  - 포인터를 잃은 객체는 지울 방법이 거의 없음
- 출력에서 볼 것
  - `ERROR: LeakSanitizer: detected memory leaks`: 프로그램이 끝날 때 아직 돌려주지 않은 메모리를 찾음
  - `Direct leak ... example.cpp:23`: 첫째 `Sensor` 자체. 아무도 가리키지 않는 메모리
  - `Indirect leak ... Sensor::Sensor() example.cpp:6`: 첫째 `Sensor` 안의 `int`. 누수된 객체를 거쳐서만 닿을 수 있던 메모리
- 원인은 대개 의사소통이나 문서의 부족
  - 부르는 쪽은 변수가 참조로 넘어가서 포인터가 바뀔 줄 몰랐을 수 있음
  - 매개변수가 "`const`가 아닌 포인터의 참조"(`Sensor*&`)라는 것을 눈치챘다면 의심했겠지만, 그 동작을 설명하는 주석이 없었음
- 실제 코드에서는 `m_reading`도 `sensor`도 맨 포인터가 아니라 스마트 포인터여야 함(다음 글)

### 누수를 찾는 도구들

- 누수를 추적하기 어려운 이유: 메모리를 들여다보고 어떤 객체가 안 쓰이는지, 원래 어디서 잡혔는지 쉽게 볼 수 없음
- 그것을 대신해 주는 도구가 있음. 비싼 상용 제품부터 무료 도구까지

| 도구 | 환경 | 쓰는 법 |
| --- | --- | --- |
| AddressSanitizer(LeakSanitizer 포함) | GCC, Clang | `-fsanitize=address -g`로 컴파일해 실행. 위 예제처럼 끝날 때 누수를 보고 |
| Valgrind | Linux | 프로그램을 다시 컴파일하지 않고 `valgrind --leak-check=full ./program`처럼 실행. 누수된 메모리를 잡은 정확한 줄을 알려 주는 무료 오픈 소스 도구 |
| Visual C++ 디버그 힙 | Windows, Visual C++ | 디버그 빌드에서 C 런타임(CRT) 라이브러리의 누수 검사를 켬. 프로그램이 끝날 때 디버그 출력 창에 누수를 보고 |

- Visual C++ 디버그 힙을 켜는 법 (MFC 프로젝트가 아니면 기본으로 꺼져 있음)
  - 소스 맨 앞에 정해진 매크로와 헤더를 넣음: `_CRTDBG_MAP_ALLOC` 정의, `<cstdlib>`, `<crtdbg.h>`
  - 디버그 빌드에서 `new`가 파일 이름과 줄 번호를 기록하도록 다시 정의함
  - `main()` 첫 줄에서 `_CrtSetDbgFlag(_CRTDBG_ALLOC_MEM_DF | _CRTDBG_LEAK_CHECK_DF);`를 부름
  - 출력에 누수된 블록마다 파일, 줄 번호, 할당 일련번호(`{147}` 같은)가 나옴. 출력 창에서 두 번 누르면 그 줄로 감
  - `_CrtSetBreakAlloc(147);`처럼 일련번호를 주면 그 할당이 일어날 때 디버거가 멈춤
  - 매크로(`#define`, `#ifdef`)는 11장에서 다룸
- 도구는 누수를 **고쳐 주지 않음**. 실마리를 줄 뿐
  - 보통은 디버거로 코드를 한 줄씩 따라가며, 원래 객체를 지우지 않고 포인터를 덮어쓴 곳을 찾음
  - 대부분의 디버거는 어떤 값이 바뀔 때 실행을 멈추는 **감시점** (watch point) 기능이 있음

:::caution
메모리 누수를 피하려면 `std::vector`, `std::array`, `std::string`, 스마트 포인터 같은 현대 C++ 도구를 쓰는 것을 강력히 권한다.
:::

## 두 번 지우기와 해제된 메모리 쓰기

- `delete`로 메모리를 돌려주면 그 메모리는 프로그램의 다른 곳이 쓸 수 있게 됨
- 그런데 그 포인터를 계속 쓰는 것을 막는 장치는 없음. 그 포인터는 이제 **매달린 포인터** (dangling pointer)
- **두 번 지우기** (double deletion): 같은 포인터에 `delete`를 또 함. 그사이 다른 객체에 넘어간 메모리를 돌려줘 버릴 수 있음

<RunCode client:load code={danglingCode} flags="-std=c++23 -Wall -Wextra -fsanitize=address -g" />

- 볼 것
  - `heap-use-after-free`: 해제된 메모리를 읽음. `freed by ... example.cpp:6`이 돌려준 줄, `example.cpp:9`가 읽은 줄
  - 해 볼 것: 출력 줄을 지우고 `delete price;`의 주석을 풀면 `attempting double-free`
  - `-fsanitize=address` 없이 실행하면 알 수 없는 숫자가 하나 출력되고 정상 종료함. 아무 경고도 없음
- 왜 찾기 어려운가: 증상이 바로 나타나지 않을 수 있음
  - 두 번 지우기가 짧은 간격으로 일어나면, 그 메모리가 아직 다시 쓰이지 않아 프로그램이 한동안 멀쩡히 돌 수 있음
  - 지운 객체를 곧바로 쓰면 대개 아직 내용이 그대로 남아 있음
  - 그러나 그렇게 동작한다는 보장은 전혀 없음. 할당자는 지운 객체를 보존할 의무가 없음. 동작한다 해도 지운 객체를 쓰는 것은 매우 나쁜 코드
- 막는 방법: 메모리를 돌려준 뒤 포인터를 `nullptr`로 비움
  - `nullptr`을 지우는 것은 아무 일도 하지 않으므로 두 번 지우기가 무해해짐
  - `nullptr`을 역참조하면 대개 곧바로 프로그램이 죽어서, 조용히 틀린 값을 쓰는 것보다 훨씬 찾기 쉬움
- 많은 누수 검사 도구가 두 번 지우기와 해제된 메모리 사용도 함께 잡음. AddressSanitizer가 그 예

## 이전 표준에서는

- 이 글의 내용은 표준 버전과 상관없음. `new`, `delete`, `strcpy`, `std::string`은 처음 표준(C++98)부터 있음
- AddressSanitizer는 언어 표준이 아니라 컴파일러가 제공하는 기능. C++11로 컴파일하는 프로젝트에서도 쓸 수 있음. 쓰는 컴파일러가 지원하는지는 그 컴파일러의 문서에서 확인

| 이 글에서 쓴 것 | 들어온 표준 | 그 이전에는 |
| --- | --- | --- |
| `std::println` | C++23 | `std::cout <<` |

## 헷갈리기 쉬운 점

- 프로그램이 정상 종료했으니 메모리 실수가 없다?
  - 이 글의 버그 예제들은 검사 도구 없이 실행하면 모두 정상 종료함. 정의되지 않은 동작은 "멀쩡해 보이는 것"도 포함함
- `strlen`으로 잰 길이만큼 잡으면 문자열을 담을 수 있다?
  - `strlen`은 `'\0'`을 세지 않음. C 스타일 문자열을 담으려면 한 칸 더 필요함
- 클래스마다 `new`와 `delete`의 짝을 맞추면 누수가 없다?
  - 포인터를 덮어쓰거나 잃어버리면 짝이 맞아도 누수가 생김. 위 `replace()` 예제가 그 경우
- Direct leak과 Indirect leak
  - Direct: 아무것도 가리키지 않게 된 메모리. Indirect: 누수된 메모리 안에서만 가리키던 메모리. Direct를 고치면 Indirect도 대개 함께 사라짐
- 도구가 누수를 알려 주면 고쳐 준다?
  - 어디서 잡은 메모리가 새는지만 알려 줌. 왜 돌려주지 못했는지는 코드를 따라가며 직접 찾아야 함

## 정리

| 실수 | 결과 | 막는 법 |
| --- | --- | --- |
| 버퍼를 모자라게 잡기 | 범위 밖 쓰기, 메모리 손상 | `std::string`, `std::vector` |
| 범위 밖 접근 / 버퍼 오버플로 | 손상, 종료, 보안 취약점 | 크기를 아는 컨테이너, `at()` |
| 메모리 누수 | 메모리를 점점 더 먹음 | 스마트 포인터, 컨테이너 |
| 해제된 메모리 쓰기 | 정의되지 않은 동작 | 돌려준 뒤 `nullptr` |
| 두 번 지우기 | 다른 객체의 메모리를 돌려줌 | 돌려준 뒤 `nullptr` |

| 도구 | 찾는 것 |
| --- | --- |
| AddressSanitizer (`-fsanitize=address -g`) | 범위 밖 접근, 누수, 해제된 메모리 쓰기, 두 번 지우기 |
| Valgrind | 누수와 잘못된 메모리 접근. 다시 컴파일하지 않고 |
| Visual C++ 디버그 힙 | 누수. 파일과 줄 번호, 할당 일련번호 |

## 복습 질문

<details>
<summary>`char* copy{ new char[std::strlen(text)] }; std::strcpy(copy, text);`의 문제는?</summary>

- `'\0'`을 담을 한 칸이 모자람. `strcpy`가 버퍼 밖에 씀
- `new char[std::strlen(text) + 1]`이어야 하고, 더 나은 해결은 `std::string copy{ text };`

</details>

<details>
<summary>AddressSanitizer 출력에서 실수가 일어난 줄은 어디서 찾는가?</summary>

- `ERROR:` 줄 아래 호출 목록의 `in main /app/example.cpp:줄번호`
- `SUMMARY:` 줄에도 파일과 줄 번호가 나옴

</details>

<details>
<summary>함수 매개변수가 `Widget*&`이다. 부르는 쪽이 조심해야 할 점은?</summary>

- 함수가 부르는 쪽의 포인터 자체를 바꿀 수 있음
- 바꾸기 전에 원래 객체를 누가 지우는지 분명하지 않으면 누수가 생김. 문서를 확인하거나 스마트 포인터로 소유권을 분명히 함

</details>

<details>
<summary>해제된 메모리를 곧바로 읽었더니 원래 값이 나왔다. 괜찮은 코드인가?</summary>

- 아님. 정의되지 않은 동작이 우연히 멀쩡해 보였을 뿐
- 할당자는 지운 메모리를 보존할 의무가 없고, 언제 다른 데 쓰일지 모름

</details>

<details>
<summary>`delete p;` 다음에 `p = nullptr;`를 두면 막을 수 있는 실수 두 가지는?</summary>

- 두 번 지우기: `nullptr`을 지우는 것은 아무 일도 하지 않음
- 해제된 메모리 쓰기: 조용히 틀린 값을 쓰는 대신, 대개 곧바로 죽어서 찾기 쉬워짐

</details>
