## 재정의하는 함수의 반환 타입 바꾸기

- 멤버 함수를 재정의하는 이유는 대개 구현을 바꾸기 위해서. 그런데 반환 타입 같은 다른 특성을 바꾸고 싶을 때도 있음
- 기본 원칙: 기반 클래스와 **똑같은 선언**(원형)으로 재정의함. 구현은 바뀌어도 원형은 그대로
- 예외: 기반 클래스의 반환 타입이 **클래스의 포인터나 참조**라면, 파생 클래스에서 그 클래스를 상속한 **더 구체적인 클래스**의 포인터나 참조로 바꿀 수 있음
  - 이런 타입을 **공변 반환 타입** (covariant return type)이라고 함 <CppRef path="cpp/language/virtual" />
  - 기반 클래스와 파생 클래스가 **평행한 계층**의 객체를 다룰 때 쓸모 있음. 평행한 계층: 첫 계층과 따로 있지만 관련된 다른 클래스 묶음

### 예: 기록 장치와 저장 매체

- 두 계층
  - 기록 장치: `Recorder` ← `Dashcam`(블랙박스), `Doorbell`(초인종 카메라)
  - 저장 매체: `Storage` ← `SdCard`, `CloudDrive`
- `SdCard`에는 `format()`, `CloudDrive`에는 `sync()`가 있음
- `Recorder`는 기록할 준비가 된 저장 매체를 돌려주는 순수 가상 함수 `readyStorage()`를 가짐

```cpp
class Recorder
{
public:
    virtual Storage& readyStorage() = 0;
};
```

- `SdCard`는 `Storage`이므로 `Dashcam`은 `Storage&`를 돌려주는 판으로 구현할 수 있음
- 그런데 `Dashcam`은 **언제나** `SdCard`를 돌려줌. 반환 타입을 바꿔 사용하는 쪽에 그 사실을 알릴 수 있음

```cpp
class Dashcam : public Recorder
{
public:
    SdCard& readyStorage() override;
};
```

- 그러면 `Dashcam`으로 직접 다룰 때는 캐스트 없이 `cam.readyStorage().format()`을 부를 수 있음

### 바꿔도 되는지 판단하기

- 기존 코드가 여전히 동작하는지 생각해 봄: **리스코프 치환 원칙** (Liskov substitution principle, LSP)
  - `readyStorage()`가 `Storage`를 돌려준다고 가정한 코드는 그대로 컴파일되고 올바르게 동작함
  - `SdCard`와 `CloudDrive`는 모두 `Storage`이므로, `Storage`에 대고 부르던 함수는 모두 그대로 부를 수 있음
- 전혀 관계없는 타입으로는 바꿀 수 없음
  - `int& readyStorage() override`는 오류: `conflicting return type specified for 'virtual int& Doorbell::readyStorage()'`
- 스마트 포인터로는 안 됨
  - 기반 클래스가 `std::shared_ptr<Storage>`를 돌려준다면, 파생 클래스가 `std::shared_ptr<SdCard>`로 바꿀 수 없음
  - `shared_ptr`는 클래스 템플릿이라 `shared_ptr<Storage>`와 `shared_ptr<SdCard>`는 서로 전혀 관계없는 두 타입
  - 오류: `invalid covariant return type for 'virtual std::shared_ptr<SdCard> ...'`

## 기반 클래스 가상 함수에 오버로드 더하기

- 파생 클래스에서 기반 클래스 가상 함수의 **새 오버로드**를 더하면서, 기반 클래스의 판도 계속 물려받을 수 있음
- 그냥 같은 이름으로 다른 매개변수의 함수를 더하면 기반 클래스의 같은 이름 함수가 모두 **감춰짐**
  - 파생 클래스 객체로 `describe()`를 부르면 오류: `no matching function for call to 'Sensor::describe()'`
- `using` 선언으로 기반 클래스의 판을 명시적으로 파생 클래스에 들여옴

```cpp
class Sensor : public Device
{
public:
    using Device::describe;                       // 기반 클래스의 판을 계속 씀
    virtual void describe(bool verbose) const;    // 새 오버로드
};
```

:::note
기반 클래스의 멤버 함수와 이름은 같고 매개변수 목록이 다른 멤버 함수를 파생 클래스에 두는 일은 드물다.
:::

## 생성자 물려받기

- `using` 선언은 보통 멤버 함수뿐 아니라 **생성자**에도 쓸 수 있음. 기반 클래스의 생성자를 물려받음 <Badge text="C++11" /> <CppRef path="cpp/language/using_declaration" />
- 문제 상황: 파생 클래스 생성자가 매개변수를 기반 클래스 생성자에 넘기는 일만 할 때

```cpp
class Device
{
public:
    Device() = default;
    explicit Device(std::string_view name);
    explicit Device(int serial);
};

class Sensor : public Device
{
public:
    explicit Sensor(std::string_view name) : Device{ name } {}   // 넘기기만 함
};
```

- 이러면 `Sensor`는 자기가 정의한 생성자로만 만들 수 있음. `Device`에 기본 생성자가 있어도 `Sensor s;`는 오류
- `using`으로 기반 클래스의 생성자를 모두 물려받음

```cpp
class Sensor : public Device
{
public:
    using Device::Device;
};

Sensor a;              // 물려받은 기본 생성자
Sensor b{ "부엌" };    // 물려받은 string_view 생성자
Sensor c{ 1002 };      // 물려받은 int 생성자
```

- 물려받은 생성자의 접근 지정자는 기반 클래스에서와 같음(`public`, `protected`, `private`)
- 기반 클래스에서 `= delete`로 지운 생성자는 파생 클래스에서도 지워져 있음

### 물려받은 생성자 감추기

- 파생 클래스가 물려받은 생성자와 **매개변수 목록이 같은** 생성자를 직접 정의하면, 파생 클래스의 것이 우선함. 물려받은 것은 감춰짐
- 예: `Sensor`가 `explicit Sensor(int serial)`을 직접 정의하면, `Sensor c{ 1002 }`는 그것을 부름. `string_view`와 기본 생성자는 여전히 물려받은 것
- 제약
  - 물려받을 때는 **전부** 물려받음. 일부만 고를 수 없음
  - 접근 지정은 기반 클래스에서와 같음. `using` 선언이 어느 접근 지정자 아래에 있든 상관없음

### 생성자 상속과 다중 상속

- 다른 기반 클래스에 매개변수 목록이 같은 생성자가 있으면, 한쪽의 생성자를 물려받을 수 없음. 모호해지기 때문

```cpp
class Base1 { public: explicit Base1(float f); };
class Base2 { public: explicit Base2(float f); };

class Derived : public Base1, public Base2
{
public:
    using Base1::Base1;
    using Base2::Base2;   // Derived(float)가 두 개가 됨
};

Derived d{ 1.2f };   // 오류: call of overloaded 'Derived(...)' is ambiguous
```

- 해결: 충돌하는 생성자를 파생 클래스가 직접 선언함. 원하면 그 안에서 두 기반 클래스 생성자를 모두 부를 수 있음

```cpp
class Derived : public Base1, public Base2
{
public:
    using Base1::Base1;
    using Base2::Base2;
    explicit Derived(float f) : Base1{ f }, Base2{ f } {}
};
```

### 물려받은 생성자와 데이터 멤버

- 생성자를 물려받을 때는 파생 클래스의 데이터 멤버가 모두 제대로 초기화되는지 확인해야 함
- 물려받은 생성자는 **기반 클래스 부분만** 초기화함. 파생 클래스의 데이터 멤버는 손대지 않음
  - 예: `Sensor`가 `int m_channel;`을 가졌는데, 물려받은 `Sensor{ "부엌" }`으로 만들면 `m_channel`은 초기화되지 않음
- 해결: 파생 클래스의 데이터 멤버에 **클래스 안 멤버 초기화**(8장)를 줌: `int m_channel{ 0 };`
  - 직접 정의한 생성자는 여전히 다른 값으로 초기화할 수 있음

- 볼 것
  - `a`, `b`는 물려받은 생성자로 만들었고, `m_channel`은 클래스 안 초기화 덕분에 0
  - `c`는 `Sensor`가 직접 정의한 `int` 생성자. 물려받은 `int` 생성자는 감춰짐
  - `describe()`와 `describe(bool)`이 모두 쓰임. `using Device::describe;`가 없으면 `a.describe()`는 오류

## 헷갈리기 쉬운 점

- 재정의할 때 반환 타입은 절대 바꿀 수 없다?
  - 클래스의 포인터·참조라면 파생 클래스의 포인터·참조로 바꿀 수 있음(공변 반환 타입)
- `shared_ptr<Base>`를 `shared_ptr<Derived>`로 바꿔 돌려줄 수 있다?
  - 안 됨. 두 템플릿 인스턴스는 관계없는 타입
- 파생 클래스에 같은 이름의 오버로드를 더해도 기반 클래스의 판은 그대로 쓸 수 있다?
  - 감춰짐. `using Base::f;`로 들여와야 함
- `using Base::Base;`로 원하는 생성자만 골라 물려받는다?
  - 전부 물려받음. 바꾸고 싶은 것은 같은 매개변수로 직접 정의해 감춤
- 물려받은 생성자가 파생 클래스의 멤버도 초기화한다?
  - 기반 부분만. 파생 클래스 멤버는 클래스 안 초기화로 기본값을 줌

## 정리

| 요소 | 핵심 |
| --- | --- |
| 공변 반환 타입 | 기반의 `Base&`/`Base*`를 파생에서 `Derived&`/`Derived*`로. 스마트 포인터는 불가 |
| LSP | 기존 코드가 그대로 동작하는지로 판단 |
| 오버로드 더하기 | `using Base::f;` + 새 오버로드 |
| 생성자 상속 | `using Base::Base;`. 전부 물려받음, 접근 지정 유지 |
| 감추기 | 같은 매개변수 생성자를 직접 정의하면 그것이 우선 |
| 다중 상속 충돌 | 충돌하는 생성자를 직접 선언 |
| 멤버 초기화 | 물려받은 생성자는 파생 멤버를 초기화하지 않음. 클래스 안 초기화로 |
