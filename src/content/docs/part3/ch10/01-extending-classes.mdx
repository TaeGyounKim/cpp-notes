- 10장에서는 C++의 상속을 다룸: 클래스를 확장하고, 코드를 재사용하고, 다형성을 얻고, 다중 상속과 그 밖의 미묘한 문제, 그리고 타입 변환(캐스트)까지
- 이 글에서 배우는 요소: 상속 문법, 기반 클래스와 파생 클래스, 사용하는 쪽과 파생 클래스 쪽에서 본 상속, `protected`, `final` 클래스

## 왜 상속인가

- 5장의 is-a 관계: 현실의 대상은 계층을 이루는 경향이 있음
- 프로그래밍에서는 다른 클래스를 바탕으로 하거나 조금만 바꾼 클래스가 필요할 때 이 관계가 중요해짐
- 복사해서 붙여 넣고 일부를 고치는 방법도 있지만 문제가 많음
  - 원래 클래스의 버그를 고쳐도 새 클래스에는 반영되지 않음. 코드가 완전히 따로임
  - 컴파일러는 두 클래스의 관계를 모름. 같은 것의 변형이 아니므로 다형적이지 않음(5장)
  - 진짜 is-a 관계가 아님. 코드가 비슷할 뿐 같은 종류의 객체인 것은 아님
  - 원래 코드를 구할 수 없을 수도 있음. 미리 컴파일된 바이너리로만 있다면 복사할 수도 없음
- C++은 진짜 is-a 관계를 언어 차원에서 지원함

## 클래스 확장하기

- 클래스를 정의할 때, 이 클래스가 기존 클래스를 **상속한다** (inherit from), **파생한다** (derive from), **확장한다** (extend)고 컴파일러에게 알릴 수 있음 <CppRef path="cpp/language/derived_class" />
  - 원래 클래스: **부모 클래스**, **기반 클래스** (base class), **상위 클래스** (superclass)
  - 새 클래스: **자식 클래스**, **파생 클래스** (derived class), **하위 클래스** (subclass)
- 파생 클래스는 기반 클래스의 데이터 멤버와 멤버 함수를 저절로 가짐. 그래서 **기반 클래스와 다른 점만** 적으면 됨

```cpp
class Sensor
{
public:
    explicit Sensor(std::string id);
    const std::string& id() const;
protected:
    double lastRaw() const;
    void storeRaw(double raw);
private:
    std::string m_id;
    double m_raw{ 0.0 };
};

class Thermometer : public Sensor
{
public:
    explicit Thermometer(std::string id);
    void measure(double raw);
    double celsius() const;
};
```

- 문법: 클래스 이름 뒤에 `: public 기반클래스`. `public`의 뜻은 이 장 뒤쪽에서 설명함
- `Thermometer`는 `Sensor`의 특성을 공유할 뿐 완전한 클래스. 보통 객체처럼 선언해 씀
- 상속의 여러 모양
  - 사슬: `Thermometer`를 상속하는 세 번째 클래스를 또 만들 수 있음
  - 형제: `Sensor`를 상속하는 다른 클래스(`Hygrometer` 등)도 여럿 만들 수 있음
- 내부적으로 파생 클래스 객체는 기반 클래스 객체를 **하위 객체** (subobject)로 품고 있음
  - `Thermometer` 객체 안에 `Sensor` 부분이 있고, 그 뒤에 `Thermometer`가 더한 부분이 붙는 모양

## 사용하는 쪽에서 본 상속

- 사용하는 쪽에게 `Thermometer` 객체는 **`Sensor` 객체이기도 함**. `Thermometer`가 `Sensor`를 상속하기 때문
  - `Sensor`의 `public` 멤버와 `Thermometer`의 `public` 멤버를 모두 쓸 수 있음
  - 어느 클래스가 정의한 멤버 함수인지 알 필요 없음: `kitchen.id()`(`Sensor`의 것), `kitchen.celsius()`(`Thermometer`의 것)
- 상속은 **한 방향**뿐
  - `Thermometer`는 `Sensor`와의 관계를 알지만, `Sensor`는 `Thermometer`에 대해 아무것도 모름
  - `Sensor`는 `Thermometer`가 아니므로, `Sensor` 객체로는 `Thermometer`의 멤버를 쓸 수 없음

:::note
객체를 쓰는 코드의 관점에서, 객체는 자기 클래스에 속하면서 동시에 모든 기반 클래스에도 속한다.
:::

- 클래스 타입의 포인터나 참조는 그 클래스의 객체뿐 아니라 **파생 클래스의 객체**도 가리킬 수 있음(자세히는 이 장 뒤쪽)

```cpp
Sensor* sensor{ new Thermometer{ "T-01" } };   // 타입이 안 맞는 것 같지만 됨
```

- 그러나 기반 클래스 포인터로는 기반 클래스에 있는 멤버만 쓸 수 있음
  - `sensor->celsius()`는 오류. 객체는 실제로 `Thermometer`이지만 컴파일러는 `Sensor`로만 봄
  - 오류: `'class Sensor' has no member named 'celsius'`
- 이 덕분에 `Sensor`를 다루는 코드는 `Thermometer`도 다룰 수 있음

## 파생 클래스에서 본 상속

- 파생 클래스를 쓰는 방법은 보통 클래스와 크게 다르지 않음. 멤버 함수와 데이터 멤버를 똑같이 정의함
  - 위의 `Thermometer`는 `measure()`와 `celsius()`를 더해 `Sensor`를 늘린 것
- 파생 클래스는 기반 클래스의 `public`·`protected` 멤버를 **자기 멤버처럼** 씀. 실제로 자기 멤버이기도 함
  - `Thermometer::measure()`는 `Sensor`의 `protected` 멤버 함수 `storeRaw()`를 그냥 부름
- 기반 클래스의 `private` 멤버에는 접근할 수 **없음**
  - `Thermometer`에서 `m_raw`를 읽으면 오류: `'double Sensor::m_raw' is private within this context`
  - `private`은 앞으로 생길 파생 클래스가 이 클래스와 어떻게 상호작용할지 통제하는 수단

### 접근 지정자 정리

- 4장의 규칙(데이터 멤버는 모두 `private`, 밖에서 써야 하면 `public` 게터·세터)에 `protected`를 더함

:::caution
데이터 멤버는 모두 `private`으로 둔다. 클래스 밖에서 써야 하면 `public` 게터·세터를, 파생 클래스만 써야 하면 `protected` 게터·세터를 제공한다.
:::

- `private`이 기본인 이유: 캡슐화가 가장 높음
  - 데이터를 어떻게 담는지 바꿔도 `public`·`protected` 인터페이스는 그대로 둘 수 있음
  - 데이터에 직접 접근하게 하지 않으면 `public`·`protected` 세터에서 입력 검사를 쉽게 추가할 수 있음
- 멤버 함수도 기본은 `private`. `public`으로 설계한 것만 `public`, 파생 클래스만 써야 하면 `protected`

| 접근 지정자 | 의미 | 쓰는 곳 |
| --- | --- | --- |
| `public` | 어떤 코드든 접근 가능 | 사용하는 쪽에 제공할 동작(멤버 함수). `private`·`protected` 데이터의 게터·세터 |
| `protected` | 그 클래스와 **파생 클래스**의 멤버 함수가 접근 가능 | 사용하는 쪽에는 감추고 파생 클래스에만 주는 도우미 |
| `private` | 그 클래스의 멤버 함수만 접근 가능. 파생 클래스도 불가 | 기본값. 특히 데이터 멤버 |

:::note
파생 클래스의 관점에서, 기반 클래스의 `public`·`protected` 데이터 멤버와 멤버 함수는 모두 쓸 수 있다.
:::

## 상속 막기

- 클래스 이름 바로 뒤에 `final`을 붙이면 <Badge text="C++11" /> 그 클래스를 상속할 수 없음 <CppRef path="cpp/language/final" />

```cpp
class Thermometer final : public Sensor { /* ... */ };
```

- 상속하려 하면 오류: `cannot derive from 'final' base 'Thermometer' in derived type ...`

## 이전 표준에서는

| 이 글에서 쓴 것 | 들어온 표준 | 그 이전에는 |
| --- | --- | --- |
| `final` 클래스 | C++11 | 막을 방법이 없음. 문서나 주석으로 알림 |
| 클래스 안 멤버 초기화 | C++11 | 생성자 초기화 목록 |
| `std::println` | C++23 | `std::cout <<` |

## 헷갈리기 쉬운 점

- 기반 클래스도 파생 클래스의 멤버를 쓸 수 있다?
  - 상속은 한 방향. 기반 클래스는 파생 클래스를 모름
- 파생 클래스는 기반 클래스의 모든 멤버에 접근할 수 있다?
  - `public`·`protected`만. `private`은 파생 클래스도 불가
- 기반 클래스 포인터가 파생 객체를 가리키면 파생 클래스의 멤버도 부를 수 있다?
  - 컴파일러는 기반 클래스 타입으로만 봄. 기반 클래스에 있는 멤버만 부를 수 있음
- `protected` 데이터 멤버면 편하다?
  - 파생 클래스가 직접 건드리게 되어 캡슐화가 약해짐. 데이터는 `private`, 접근은 `protected` 게터·세터로

## 정리

| 요소 | 핵심 |
| --- | --- |
| 상속 문법 | `class 파생 : public 기반` |
| 파생 클래스 | 기반 클래스의 멤버를 가짐. 다른 점만 적음 |
| 사용하는 쪽 | 파생 객체는 기반 클래스 객체이기도 함. 기반 포인터·참조로 가리킬 수 있음 |
| 한 방향 | 기반 클래스는 파생 클래스를 모름 |
| `protected` | 파생 클래스에서만 접근 가능 |
| `final` 클래스 | 더 상속할 수 없음 |

## 복습 질문

<details>
<summary>`class Hygrometer : public Sensor { ... };`의 객체로 `id()`를 부를 수 있는 이유는?</summary>

- `id()`는 `Sensor`의 `public` 멤버이고, `Hygrometer`는 `Sensor`의 멤버를 물려받기 때문

</details>

<details>
<summary>`Sensor& s{ kitchen };`(`kitchen`은 `Thermometer`)에서 `s.celsius()`가 오류인 이유는?</summary>

- 컴파일러는 `s`를 `Sensor`로만 봄. `Sensor`에는 `celsius()`가 없음

</details>

<details>
<summary>파생 클래스에서는 쓰게 하고 사용하는 쪽에는 감추려면 어떤 접근 지정자를 쓰는가?</summary>

- `protected`. 데이터 멤버라면 `private`으로 두고 `protected` 게터·세터를 제공함

</details>

<details>
<summary>어떤 클래스를 더 이상 상속하지 못하게 하려면?</summary>

- 클래스 이름 뒤에 `final`: `class Thermometer final : public Sensor { ... };`

</details>
