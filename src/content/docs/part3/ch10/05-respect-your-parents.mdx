## 부모의 생성자

- 객체는 한 번에 생겨나지 않음. 부모, 그리고 안에 든 객체들과 함께 만들어짐
- C++이 정한 생성 순서 <CppRef path="cpp/language/constructor" />
  1. 기반 클래스가 있으면 기반 클래스의 생성자를 실행함. 생성자 초기화 목록에서 기반 클래스 생성자를 불렀다면 그것을, 아니면 기본 생성자를
  2. 비`static` 데이터 멤버를 선언된 순서대로 만듦
  3. 이 클래스 생성자의 본문을 실행함
- 이 규칙은 재귀적으로 적용됨. 조부모가 있으면 조부모가 부모보다 먼저 초기화됨

### 기반 클래스 생성자에 인수 넘기기

- 기반 클래스의 기본 생성자는 저절로 불림
- 기반 클래스에 기본 생성자가 없거나, 다른 생성자를 쓰고 싶다면 생성자 초기화 목록에서 직접 부름. 데이터 멤버를 초기화하는 것과 같은 자리

```cpp
class Device
{
public:
    explicit Device(int id);
};

class Station : public Device
{
public:
    explicit Station(int id) : Device{ id } { }
};
```

- 부르지 않으면 오류: `no matching function for call to 'Device::Device()'`
- 파생 클래스 생성자의 **인수**를 기반 클래스에 넘기는 것은 아주 흔하고 괜찮음
- 그러나 파생 클래스의 **데이터 멤버**를 넘기면 안 됨
  - 컴파일은 되지만, 데이터 멤버는 기반 클래스가 만들어진 **뒤에야** 초기화됨. 넘기는 시점에는 초기화되지 않은 값

## 부모의 소멸자

- 소멸자는 인수를 받지 않으므로 언어가 언제나 부모의 소멸자를 저절로 부를 수 있음
- 소멸 순서는 생성 순서의 정반대
  1. 이 클래스 소멸자의 본문을 실행함
  2. 데이터 멤버를 생성의 역순으로 소멸시킴
  3. 기반 클래스가 있으면 소멸시킴
- 역시 재귀적. 사슬의 가장 아래가 언제나 먼저 소멸함

- 볼 것
  - 만들 때 1 → 2 → 3, 없앨 때 4 → 5 → 6
  - 기반 포인터로 `delete`해도 4, 5, 6이 모두 불림. 소멸자가 `virtual`이기 때문
- 소멸자가 `virtual`이 아니었다면 기반 포인터로 `delete`할 때 `Device`의 소멸자만 불리고, `Station`의 소멸자와 그 데이터 멤버들의 소멸자는 불리지 않았을 것(3편)
- 기반 클래스의 소멸자만 `virtual`이어도 파생 클래스에 저절로 적용됨. 그래도 모든 소멸자를 명시적으로 `virtual`로(파생 클래스는 `override`로) 표시해 두면 신경 쓸 일이 없음

:::caution
소멸자는 언제나 `virtual`로 만든다. 컴파일러가 만드는 기본 소멸자는 `virtual`이 아니므로, 적어도 `final`이 아닌 기반 클래스에는 `virtual` 소멸자를 정의하거나 `= default`로 명시한다.
:::

## 생성자와 소멸자 안의 가상 함수 호출

- 생성자와 소멸자 안에서는 가상 함수가 다르게 동작함
  - 기반 클래스의 생성자나 소멸자에서 가상 함수를 부르면, 파생 클래스가 재정의했더라도 **기반 클래스의 판**이 불림
  - 즉 생성자·소멸자 안의 가상 함수 호출은 정적으로 결정되는 것처럼 동작함
- 위 예제의 `Device` 생성자도 `describe()`를 불렀지만 `Device`판이 나왔음
- 이유
  - 생성자: 파생 객체를 만들 때 기반 클래스 생성자가 먼저 실행됨. 그때 파생 부분은 아직 초기화되지 않았으므로, 파생 클래스의 재정의 함수를 부르면 위험함
  - 소멸자: 반대 이유. 기반 클래스 소멸자가 실행될 때 파생 부분은 이미 소멸했음
- 생성 중에 다형적 동작이 꼭 필요하다면(권하지 않음): 기반 클래스에 가상 함수 `initialize()`를 두고 파생 클래스가 재정의함. 사용하는 쪽이 생성이 끝난 뒤 `initialize()`를 따로 부름
  - 소멸 쪽도 마찬가지로 `shutdown()` 같은 가상 함수를 두고 소멸 전에 부르게 함

## 부모의 이름 부르기

- 파생 클래스에서 멤버 함수를 재정의하면, 다른 코드 입장에서는 원래 판이 대체됨. 그러나 부모의 판은 여전히 있고 쓸 수 있음
- 흔한 모양: 재정의한 함수가 기반 클래스가 하던 일을 그대로 하고, 거기에 무언가를 더함
- 예: `Device::describe()`가 `"장치"`를 돌려준다면, `Sensor`는 앞에 `"센서 "`를 붙이고 싶음

```cpp
std::string Sensor::describe() const
{
    return "센서 " + describe();   // 버그!
}
```

- 이것은 동작하지 않음
  - C++의 이름 찾기 규칙은 지역 범위, 그다음 클래스 범위를 먼저 봄. 결국 `Sensor::describe()` 자신을 부름
  - 스택이 바닥날 때까지 끝없이 재귀함. 이 오류를 컴파일 중에 알려 주는 컴파일러도 있지만, GCC는 `-Wall`과 `-Wextra`를 줘도 이 경우 아무 말이 없었음
- 범위 지정 연산자로 부모의 판을 명시함

```cpp
std::string Sensor::describe() const
{
    return "센서 " + Device::describe();
}
```

- 참고: Microsoft Visual C++은 비표준 키워드 `__super`를 지원해 `__super::describe()`처럼 쓸 수 있음. 다른 컴파일러에서는 안 됨
- 현재 멤버 함수의 부모 판을 부르는 것은 흔한 패턴. 파생 클래스 사슬이 있으면 각 단계가 부모의 일을 하고 자기 일을 더함

## 업캐스트와 다운캐스트

### 업캐스트

- 객체를 기반 클래스로 바꾸거나 대입할 수 있음

```cpp
Thermometer thermo;
Device device{ thermo };    // 슬라이싱!
Device& ref{ thermo };      // 슬라이싱 없음
```

- 기반 클래스 **객체**로 받으면 슬라이싱이 일어남. 결과는 `Device` 객체이고, `Device`에는 파생 클래스의 기능이 없음
- 기반 클래스의 **참조나 포인터**로 받으면 슬라이싱이 없음
- 파생 클래스 객체를 기반 클래스로 가리키는 것: **업캐스트** (upcasting). 대개 참조나 포인터로 하는 것이 맞음
  - 그래서 함수는 클래스 객체를 직접 받기보다 참조로 받는 것이 좋음. 파생 클래스를 넘겨도 슬라이싱되지 않음

:::caution
업캐스트할 때는 기반 클래스의 포인터나 참조를 써서 슬라이싱을 피한다.
:::

### 다운캐스트

- 기반 클래스에서 파생 클래스로 바꾸는 것: **다운캐스트** (downcasting)
- 숙련된 C++ 프로그래머들은 대개 꺼림
  - 객체가 정말 그 파생 클래스라는 보장이 없음
  - 다운캐스트가 필요하다는 것 자체가 설계가 좋지 않다는 신호

```cpp
void presumptuous(Device* device)
{
    auto* t{ static_cast<Thermometer*>(device) };   // 무조건 Thermometer라고 가정
    // t로 Thermometer의 멤버 함수를 씀
}
```

- 이 함수를 쓴 사람이 부르는 쪽도 직접 쓴다면 아마 괜찮음(여전히 보기 흉하지만)
- 다른 사람이 부르면 `Thermometer`가 아닌 `Device*`를 넘길 수 있음. 인수 타입을 강제할 컴파일 시점 검사가 없고, 함수는 맹목적으로 가정함

### dynamic_cast

- 다운캐스트가 필요할 때도 있음. 통제된 상황에서는 효과적으로 쓸 수 있음
- 다운캐스트를 한다면 `dynamic_cast`를 씀 <CppRef path="cpp/language/dynamic_cast" />
  - 객체가 자기 타입에 대해 알고 있는 정보를 써서, 말이 안 되는 캐스트를 거부함
  - 그 정보는 대개 vtable에 있음. 그래서 vtable이 있는 객체, 즉 **가상 멤버가 하나 이상 있는** 클래스에서만 쓸 수 있음
  - 포인터 캐스트가 실패하면 엉뚱한 데이터를 가리키는 대신 `nullptr`
  - 참조 캐스트가 실패하면 `std::bad_cast` 예외

```cpp
void lessPresumptuous(Device* device)
{
    auto* t{ dynamic_cast<Thermometer*>(device) };
    if (t != nullptr) {
        // t로 Thermometer의 멤버 함수를 씀
    }
}
```

<RunCode client:load code={castingCode} />

- 이 예제의 `if (auto* t{ ... }; t != nullptr)`는 `if` 문 안의 초기화 <Badge text="C++17" />(1장)
- 그래도 다운캐스트는 나쁜 설계의 신호인 경우가 많음. 없앨 수 있게 설계를 다시 생각할 것
  - 위 함수가 사실 `Thermometer`에만 쓸모 있다면, 처음부터 `Thermometer*`를 받으면 됨
  - 여러 파생 클래스에 두루 동작해야 한다면 다형성을 쓰는 해법을 찾음(다음 글)
- 여러 캐스트의 자세한 차이는 이 장의 마지막 글에서 다룸

:::caution
다운캐스트는 정말 필요할 때만 쓰고, 쓸 때는 `dynamic_cast`를 쓴다.
:::

## 헷갈리기 쉬운 점

- 파생 클래스의 생성자가 먼저 실행된다?
  - 기반 클래스 생성자 → 데이터 멤버 → 파생 클래스 생성자 본문. 소멸은 그 반대
- 기반 클래스 생성자에 파생 클래스의 데이터 멤버를 넘겨도 된다?
  - 그 시점에는 아직 초기화되지 않은 값. 생성자의 인수를 넘김
- 기반 클래스 생성자에서 가상 함수를 부르면 파생 클래스의 판이 불린다?
  - 기반 클래스의 판이 불림. 파생 부분이 아직 없기 때문
- 재정의한 함수 안에서 같은 이름을 부르면 부모의 판이 불린다?
  - 자기 자신이 불려 무한 재귀. `기반클래스::함수()`로 명시
- `dynamic_cast`는 어떤 클래스에나 쓸 수 있다?
  - 가상 함수가 하나 이상 있는(다형적인) 클래스에만

## 정리

| 요소 | 핵심 |
| --- | --- |
| 생성 순서 | 기반 클래스 → 데이터 멤버(선언 순) → 생성자 본문 |
| 소멸 순서 | 소멸자 본문 → 데이터 멤버(역순) → 기반 클래스 |
| 기반 생성자 호출 | 초기화 목록에서 `Base{ 인수 }`. 데이터 멤버는 넘기지 않음 |
| 생성자·소멸자 안의 가상 함수 | 그 클래스의 판이 불림 |
| 부모의 판 부르기 | `Base::함수()` |
| 업캐스트 | 참조·포인터로. 객체로 받으면 슬라이싱 |
| 다운캐스트 | 되도록 피함. 할 때는 `dynamic_cast`. 실패하면 `nullptr` 또는 `std::bad_cast` |
