- 다루는 것: 여러 처리 장치를 함께 쓰는 **멀티스레드 프로그래밍** (multithreaded programming)의 바탕 개념과 흔한 문제
- 이 장은 표준 스레드 라이브러리로 멀티스레드를 소개함. 주제가 넓어 모든 세부를 다루지는 못함
- 이 글에서 배우는 요소: 동시·병렬 실행, 경쟁 조건, 찢어짐, 교착 상태, 거짓 공유

## 왜 멀티스레드인가

- 처리 장치가 여럿인 컴퓨터
  - 독립된 CPU 칩 여러 개, 또는 칩 하나 안의 독립된 CPU 여러 개(**코어** core, **멀티코어 프로세서** multicore processor), 또는 둘 다
  - 지금은 서버부터 스마트폰까지 거의 모든 기기가 멀티코어. 이를 다 쓰려면 멀티스레드 코드를 쓸 줄 알아야 함
- 예전에는 플랫폼·운영체제마다 다른 API를 써야 했음. **C++11**이 표준 스레드 라이브러리를 넣어 플랫폼에 독립적인 코드가 쉬워짐 <Badge text="C++11" /> <CppRef path="cpp/thread" />
  - 표준 밖의 라이브러리(pthreads, Boost.Thread 등)도 있지만 이 장은 표준만 다룸
- 현재 표준은 CPU만 대상으로 하고 GPU는 대상이 아님

### 실행 방식 셋

| 방식 | 뜻 |
| --- | --- |
| **순차 실행** (sequential) | 일을 하나씩 차례로 |
| **동시 실행** (concurrent) | 여러 일이 동시에 진행되는 것처럼 보임. 운영체제가 일마다 짧은 **시간 조각** (time slice)을 번갈아 줄 수도 있음 |
| **병렬 실행** (parallel) | 여러 일이 정말로 같은 순간에 실행됨. 예: 여러 코어에서 |

- 멀티스레드 프로그래밍은 여러 일을 동시에(어쩌면 병렬로) 실행하게 함
- 2005년 무렵까지는 클럭 속도 경쟁, 그 뒤로는 전력과 발열 문제로 **코어 수** 경쟁. 4코어, 8코어는 흔하고 128코어가 넘는 것도 있음
- 그래픽 카드의 GPU는 코어가 수만 개인 대규모 병렬 프로세서. 게임뿐 아니라 인공지능, 영상 처리, 단백질 접힘 계산 등에도 씀

### 멀티스레드 코드를 쓰는 두 가지 이유

- **성능**: 계산을 서로 독립적인 작은 조각으로 나눠 여러 코어에서 병렬로 돌리면 크게 빨라짐
  - 예: 이웃 픽셀 정보가 필요 없는 이미지 처리. 이미지를 넷으로 나누면 4코어에서 거의 4배
  - 늘 독립적으로 나눌 수는 없지만, 일부만이라도 병렬로 만들면 빨라짐. 알고리즘을 병렬로 만드는 것 자체가 어려운 부분
- **기능 분리**: 서로 직교하는 축으로 나눔. 예: 오래 걸리는 계산을 **작업자 스레드** (worker thread)에서 돌려 UI 스레드가 멈추지 않게

### 스레드 안전하게 만드는 방법

| 방법 | 뜻 |
| --- | --- |
| 바뀌지 않는 데이터 | 상수 데이터는 여러 스레드가 읽어도 안전 |
| 원자적 연산 | 스레드 안전한 연산을 주는 저수준 타입(4편) |
| 상호 배제와 다른 동기화 | 공유 데이터 접근을 조율(5~7편) |
| 스레드 지역 저장소 | `thread_local` 변수는 스레드마다 따로 있어 대개 안전(2편) |

:::note
멀티스레드 문제를 피하는 가장 좋은 방법은 여러 스레드가 공유 메모리를 읽고 쓸 필요가 없도록 설계하는 것이다. 그럴 수 없을 때 동기화 수단이나 원자적 연산을 쓴다.
:::

## 경쟁 조건

- **경쟁 조건** (race condition): 여러 스레드가 공유 자원에 접근할 때 실행 순서에 따라 결과가 달라지는 것
- 공유 메모리에서의 경쟁 조건이 **데이터 경쟁** (data race): 여러 스레드가 같은 변수에 접근하고, 그중 **적어도 하나가 쓰는** 경우 <CppRef path="cpp/language/memory_model" />
  - C++에서 데이터 경쟁은 **정의되지 않은 동작**
- 예: 공유 변수를 한 스레드는 1 늘리고 다른 스레드는 1 줄임
  - 늘리기는 "메모리에서 읽기 → 더하기 → 메모리에 쓰기"의 여러 단계. 현대 x86의 증감 명령도 원자적이지 않아 중간에 다른 명령이 끼어들 수 있음
  - 한쪽이 끝난 뒤 다른 쪽이 시작하면 결과는 처음 값 그대로
  - 단계가 섞이면 한쪽의 결과가 사라짐

## 찢어짐

- **찢어짐** (tearing): 데이터 경쟁의 한 가지 결과
  - **찢어진 읽기** (torn read): 한 스레드가 데이터의 일부만 쓴 순간 다른 스레드가 읽으면, 앞뒤가 맞지 않는 값을 봄
  - **찢어진 쓰기** (torn write): 두 스레드가 동시에 쓰면 한쪽은 앞부분을, 다른 쪽은 뒷부분을 써서 최종 값이 섞임
- 예: 64비트 값을 32비트씩 두 번에 나눠 쓰는 환경에서 중간에 읽기

## 교착 상태

- 경쟁 조건을 상호 배제 같은 동기화로 풀면 다른 문제가 생길 수 있음
- **교착 상태** (deadlock): 두 스레드(또는 그 이상)가 **서로 상대가 무언가 하기를 기다리며** 영원히 멈춤
- 공유 자원을 쓰려면 허락(예: **뮤텍스** mutex를 잠그기, 5편)을 받아야 함
- 예: 자원 A, B를 지키는 뮤텍스 둘. 두 스레드가 둘 다 잡되 **순서가 다름**

| 스레드 1 | 스레드 2 |
| --- | --- |
| A 잡기 | B 잡기 |
| B 잡기 | A 잡기 |
| … 계산 … | … 계산 … |
| B 놓기 | A 놓기 |
| A 놓기 | B 놓기 |

- 이렇게 실행되면 교착
  1. 스레드 1: A 잡기(성공)
  2. 스레드 2: B 잡기(성공)
  3. 스레드 1: B 잡기(스레드 2가 가졌으므로 기다림)
  4. 스레드 2: A 잡기(스레드 1이 가졌으므로 기다림)
- 그림으로 그리면 "스레드 1 → B → 스레드 2 → A → 스레드 1"의 **순환**이 생김
- 피하는 법
  - 늘 **같은 순서**로 잡음
  - 일정 시간만 시도하고, 못 잡으면 가진 것도 놓은 뒤 잠시 쉬었다 다시 시도. 효과는 상황에 따라 다름
  - 표준의 `std::lock()`, `std::scoped_lock`(5편)은 여러 자원을 교착 없이 한 번에 잡음. 직접 만들지 말고 이것을 씀
  - 가장 좋은 것은 여러 락을 한꺼번에 잡을 일이 없게, 더 나아가 락이 필요 없게 설계하는 것

## 거짓 공유

- 대부분의 캐시는 **캐시 줄** (cache line) 단위로 동작함. 요즘 CPU는 보통 64바이트
- 캐시 줄에 무언가를 쓰려면 그 줄 전체를 잠가야 함
- **거짓 공유** (false sharing): 두 스레드가 **서로 다른** 데이터를 쓰지만 그 데이터가 **같은 캐시 줄**에 있으면, 한 스레드가 쓸 때 다른 스레드가 막힘. 공유하지 않는데도 공유하는 것처럼 느려짐
- 해결: 여러 스레드가 따로 쓰는 데이터가 캐시 줄을 함께 쓰지 않도록 **정렬**함
  - `std::hardware_destructive_interference_size`(`<new>`): 동시에 접근하는 두 객체 사이에 권장되는 최소 간격 <Badge text="C++17" /> <CppRef path="cpp/thread/hardware_destructive_interference_size" />
  - `alignas`와 함께 씀 <CppRef path="cpp/language/alignas" />

```cpp
struct Counters {
    alignas(std::hardware_destructive_interference_size) std::atomic<int> a;
    alignas(std::hardware_destructive_interference_size) std::atomic<int> b;
};
```

- 볼 것
  - 보통 `int`는 두 스레드가 20만 번씩 늘려도 40만이 되지 않음(갱신이 사라짐). 원자적 카운터는 정확히 40만
  - 같은 코드를 다시 실행하면 서버가 이전 결과를 돌려줄 수 있음. 숫자를 조금 바꿔 실행하면 다른 결과를 볼 수 있음
  - `Spread`는 두 카운터를 캐시 줄 간격만큼 떨어뜨려 크기가 커짐
  - `hardware_concurrency()`: 실행 환경의 하드웨어 스레드 수 추정값(2편)

## 헷갈리기 쉬운 점

- 동시 실행과 병렬 실행은 같다?
  - 동시는 번갈아 진행하는 것도 포함. 병렬은 정말 같은 순간에
- `++x`는 명령 하나라 스레드 안전하다?
  - 읽기, 계산, 쓰기로 나뉘며 원자적이지 않음. 보통 변수의 데이터 경쟁은 정의되지 않은 동작
- 두 스레드가 읽기만 해도 데이터 경쟁이다?
  - 적어도 하나가 **써야** 데이터 경쟁
- 다른 변수를 쓰면 서로 영향이 없다?
  - 같은 캐시 줄이면 거짓 공유로 느려짐
- 교착 상태는 뮤텍스를 잡는 순서와 상관없다?
  - 순서가 엇갈리면 생김. 같은 순서로, 또는 `std::scoped_lock`으로 한 번에

## 정리

| 요소 | 핵심 |
| --- | --- |
| 실행 방식 | 순차, 동시(번갈아), 병렬(정말 동시에) |
| 쓰는 이유 | 성능(병렬 분할), 기능 분리(작업자 스레드) |
| 데이터 경쟁 | 같은 변수, 하나 이상이 쓰기. 정의되지 않은 동작 |
| 찢어짐 | 일부만 쓴 값을 읽거나, 두 쓰기가 섞임 |
| 교착 상태 | 서로를 기다리는 순환. 같은 순서, `std::lock`, 설계로 피함 |
| 거짓 공유 | 같은 캐시 줄의 다른 데이터. `alignas` + `hardware_destructive_interference_size` |

## 복습 질문

<details>
<summary>스레드 셋이 각각 뮤텍스 A·B, B·C, C·A 순서로 잡는다면 교착 상태가 생길 수 있는가?</summary>

- 생길 수 있음. 셋이 각자 첫 번째를 잡은 뒤 두 번째를 기다리면 A → B → C → A 순환이 됨
- 모든 스레드가 A, B, C처럼 정해진 전체 순서를 따르면(예: C·A 대신 A·C) 순환이 생기지 않음

</details>

<details>
<summary>`std::vector<int> counts(threads)`에서 스레드 `i`가 `counts[i]`만 계속 늘리면 데이터 경쟁인가? 성능 문제는 없는가?</summary>

- 서로 다른 원소라 데이터 경쟁은 아님
- 그러나 이웃 원소들이 같은 캐시 줄에 있어 거짓 공유로 느려질 수 있음. 지역 변수에 모았다가 마지막에 한 번 쓰거나, 원소를 캐시 줄 간격으로 떨어뜨림

</details>

<details>
<summary>여러 스레드가 함께 읽기만 하는 설정 값은 어떻게 다루면 안전한가?</summary>

- 스레드를 시작하기 전에 다 만든 뒤 `const`로 두고 읽기만 함. 바뀌지 않는 데이터는 동기화 없이 안전
