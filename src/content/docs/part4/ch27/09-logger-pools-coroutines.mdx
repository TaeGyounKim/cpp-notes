## 멀티스레드 로거

- 여러 스레드가 로그 메시지를 큐에 넣고, 로거의 **백그라운드 스레드 하나**가 큐를 처리해 파일(여기서는 화면)에 차례로 씀
- 표준에는 스레드 안전한 큐가 없으므로, 큐 접근을 **뮤텍스**로 보호하고 새 항목을 **조건 변수**로 알림
- 두 단계로 설계하며 멀티스레드 코드에서 흔히 부딪히는 문제를 봄

### 첫 설계

- `log(entry)`: 락을 잡고 큐에 넣은 뒤 `notify_all()`
- 백그라운드 함수: 큐가 빌 동안 조건 변수에서 기다리다가, 깨면 큐의 항목을 처리
- 처리 요령: 락을 쥔 동안에는 현재 큐를 **빈 지역 큐와 바꾸기**(`swap`)만 하고 바로 락을 놓음. 느린 쓰기는 락 **밖에서** 지역 큐로 함
  - 그동안 다른 스레드는 막히지 않고 새 (빈) 큐에 넣을 수 있음

```cpp
std::queue<std::string> local;
local.swap(m_queue);      // 락 안에서: 순식간
lock.unlock();
write_all(local);         // 락 밖에서: 느린 일
lock.lock();
```

- 문제: 로거의 `thread` 멤버를 `join()`도 `detach()`도 하지 않음
  - 프로그램이 끝나며 join 가능한 `thread`가 소멸하면 `std::terminate()`(2편). 큐에 남은 메시지도 쓰이지 않음
  - 일부 런타임은 오류를 띄우거나 크래시 덤프를 만듦

### 안전한 종료

- 소멸자와 불리언 `m_exit`를 더함
  - 소멸자: `m_exit = true` → 조건 변수로 깨움 → 백그라운드 스레드가 끝날 때까지 `join()`
  - 백그라운드 함수: 깨어났을 때 `m_exit`이면 **큐에 남은 것을 다 쓴 뒤** 반복을 끝냄
- `m_exit`을 바꿀 때 **락을 잡아야** 함
  - 백그라운드 스레드가 `m_exit`을 검사한 직후, `wait()`에 들어가기 직전일 수 있음
  - 이때 락 없이 `m_exit = true`와 `notify_all()`을 하면, 백그라운드 스레드는 새 값도 못 보고 알림도 놓침(**놓친 알림**)
  - 결과는 교착: 소멸자는 `join()`에서, 백그라운드 스레드는 `wait()`에서 서로를 영원히 기다림
- 알림(`notify_all()`)은 락을 쥔 채 해도 되고 놓은 뒤 해도 되지만, `join()` 전에는 **반드시 놓아야** 함. 그래서 중괄호 블록으로 락의 범위를 좁힘

```cpp
~Logger()
{
    {
        std::lock_guard lock{ m_mutex };
        m_exit = true;
    }
    m_cv.notify_all();
    m_worker.join();   // jthread 멤버면 생략: 소멸자가 join
}
```

- 반복의 바깥 조건에 `m_exit`만 넣으면 안 됨: 종료 요청이 왔어도 큐에 남은 항목이 있을 수 있음
- 멀티스레드 코드를 시험할 때 특정 위치에 **일부러 지연**을 넣어 경쟁 상황을 만들어 볼 수 있음(예: 로그 없이 바로 소멸자가 불리게 하고 백그라운드 함수 시작에 잠깐 재우기). 시험용이므로 최종 코드에서는 빼야 함

:::note
`thread` 대신 `jthread`를 권한다. 소멸자에서 자동으로 join하므로 로거 소멸자의 명시적 `join()`이 필요 없다. `jthread` 멤버는 다른 멤버가 모두 초기화된 뒤 시작하도록 **마지막에** 선언한다.
:::

:::caution
이 간단한 일에서도 보듯, 올바른 멀티스레드 코드를 쓰기는 어렵다. 표준 라이브러리에는 아직 동시성 자료 구조가 없다. 실제 제품 코드에서는 직접 만들지 말고 검증된 외부 동시성 자료 구조를 쓴다(예: Boost의 잠금 없는 큐).
:::

## 스레드 풀

- 프로그램 내내 스레드를 동적으로 만들고 없애는 대신, 스레드를 미리 **풀**(pool)로 만들어 두고 필요할 때 씀
  - 어떤 사건을 스레드에서 처리하는 프로그램에서 흔함
- 알맞은 스레드 수
  - 대부분 환경에서 **코어 수**와 같은 것이 이상적. 더 많으면 스레드를 멈췄다 돌렸다 해야 해서 부담이 생김
  - 단, 스레드가 계산만 하고 입출력 등으로 막히지 않을 때 이야기. 막힐 수 있으면 코어보다 많이 두는 것이 알맞을 때가 많음. 최적값은 측정으로 정함
- 처리할 일이 다 같지는 않으므로, 풀의 스레드가 **할 계산을 나타내는 호출 가능 객체**를 입력으로 받는 경우가 많음
- 장점
  - 이미 있는 스레드를 일정에 올리는 것이 새로 만드는 것보다 훨씬 효율적
  - 만드는 스레드 수를 관리할 수 있음
- Intel TBB, Microsoft PPL 같은 라이브러리가 스레드 풀을 구현함. 직접 만들기보다 이런 라이브러리를 권함. 객체 풀 구현 예는 29장

## 코루틴 <Badge text="C++20" />

- **코루틴** (coroutine): 실행 도중에 **멈췄다가** 나중에 **이어서** 실행할 수 있는 함수 <CppRef path="cpp/language/coroutines" />
- 본문에 다음 키워드 중 하나가 있으면 코루틴

| 키워드 | 뜻 |
| --- | --- |
| `co_await` | 다른 계산이 끝나기를 기다리는 동안 코루틴을 멈춤. 끝나면 이어 감 |
| `co_return` | 값을 돌려주고 코루틴을 끝냄. 이후에는 이어 갈 수 없음 |
| `co_yield` | 값을 내주고 멈춤. 다시 부르면 멈춘 곳부터 이어 감 |

- 종류 둘
  - **스택 있는** (stackful): 깊이 중첩된 호출 안 어디서든 멈출 수 있음
  - **스택 없는** (stackless): 맨 위 스택 프레임에서만 멈춤. 멈출 때 함수 본문의 자동 변수와 임시 객체만 저장하고 호출 스택은 저장하지 않음. 메모리를 아주 적게 써서 수백만, 수십억 개를 동시에 돌릴 수 있음
  - C++는 **스택 없는** 코루틴만 지원
- 코루틴은 꼭 멀티스레드와 관련된 것은 아님. 함수를 멈췄다 이어 가는 방법일 뿐이며, 필요하면 멀티스레드 환경에서도 씀
- 비동기 동작을 동기 코드 모양으로 쓰게 해 줌. 쓰임: 생성기, 비동기 입출력, 지연 계산, 사건 기반 프로그램, 상태 기계

### std::generator <Badge text="C++23" />

- 저수준 언어 부품은 다 있지만 고수준 코루틴 기능은 적음. C++23 표준 라이브러리가 넣은 하나가 **생성기** `std::generator`(`<generator>`) <CppRef path="cpp/coroutine/generator" />
  - 스레드 하나가 "값 만들기"와 "값 쓰기"를 번갈아 하게 함. 스레드를 여럿 쓰지 않음

```cpp
std::generator<int> squares(int n)
{
    for (int i{ 1 }; i <= n; ++i) {
        co_yield i * i;   // 값을 내고 멈춤
    }
}

for (int v : squares(5)) { /* 1, 4, 9, 16, 25 */ }
```

- 반복할 때마다 다음 값을 요청하면 코루틴이 이어서 반복문 한 바퀴를 돌고 `co_yield`에서 다시 멈춤
- `std::generator` 같은 코루틴 타입을 직접 만드는 것은 복잡하고 어려움. 전문가가 만든 것을 쓰기를 권함. 표준 밖에 cppcoro, concurrencpp 같은 고수준 코루틴 라이브러리가 있음

## 멀티스레드 설계 원칙

- **병렬 표준 알고리즘을 씀**: 60개가 넘는 표준 알고리즘이 병렬 실행을 지원함(20장). 직접 멀티스레드 코드를 쓰기보다 먼저 고려 <CppRef path="cpp/algorithm/execution_policy_tag_t" />
- **`thread`보다 `jthread`**: 소멸자에서 자동 join하므로 잘못 쓰기 어려움
- **끝내기 전에 모든 `thread`를 join 불가능하게**: `thread`를 쓴다면 `join()`이나 `detach()`를 꼭 부름
- **가장 좋은 동기화는 동기화가 없는 것**: 스레드들이 공유 데이터를 읽기만 하거나, 다른 스레드가 쓰지 않는 부분만 쓰도록 설계하면 락이 필요 없음
- **단일 스레드 소유 패턴**: 데이터 블록을 한 번에 한 스레드만 소유함. 소유는 읽기·쓰기 권한. 다 쓰면 다른 스레드에 넘김. 넘긴 뒤에는 그 데이터를 건드리지 않음
- **가능하면 원자적 타입과 연산**: 동기화를 알아서 해 주므로 올바른 코드를 쓰기 쉬움. 안 되면 락
- **변경 가능한 공유 데이터는 락으로 보호**
- **락은 최대한 빨리 놓음**: 락을 쥔 동안 같은 락을 기다리는 다른 스레드가 막힘
- **RAII 락 객체를 씀**: `lock_guard`, `unique_lock`, `shared_lock`, `scoped_lock`
- **여러 락을 직접 잡지 말고** `std::lock()`, `std::try_lock()`, `scoped_lock`
- **멀티스레드를 아는 프로파일러를 씀**: 병목과, 스레드들이 처리 능력을 다 쓰는지 확인
- **디버거의 멀티스레드 기능을 익힘**: 실행 중인 스레드 목록, 스레드마다 호출 스택. 교착을 조사할 때 각 스레드가 무엇을 하는지 볼 수 있음
- **스레드를 많이 만들고 없애는 대신 스레드 풀**
- **고수준 멀티스레드 라이브러리를 씀**: 표준은 기본 부품만 줌. 올바르게 쓰기 쉽지 않음. 바퀴를 다시 만들면 생각만큼 둥글지 않은 경우가 많음

## 헷갈리기 쉬운 점

- 로거의 백그라운드 스레드를 그냥 두어도 프로그램이 끝나면 정리된다?
  - join 가능한 `thread`가 소멸하면 `terminate`. 남은 메시지도 사라짐
- 종료 깃발은 락 없이 바꿔도 된다?
  - 검사와 `wait()` 사이에 바뀌면 알림을 놓쳐 교착. 락 안에서 바꿈
- 큐를 처리하는 동안 내내 락을 쥐는 것이 안전하다?
  - 다른 스레드가 오래 막힘. 지역 큐와 바꾼 뒤 락을 놓고 처리
- 스레드는 많을수록 빠르다?
  - 계산만 하는 스레드는 코어 수 정도가 알맞음. 그 이상은 전환 비용
- 코루틴은 스레드를 새로 만든다?
  - 함수를 멈췄다 이어 갈 뿐. `std::generator`는 한 스레드에서 번갈아 실행됨

## 정리

| 요소 | 핵심 |
| --- | --- |
| 로거 | 뮤텍스 + 조건 변수 + 백그라운드 스레드. 큐를 지역 큐와 바꾸고 락 밖에서 처리 |
| 안전한 종료 | 락 안에서 종료 깃발, 알림, join. 남은 항목까지 처리 |
| 스레드 풀 | 미리 만든 스레드 재사용. 계산 위주면 코어 수 정도 |
| 코루틴 | `co_await`, `co_yield`, `co_return`. 스택 없는 코루틴만 |
| `std::generator` | `co_yield`로 값을 하나씩 내는 생성기(C++23) |
| 설계 원칙 | 병렬 알고리즘, `jthread`, 동기화 최소화, RAII 락, 고수준 라이브러리 |
