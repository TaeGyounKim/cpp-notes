- 다루는 것: 버그는 반드시 생기므로, 그때 디버깅을 쉽게 해 줄 기능을 프로그램에 미리 넣어 둠
- 이 글에서 배우는 것: 오류 로그, 디버그 추적, 디버그 모드, 링 버퍼, 단언, 크래시 덤프

## 오류 로그

- 장면 1: 새 버전을 냈는데 사용자가 "프로그램이 멈췄다"고 함. 무슨 작업 중이었는지, 오류 메시지가 있었는지 기억하지 못함. 어떻게 디버깅할까?
- 장면 2: 같은 상황이지만 사용자 컴퓨터의 **오류 로그**를 볼 수 있음. "오류: settings.json을 열 수 없음"이 있고, 그 근처 코드에서 파일이 열렸는지 확인하지 않고 읽는 줄을 찾음. 근본 원인을 찾았음
- **오류 로그** (error logging): 오류 메시지를 영구 저장소에 써서, 프로그램이나 기계가 죽은 뒤에도 남게 하는 것
- 동작만 보면 알 수 있지 않을까?
  - 사용자 보고는 늘 정확하거나 완전하지 않음
  - 운영체제 커널, 오래 도는 서비스(데몬)처럼 사람 없이 도는 프로그램은 로그로만 말할 수 있음
  - 일부 오류는 자동으로 복구해 사용자에게 숨기기도 함. 그래도 로그가 있으면 안정성을 높이는 데 귀함
- C++에는 표준 로그 기능이 **없음**. 플랫폼마다 다름: Unix의 syslog, Windows의 이벤트 보고 API
  - 플랫폼에 상관없는 오픈 소스: [spdlog](https://github.com/gabime/spdlog), [Boost.Log](https://www.boost.org/libs/log/), log4cpp

### 무엇을 기록할까

- 몇 줄마다 메시지를 남겨 실행 경로를 다 추적하고 싶어짐. 이런 메시지를 **추적** (trace)이라 함. 추적은 로그 파일에 쓰지 않음
  - 영구 저장소에 쓰기는 느림. 비동기로 써도 그만큼 많으면 프로그램이 느려짐
  - 추적 내용 대부분은 최종 사용자에게 맞지 않음. 헷갈리게 하고 쓸데없는 지원 문의를 부름
- 기록할 오류
  - **복구할 수 없는 오류**: 시스템 호출이 예상 밖으로 실패
  - **관리자가 조치할 수 있는 오류**: 메모리 부족, 형식이 틀린 데이터 파일, 디스크에 쓸 수 없음, 네트워크 끊김
  - **예상 밖의 오류**: 절대 지나지 않으리라 생각한 경로, 예상 밖의 변수 값. 반면 사용자가 잘못된 데이터를 넣는 것은 "예상"하고 처리해야 함. 예상 밖의 오류는 프로그램의 버그
  - **보안 위협 가능성**: 허가되지 않은 주소에서의 연결, 너무 많은 연결 시도(서비스 거부)
- 함께 남길 것
  - 최소한 날짜와 시각, 오류 메시지
  - 멀티스레드라면 스레드 ID
  - `std::stacktrace`<Badge text="C++23" />로 그 순간의 호출 스택(일부라도)(14장) <CppRef path="cpp/utility/basic_stacktrace" />
- **경고**(복구 가능한 오류)도 기록하면 피할 수 있었는지 조사할 수 있음
- **로그 수준** (log level): 보통 최소한 오류, 경고, 정보
  - 오류가 아닌 상황(중요한 상태 변화, 시작과 종료)은 정보 수준으로
  - 사용자가 실행 중에 로그 수준을 바꿔 기록 양을 조절하게 할 수도 있음

## 디버그 추적

- 복잡한 문제에는 공개 오류 메시지만으로 정보가 모자람. 실행 경로 전체나 버그 직전의 변수 값이 필요함
- 추적에 함께 넣으면 좋은 것: 스레드 ID(멀티스레드라면), 추적을 남긴 **함수 이름**, 그 함수의 **소스 파일 이름**
- 넣는 방법: 디버그 모드, 링 버퍼(아래)
- 멀티스레드 프로그램에서는 추적 기록을 스레드에 안전하게 만들어야 함(27장)

:::caution
추적을 텍스트로 쓴다면 너무 자세히 쓰지 않는다. 로그로 지적 재산이 새어 나가거나, 해커가 구현 세부를 얻을 수 있다.
:::

### 디버그 모드

- **디버그 모드**: 추적을 표준 오류나 파일로 쓰고, 실행 중 추가 검사도 하는 모드

| 방식 | 켜는 법 | 장점 | 단점 |
| --- | --- | --- | --- |
| **시작 시** | 명령줄 인수(예: `-d`) | 출시 바이너리에 디버그 코드가 있어 고객 현장에서 켤 수 있음 | 켜려면 다시 시작해야 해서, 어떤 버그의 정보는 이미 놓침 |
| **컴파일 시** | 전처리기 기호(`DEBUG_MODE`)와 `#ifdef`. GCC는 `-DDEBUG_MODE`, Visual C++는 `/D DEBUG_MODE`. 또는 릴리스에서 정의되는 `NDEBUG` | 디버그 코드가 출시 바이너리에 없어 크기가 늘지 않음 | 고객 현장에서 켤 방법이 없음 |
| **실행 중** | 비동기 인터페이스(소켓, 시그널, 원격 호출 등 프로세스 간 통신)나 UI 메뉴로 켜고 끔 | 가장 유연 | 표준 C++에는 프로세스 간 통신이나 UI가 없어 플랫폼 기능 필요 |

- 로그 호출에 함수 이름을 자동으로 넣으려고 매크로를 쓰기도 함. `__func__`는 현재 함수 이름을 담은 미리 정의된 변수
  - C++의 매크로는 디버깅하기 어려워 되도록 피함. 로그용 간단한 매크로 정도는 괜찮지만, `std::source_location`<Badge text="C++20" />을 기본 인수로 받으면 매크로 없이도 부른 곳의 함수 이름과 줄을 얻음 <CppRef path="cpp/utility/source_location/function_name" />

```cpp
void trace(const std::string& message,
           std::source_location where = std::source_location::current());

trace("parse 시작");   // where에는 이 줄을 부른 함수와 줄 번호가 들어감
```

:::caution
컴파일 시 디버그 모드에서 `DEBUG_MODE`가 없으면 로그 매크로가 아무것도 아닌 것(no-op)으로 바뀐다. 프로그램이 제대로 돌려면 꼭 실행되어야 하는 코드를 로그 호출 안에 넣지 않는다. 예: `LOG("결과", compute())`라고 쓰면 릴리스에서는 `compute()` 호출도 사라진다.
:::

- 로그 코드가 사라져 쓰이지 않는 변수가 생기면 경고가 남. `[[maybe_unused]]`<Badge text="C++17" />로 막음 <CppRef path="cpp/language/attributes/maybe_unused" />

### 링 버퍼

- 디버그 모드는 재현되는 문제와 테스트에 좋음. 그러나 버그는 디버그 모드가 **꺼진** 상태에서 자주 나타나고, 그제야 켜면 이미 늦음
- 해법: 추적을 **늘** 켜 둠. 디버깅에는 대개 가장 최근 추적만 필요하므로 최근 것만 보관
  - 로그 파일 순환(rotation)으로도 할 수 있지만, 성능 때문에 디스크에 계속 쓰지 않는 편이 나음
  - 메모리에 두었다가 필요할 때 표준 오류나 파일로 **내보냄**
- **링 버퍼** (ring buffer, 원형 버퍼): 고정된 크기의 메모리에 메시지를 저장. 가득 차면 처음으로 돌아가 가장 오래된 메시지를 덮어씀. 끝없이 반복
- 내보내는 방법
  - 디버그 모드를 켜는 인터페이스와 비슷한 "훅"으로 요청받아 내보냄
  - 치명적 오류로 끝날 때 자동으로 로그 파일에 내보냄
  - 프로그램의 메모리 덤프에서 꺼냄(플랫폼마다 방법이 다름)
- 문자열 고정 개수를 저장하는 구현은 가장 효율적이지는 않음. 고정 바이트 수 버퍼 등 다른 방법도 있지만, 고성능이 아니라면 충분함
- 멀티스레드라면 항목마다 스레드 ID를 넣고 스레드에 안전하게 만들어야 함

## 단언

- `<cassert>`의 `assert()` 매크로: 식이 거짓이면 오류 메시지를 출력하고 프로그램을 **끝냄**. 참이면 아무것도 안 함 <CppRef path="cpp/error/assert" />
- 보통은 프로그램을 끝내는 함수나 매크로를 피하지만 `assert()`는 예외
  - 단언이 실패했다는 것은 가정이 틀렸거나 무언가 돌이킬 수 없이 잘못되었다는 뜻. 계속 가는 것보다 그 자리에서 끝내는 것이 유일하게 온당함
- 버그가 **생긴 바로 그 자리**에서 드러나게 함. 단언이 없으면 잘못된 값으로 계속 가다 한참 뒤에야 증상이 나타남
- `NDEBUG`가 정의되어 있으면 `assert()`는 무시됨. 컴파일러는 릴리스 빌드에서 흔히 이 기호를 정의함
  - 릴리스에도 단언을 남기려면 설정을 바꾸거나 `NDEBUG`의 영향을 받지 않는 단언을 직접 만듦
  - `NDEBUG`에 따라 동작이 바뀌므로 `<cassert>`는 모듈로 가져올 수 없음. `import` 대신 `#include <cassert>`
- 쓰는 곳: 변수 상태를 "가정"하는 곳
  - 예: 절대 `nullptr`를 돌려주지 않는다는 라이브러리 함수를 부른 뒤, 정말 아닌지 단언
- 가능한 한 적게 가정함
  - 예: 라이브러리 함수를 쓴다면 매개변수가 올바르다고 단언하지 말고, **검사**해서 오류 코드를 돌려주거나 예외를 던짐
- 정말 문제가 되는 경우에만 씀. 개발 중 단언이 실패하면 단언을 끄지 말고 **고침**
- 사용자 메시지를 붙이는 요령

```cpp
assert(points.size() == 3 && "삼각형은 꼭짓점이 셋");   // 문자열 리터럴은 늘 참
assert(!"여기에 오면 안 됨");                           // 늘 실패하는 단언
```

:::caution
단언 안에 꼭 실행되어야 할 코드를 넣지 않는다. 예: `assert(save_file())`는 릴리스 빌드에서 단언이 사라질 때 `save_file()` 호출도 함께 사라진다.
:::

## 크래시 덤프

- **크래시 덤프** (crash dump, memory dump, core dump): 프로그램이 죽을 때 만들어지는 파일. 그때 돌던 스레드, 모든 스레드의 호출 스택 등이 담김
- 만드는 법은 플랫폼마다 다름. 플랫폼 문서를 보거나 라이브러리를 씀. 예: [Breakpad](https://github.com/google/breakpad)(여러 플랫폼에서 덤프를 쓰고 처리)
- 함께 갖출 것
  - **심볼 서버** (symbol server): 출시한 바이너리의 디버깅 심볼을 보관. 덤프를 분석할 때 심볼로 주소를 함수 이름과 줄로 바꿈
  - **버전 관리 서버**(28장): 덤프를 만든 바로 그 리비전의 소스 코드를 가져옴
- 크래시 덤프 하나가 버그 보고서 천 개보다 값질 때가 많음

## 헷갈리기 쉬운 점

- 자세할수록 좋으니 추적도 로그 파일에 다 쓴다?
  - 느려지고 사용자를 헷갈리게 함. 추적은 디버그 모드나 링 버퍼로
- 사용자가 잘못 입력한 것도 "예상 밖의 오류"로 로그한다?
  - 잘못된 입력은 예상하고 처리할 일. 예상 밖은 프로그램의 버그
- 라이브러리 함수의 인수 검사는 `assert`로 한다?
  - 릴리스에서 사라짐. 검사하고 예외나 오류 코드로
- `assert`가 실패하면 그 단언을 지운다?
  - 가정이 깨졌다는 신호. 원인을 고침
- 디버그 모드를 켜면 언제든 정보를 얻는다?
  - 문제가 난 뒤 켜면 늦을 수 있음. 링 버퍼가 그 빈틈을 메움

| --- | --- |
| 오류 로그 | 영구 저장. 복구 불가·조치 가능·예상 밖·보안 오류. 시각, 메시지, 스레드 ID, 스택. 로그 수준 |
| 디버그 추적 | 실행 경로와 값. 함수·파일 이름. 너무 자세히 쓰지 않기 |
| 디버그 모드 | 시작 시(인수), 컴파일 시(`#ifdef`), 실행 중(프로세스 간 통신) |
| 링 버퍼 | 최근 N개만 메모리에. 치명적 오류 때 내보냄 |
| `assert` | 가정이 깨진 그 자리에서 멈춤. `NDEBUG`면 사라짐. 부작용 넣지 않기 |
| 크래시 덤프 | 스레드와 호출 스택. 심볼 서버와 버전 관리 서버 |

## 복습 질문

<details>
<summary>고객 현장에서만 가끔 나는 버그가 있다. 다시 시작하면 사라진다. 시작 시 디버그 모드와 링 버퍼 중 무엇이 도움이 되는가?</summary>

- 링 버퍼. 시작 시 디버그 모드는 다시 시작해야 켜지므로 그때는 버그가 사라짐. 링 버퍼는 늘 최근 추적을 기억하다가 문제가 생긴 순간 내보낼 수 있음

</details>

<details>
<summary>`assert(queue.pop() != nullptr);`는 무엇이 위험한가?</summary>

- 단언 안에서 `pop()`으로 상태를 바꿈. `NDEBUG`로 단언이 사라지면 `pop()`도 사라져 릴리스와 디버그의 동작이 달라짐. 먼저 꺼내 변수에 담고 그 변수를 단언함

</details>

<details>
<summary>오류 로그에 꼭 넣을 정보 세 가지는?</summary>

- 날짜와 시각, 오류 메시지, (멀티스레드라면) 스레드 ID. 가능하면 호출 스택 일부도

</details>
