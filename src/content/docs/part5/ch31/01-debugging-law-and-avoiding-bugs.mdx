- 다루는 것: 코드에는 버그가 **있을 것**. 버그 없는 코드를 쓰고 싶지 않은 프로그래머는 없지만 성공하는 사람은 드묾
  - 동료에게 뇌물을 주고 모든 버그를 맡길 게 아니라면, 디버깅을 모르고는 전문 C++ 프로그래머가 될 수 없음
  - 경험 많은 프로그래머와 초보를 가르는 요소 중 하나가 디버깅 실력
- 디버깅은 누구나 알기를 바라지만 가르치는 법은 아무도 모르는 기술처럼 여겨짐. 이 장은 구체적인 지침과 기법을 줌
- 이 장의 순서
  - 1편: 디버깅의 기본 법칙, 버그 분류, 버그 피하기
  - 2편: 버그에 대비하기(오류 로그, 디버그 추적, 링 버퍼, 단언, 크래시 덤프)
  - 3편: 디버깅 기법(재현, 재현되지 않는 버그, 회귀, 메모리 오류, 멀티스레드)
  - 4편: 단계별 디버깅 예

## 디버깅의 기본 법칙

- 첫 규칙: 자신에게 솔직해지기. 내 코드에는 버그가 **있다**고 인정함
- 이 현실적인 판단 덕분에 두 가지를 함께 할 수 있음
  - 처음부터 버그가 기어들지 않게 최선을 다함
  - 동시에 디버깅을 최대한 쉽게 할 기능을 넣어 둠

:::caution
디버깅의 기본 법칙: 코딩할 때는 버그를 **피하고**, 코드에는 버그가 있을 것에 **대비**한다.
:::

## 버그의 분류

- **버그** (bug): 프로그램의 잘못된 실행 시간 동작

| 종류 | 뜻 | 예 |
| --- | --- | --- |
| **치명적 버그** (catastrophic bug) | 끔찍한 결과 | 프로그램 중단, 데이터 손상, 운영체제 장애. 소프트웨어 밖으로도 번짐: 의료 소프트웨어가 환자에게 방사선을 지나치게 쬐는 경우 |
| **비치명적 버그** (noncatastrophic bug), **논리 버그** (logical bug) | 더 미묘하게 잘못 동작 | 웹 브라우저가 엉뚱한 페이지를 돌려줌, 스프레드시트가 열의 표준 편차를 틀리게 계산 |
| **외관상 버그** (cosmetic bug) | 보이는 것만 잘못됨. 동작은 맞음 | 비활성이어야 할 버튼이 활성으로 보이지만 눌러도 아무 일 없음 |

- **근본 원인** (root cause): 잘못된 동작을 일으키는 프로그램 속 실수
- 디버깅 = 근본 원인을 찾는 일 + 다시 일어나지 않게 코드를 고치는 일

## 버그 피하기

- 버그 없는 코드는 불가능하지만 줄일 수는 있음

| 습관 | 내용 |
| --- | --- |
| **언어를 깊이 알기** | 특히 포인터와 메모리 관리. 이 사이트의 앞 장들 |
| **코딩 전에 설계** | 설계 없이 기능을 쓰기 시작하면 이해하기 어렵고 오류가 잦은 복잡한 설계가 되고, 경계 조건과 오류 조건을 빠뜨리기 쉬움. 구현 중에 미처 생각 못 한 문제를 만나면 설계를 바꾸는 것도 괜찮음 |
| **코드 리뷰** | 전문 환경에서는 모든 줄을 동료가 리뷰. 새로운 눈이 문제를 봄 |
| **테스트, 또 테스트** | 철저히 시험하고 남에게도 시험받음. 내가 생각 못 한 문제를 찾음 |
| **자동 단위 테스트** | 모든 기능에. 지속적 통합이나 로컬 컴파일 때마다 자동 실행(30장) |
| **오류 조건 예상하고 처리** | 특히 파일과 네트워크 연결. 오류는 **반드시** 일어남(13장, 14장) |
| **스마트 포인터** | 필요 없어지면 자원을 자동으로 해제해 누수를 막음 |
| **컴파일러 경고 무시하지 않기** | 높은 경고 수준으로 컴파일. 가능하면 경고를 오류로 다룸: GCC·Clang은 `-Werror`, Visual C++는 프로젝트 속성 C/C++ → General → Treat Warnings As Errors |
| **정적 분석** | 소스 코드를 분석해 문제를 짚어 줌. IDE에서 입력하며 실시간으로, 또는 빌드 과정에서 자동으로. 예: [clang-tidy](https://clang.llvm.org/extra/clang-tidy/), Visual Studio 코드 분석 |
| **좋은 코딩 스타일** | 읽기 쉽고 분명하게, 뜻 있는 이름, 줄임말 피하기, 인터페이스뿐 아니라 구현에도 주석, `override`와 `explicit` 쓰기(3장) |

## 경고가 가리키는 버그

- 아래 코드는 컴파일되고 실행도 되지만 경고가 넷 나오고, 그중 셋은 실제 버그를 가리킴. 출력 창에서 경고부터 읽음
- 경고 목록과 각 옵션의 뜻: [GCC 경고 옵션](https://gcc.gnu.org/onlinedocs/gcc/Warning-Options.html)

<RunCode client:load code={wCode} />

| 경고 | 버그 |
| --- | --- |
| `-Wsign-compare` | `int`와 `size_t`(부호 없음) 비교. 음수가 섞이면 비교가 뒤집힘 |
| `-Wparentheses` | 조건에 `=`(대입). `limit`이 0이 아니면 늘 참이고, 값도 덮어씀. 의도는 `>` |
| `-Wreturn-type` | `x`가 0이면 `return` 없이 함수 끝에 닿음. 정의되지 않은 동작 |
| `-Wunused-variable` | 쓰지 않는 변수. 버그는 아니지만 무언가 빠뜨렸다는 신호일 수 있음 |

- 경고가 안 나온 버그도 있음: `count`를 초기화하지 않음. 그래서 결과가 쓰레기 값
  - GCC는 최적화를 켜야(`-O2`) 이런 흐름 분석 경고(`-Wmaybe-uninitialized`)를 더 잘 냄. 경고 없음이 버그 없음은 아님
  - 정적 분석기와 새니타이저(3편)가 이런 것을 더 잡아 줌
- 직접 해 볼 것: 경고를 하나씩 고쳐 출력이 `2`와 `1`이 되게 만들기

## 고친 판

- 경고를 모두 고친 코드. `-Werror`를 줘도 컴파일됨. C++11 옵션으로 컴파일됨

<RunCode client:load code={wFixedCode} flags="-std=c++11 -Wall -Wextra -Werror" />

- 고친 점
  - `count`를 0으로 초기화
  - 인덱스를 `std::size_t`로
  - 조건을 `values[i] > limit`으로
  - `sign_of`의 마지막에 `return 0;`

## 헷갈리기 쉬운 점

- 경고는 컴파일이 되니 무시해도 된다?
  - 많은 경고가 실제 버그를 가리킴. 경고를 오류로 다루면 바로 고치게 됨
- 경고가 하나도 없으면 버그가 없다?
  - 컴파일러가 못 보는 버그가 많음. 테스트, 정적 분석, 새니타이저를 함께
- 외관상 버그는 버그가 아니다?
  - 동작은 맞아도 잘못된 동작. 사용자를 헷갈리게 함
- 증상을 없애면 디버깅이 끝난다?
  - 근본 원인을 찾아 다시 일어나지 않게 고쳐야 끝
- 구현을 시작했으면 설계를 바꾸면 안 된다?
  - 생각 못 한 문제를 만나면 바꾸는 게 맞음

## 정리

| 요소 | 핵심 |
| --- | --- |
| 기본 법칙 | 코딩할 때 버그를 피하고, 버그가 있을 것에 대비 |
| 버그 분류 | 치명적, 비치명적(논리), 외관상. 근본 원인을 찾아 고침 |
| 버그 피하기 | 설계, 코드 리뷰, 테스트, 자동 단위 테스트, 오류 처리, 스마트 포인터, 경고, 정적 분석, 좋은 스타일 |
| 경고 | 높은 수준 + `-Werror`. 최적화를 켜면 더 많이 잡힘 |

## 복습 질문

<details>
<summary>`if (status = READY)`는 무엇이 문제이고 어떤 경고가 잡아 주는가?</summary>

- 비교가 아니라 대입. `READY`가 0이 아니면 조건은 늘 참이고 `status` 값도 바뀜
- GCC·Clang의 `-Wparentheses`(`-Wall`에 포함)가 "대입을 조건으로 쓴다"고 경고함

</details>

<details>
<summary>계산은 맞는데 진행 막대가 끝나도 100%가 아니라 99%로 표시된다. 어떤 종류의 버그인가?</summary>

- 외관상 버그에 가까움. 동작은 맞지만 보이는 것이 틀림. 다만 원인(반올림, 마지막 갱신 누락)을 찾아 고쳐야 하는 버그임은 같음

</details>
