- 다루는 것: 버그가 있는 작은 프로그램을 앞 글들의 기법으로 하나씩 고쳐 봄

## 상황

- 점수표 프로그램: 한 줄에 선수 이름과 점수들이 있음. 선수마다 평균을 출력
  - 예: `Mina 90 85 88` → Mina의 평균 87.67
- `ScoreSheet` 클래스가 한 줄을 읽어 이름과 점수를 저장함
  - 점수 개수를 먼저 센 뒤 그 크기의 **원시 배열**을 `new[]`로 만들고 다시 읽어 채움
  - 원시 배열은 일부러 고른 나쁜 설계. 메모리 버그를 보여 주려는 것. 실제로는 `std::vector`를 씀
- `report()`가 시트를 **값으로** 받아 평균을 출력함. 이것도 일부러 고른 것(보통은 `const` 참조)

아래 코드에는 버그가 있다. 그대로 쓰거나 본보기로 삼지 않는다.
:::

- 입력 두 줄로 시험함: 점수가 있는 `Mina`, 점수가 없는 `Lee`
- 주소 새니타이저를 켜고 컴파일되어 있음(3편)

## 1단계: 두 번 해제 — 새니타이저 보고서 읽기

- 실행하면 평균은커녕 `attempting double-free`로 끝남
- 보고서는 스택 추적 세 묶음. 위에서부터 **내 코드의 첫 줄**을 찾음(라이브러리 함수 줄은 건너뜀)

| 묶음 | 내 코드의 첫 줄 | 뜻 |
| --- | --- | --- |
| 두 번째 해제 | `~ScoreSheet()` 25줄 ← `main` 53줄 | `main`의 `sheet`가 소멸하며 해제 |
| 처음 해제(freed by) | `~ScoreSheet()` 25줄 ← `main` 52줄 | `report(sheet)` 호출이 끝나며 **매개변수** 복사본이 소멸하며 해제 |
| 할당(allocated by) | `ScoreSheet(const std::string&)` 16줄 | 생성자의 `new int[m_count]` |

- 추론
  - 한 번 할당한 배열을 두 객체가 각자 해제함 → 두 객체가 **같은 포인터**를 가짐
  - 두 번째 객체는 `report()`의 값 매개변수, 즉 **복사 생성자**로 만들어짐
  - 복사 생성자를 보면 `m_scores{ other.m_scores }`: 포인터만 복사하는 **얕은 복사**
- 고치는 법
  - 복사 생성자가 새 배열을 할당해 원소를 복사하게 함(깊은 복사). 대입 연산자도 마찬가지(9장)
  - 또는 처음부터 `std::vector`를 써서 **0의 규칙**을 따름(마지막 단계에서)
  - 어쨌든 `report()`는 `const ScoreSheet&`로 받는 것이 맞음
- 직접 해 볼 것: `report`의 매개변수를 `const ScoreSheet& sheet`로 바꾸고 실행

## 2단계: 0으로 나누기 — 디버거로 좁히기

- 1단계를 고치면 `Mina` 줄은 출력되지만 `Lee` 줄에서 `SIGFPE`로 죽음
  - SIGFPE는 산술 예외. 정수를 0으로 나누면 흔히 이 신호로 끝남
- 디버거로 원인을 찾음. 먼저 디버그 심볼을 넣어 컴파일(`-g`)

### GDB

```text
$ g++ -std=c++23 -g score.cpp -o score
$ gdb ./score
(gdb) run < input.txt          # 입력 파일을 넣어 실행
Program received signal SIGFPE, Arithmetic exception.
(gdb) bt                       # 호출 스택. #0이 가장 최근 프레임
(gdb) frame 0                  # 살펴볼 프레임 고르기(up, down으로도 이동)
(gdb) list                     # 그 프레임의 현재 줄 근처 소스
(gdb) print m_count            # 변수 값 보기
(gdb) print *this              # 객체 전체 보기
```

- `bt` (backtrace): 가장 최근 호출이 맨 위 `#0`. 위에서부터 **내 코드의 첫 프레임**을 찾음
  - 이번에는 나눗셈이 내 코드 안에서 일어나 `#0`이 곧 `ScoreSheet::average()`. 그 아래 `report()`, `main()`
  - 라이브러리 안에서 죽었다면 `frame 번호`로 내 코드의 프레임까지 올라감
- `list`로 `return sum / m_count;` 줄을 보고, `print m_count`가 0임을 확인함
- 원인: 점수가 없는 줄은 `m_count`가 0인데 그대로 나눔. 빈 점수표를 처리하지 않은 것
- GDB 사용법: [GDB 문서](https://sourceware.org/gdb/documentation/)

### Visual Studio 디버거

- 구성을 **Debug**로 두고 Debug → Start Debugging
- 예외가 나면 디버거가 멈추고 무엇이 났는지 보여 줌. 멈춘 곳이 내 코드가 아니면 **호출 스택** 창(Debug → Windows → Call Stack)에서 내 코드가 있는 첫 줄을 찾아 더블 클릭해 그 줄로 감
- 변수 위에 마우스를 올리면 값이 보임. **자동** 창(Debug → Windows → Autos)에서 변수 목록과 멤버를 펼쳐 볼 수도 있음

### 디버거 없이

- 정의되지 않은 동작 새니타이저(`-fsanitize=undefined`)를 켜면 `runtime error: division by zero`와 함께 **파일과 줄**을 알려 줌
- 직접 해 볼 것: 위 예제의 옵션에서는 바꿀 수 없으므로, "Compiler Explorer에서 열기"로 열어 컴파일 옵션에 `-fsanitize=undefined`를 더해 봄

## 3단계: 틀린 평균 — 메시지 기반 디버깅

- 빈 줄 처리를 고치고 나면 `Mina: 평균 87.00`. 90, 85, 88의 평균은 87.67이어야 함. 죽지는 않지만 **틀린 결과**
- 이번엔 출력을 넣어 봄. 의심 가는 `average()`에서 중간 값을 찍음

```cpp
double average() const
{
    int sum{ 0 };
    for (int i{ 0 }; i < m_count; ++i) { sum += m_scores[i]; }
    std::println("[debug] sum={} count={} sum/count={}",
                 sum, m_count, sum / m_count);
    return sum / m_count;
}
```

- 출력: `[debug] sum=263 count=3 sum/count=87`
  - 합과 개수는 맞음 → 읽기는 정상
  - `sum / m_count`가 87 → **정수 나눗셈**. 소수부가 버려진 뒤 `double`로 바뀜
- 고침: 한쪽을 실수로 바꿔 나눔. `static_cast<double>(sum) / m_count`
- 원인을 찾았으면 디버그 출력은 지움(또는 2편의 추적으로 바꿈)

## 마지막: 설계 다시 보기

- 버그 셋을 하나씩 고쳤지만, 원인 둘은 **설계**에서 왔음
  - 원시 배열과 손으로 쓴 복사 생성자 → 두 번 해제
  - 개수를 세고 다시 읽는 두 번의 읽기 → 복잡함
- 다시 씀
  - `std::vector<int>`로 바꿔 복사·이동·소멸을 맡김(**0의 규칙**). 복사 생성자와 소멸자를 지움
  - `std::istream_iterator`로 한 번에 읽음 <CppRef path="cpp/iterator/istream_iterator" />
  - 합은 `std::accumulate`로 `double`에서 시작해 더함 <CppRef path="cpp/algorithm/accumulate" />
  - 점수가 없으면 평균이 "없음"이므로 `std::optional<double>`<Badge text="C++17" />로 돌려줌
  - `report()`는 `const` 참조로 받음

## 이 예에서 배울 것

- 작은 예라 대표성이 없다고 여길 수 있지만, 큰 프로젝트에서도 클래스 하나하나는 이 정도 크기인 경우가 많음
- 이 클래스를 충분히 시험하지 않고 프로젝트에 넣었다면, 나중에 버그가 드러났을 때 범위를 좁히는 데만 훨씬 많은 시간이 들었을 것
- 버그는 바로 드러나지 않음. 도구(새니타이저, 디버거)와 끈기가 필요함
- 증상(두 번 해제, SIGFPE, 틀린 값)에서 출발해 근본 원인(얕은 복사, 빈 입력 미처리, 정수 나눗셈)까지 가고, 마지막엔 같은 종류의 버그가 다시 생기지 않게 설계를 고침

## 헷갈리기 쉬운 점

- 스택 추적의 맨 위 줄이 원인이다?
  - 맨 위는 대개 라이브러리 함수. 위에서부터 내 코드의 첫 줄을 찾음
- 두 번 해제는 `delete`를 두 번 쓴 곳만 찾으면 된다?
  - `delete`는 소멸자에 한 번뿐이어도, 같은 포인터를 가진 객체가 둘이면 두 번 해제됨. 얕은 복사를 의심
- 죽지 않으면 버그가 아니다?
  - 87.00처럼 조용히 틀린 값이 더 위험할 수 있음
- 디버그 출력은 남겨 둬도 된다?
  - 원인을 찾았으면 지우거나 추적 장치로 옮김
- 증상을 고쳤으면 끝이다?
  - 같은 종류의 버그가 다시 생기지 않게 설계를 고칠 수 있는지 봄

## 복습 질문

<details>
<summary>새니타이저가 `heap-use-after-free`를 보고했는데, "freed by" 스택에 `std::vector<int>::push_back`이 보인다. 무엇을 의심하는가?</summary>

- `push_back`이 용량을 늘리며 원소를 새 메모리로 옮기고 옛 메모리를 해제함. 그 전에 받아 둔 원소의 참조·포인터·반복자를 계속 쓰는 코드가 있다는 뜻(반복자 무효화)
- 해제 뒤 접근한 줄(맨 위 묶음)에서 그 참조를 어디서 얻었는지 찾아, `push_back` 뒤에 다시 얻게 고침

</details>

<details>
<summary>새니타이저 보고서의 "freed by"와 "previously allocated by" 묶음은 각각 무엇을 알려 주는가?</summary>

- freed by: 그 메모리를 **처음** 해제한 곳의 호출 스택
- previously allocated by: 그 메모리를 할당한 곳의 호출 스택
- 맨 위 묶음(오류가 난 곳)과 함께 보면 할당 → 첫 해제 → 문제의 접근 순서가 보임

</details>

<details>
<summary>평균이 늘 소수부 없이 나온다. 디버거 없이 가장 빨리 확인하는 방법은?</summary>

- 나눗셈 직전에 피연산자와 결과를 출력해 봄. 둘 다 정수이고 결과가 잘린 값이면 정수 나눗셈

</details>

## 31장을 마치며

- 가장 중요한 개념은 디버깅의 기본 법칙: 코딩할 때 버그를 피하고, 코드에는 버그가 있을 것에 대비함
- 오류 로그, 디버그 추적, 단언으로 준비해 두면 실제 디버깅이 훨씬 쉬워짐
- 디버깅의 가장 중요한 규칙은 **재현**. 그다음 심볼릭 디버거나 로그로 근본 원인을 추적함
- 메모리 오류는 특히 어렵고 오래된 C++ 코드 버그의 대부분을 차지함. 종류와 증상을 알고, 새니타이저 같은 도구를 씀
- 디버깅은 익히기 어려운 기술. 전문가 수준이 되려면 많이 연습해야 함
