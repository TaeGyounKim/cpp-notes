- 다루는 것: 디버깅은 몹시 답답할 수 있지만 **체계적으로** 하면 훨씬 쉬워짐
- 첫걸음은 늘 **버그 재현**. 재현되는지에 따라 다음 접근이 달라짐
- 이 글에서 배우는 것: 재현, 재현되는 버그, 재현되지 않는 버그, 회귀, 메모리 오류, 멀티스레드

## 버그 재현하기

- 늘 재현할 수 있으면 근본 원인을 찾기가 훨씬 쉬움
  - 어떤 사람에게선 재현되고 다른 사람에게선 안 된다면, 그 차이 자체가 단서
  - 재현되지 않는 버그의 원인 찾기는 불가능에 가까울 만큼 어려움
- 처음 버그가 났을 때와 **비슷한 환경**(하드웨어, 운영체제 등)에서 **같은 입력**으로 실행
  - 시작부터 버그가 날 때까지의 **모든 입력**을 넣음
  - 흔한 실수: 버그를 일으킨 마지막 동작만 해 보기. 버그는 동작 **전체의 순서** 때문일 수 있음
  - 예: 어떤 웹 페이지를 요청하면 브라우저가 죽음. 그 주소가 메모리를 망가뜨려서일 수도 있지만, 요청을 100만 칸짜리 큐에 기록하는데 이번이 1,000,001번째였기 때문일 수도 있음. 다시 시작해 요청 하나만 보내면 재현되지 않음
- 전체 순서를 흉내 낼 수 없을 때(보고자가 기억 못 함, 너무 오래 돌았음) 시도할 것
  - 올바른 환경에서, 처음 보고와 최대한 비슷한 입력으로 마지막 동작을 반복
  - 버그와 관련된 코드를 빠르게 훑어보기. 그럴듯한 원인이 보이면 재현 방향이 잡힘
  - 비슷한 기능을 시험하는 **자동 테스트**를 돌림. 24시간 테스트해야 나타나는 버그라면 내 시간 24시간보다 테스트가 혼자 돌게 하는 편이 나음
  - 기계가 있다면 조금씩 다른 테스트를 여러 기계에서 동시에
  - **스트레스 테스트**: 웹 서버가 어떤 요청에 죽었다면 그 요청을 보내는 클라이언트를 최대한 많이 동시에
- 늘 재현되면 **가장 짧은 재현 순서**를 찾음
  - 마지막 동작만 담은 최소 순서에서 시작해, 시작부터 버그까지의 전체 순서로 조금씩 늘려 감
  - 가장 단순하고 빠른 재현 테스트가 생겨 원인 찾기와 수정 확인이 쉬워짐

## 재현되는 버그

- 목표: 문제를 일으키는 **정확한 코드 줄** 찾기. 두 전략

| 전략 | 방법 | 주의 |
| --- | --- | --- |
| **디버거** (debugger) | 실행을 한 단계씩 따라가며 여러 지점에서 메모리 상태와 변수 값을 봄. 소스가 있으면 변수·클래스 이름 같은 기호를 쓰는 **심볼릭 디버거**를 씀. 컴파일러에 디버그 심볼 생성을 지시해야 함(GCC·Clang `-g`) | 대개 가장 강력함 |
| **디버그 메시지 로그** | 메시지를 충분히 넣고 재현하며 출력을 봄 | 디버거가 있으면 코드를 고쳐야 하는 이 방법은 덜 권함. 다만 2편처럼 미리 넣어 둔 추적이 있으면 디버그 모드로 재현만 해도 됨. 로그를 켜면 타이밍이 바뀌어 버그가 사라지기도 함 |

- 두 방법 모두 4편의 예에서 실제로 해 봄

## 재현되지 않는 버그

- 정보가 적고 짐작이 많이 필요해 훨씬 어려움. 도움이 되는 전략
  - **재현되는 버그로 바꾸기**: 근거 있는 짐작으로 대략의 위치를 정하고 재현에 시간을 씀. 재현되면 앞의 기법으로
  - **오류 로그 분석**: 버그 직전에 기록된 오류는 버그에 기여했을 가능성이 큼. 잘 만든 프로그램이라면 정확한 이유가 로그에 있기도 함
  - **추적 얻어 분석**: 링 버퍼 등으로 버그 순간의 추적을 얻었다면 위치로 바로 이끌어 줌
  - **크래시/메모리 덤프 조사**: 비정상 종료 때 덤프를 자동으로 만드는 플랫폼이 있음(Unix·Linux의 core 파일). 도구로 스택 추적과 죽기 직전의 메모리 내용을 봄
  - **코드 살펴보기**: 안타깝게도 유일한 방법일 때가 많지만 의외로 잘 통함. 방금 난 버그의 관점으로 보면 내가 쓴 코드에서도 놓친 실수가 보임. 몇 시간 노려보기보다 코드 경로를 손으로 따라가 봄
  - **메모리 검사 도구**(아래): 늘 오동작을 일으키지는 않지만 원인일 수 있는 메모리 오류를 알려 줌
  - **버그 보고서 등록·갱신**: 원인을 못 찾아도 시도한 기록이 다음에 쓸모 있음
- 원인을 못 찾았다면 다음에 나타날 때를 위해 로그나 추적을 **더 넣어 둠**
- 원인을 찾았으면 **재현 테스트를 만들어** 재현되는 버그로 옮김
  - 재현할 수 없으면 수정을 어떻게 시험할까? 흔한 실수는 엉뚱한 문제를 고치는 것. 고쳤는지 모르니 한 달 뒤에 다시 나타나도 놀랄 일이 아님

## 회귀 버그

- **회귀 버그** (regression bug): 예전에는 잘 되던 기능이 어느 시점부터 안 됨
- 관련 파일의 **변경 기록** 보기: 아직 되던 때를 안다면 그 뒤의 모든 변경을 봄. 수상한 것이 원인으로 이끌기도 함
- **이분 탐색** (bisecting): 이전 버전들로 이분 탐색해 언제부터 잘못되었는지 찾음
  - 이전 바이너리를 보관했다면 그것으로, 아니면 소스를 예전 리비전으로 되돌려 빌드
  - 시점을 찾으면 그때의 변경 기록을 봄
  - 버그를 **재현할 수 있어야만** 가능함
- Git에는 이 과정을 돕는 [`git bisect`](https://git-scm.com/docs/git-bisect)가 있음

## 메모리 오류

- 프로그램이 죽는 것 같은 치명적 버그 대부분, 그리고 많은 비치명적 버그가 메모리 오류에서 옴
- 뻔한 것도 있음: 널 포인터 역참조는 보통 프로그램을 끝냄
  - 거의 모든 플랫폼이 치명적 오류에 대응할 길을 줌. 얼마나 공을 들일지는 사용자에게 복구가 얼마나 중요한지에 달림. 예: 텍스트 편집기는 고친 내용을 ("복구됨" 이름으로라도) 저장하려 애써야 함
- 더 음흉한 것도 있음
  - 배열 끝을 넘어 써도 그 자리에서 죽지 않을 수 있음
  - 스택 배열이었다면 다른 변수를 덮어써, 한참 뒤에야 이상한 값으로 드러남
  - 자유 공간(힙) 배열이었다면 힙을 망가뜨려, 나중에 할당하거나 해제할 때 오류가 남
- 7장은 "피해야 할 것"의 관점이었다면, 여기서는 이미 버그가 난 코드에서 찾는 관점

:::caution
아래 메모리 문제는 거의 모두 원시 포인터 대신 스마트 포인터를 쓰면 피할 수 있다.
:::

### 메모리 해제 오류

- **증상** (symptom)은 버그가 아님. 버그 때문에 관찰되는 동작

| 오류 | 증상 |
| --- | --- |
| **메모리 누수** | 프로세스의 메모리 사용이 점점 늘고 느려짐. 결국 메모리가 모자라 작업과 시스템 호출이 실패함 |
| **할당과 해제 짝이 안 맞음**(`malloc`↔`delete`, `new`↔`delete[]`, `new[]`↔`free`) | 바로 죽지는 않음. 어떤 플랫폼에서는 메모리를 망가뜨려 나중에 죽음. 누수가 되기도 함 |
| **두 번 해제** | 두 해제 사이에 그 메모리가 다른 할당에 넘어갔다면 죽을 수 있음 |
| **할당하지 않은 메모리 해제** | 대개 죽음 |
| **스택 메모리 해제** | 할당하지 않은 메모리 해제의 특수한 경우. 대개 죽음 |

- 죽는 모습은 플랫폼마다 다름: 세그멘테이션 오류, 버스 오류, 접근 위반 등
- 일부는 바로 끝나지 않아 더 미묘함. 나중에야 문제가 드러남

### 메모리 접근 오류

| 오류 | 증상 |
| --- | --- |
| **잘못된 메모리 접근** | 거의 늘 바로 죽음 |
| **해제된 메모리 접근** | 대개 죽지 않음. 그 메모리가 다른 할당에 넘어갔다면 "이상하고" 위험한 값이 갑자기 나타남 |
| **다른 할당의 메모리 접근**(배열 범위 밖) | 대개 죽지 않음. 다른 변수나 임시 객체에 이상한 값이 나타나거나 제어 흐름까지 바뀜 |
| **초기화하지 않은 메모리 읽기** | 그 값을 포인터나 인덱스로 써서 역참조하지 않는 한 죽지 않음. 그래도 늘 죽지는 않음 |

- 죽지 않고 **틀린 결과**를 내는 것이 더 위험할 수 있음. 로봇 팔, X선 장비, 방사선 치료, 생명 유지 장치처럼 컴퓨터가 외부 장치를 제어할 때 특히
- 위 증상은 릴리스 빌드의 기본 증상. 디버그 빌드는 다르게 동작하기 쉽고, 디버거 안에서는 오류 순간에 멈추기도 함

### 실행 예제: 새니타이저로 잡기

- **주소 새니타이저** (AddressSanitizer, ASan): 컴파일러가 메모리 접근마다 검사 코드를 넣어, 범위 밖 접근, 해제 후 사용, 두 번 해제, 짝 안 맞는 해제 등을 **일어난 바로 그 자리에서** 잡음. GCC·Clang `-fsanitize=address -g`, Visual C++ `/fsanitize=address` ([문서](https://clang.llvm.org/docs/AddressSanitizer.html))
- 아래 예제는 이 옵션을 켜고 컴파일됨. 입력 칸의 숫자로 오류를 고름: 0 없음, 1 힙 범위 밖 쓰기, 2 해제 후 사용, 3 두 번 해제, 4 스택 배열 범위 밖, 5 `new[]`를 `delete`로 해제

<RunCode client:load code={meCode} stdin="1" flags="-std=c++23 -Wall -Wextra -fsanitize=address -g" />

- 볼 것
  - 표준 오류에 `ERROR: AddressSanitizer: heap-buffer-overflow`와 함께 잘못 쓴 줄(`for` 안의 `values[i] = i;`)이 나옴. 마지막 `SUMMARY` 줄이 요점
  - 2는 `heap-use-after-free`, 3은 `double-free`, 4는 `stack-buffer-overflow`, 5는 `alloc-dealloc-mismatch`
  - 새니타이저가 프로그램을 즉시 끝내므로 앞의 `println` 출력이 보이지 않을 수 있음

- 5번은 컴파일러가 `-Wmismatched-new-delete` 경고로도 미리 알려 줌

### 메모리 오류 디버깅 요령

- 실행할 때마다 **조금씩 다른 곳에서** 나타나는 버그라면 메모리 손상을 의심함. 힙 손상은 할당·해제·사용 중 언제 터질지 모르는 시한폭탄
- 의심되면 메모리 검사 도구를 씀
  - Visual C++ 디버거로 디버그 빌드를 돌리면 대부분 잡힘
  - [Valgrind](https://valgrind.org/)(Linux), 주소 새니타이저, Windows SDK의 Application Verifier(릴리스 빌드에도)
  - 이런 도구는 자기만의 할당·해제 루틴을 끼워 넣어 동적 메모리 오용을 검사함
- 도구가 없으면 코드를 살핌. 먼저 범위를 좁히고, **원시 포인터**를 모두 봄. 괜찮은 품질의 코드라면 대부분 스마트 포인터에 싸여 있을 테니 원시 포인터가 수상함
- 객체와 클래스 관련
  - 동적 메모리를 가진 클래스의 소멸자가 할당한 만큼 **정확히** 해제하는지
  - 복사 생성자·대입이 올바른지(9장). 이동 생성자·대입이 원본의 포인터를 `nullptr`로 만들어 원본 소멸자가 해제하지 않게 하는지
  - 수상한 캐스트. 포인터를 다른 타입으로 바꾼다면 정말 유효한지. 가능하면 `dynamic_cast` <CppRef path="cpp/language/dynamic_cast" />
  - 소유권을 원시 포인터로 다루는 곳은 스마트 포인터로 바꾸고 **0의 규칙**으로 리팩터링하면 앞의 두 종류 오류가 사라짐
- 일반
  - `new`마다 `delete` 정확히 한 번, `new[]`마다 `delete[]` 한 번, `malloc`/`calloc`마다 `free` 한 번. 해제 후 포인터를 `nullptr`로
  - 버퍼 넘침: 배열을 돌거나 C 스타일 문자열을 읽고 쓸 때 끝을 넘지 않는지. 표준 컨테이너와 `std::string`으로 피함
  - 잘못된 포인터 역참조
  - 스택의 포인터(스칼라 타입 모두)는 선언할 때 초기화: `T* p{ nullptr };`. `T* p;`는 금지. 더 좋은 건 스마트 포인터
  - 클래스의 포인터 멤버도 클래스 안 초기화나 생성자에서 늘 초기화

## 멀티스레드 프로그램 디버깅

- 멀티스레드 버그는 운영체제 스케줄링의 **타이밍 차이** 때문인 경우가 많아 재현이 어려움(27장)

| 기법 | 내용 |
| --- | --- |
| **디버거** | 교착 상태에 좋음. 멈췄을 때 디버거로 들어가 스레드들을 보면 어느 스레드가 어느 줄에서 막혔는지 보임. 어떻게 거기 이르렀는지 보여 주는 추적 로그와 함께면 대개 충분 |
| **로그 기반 디버깅** | 임계 영역 앞뒤, 락을 얻기 전과 푼 뒤에 로그. 경쟁 상태 조사에 특히 좋음. 다만 로그가 타이밍을 바꿔 버그가 숨을 수 있음 |
| **강제 sleep과 문맥 전환** | 재현이 잘 안 되거나 원인을 짐작해 확인하고 싶을 때, `std::this_thread::sleep_for()`·`sleep_until()`로 특정 스케줄링을 강제함. 락을 풀기 직전, 조건 변수에 신호하기 직전, 공유 데이터에 접근하기 직전에 몇 초 잠들면 숨은 경쟁 상태가 드러남 |
| **코드 리뷰** | 동기화 코드를 다시 봄. "일어난 일은 불가능하다"를 거듭 증명해 보다가 어떻게 가능한지 보이게 됨. 그 "증명"을 주석으로 남겨도 좋음. 동료와 **짝 디버깅** |

- `sleep_for` <CppRef path="cpp/thread/sleep_for" />
- **스레드 새니타이저** (ThreadSanitizer, `-fsanitize=thread`)는 데이터 경쟁을 실행 중에 찾아 줌 ([문서](https://clang.llvm.org/docs/ThreadSanitizer.html))

:::caution
강제 sleep으로 원인을 찾았다면, sleep을 **뺀 뒤에도** 올바르게 동작하도록 고친다. sleep을 코드에 남기는 것은 잘못된 "수정"이다.
:::

## 헷갈리기 쉬운 점

- 버그를 일으킨 마지막 동작만 반복하면 재현된다?
  - 그 전의 순서 전체가 원인일 수 있음. 시작부터의 입력을 모두
- 재현은 안 되지만 그럴듯한 곳을 고쳤으니 끝났다?
  - 재현 테스트 없이는 고쳤는지 모름. 엉뚱한 곳을 고쳤을 수 있음
- 범위 밖 쓰기를 해도 죽지 않았으니 괜찮다?
  - 다른 변수를 덮었을 수 있음. 증상은 나중에 다른 곳에서
- 로그를 켰더니 버그가 사라졌으니 해결됐다?
  - 타이밍이 바뀌어 숨었을 뿐. 경쟁 상태를 의심
- 강제 sleep으로 버그가 안 나니 그대로 둔다?
  - 진짜 수정이 아님. 동기화를 고침
