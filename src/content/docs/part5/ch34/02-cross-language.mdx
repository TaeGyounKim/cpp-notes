## C와 C++ 섞기

- C++는 C의 거의 상위 집합. 대부분의 C 코드는 쉽게 C++로 옮겨지지만 주의할 점이 있음
  - C에만 있는 기능: 예를 들어 가변 길이 배열(VLA)
  - **예약어**: C에서는 `class`, `new`, `template` 같은 낱말이 아무 뜻이 없어 변수 이름으로 쓸 수 있음. `int new = 1;`은 C에서는 되지만 C++에서는 오류. 옮길(**포팅**) 때 만나는 이런 오류는 이름만 바꾸면 대개 쉽게 고쳐짐
- 모든 C++ 컴파일러는 C 컴파일러이기도 함. C 코드를 굳이 C++로 컴파일할 필요 없이 C로 컴파일해 C++ 오브젝트 파일과 함께 **링크**하면 됨
  - C로 쓰인 유용한 라이브러리나 오래된 코드를 C++ 프로그램에 넣기 쉬움

### 패러다임 바꾸기: 객체 지향 퍼사드

- C와 C++를 섞으면 프로그램이 객체 지향 성질을 잃기 쉬움
  - 예: 객체 지향으로 짠 프로그램이 절차적 C 네트워크 라이브러리를 곳곳에서 직접 부름
- 그 라이브러리를 많이 쓴다면 **객체 지향 래퍼**를 씀. 33장 끝에서 본 **퍼사드** (facade) 패턴: 복잡한 하위 시스템 앞에 쓰기 쉬운 높은 수준 인터페이스
- C 스타일 API의 전형적인 모양: 핸들(포인터)을 열고, 함수에 핸들을 넘기고, 오류 코드를 확인하고, 직접 닫음
  - 응집된 클래스가 아니고 실수하기 쉬움. 하지만 라이브러리 사용자는 주어진 것을 받아들여야 함. 래퍼는 인터페이스를 내 마음대로 다듬을 기회
- 래퍼 설계(5장, 6장): 라이브러리의 **흔한 사용 방식**을 담음
  - 핸들은 `std::unique_ptr`에 **커스텀 삭제자**로 담아 RAII로 자동 해제(7장, 32장)
  - 오류 코드는 예외나 `std::optional`로 바꿈
  - C 문자열은 `std::string`으로 바꿔 돌려줌

```cpp
class Store final {
public:
    Store() : m_handle{ kv_open(), kv_close } {}   // 소멸하면 kv_close
    // 실패하면 예외
    void put(const std::string& key, const std::string& value);
    // NULL이면 nullopt
    std::optional<std::string> get(const std::string& key) const;
private:
    std::unique_ptr<kv_store, decltype(&kv_close)> m_handle;
};
```

- 추상화를 두면 클라이언트 코드에 영향 없이 아래 구현을 바꾸거나, 연결 재사용·자동 재연결 같은 기능을 보탤 수 있음

## C 코드와 링크하기

- C 소스가 아니라 **컴파일된** C 라이브러리만 있어도 C++에서 쓸 수 있지만 몇 단계가 더 필요함

### 이름 맹글링

- C++는 오버로딩을 위해 함수 이름을 매개변수 타입까지 담은 이름으로 바꿈. 이것이 **이름 맹글링** (name mangling)
  - 그러지 않으면 링커는 `area`라는 같은 이름의 함수 여럿 중 무엇을 부를지 모름
- 실제 GCC(Itanium C++ ABI)에서 오브젝트 파일의 이름

| 소스 | 오브젝트 파일의 이름 |
| --- | --- |
| `void area(double)` | `_Z4aread` |
| `void area(int)` | `_Z4areai` |
| `void area(int, int)` | `_Z4areaii` |
| `extern "C" void area_c(int)` | `area_c` |

- 맹글링 규칙은 표준이 정하지 않아 컴파일러마다 다름. 예: Visual C++는 `?area@@YAXN@Z` 같은 꼴
- C는 오버로딩이 없어 이름이 단순함(`area` 또는 `_area`)
- 문제: C++ 코드가 C 함수를 부르면 컴파일러는 **맹글링된** 이름을 찾도록 만들고, C 라이브러리에는 그 이름이 없어 링커가 실패함

### extern "C"

- 맹글링하지 말고 C 방식 이름과 호출 규약을 쓰라고 알림 <CppRef path="cpp/language/language_linkage" />
  - 헤더에(부르는 쪽이 C 호환 이름을 찾게)
  - 라이브러리가 C++로 쓰였다면 정의에도(C 호환 이름으로 내보내게)

```cpp
extern "C" int c_function(int value);   // 하나

extern "C" {                             // 여럿
    void draw_circle(double r);
    void draw_square(double side);
}
```

- 표준은 어떤 언어 지정도 허용하지만 실제로 대부분의 컴파일러는 `"C"`(와 `"C++"`)만 지원함
- 흔한 쓰임은 **헤더 수준**. C 라이브러리의 헤더가 C로도 C++로도 컴파일되도록, C++ 컴파일러만 정의하는 `__cplusplus` 기호로 감쌈

```cpp
#ifdef __cplusplus
extern "C" {
#endif

void draw_circle(double r);
void draw_square(double side);

#ifdef __cplusplus
}
#endif
```

- C++는 C의 거의 상위 집합이지만 설계 목표가 다른 별개의 언어. C 코드를 C++에서 그대로 쓰는 일은 흔하지만, 절차적 C 코드를 **객체 지향 C++ 래퍼로 감싸는 편이 대개 훨씬 나음**

## C#에서 C++ 부르기

- C#의 **상호 운용** (Interop) 서비스로 C++ 코드를 꽤 쉽게 부름. 예: GUI는 C#으로, 성능이 중요한 계산은 C++로
- C++ 쪽: 라이브러리(Windows에서는 `.dll`)로 컴파일. 프로그램이 아니므로 `main()`이 없음

```cpp
// 공유 라이브러리로 빌드(Visual C++: 구성 형식을 "동적 라이브러리"로)
extern "C" __declspec(dllexport) int count_vowels(const wchar_t* text)
{
    int n{ 0 };
    for (; *text; ++text) {
        if (std::wcschr(L"aeiouAEIOU", *text)) { ++n; }
    }
    return n;
}
```

- `__declspec(dllexport)`는 이 함수를 라이브러리 사용자에게 내보내라는 Visual C++의 방법. 다른 링커는 방식이 다름
- C# 쪽: **P/Invoke**로 함수 원형과 위치를 알려 주고 부름([문서](https://learn.microsoft.com/en-us/dotnet/standard/native-interop/pinvoke))

```text
using System.Runtime.InteropServices;

[DllImport("TextTools.dll", CharSet = CharSet.Unicode)]
static extern int count_vowels(string text);

Console.WriteLine(count_vowels("Interop is easy"));
```

### C++/CLI

- C#의 **클래스**를 C++에서 쓰거나, C++ 클래스를 C#에서 쓰려면 **C++/CLI**
  - CLI(Common Language Infrastructure)는 C#, Visual Basic .NET 같은 모든 .NET 언어의 바탕. C++/CLI는 Microsoft가 만들었고 ECMA-372로 표준화됨
  - 관리되는 객체는 가비지 컬렉터가 정리하므로 `new` 대신 `gcnew`로 만들고, 일반 포인터 대신 **핸들** `MyClass^`("햇")에 담음
  - `public ref class`로 쓴 C++ 클래스는 다른 CLI 언어에서 쓸 수 있음
- 최신 C++ 표준을 늦게 따라갈 수 있음. 기본 타입(`double` 등)은 쉽지만 문자열, 컨테이너 같은 타입은 **마샬링** (marshaling, 두 세계 사이 변환)이 필요해 복잡해짐

## Java에서 C++ 부르기: JNI

- **JNI** (Java Native Interface): Java가 아닌 언어로 쓰인 기능에 접근하게 하는 Java의 일부([명세](https://docs.oracle.com/en/java/javase/21/docs/specs/jni/))
  - 원래 목적은 크로스 플랫폼인 Java가 운영체제와 상호 작용하는 것. C++ 라이브러리를 쓰는 데도 씀: 성능이 중요한 코드, 오래된 코드
  - C++ 프로그램 안에서 Java 코드를 실행할 수도 있지만 드묾
- 순서

<div>

1. Java 클래스에 구현 없는 `native` 메서드를 선언하고, `static` 블록에서 `System.loadLibrary("textnative")`로 공유 라이브러리를 읽음
2. `javac -h . TextApp.java`로 컴파일하며 C/C++ 헤더를 만듦(예전 JDK의 `javah` 도구는 JDK 10에서 없어짐). 헤더에 `Java_TextApp_countVowels` 같은 C 함수 원형이 생김
3. C++로 그 함수를 구현함. `jni.h`와 생성된 헤더를 포함
4. 공유 라이브러리로 컴파일: Linux라면 `g++ -shared -fPIC -I$JAVA_HOME/include -I$JAVA_HOME/include/linux text.cpp -o libtextnative.so`
5. 라이브러리가 찾을 수 있는 경로에 있으면 `java TextApp`으로 실행

</div>

- 함수의 매개변수(`JNIEnv*` 등)로 Java 환경과 부른 객체에 접근함. 운영체제 고유 기능이나 하드웨어 드라이버와의 연동에도 씀
- 참고: Python에서 C++를 부를 때는 [pybind11](https://pybind11.readthedocs.io/) 같은 라이브러리가 널리 쓰임

## 스크립트와 C++

### C++에서 스크립트 부르기

- 초기 Unix의 C 라이브러리는 기능이 적어, 프로그래머들이 응용에서 스크립트(Perl, Python, 셸 스크립트)를 띄워 일을 시키는 습관이 생김
- `<cstdlib>`의 `std::system()`: 실행할 명령 문자열 하나를 받음 <CppRef path="cpp/utility/program/system" />

```cpp
int rc{ std::system("python3 make_report.py --month 11") };
```

- 위험이 큼
  - 스크립트에 오류가 나도 부른 쪽이 자세한 오류를 받지 못할 수 있음
  - 새 **프로세스** 전체를 만들어야 해 매우 무거움. 성능 병목이 될 수 있음
  - 사용자 입력을 명령 문자열에 넣으면 명령 주입 위험
- 대개 C++ 라이브러리에 더 나은 방법이 있음
  - 네트워크와 저수준 입출력: [Asio](https://think-async.com/Asio/)(또는 [Boost.Asio](https://www.boost.org/libs/asio/))
  - 파일 시스템: `<filesystem>`<Badge text="C++17" />(13장) <CppRef path="cpp/filesystem" />
  - 문자열 처리: `<regex>`(21장)

### 스크립트에서 C++ 부르기

- C++에는 다른 언어·환경과 이어지는 범용 장치가 원래 있음: `main()`의 **인수와 반환값** <CppRef path="cpp/language/main_function" />
  - 명령줄 인수를 받고, 부른 쪽이 해석할 **상태 코드**를 돌려줌. Unix 관례는 0이 성공, 0이 아니면 실패
  - `argc`를 늘 확인함. `argv[0]`은 보통 프로그램 이름이지만, 프로세스를 띄운 쪽이 정하므로 무엇이든 될 수 있음. 보장되는 것은 `argv[0]`~`argv[argc-1]`이 널 종료 문자열이고 `argv[argc]`가 널 포인터라는 것
- 예: 관리자가 사용자 활동 로그에서 비밀번호 줄을 찾아 가리고 싶음. 스크립트가 로그를 줄 단위로 읽어 정규식으로 비밀번호 줄을 찾고, 비밀번호만 C++ 프로그램에 넘겨 가린 값을 표준 출력으로 받아 씀. 프로그램의 종료 코드가 0이 아니면 스크립트도 멈춤

```text
# 셸 스크립트 쪽(개념): 비밀은 인수가 아니라 표준 입력으로 넘김
masked=$(printf '%s' "$secret" | ./mask_secret) || exit 1
```

- 주의
  - 비밀을 **명령줄 인수**로 넘기면 같은 기계의 다른 사용자가 프로세스 목록으로 볼 수 있음. **표준 입력**으로 넘기는 편이 안전함(위 실행 예제처럼)
  - 외부 프로세스를 띄우는 것은 비싸므로, 자주 부르는 일이라면 피함. 이 예처럼 `<regex>`가 있으면 아예 C++만으로 하는 편이 훨씬 빠름
- 스크립트 언어는 운영체제와 상호 작용하고 흐름을 조절하고, C++는 무거운 계산을 맡는 식으로 강점을 합칠 수 있음

## 어셈블리 코드

- C++는 빠르지만, 속도가 정말 결정적인 드문 경우 **어셈블리** 코드를 쓰기도 함
- 컴파일러와 링커(링크 시간 코드 생성을 지원하면)는 최적화 알고리즘으로, MMX·SSE·AVX 같은 특수 명령까지 써서 빠른 코드를 만듦. 이런 명령의 세부를 모두 알지 않는 한 컴파일러보다 빠른 어셈블리를 손으로 쓰기는 어려움
- `asm` 키워드: 표준에 있지만 구현은 컴파일러가 정함 <CppRef path="cpp/language/asm" />
  - 대상 아키텍처에 따라 지원이 다르고, 비표준 키워드를 쓰기도 함. 예: Visual C++는 `asm`을 지원하지 않고, 32비트에서만 `__asm`을, 64비트에서는 인라인 어셈블리를 아예 지원하지 않음
- 피해야 할 이유
  - 다른 프로세서로 이식할 수 없음
  - 대부분의 프로그래머가 어셈블리를 몰라 고치거나 유지 보수하지 못함
  - 읽기 어려워 코드 스타일을 해침
  - 대개 필요 없음. 느리면 먼저 알고리즘 문제를 찾음(29장)

:::caution
성능 문제를 만나면 프로파일러로 진짜 병목을 찾고 알고리즘 개선부터 본다. 어셈블리는 그 뒤에도 방법이 없을 때만, 단점을 따져 보고 쓴다.
:::

- 정말 쓴다면
  - 무거운 부분을 C++ 함수 하나로 떼어 `extern "C"`로 선언함(맹글링 없는 단순한 이름)
  - 같은 함수를 어셈블리 모듈로 따로 써서 어셈블러로 빌드함. 인라인 `asm`보다 이쪽이 나음(많은 64비트 x86 컴파일러가 인라인을 지원하지 않음)
  - 플랫폼과 무관한 C++ **참조 구현**과 플랫폼별 고성능 구현을 함께 두고, 둘 중 하나를 링크함
- **암달의 법칙** (Amdahl's law)을 잊지 않음: 실행 시간의 10%를 차지하는 부분을 10배 빠르게 해도 전체는 약 9%만 빨라짐(0.9 + 0.1/10 = 0.91)

## 헷갈리기 쉬운 점

- C 코드는 C++ 컴파일러로 컴파일해야 섞을 수 있다?
  - C로 컴파일해 링크하면 됨. 헤더에 `extern "C"`
- `extern "C"`는 C 언어로 컴파일하라는 뜻이다?
  - 컴파일은 C++로 하되 **이름과 호출 규약**만 C 방식으로
- `extern "C"` 함수도 오버로딩할 수 있다?
  - 이름이 하나뿐이라 같은 이름으로 둘을 둘 수 없음
- `std::system()`이 간편하니 자주 쓴다?
  - 무겁고 오류 처리가 약하며 주입 위험. 라이브러리를 먼저 찾음
- 비밀번호는 명령줄 인수로 넘기면 된다?
  - 프로세스 목록에 보일 수 있음. 표준 입력으로
- 어셈블리로 바꾸면 프로그램이 크게 빨라진다?
  - 컴파일러가 대개 더 잘함. 바꾼 부분의 비중만큼만 빨라짐(암달)

## 정리

| 주제 | 핵심 |
| --- | --- |
| C와 섞기 | 예약어 충돌, C로 컴파일해 링크, 객체 지향 퍼사드로 감싸기 |
| 이름 맹글링 | 오버로딩 때문. 규칙은 컴파일러마다 다름 |
| `extern "C"` | C 이름·호출 규약. `__cplusplus`로 겸용 헤더 |
| C# | P/Invoke(`DllImport`), C++/CLI(`gcnew`, `^`, `ref class`) |
| Java | JNI: `native`, `javac -h`, 공유 라이브러리 |
| 스크립트 | `std::system`은 무거움. `main`의 인수·종료 코드, 비밀은 표준 입력으로 |
| 어셈블리 | 거의 필요 없음. `extern "C"` 함수로 분리, 참조 구현 유지, 암달의 법칙 |
