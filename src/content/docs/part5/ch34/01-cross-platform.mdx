- 다루는 것: C++는 여러 플랫폼에서 비슷하게 프로그래밍하도록 엄밀히 정의되어 있지만, 전문적인 프로그램을 쓰다 보면 결국 플랫폼 차이를 만남. 한 플랫폼만 쓰더라도 컴파일러의 작은 차이가 큰 골칫거리가 되기도 함
- **플랫폼** (platform): 개발·실행 시스템을 이루는 세부 전체
  - 예: Windows 11 위 Intel Core i7에서 도는 Visual C++ 2022 컴파일러
  - 예: Linux 위 PowerPC에서 도는 GCC
  - 둘 다 C++를 컴파일하고 실행하지만 차이가 큼
- 이 장의 순서
  - 1편: 크로스 플랫폼 개발
  - 2편: C++와 다른 언어 함께 쓰기

## 플랫폼 문제가 생기는 이유

- C++는 높은 수준의 언어라 표준이 일부 저수준 세부를 정하지 않음
  - 예: 객체의 메모리 배치(패딩, 정렬)는 컴파일러에 맡겨짐. C++23부터 멤버 순서는 선언 순서로 정해졌지만 그 밖의 배치는 플랫폼마다 다름
- 표준 언어와 표준 라이브러리는 있지만 **표준 구현**은 없음. 컴파일러·라이브러리 제작사마다 명세를 다르게 해석할 수 있음
- C++가 표준으로 주는 기능은 선별적임. 프로그램에는 언어나 표준 라이브러리에 없는 기능이 필요하고, 그것은 서드파티나 플랫폼 라이브러리에서 오며 크게 다를 수 있음

## 아키텍처 문제

- **아키텍처** (architecture): 프로그램이 도는 프로세서(군). 보통 PC는 x86이나 x64, 휴대 기기는 ARM
- 대부분의 차이는 C++가 가려 줌. 어떤 명령이 한 프로세서에서는 하나, 다른 프로세서에서는 여섯이어도 몰라도 됨. 컴파일러가 고유 기계어로 바꿔 주기 때문
- 그래도 C++ 코드까지 올라오는 차이가 있음. 정수 크기는 크로스 플랫폼 코드라면 꼭 알아야 하고, 나머지는 저수준 작업을 할 때 만남

### 정수의 크기

- 표준은 정수 타입의 **정확한 크기를 정하지 않음**. `signed char`, `short`, `int`, `long`, `long long` 순으로 앞의 것보다 **작지 않다**는 것과 최소 범위 정도만 정함 <CppRef path="cpp/language/types" />
  - 실제 크기는 컴파일러와 플랫폼에 따라 다름. 예: `long`은 64비트 Linux에서 8바이트, 64비트 Windows에서 4바이트
- 크기가 분명한 타입은 `<cstdint>`의 `std` 이름 공간에 있음(일부는 선택적) <CppRef path="cpp/types/integer" />

| 타입 | 뜻 |
| --- | --- |
| `int8_t`, `int16_t`, `int32_t`, `int64_t` | 정확히 8, 16, 32, 64비트. 특이한 플랫폼에서는 없을 수 있음 |
| `int_fast8_t` ... `int_fast64_t` | 최소 그 비트 수를 만족하는 가장 **빠른** 타입 |
| `int_least8_t` ... `int_least64_t` | 최소 그 비트 수를 만족하는 가장 **작은** 타입. 늘 있음 |
| `intmax_t` | 컴파일러가 지원하는 가장 큰 정수 |
| `intptr_t` | 포인터를 담을 만큼 큰 정수. 선택적이지만 대부분 지원 |

- 각각 부호 없는 판(`uint8_t`, `uint_fast8_t` 등)도 있음
- 크로스 플랫폼 코드에서는 기본 정수 타입보다 `<cstdint>` 타입을 권함. 특히 파일·네트워크로 주고받는 값

### 이진 호환성

- Intel 컴퓨터용으로 컴파일한 프로그램은 PowerPC 맥에서 돌지 않음. 프로세서가 지원하는 명령 집합이 달라 **이진 호환되지 않음**
  - 컴파일하면 소스가 이진 명령으로 바뀌는데, 그 형식은 C++가 아니라 **플랫폼**이 정함
- 해결
  - 대상 플랫폼마다 그 플랫폼의 컴파일러로 따로 빌드
  - **교차 컴파일** (cross-compilation): 플랫폼 X에서 개발하며, X의 교차 컴파일러로 Y, Z용 바이너리를 만듦
  - 오픈 소스로 공개: 사용자가 자기 시스템에서 직접 컴파일(4장)

### 주소 크기

- "64비트 아키텍처"는 대개 **주소 크기**가 64비트(8바이트)라는 뜻. 주소가 크면 더 많은 메모리를 다룸
- 포인터는 메모리 주소이므로 주소 크기에 묶임. "포인터는 늘 8바이트"는 틀림: 32비트 x86에서는 4, x86-64에서는 8
- 포인터 크기가 정수 크기와 같다는 보장도 없음. 64비트 플랫폼에서 포인터는 64비트인데 `int`는 32비트일 수 있어, 포인터를 `int`로 바꾸면 32비트를 잃음
- `std::uintptr_t`: 포인터를 담기에 충분히 큰 정수 타입(선택적이지만 사실상 모든 컴파일러가 지원)

:::caution
포인터가 32비트나 64비트라고 가정하지 않는다. 포인터를 정수로 바꿔야 한다면 `std::uintptr_t`만 쓴다.
:::

### 바이트 순서

- 같은 수도 플랫폼에 따라 메모리 표현이 다를 수 있음
- 메모리는 대개 **바이트 단위로 주소**가 있고, 여러 바이트짜리 수는 나눠서 저장함
  - 예: `short` 513은 2진수로 `0000 0010 0000 0001`. 상위 바이트 `0x02`, 하위 바이트 `0x01`
  - 어느 바이트를 앞 주소에 둘지가 아키텍처마다 다름

| 순서 | 앞 주소에 | 예 |
| --- | --- | --- |
| **빅 엔디언** (big-endian) | 상위 바이트 먼저: `02 01` | PowerPC, SPARC, 네트워크 바이트 순서 |
| **리틀 엔디언** (little-endian) | 하위 바이트 먼저: `01 02` | x86, x64, 대부분의 ARM 설정 |

- 이 용어는 컴퓨터보다 수백 년 앞서, 18세기 소설 『걸리버 여행기』에서 달걀을 어느 쪽 끝으로 깨야 하는지 다투는 두 진영을 가리키는 말이었음
- 프로그램 안에서 수를 쓸 때는 바이트 순서를 신경 쓰지 않아도 됨. **데이터가 아키텍처 사이를 오갈 때**만 문제가 됨
  - 네트워크로 이진 데이터를 보낼 때: 표준 **네트워크 바이트 순서**(늘 빅 엔디언)로 바꿔 보내고, 받으면 자기 순서로 바꿈
  - 이진 파일을 쓸 때: 반대 순서의 시스템에서 읽힐 수 있음. 파일 형식에서 순서를 정해 둠
- `<bit>`의 `std::endian`<Badge text="C++20" />으로 현재 시스템의 순서를 알 수 있음 <CppRef path="cpp/types/endian" />
- `std::byteswap`<Badge text="C++23" />은 바이트 순서를 뒤집음 <CppRef path="cpp/numeric/byteswap" />
- 가장 이식성 좋은 방법은 시프트로 **직접** 원하는 순서의 바이트를 만드는 것. 기계의 순서와 상관없이 같은 결과가 나옴

```cpp
std::array<std::uint8_t, 4> to_big_endian(std::uint32_t v)
{
    return { static_cast<std::uint8_t>(v >> 24),   // 상위 바이트 먼저
             static_cast<std::uint8_t>(v >> 16),
             static_cast<std::uint8_t>(v >> 8),
             static_cast<std::uint8_t>(v) };
}
```

## 구현 문제

- 컴파일러는 2,000쪽이 넘는 표준(산문, 의사 코드, 예)을 사람이 해석해 만듦. 두 사람이 모든 부분을 똑같이 해석하거나 모든 경계 조건을 잡기는 어려움. 그래서 컴파일러에도 **버그**가 있음

### 컴파일러의 특이점과 확장

- 컴파일러 버그를 찾거나 피하는 간단한 규칙은 없음
  - 컴파일러 업데이트를 따라가고, 메일링 리스트나 이슈 트래커를 봄
  - 버그가 의심되면 오류 메시지로 검색하면 우회책이나 패치를 찾기도 함
- 최신 표준에 새로 들어온 기능이 특히 문제를 일으키기 쉬움. 요즘은 주요 컴파일러가 꽤 빨리 지원함
- 컴파일러가 **자기만의 언어 확장**을 티 나지 않게 허용하기도 함
  - 예: 크기가 실행 중에 정해지는 스택 배열(**VLA**, variable-length array)은 C에는 있지만 C++ 표준에는 없음. g++는 C++ 코드에서도 받아 줌
  - 언젠가 컴파일러를 바꿀 수 있다면 확장을 피하는 **엄격 모드**를 씀. g++에 `-pedantic`을 주면 `warning: ISO C++ forbids variable length array` 경고가 남
- `#pragma`: 표준이 허용하는 구현 정의 확장 장치. 구현이 모르는 지시는 무시함. 예: 일부 컴파일러는 `#pragma`로 경고를 잠시 끔 <CppRef path="cpp/preprocessor/impl" />

### 라이브러리 구현

- 표준 라이브러리도 C++로 쓰였으므로 컴파일러에 딸린 구현을 꼭 써야 하는 것은 아님. 속도에 최적화한 서드파티 구현을 쓰거나 직접 쓸 수도 있음
  - 예: GCC는 libstdc++, Clang은 libc++나 libstdc++, Visual C++는 MSVC STL
- 라이브러리 구현자도 해석 문제를 겪고, 구현마다 절충이 다름. 예: 하나는 속도를, 다른 하나는 실행 중 오용 검출을 우선함
- 표준 라이브러리든 다른 서드파티 라이브러리든 설계자가 한 절충을 고려함(4장)

## 여러 구현 다루기

- 개발자는 대개 **툴체인** (toolchain, 컴파일러 하나와 표준 라이브러리 구현 하나) 하나만 씀. 모든 변경을 지원해야 하는 모든 툴체인으로 직접 확인하기는 어려움
- 해법: **지속적 통합**과 **자동 테스트**(28장, 30장)
  - 모든 변경을 지원하는 모든 툴체인에서 자동으로 빌드. 어느 하나에서 빌드가 깨지면 깨뜨린 개발자에게 바로 알림
  - 빌드가 나오면 자동 테스트를 돌리고, 실패하면 역시 알림
- 개발 환경마다 프로젝트 파일 형식이 다름. 환경마다 따로 손으로 관리하면 유지 보수의 악몽
  - 한 가지 형식의 설정이나 빌드 스크립트에서 각 툴체인용 프로젝트 파일을 **생성**함
  - 예: [CMake](https://cmake.org/). 소스 파일, 컴파일러 옵션, 링크할 라이브러리를 CMake 설정(스크립트 가능)으로 기술하면, Windows용 Visual C++ 프로젝트나 macOS용 Xcode 프로젝트 등을 만들어 줌

## 플랫폼 고유 기능

- 표준 라이브러리 덕분에 C++만으로 오래 코딩할 수 있지만, 전문적인 프로그램에는 언어도 표준 라이브러리도 주지 않는 기능이 필요함

| 기능 | 상황 | 방법 |
| --- | --- | --- |
| **그래픽 사용자 인터페이스** | 버튼, 창, 메뉴 개념이 C++에 없음 | 플랫폼 라이브러리, 또는 여러 플랫폼을 지원하는 [Qt](https://www.qt.io/), [wxWidgets](https://www.wxwidgets.org/) 등 |
| **네트워킹** | 표준 네트워크 기능이 아직 없음 | 대부분의 플랫폼에 있는 **소켓** 라이브러리, 또는 서드파티 네트워크 라이브러리. IPv4만이 아니라 IPv6도 지원하는 것을 고름 |
| **운영체제 사건, 응용 간 상호 작용** | 명령줄 인수 외에는 거의 없음. 클립보드 같은 것도 없음 | 플랫폼 라이브러리, 또는 클립보드 등을 추상화한 Qt, wxWidgets |
| **저수준 파일** | 운영체제 고유 파일 API(사용자 홈 디렉터리 얻기 등) | 플랫폼 API. 경로·디렉터리 다루기는 `<filesystem>`<Badge text="C++17" />이 상당 부분 덮음 |
| **스레드** | C++11부터 표준 스레드, C++17부터 병렬 알고리즘(27장, 20장) | 더 강력한 기능은 Intel [oneTBB](https://github.com/uxlfoundation/oneTBB), [HPX](https://github.com/STEllAR-GROUP/hpx) 같은 라이브러리 |

- 크로스 플랫폼 개발에서 표준에 없는 기능이 필요하면, 플랫폼 API를 직접 쓰기보다 **크로스 플랫폼 서드파티 라이브러리**를 찾음. 플랫폼 API를 직접 쓰면 플랫폼마다 따로 구현해야 해 코드가 크게 복잡해짐
- 서드파티 라이브러리는 가능하면 **소스로** 받아, 필요한 툴체인으로 직접 빌드함

## 헷갈리기 쉬운 점

- `int`는 늘 32비트다?
  - 표준은 최소 범위만 정함. 정확한 크기가 필요하면 `int32_t`
- 포인터는 64비트이니 `long`에 담아도 된다?
  - 64비트 Windows의 `long`은 32비트. `std::uintptr_t`
- 바이트 순서는 늘 신경 써야 한다?
  - 프로그램 안에서는 아님. 네트워크·파일로 다른 기계와 주고받을 때만
- g++가 받아 주면 표준 C++다?
  - 확장일 수 있음. `-pedantic`으로 확인
- 모든 툴체인으로 직접 시험해야 한다?
  - 지속적 통합이 대신 빌드하고 테스트함

## 정리

| 주제 | 핵심 |
| --- | --- |
| 정수 크기 | 표준은 상대 크기만. `<cstdint>` 고정 크기 타입 |
| 이진 호환성 | 플랫폼마다 빌드, 교차 컴파일, 소스 공개 |
| 주소 크기 | 포인터 크기를 가정하지 않음. `uintptr_t` |
| 바이트 순서 | 빅·리틀 엔디언. 주고받을 때만. 네트워크 순서는 빅 엔디언. `std::endian`, `byteswap` |
| 구현 차이 | 컴파일러 버그와 확장(`-pedantic`), `#pragma`, 라이브러리 절충 |
| 여러 툴체인 | 지속적 통합 + 자동 테스트, CMake |
| 플랫폼 기능 | GUI, 네트워크, OS 상호 작용, 저수준 파일, 고급 스레드 → 크로스 플랫폼 라이브러리 |
