## 성능과 효율

- **성능** (performance): 속도, 메모리 사용, 디스크 접근, 네트워크 사용 등 여러 면을 가리킴. 이 장은 **속도**를 다룸
- **효율** (efficiency): 낭비 없이 도는 것. 주어진 조건에서 가능한 한 빨리 일을 끝냄
  - 분야 자체가 빨리 돌 수 없는 성격이라면, 빠르지 않아도 효율적일 수 있음
- "효율적인 C++ 코드 작성"은 프로그램이 효율적으로 **돌게** 쓰는 것이지, 코드를 효율적으로 **쓰는** 것이 아님. 아끼는 시간은 사용자의 시간

### 두 수준

| 수준 | 예 | 중요도 |
| --- | --- | --- |
| **언어 수준 효율** (language-level efficiency) | 객체를 값 대신 참조로 전달 | 어느 정도까지만 |
| **설계 수준 효율** (design-level efficiency) | 효율적인 알고리즘 고르기, 불필요한 단계와 계산 피하기, 알맞은 설계 최적화 | 훨씬 중요 |

- 기존 코드를 최적화하는 일은 대개 나쁜 알고리즘이나 자료 구조를 더 나은 것으로 바꾸는 일

### 두 종류의 프로그램

- 효율은 모든 분야에서 중요하지만, 극도의 효율이 필요한 프로그램은 일부: 시스템 소프트웨어, 임베디드 시스템, 계산이 많은 응용, 실시간 게임
- 대부분은 그렇지 않음. 그런 고성능 프로그램을 쓰지 않는다면 마지막 한 방울의 속도까지 짜낼 필요는 거의 없음
  - 가족용 차와 경주용 차의 차이. 모든 차가 적당히 효율적이어야 하지만, 시속 110km를 넘지 않을 가족용 차를 속도 최적화하느라 시간을 쓰지는 않음

### C++는 비효율적인 언어인가?

- C 프로그래머 중에는 C++가 예외, 가상 함수 같은 높은 수준 기능 때문에 C보다 본래 느리다고 보는 사람이 있음. 이 주장에는 문제가 있음
- **컴파일러를 빼고 말할 수 없음**
  - 컴퓨터가 실행하는 것은 내가 쓴 코드가 아니라 컴파일러가 최적화하며 번역한 기계어
  - C와 C++ 벤치마크를 비교하면 언어가 아니라 각 컴파일러의 최적화를 비교하는 셈
  - C++ 컴파일러는 많은 높은 수준 구조를 최적화해 비슷한 C 프로그램만큼, 또는 그보다 나은 기계어를 만들 수 있음. 요즘은 C++ 컴파일러에 더 많은 연구 개발이 들어감
- **가상 함수**는 vtable과 실행 중 한 단계 간접 호출이 필요해 일반 호출보다 느릴 수 있음(10장)
  - 그러나 가상 호출은 호출만이 아니라 **실행 중에 어느 함수를 부를지 고르는** 일까지 함. 같은 일을 비가상으로 하려면 조건문이 필요함
  - 그 기능이 필요 없으면 비가상 함수를 쓰면 됨
- C++의 설계 원칙: **쓰지 않는 기능에는 비용을 치르지 않는다** (zero-overhead)
  - 가상 함수를 쓰지 않으면 쓸 수 있다는 사실 때문에 손해 보지 않음. 비가상 호출은 C 함수 호출과 성능이 같음
- 더 중요한 점: 높은 수준 기능 덕분에 설계 수준에서 더 효율적이고, 읽기 쉽고, 유지 보수하기 쉽고, 쓸모없는 코드가 쌓이지 않는 프로그램을 쓸 수 있음
- C#, Java는 가상 머신 위에서 돌지만, C++ 코드는 CPU가 직접 실행함. 하드웨어에 가까워 대부분 더 빠름

## 언어 수준의 효율

- 언어 수준의 요령은 중요하고 경우에 따라 속도를 높이지만, 전체 설계와 알고리즘 선택보다 훨씬 덜 중요함
  - 참조로 전달을 아무리 해도, 디스크 쓰기를 필요한 것의 두 배로 하면 빨라지지 않음. 참조와 포인터에 빠져 큰 그림을 놓치기 쉬움
- 좋은 최적화 컴파일러는 이런 요령 중 일부를 알아서 해 줌
- 경험칙: **프로파일러**(3편)가 병목이라고 짚어 주지 않은 곳을 최적화하느라 시간을 쓰지 않음
- 그렇지만 참조로 전달 같은 일부는 그냥 **좋은 코딩 스타일**

:::caution
언어 수준 최적화는 신중하게 한다. 먼저 깔끔하고 구조가 좋은 설계와 구현을 만들고, 프로파일러를 돌려, 병목으로 표시된 부분만 최적화에 시간을 쓴다.
:::

### 객체를 효율적으로 다루기

- C++는 특히 객체에 대해 뒤에서 많은 일을 함. 내가 쓴 코드의 성능 영향을 늘 의식함
- 아래 지침은 객체에만 해당함. `bool`, `int`, `double` 같은 기본 타입에는 해당하지 않음

#### 값으로 전달할까, 참조로 전달할까

- 규칙(1장, 9장): 함수가 **어차피 복사할** 매개변수이고 그 타입이 이동을 지원하면 값으로, 아니면 `const` 참조로
- 값으로 전달할 때 주의할 점
  - 파생 객체를 기반 타입 매개변수에 값으로 넘기면 **슬라이싱**되어 정보를 잃음(10장)
  - 참조라면 없을 복사 비용이 듦
- 예: 이름 문자열 둘과 나이를 가진 `Person`

```cpp
void process_person(Person p);          // 값으로
void process_person(const Person& p);   // const 참조로
```

- 부르는 코드는 똑같지만 값으로 받으면
  - 들어갈 때: `p`를 만들려고 복사 생성자가 불림. 직접 쓰지 않았어도 컴파일러가 만든 복사 생성자가 멤버를 하나씩 복사함. 문자열 둘도 각자 복사 생성자를 부름
  - 나갈 때: 지역 변수 `p`가 소멸함. `Person` 소멸자와 문자열 소멸자 둘이 불림
- 참조로 받으면 이런 비용이 전혀 없음
- 함수가 객체를 **고쳐야** 하면 비 `const` 참조로. 고치지 않으면 값 또는 `const` 참조로
- 포인터로 전달은 참조로 전달의 낡은 방식. C의 잔재라 C++에서는 드묾(설계에서 `nullptr`가 의미 있을 때만)

#### 값으로 반환할까, 참조로 반환할까

- 불필요한 복사를 피하려고 참조로 반환할 수 있지만, 늘 가능하지는 않음. 예: 오버로드한 `operator+`는 새 객체를 돌려줘야 함
- 함수가 끝나면 사라질 **지역 객체의 참조나 포인터는 절대 돌려주지 않음**
- 값으로 반환하는 것은 대개 괜찮음: 의무적·선택적 **복사 생략** (copy elision)과 이동 의미론이 최적화해 줌(9장) <CppRef path="cpp/language/copy_elision" />

#### 예외는 참조로 잡기

- 슬라이싱과 불필요한 복사를 피함(14장)
- 예외를 던지는 것 자체가 무거우므로 작은 개선도 도움이 됨

#### 이동 의미론 지원하기

- 클래스가 이동 생성자와 이동 대입을 지원하게 함(9장)
  - **0의 규칙**: 컴파일러가 만드는 복사·이동 멤버로 충분하게 설계
  - 컴파일러가 암묵적으로 만들 수 없으면 `= default`로 명시해 봄. 그것도 안 되면 직접 구현
- 이동이 되면 많은 연산, 특히 표준 라이브러리 컨테이너와 알고리즘이 훨씬 효율적이 됨

#### 임시 객체 줄이기

- 컴파일러는 여러 상황에서 이름 없는 **임시 객체** (temporary object)를 만듦
- `explicit`이 아닌 변환 생성자가 있으면 다른 타입 값으로 그 클래스의 연산이나 함수를 부를 수 있음 <CppRef path="cpp/language/converting_constructor" />

```cpp
class Book {
public:
    Book(double price);   // explicit 아님
};
void show(const Book& b);

show(19.9);   // double에서 임시 Book을 만들어 넘기고, 끝나면 소멸
```

- 일반적으로 한 타입의 값을 다른 타입으로 바꿔 더 큰 식에 쓸 때 임시 객체가 생김. 주로 함수 호출에서
  - `const`를 빼면 상수를 넘길 수 없음. lvalue가 필요함
- 임시 객체를 만들 수밖에 없는 상황도 있지만, 적어도 이런 일이 있다는 것을 알아야 성능 측정 결과에 놀라지 않음
- 이동 의미론이 임시 객체를 다루는 비용을 줄여 줌. 이동을 지원할 또 하나의 이유

### 메모리 미리 할당하기

- 표준 컨테이너는 메모리 관리를 알아서 해 주고 원소를 넣으면 자동으로 자람. 그런데 이것이 성능 비용이 될 수 있음
- `std::vector`는 원소를 메모리에 **연속으로** 저장함. 자라야 하면 새 블록을 할당하고 모든 원소를 옮겨(또는 복사해) 담음
  - 반복문에서 `push_back()`으로 원소 수백만 개를 넣으면 큰 비용
- 넣을 개수를 미리 알거나 대략 짐작하면 시작 전에 충분히 할당해 둠
  - **용량** (capacity): 재할당 없이 넣을 수 있는 원소 수. **크기** (size): 실제 원소 수
  - `reserve()`로 용량을 늘리거나 `resize()`로 크기를 바꿈(18장) <CppRef path="cpp/container/vector/reserve" />

### inline 함수

- 어떤 컴파일러는 `inline`을 그 함수를 더 적극적으로 최적화하라는 **힌트**로 씀(특히 낮은 최적화 수준에서) <CppRef path="cpp/language/inline" />
- 작은 함수가 병목이면 `inline`을 붙여 봄
- 남용하지 않음: 인터페이스를 바꾸지 않고 구현을 발전시킬 수 있도록 둘을 분리한다는 설계 원칙을 버리게 됨

### 도달할 수 없는 코드 표시하기 <Badge text="C++23" />

- `<utility>`의 `std::unreachable()`: 이 위치에는 절대 오지 않는다고 컴파일러에게 알려 더 잘 최적화하게 함 <CppRef path="cpp/utility/unreachable" />
- 예: 매개변수가 0, 1, 2, 3 중 하나만 온다는 것을 프로그래머는 알지만, 컴파일러에게는 그냥 `int`

```cpp
int code_to_points(int code)   // 0~3만 들어온다고 약속
{
    switch (code) {
    case 0: return 10;
    case 1: return 20;
    case 2: return 30;
    case 3: return 40;
    default: std::unreachable();
    }
}
```

- `default`가 없으면 컴파일러는 값이 0~3인지 확인하는 코드를 만들어야 함(그 밖이면 `switch` 다음으로 감)
- `default`에서 `unreachable()`을 부르면 그 확인을 빼고 바로 알맞은 `case`로 뛸 수 있음. 빡빡한 반복문에서 성능이 좋아질 수 있음
- 실행 중 실제로 `unreachable()`에 닿으면 **정의되지 않은 동작**. 위 함수에 8을 넘기면 컴파일러가 무엇을 해도 됨

## 헷갈리기 쉬운 점

- 성능 문제는 대개 값 대신 참조로 넘기면 풀린다?
  - 언어 수준은 어느 정도까지만. 큰 차이는 알고리즘과 설계에서 남
- 짐작 가는 곳부터 최적화한다?
  - 프로파일러가 병목이라고 한 곳만
- 가상 함수가 있어서 C++는 C보다 느리다?
  - 쓰지 않으면 비용이 없음. 쓰면 실행 중 선택이라는 일을 더 하는 것
- 값으로 반환하면 늘 복사된다?
  - 복사 생략과 이동으로 대개 비용이 거의 없음
- `std::unreachable()`은 거기 오면 프로그램을 안전하게 멈춘다?
  - 정의되지 않은 동작. 정말로 오지 않을 때만 씀
- `int`도 `const int&`로 넘기는 게 빠르다?
  - 기본 타입은 값으로. 참조는 오히려 간접 접근이 생김

## 정리

| 지침 | 이유 |
| --- | --- |
| 객체는 `const` 참조로(어차피 복사할 이동 가능 타입은 값으로) | 복사·소멸 비용, 슬라이싱 |
| 값으로 반환 | 복사 생략과 이동. 지역 객체 참조 반환 금지 |
| 예외는 참조로 catch | 슬라이싱과 복사 |
| 이동 지원, 0의 규칙 | 컨테이너와 알고리즘이 효율적 |
| 임시 객체 의식하기 | 변환 생성자가 숨은 생성·소멸을 만듦 |
| `reserve()` | 재할당과 원소 옮기기 |
| `inline` | 작은 병목 함수의 힌트. 남용 금지 |
| `std::unreachable()` | 검사 생략 최적화. 닿으면 UB |

## 복습 질문

<details>
<summary>`void log_all(std::vector<std::string> lines)`가 실제로는 내용을 읽기만 한다. 무엇을 바꾸는가?</summary>

- `const std::vector<std::string>&`로 받음. 값으로 받으면 부를 때마다 벡터와 모든 문자열을 복사하고, 끝날 때 모두 소멸시킴

</details>

<details>
<summary>파일에서 줄 수를 먼저 세고 나서 각 줄을 `vector`에 넣는다면 무엇을 할 수 있는가?</summary>

- 센 줄 수로 `reserve()`를 먼저 불러, 넣는 동안 재할당과 원소 옮기기가 일어나지 않게 함

</details>

<details>
<summary>`Book(double)` 생성자 때문에 생기는 숨은 임시 객체를 막으려면?</summary>

- 생성자에 `explicit`을 붙여 암묵 변환을 막음. 그러면 `show(19.9)`는 컴파일 오류가 되고, 부르는 쪽이 `show(Book{ 19.9 })`처럼 의도를 드러내야 함

</details>
