- 다루는 것: 참조로 전달 같은 언어 세부보다 성능에 훨씬 큰 영향을 주는 설계 선택
- 이 글에서 배우는 것: 알고리즘 선택, 라이브러리와 멀티스레딩, **캐시**, **객체 풀**

## 알고리즘이 먼저

- 핵심 작업에 O(n)으로 될 일을 O(n<sup>2</sup>) 알고리즘으로 하면, 필요한 연산 수의 **제곱**을 하게 됨
  - O(n)이면 1,000번으로 끝날 일이 O(n<sup>2</sup>)이면 1,000,000번
  - 그 연산 하나를 언어 수준에서 아무리 다듬어도, 1000배 많은 연산을 하는 사실은 바뀌지 않음
- 알고리즘은 늘 신중히 고름. 빅오 표기와 알고리즘 선택은 4장 참고
- 그 밖의 설계 수준 요령
  - 자료 구조와 알고리즘을 직접 쓰기보다 **기존 것**을 씀: 표준 라이브러리, Boost 등. 전문가가 썼고 널리 쓰여 버그 대부분이 이미 발견되고 고쳐짐
  - **멀티스레딩**을 설계에 넣어 기계의 모든 처리 능력을 씀(27장)
- 이 글은 두 기법을 더 봄: 캐시, 객체 풀

## 필요한 곳에 캐시

- **캐시** (cache): 나중에 쓰려고 값을 저장해 두어, 다시 가져오거나 다시 계산하지 않게 함
- 하드웨어에서 온 원리: 프로세서의 메모리 캐시는 최근에, 자주 접근한 값을 주 메모리보다 빠른 곳에 둠. 접근한 메모리는 대개 짧은 시간 안에 다시 접근되므로 계산이 크게 빨라짐
- 소프트웨어도 같음: 특히 느린 작업은 필요 이상 하지 않음. 처음 할 때 결과를 메모리에 두고 다음에 씀
- 대개 느린 작업

| 작업 | 요령 |
| --- | --- |
| 디스크 접근 | 같은 파일을 여러 번 열고 읽지 않음. 메모리가 있고 자주 쓰면 내용을 RAM에 둠 |
| 네트워크 통신 | 네트워크의 변덕에 휘둘림. 파일처럼 다루고, 바뀌지 않는 정보는 최대한 캐시 |
| 수학 계산 | 복잡한 계산 결과를 여러 곳에서 쓰면 한 번 계산해 공유. 단순한 계산은 캐시에서 꺼내는 것보다 다시 계산이 빠를 수 있음. 프로파일러로 확인 |
| 객체 할당 | 짧게 사는 객체를 많이 만들면 객체 풀(아래) |
| 스레드 생성 | 느림. 스레드 풀(27장)로 스레드를 "캐시" |

### 캐시 무효화

- 캐시에 둔 것은 대개 원본의 **사본**. 캐시가 사는 동안 원본이 바뀔 수 있음
  - 예: 설정 파일을 캐시했는데 프로그램이 도는 동안 사용자가 파일을 고치면 캐시가 낡음
- **캐시 무효화** (cache invalidation): 원본이 바뀌면 캐시를 그만 쓰거나 다시 채움
  - 원본 관리자에게 바뀔 때마다 알려 달라고 요청함. 예: 프로그램이 등록한 콜백으로
  - 또는 프로그램이 특정 사건을 주기적으로 확인(폴링)해 캐시를 다시 채움
  - 어떤 방법이든 캐시에 기대기 **전에** 이 문제를 생각해 둠

### 인터페이스 뒤에 숨기기

- 자료 구조에 캐시를 넣을 때 그 세부를 공개 인터페이스에서 숨김. 클라이언트는 캐시가 있는지 몰라야 함
- 그러면 인터페이스를 건드리지 않고 캐시 방식을 바꿀 수 있음
- `const` 멤버 함수 안에서 캐시를 채우려면 캐시 멤버를 `mutable`로 둠(9장). 겉으로 보이는 상태는 바뀌지 않으므로

```cpp
class Prices {
public:
    int get(const std::string& key) const;   // 캐시가 있는지 드러나지 않음
private:
    mutable std::map<std::string, int> m_cache;
    mutable int m_seenVersion{ 0 };          // 원본 버전이 다르면 비움
};
```

:::caution
캐시를 유지하는 데는 코드, 메모리, 처리 시간이 든다. 미묘한 버그의 원인도 된다. 프로파일러가 그곳이 병목임을 분명히 보여 줄 때만 캐시를 넣는다. 먼저 깔끔하고 올바른 코드를 쓰고, 프로파일링하고, 그다음에 최적화한다.
:::

## 객체 풀

- **객체 풀** (object pool)에는 여러 종류가 있음. 여기서 볼 것: 큰 메모리 덩어리를 **한 번에** 할당하고, 그 안에 작은 객체들을 제자리에 만듦
  - 클라이언트에게 객체를 내주고, 다 쓰면 돌려받아 다시 씀
  - 객체 하나하나마다 메모리 관리자를 불러 할당·해제하지 않음
- 효과가 큰 경우: **큰 데이터 멤버**를 가진 객체를 짧게 많이 쓸 때. 특정 상황에 맞는지는 프로파일링으로만 판단할 수 있음

- 빈 칸이 없으면 덩어리를 하나 더 받음. 풀은 자라기만 하고, 풀이 소멸할 때 모든 덩어리를 해제함
- **풀이 내준 모든 객체보다 오래 살아야** 함. 삭제자가 풀을 가리키기 때문
- 표준 `vector`를 동기화 없이 쓰므로 스레드에 안전하지 않음. 필요하면 27장처럼 뮤텍스로 보호

### 쓰이는 도구

- `std::allocator<T>::allocate(n)`: T n개 크기의 **초기화되지 않은** 메모리. `deallocate(p, n)`으로 돌려줌 <CppRef path="cpp/memory/allocator" />
- **placement new** `::new (주소) T(인수...)`: 이미 있는 메모리에 객체를 생성. 메모리를 할당하지 않음 <CppRef path="cpp/language/new" />
  - 인수는 `std::forward`로 생성자에 완벽 전달(26장)
  - new 식이 돌려준 포인터를 씀. 원래 칸 포인터로 새 객체에 접근해야 하고 T에 `const`나 참조 멤버가 있다면 `std::launder()`<Badge text="C++17" />가 필요함 <CppRef path="cpp/utility/launder" />
- `std::destroy_at(p)` <Badge text="C++17" />: 메모리는 두고 소멸자만 부름 <CppRef path="cpp/memory/destroy_at" />
- 커스텀 삭제자가 달린 `std::unique_ptr<T, Returner>`: 스코프를 벗어나면 `delete` 대신 삭제자가 불려 칸이 풀로 돌아감 <CppRef path="cpp/memory/unique_ptr" />
  - 여러 곳에서 객체를 함께 가져야 하면 삭제자를 단 `shared_ptr`로 내주는 방법도 있음

```cpp
template <typename... Args>
Handle acquire(Args&&... args)
{
    if (m_free.empty()) { add_chunk(); }
    T* slot{ m_free.back() };
    T* obj{ ::new (slot) T(std::forward<Args>(args)...) };
    m_free.pop_back();
    return Handle{ obj, Returner{ this } };
}
```

## 이전 표준에서는

| 이 글에서 쓴 것 | 들어온 표준 | 그 이전에는 |
| --- | --- | --- |
| `std::destroy_at` | C++17 | `p->~T()`로 소멸자를 직접 호출 |

## 헷갈리기 쉬운 점

- 캐시는 많을수록 좋다?
  - 코드, 메모리, 시간이 들고 무효화 버그의 원인. 병목에만
- 단순한 계산도 캐시하면 빨라진다?
  - 캐시를 찾는 비용이 다시 계산하는 비용보다 클 수 있음
- 풀에서 돌려받을 때 메모리를 해제한다?
  - 소멸자만 부르고 칸은 풀에 남겨 다시 씀. 메모리 해제는 풀이 소멸할 때
- 풀은 늘 `new`/`delete`보다 빠르다?
  - 할당자와 최적화에 따라 차이가 없을 수도 있음. 측정해야 앎
- 풀이 먼저 소멸해도 객체는 괜찮다?
  - 삭제자가 사라진 풀을 건드리게 됨. 풀이 더 오래 살아야 함

## 정리

| 요소 | 핵심 |
| --- | --- |
| 알고리즘 | 가장 큰 효과. O(n<sup>2</sup>) → O(n) |
| 라이브러리 | 검증된 표준, Boost |
| 멀티스레딩 | 모든 코어 활용 |
| 캐시 | 느린 작업 결과 저장. 무효화 필요. 인터페이스 뒤에 숨김, `mutable` |
| 객체 풀 | 덩어리 한 번 할당, placement new로 생성, 삭제자가 칸 반환 |
| 원칙 | 프로파일러가 병목을 보여 줄 때만 |

<details>
<summary>풀의 삭제자에서 `delete p`를 부르면 무슨 문제가 생기는가?</summary>

- `p`는 `new`로 따로 할당한 것이 아니라 덩어리 안의 한 칸. `delete`는 그 주소를 해제하려 해 정의되지 않은 동작이 됨. 소멸자만 부르고(`destroy_at`) 칸을 목록에 돌려놓아야 함

</details>

<details>
<summary>`add_chunk()`에서 생성자를 부르지 않는 이유는?</summary>

- 덩어리는 아직 쓰지 않을 칸들의 저장 공간일 뿐. 실제로 내줄 때 `acquire()`가 placement new로 원하는 인수로 생성함. 미리 생성하면 기본 생성자가 필요하고 쓰지 않을 객체까지 만드는 비용이 듦

</details>
