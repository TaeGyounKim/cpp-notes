## 왜 프로파일링인가

- 설계하고 코딩하면서 효율을 생각하는 것은 좋음. 상식과 경험으로 피할 수 있는 뻔한 비효율은 피함
- 그러나 설계·코딩 단계에서 성능에 **집착하지는** 않음
  - 먼저 깔끔하고 구조가 좋은 설계와 구현을 만들고, 프로파일러를 돌려, 병목으로 표시된 곳만 최적화
- **90/10 규칙**(4장): 대부분의 프로그램은 실행 시간의 90%를 코드의 10%에서 씀
  - 코드의 90%를 최적화해도 실행 시간은 10%밖에 줄지 않을 수 있음
  - 예상하는 실제 작업량에서 **가장 많이 실행되는** 부분을 최적화해야 함
- **프로파일러** (profiler): 프로그램이 도는 동안 분석해 성능 데이터를 만드는 도구
  - 대부분 함수 단위로, 각 함수에서 쓴 시간(또는 전체 대비 비율)을 보여 줌
  - 돌려 보면 어디를 최적화해야 하는지 대개 바로 보임
- 최적화 **전과 후** 모두 프로파일링함. 최적화가 실제로 효과가 있었음을 증명하려면 필수

| 환경 | 도구 |

## 예: 태그 빈도 세기

- 상황: 로그에서 모은 태그 수십만 개(중복이 아주 많음)를 읽어, 태그별 개수와 순위를 묻는 메모리 내 데이터베이스를 만듦
- 아래의 성능 문제는 일부러 뻔하게 만든 것. 실제 문제는 대개 더 미묘하지만, 그것을 보일 프로그램은 너무 길어짐

### 1차 설계: vector에서 선형 탐색

- `vector<pair<string, int>>`에 (태그, 개수)를 둠
- 태그를 하나 읽을 때마다
  - 이미 있는지 처음부터 끝까지 찾고(`exists`)
  - 있으면 다시 처음부터 찾아 개수를 늘림(`increment`)
  - 없으면 끝에 추가

```cpp
for (const auto& tag : input) {
    if (exists(tag)) { increment(tag); }   // 선형 탐색을 두 번
    else { add(tag); }
}
```

- 태그가 수십만 개면 선형 탐색이 많아져 느려짐. 이미 눈치챘을 수도 있지만, 프로파일러로 확인해 봄

- 보고서는 두 부분
  - **플랫 프로파일** (flat profile): 함수마다 자기 자신이 실행된 시간
  - **호출 그래프** (call graph): 함수와 그 함수가 부른 **자손**까지 포함한 시간. 이쪽이 더 쓸모 있음
- 호출 그래프의 열

| 열 | 뜻 |
| --- | --- |
| index | 호출 그래프 안 항목 번호. 이름 뒤 `[n]`은 다른 항목을 가리킴 |
| %time | 이 함수와 자손이 전체 실행 시간에서 차지한 비율 |
| self | 함수 자신이 실행된 초 |
| children | 자손이 실행된 초 |
| called | 호출 횟수(`부른 횟수/전체 횟수`) |
| name | 함수 이름 |

- 읽는 법(숫자는 기계마다 다름)
  - `main` 항목: 전체가 예를 들어 10초. 그 아래 자손 중 데이터베이스 생성자가 9.9초를 차지 → 문제는 생성자
  - 생성자의 `[n]` 항목으로 감: 자손 중 `exists`와 `increment`가 시간 대부분을 차지하고, 둘의 **호출 횟수가 거의 같음**
- 여기서 바로 알 수 있는 것
  - 수십만 개 입력에 몇 초씩 걸리면 느림. 더 나은 자료 구조가 필요
  - `exists`와 `increment`의 시간과 호출 수가 비슷함. 입력이 대부분 중복이므로 `exists` 호출 뒤에는 거의 늘 `increment`가 불리기 때문. 두 함수는 하는 일(탐색)이 같으니 **합칠 수 있음**
  - 시간 대부분이 탐색. 정렬된 자료 구조로 탐색 시간을 줄여야 함

### 2차 설계: map

- `map`은 키를 정렬해 두고 O(log n)으로 찾음. `vector`의 O(n) 선형 탐색 대신(18장)
- 탐색을 한 번만: `operator[]`는 키가 없으면 값을 0으로 초기화한 항목을 넣고 그 참조를 돌려줌 <CppRef path="cpp/container/map/operator_at" />

```cpp
std::map<std::string, int> counts;
for (const auto& tag : input) {
    ++counts[tag];   // 있으면 1 늘리고, 없으면 0으로 넣고 1 늘림
}
```

- 다시 프로파일링하면 생성자 시간이 수십 배 줄어듦. 너무 빨라져서 보고서에 내 함수보다 `map` 내부 함수가 더 많이 보이기도 함
- 더 해 볼 것
  - `std::unordered_map`<Badge text="C++11" />은 평균 O(1) 탐색. 이 작업에서 `map`보다 빠른지 프로파일링으로 확인 <CppRef path="cpp/container/unordered_map" />
  - 순위 조회가 여전히 모든 항목을 도는 선형 작업이라면, 그것을 피할 자료 구조도 생각해 봄(예: 개수가 바뀌지 않는다면 한 번 정렬해 순위를 미리 계산)

### Visual Studio 프로파일러

- 그래픽 사용자 인터페이스를 갖춘 내장 프로파일러
- 순서
  - 프로젝트를 열고 구성을 **Release**로(Debug는 최적화가 꺼져 결과가 왜곡됨)
  - Debug 메뉴 → Performance Profiler
  - 도구를 고르고 Start
- 도구 두 가지

| 도구 | 특징 |
| --- | --- |
| **CPU 사용량** (CPU Usage) | 표본 추출 방식. 오버헤드가 작아 대상 프로그램에 영향이 적음. 먼저 이것으로 병목을 봄 |
| **계측** (Instrumentation) | 코드를 덧붙여 호출 횟수와 각 호출 시간을 정확히 셈. 오버헤드가 큼. CPU 사용량으로 정보가 부족할 때 |

- 실행이 끝나면 보고서가 열리고 **핫 패스** (hot path, 시간을 가장 많이 쓴 호출 경로)가 바로 보임
- 함수를 누르면 드릴다운 보기: 위에는 핫 패스, 아래에는 실제 코드와 줄마다 실행 시간 비율. 시간이 많이 든 줄은 붉은 색조로 표시됨
  - 1차 설계라면 `exists`와 `increment` 줄이 비슷하게 붉게 보임

## 코드 안에서 재기

- 프로파일러보다 거칠지만(어디를 잴지 내가 정해야 함), 전후 비교에는 충분함

## 헷갈리기 쉬운 점

- 코드를 많이 최적화할수록 빨라진다?
  - 90/10 규칙. 많이 실행되는 10%가 아니면 효과가 작음
- 최적화 후에는 다시 잴 필요가 없다?
  - 전후를 모두 재야 효과가 있었는지 앎
- Debug 빌드로 프로파일링해도 된다?
  - 최적화가 꺼져 실제와 다른 곳이 병목으로 보일 수 있음. Release로
- 계측 도구가 늘 더 정확하니 먼저 쓴다?
  - 오버헤드가 커서 측정이 왜곡될 수 있음. 표본 추출(CPU 사용량)부터
- `map`의 `operator[]`는 조회만 한다?
  - 키가 없으면 항목을 **넣음**. 조회만 하려면 `find()`나 `contains()`<Badge text="C++20" />

## 정리

| 요소 | 핵심 |
| --- | --- |
| 원칙 | 깔끔하게 먼저, 그다음 프로파일링, 병목만 최적화. 전후 측정 |
| 90/10 | 실행 시간 대부분은 코드 일부에서 |
| gprof | `-pg`로 컴파일, 실행해 `gmon.out`, `gprof`로 보고서. 호출 그래프에서 자손 시간 추적 |
| Visual Studio | Release, Performance Profiler. CPU 사용량 먼저, 필요하면 계측. 핫 패스와 줄별 시간 |
| 고친 방법 | 선형 탐색 → `map`(O(log n)) → `unordered_map`(평균 O(1)), 탐색 두 번을 한 번으로 |
