- 다루는 것: 단위 테스트는 버그에 맞서는 가장 좋은 첫 방어선이지만 더 큰 테스트 과정의 일부일 뿐

## 퍼징

- **퍼징** (fuzzing, fuzz testing): **퍼저** (fuzzer)가 프로그램이나 구성 요소에 넣을 입력을 무작위로 자동 생성해, 처리하지 못한 경계 조건을 찾음
- 보통 입력이 어떤 구조여야 하는지 **규칙** (recipe)을 줌
  - 구조가 뻔히 틀린 입력은 입력 파서가 바로 거부하므로 소용이 적음
  - 퍼저의 일: 바로 거부되지 않을 만큼은 그럴듯하지만, 실행이 더 진행된 뒤 잘못된 논리를 건드릴 입력을 만드는 것
- 무작위라서 입력 공간 전체를 덮으려면 자원이 많이 듦. 클라우드에서 돌리기도 함
- 도구: [libFuzzer](https://llvm.org/docs/LibFuzzer.html), [honggfuzz](https://github.com/google/honggfuzz), [AFL++](https://github.com/AFLplusplus/AFLplusplus)
  - 실제 퍼저는 코드 커버리지를 보며 새 경로를 여는 입력을 골라 변형해 나감(무작위보다 훨씬 효율적)
  - 메모리 오류 검사기(주소 새니타이저 등)와 함께 돌려, 겉으로 드러나지 않는 범위 밖 접근도 잡음
- 시드(seed)를 기록해 두면 실패한 입력을 다시 만들 수 있음

## 상위 수준 테스트

- 단위 테스트가 좁은 범위를 본다면, 상위 수준 테스트는 **조각들이 함께** 어떻게 동작하는지 봄
- 무엇을 써야 할지 덜 분명해서 쓰기가 더 어려움. 그래도 조각들이 함께 동작함을 시험하기 전에는 프로그램이 동작한다고 말할 수 없음

### 통합 테스트

- **통합 테스트** (integration test): 구성 요소가 **만나는 곳**을 시험. 보통 클래스 둘 이상이 관여함
  - 서로 다른 프로그래머가 쓴 두 구성 요소의 상호 작용을 시험하는 데 뛰어남
  - 쓰는 과정에서 설계 사이의 중요한 불일치가 드러나기도 함
- 정해진 규칙은 없음. 예를 보며 감을 익힘

| 상황 | 통합 테스트 |
| --- | --- |
| **JSON 직렬화 + 파일 API**: 객체를 JSON으로 바꾸는 층이 파일 API 위에 있음. 둘 다 단위 테스트는 충분히 됨 | 객체를 JSON 층으로 디스크에 저장했다가 다시 읽어 원본과 비교 |
| **공유 자원의 읽는 쪽과 쓰는 쪽**: 주식 거래 프로그램의 매수·매도 요청 큐. 요청 받는 쪽이 넣고 거래하는 쪽이 꺼냄 | 큐만 아무리 단위 테스트해도 실제 사용자와 써 보기 전엔 가정이 맞는지 모름. 실제 두 구성 요소를 클라이언트로 써서 주문이 들어갔다 나오는지 확인 |
| **외부 라이브러리 래퍼**: 데이터베이스 연결 라이브러리에 연결 캐시나 더 편한 인터페이스를 더한 객체 지향 래퍼 | 래퍼가 원래 라이브러리를 잘못 쓰지 않는지. 래퍼는 좋지만 버그를 들여오는 래퍼는 재앙 |

- 단위 테스트와의 경계는 흐림. 단위 테스트가 다른 구성 요소를 건드리면 통합 테스트인가?
  - 좋은 테스트는 종류와 상관없이 좋은 테스트. 두 개념은 테스트의 두 **접근법**으로 쓰고, 테스트마다 꼬리표 붙이기에 매달리지 않음
- 통합 테스트도 대개 단위 테스트 프레임워크로 씀. 프레임워크 입장에서는 같은 예/아니요 테스트
- 그래도 성능이나 조직상의 이유로 나누기도 함
  - 예: 체크인 전에는 통합 테스트를 반드시 돌리고, 관련 없는 단위 테스트는 조금 느슨하게
  - 나누면 결과의 가치도 올라감: JSON 클래스 테스트가 실패하면 그 클래스의 버그이지 파일 API와의 상호 작용 문제가 아님이 분명함

### 시스템 테스트

- **시스템 테스트** (system test): 통합 테스트보다 높은 수준에서 프로그램을 **전체로** 시험
- 사람이 프로그램을 쓰는 것을 흉내 내는 **가상 사용자**를 자주 씀. 할 동작을 스크립트로 정해 둠. 스크립트나 고정된 입력과 기대 출력에 기대는 테스트도 있음
- 개별 시스템 테스트도 특정한 것을 시험하고 특정 결과를 기대함. 여러 기능이 **함께** 동작하는지 확인하는 데 흔히 씀
  - 이론상 모든 기능의 모든 순열을 시험해야 하지만 금세 감당할 수 없게 됨. 그래도 많은 조합을 시험하려 애씀
  - 예: 그래픽 프로그램에서 이미지를 가져와 회전하고, 흐림 필터를 걸고, 흑백으로 바꾸고, 저장한 뒤 기대 결과 파일과 비교
- 응용에 따라 크게 다름
  - 사용자 상호 작용 없이 파일을 처리하는 프로그램: 단위·통합 테스트처럼 씀
  - 그래픽 프로그램: 가상 사용자
  - 서버: 네트워크 트래픽을 흉내 내는 스텁 클라이언트
- 핵심: 프로그램의 일부가 아니라 **실제 쓰임**을 시험

### 회귀 테스트

- **회귀 테스트** (regression test): 테스트의 종류라기보다 개념
- 기능이 동작하면 개발자는 내려놓고 계속 동작하리라 가정함. 그러나 새 기능과 다른 변경이 예전에 되던 기능을 깨뜨리곤 함
- 거의 완성되어 동작하는 기능의 확인용으로 둠. 잘 쓴 회귀 테스트는 기능을 깨뜨리는 변경이 들어오면 실패함
- 방식
  - **수동**: QA 테스터가 사용자처럼 지난 출시에서 되던 모든 기능을 차례로 시험. 꼼꼼하면 정확하지만 규모를 키우기 어려움
  - **완전 자동**: 모든 기능을 가상 사용자로 실행. 스크립트 작성이 큰 일이지만 돕는 도구가 있음
  - 중간: **스모크 테스트** (smoke test). 가장 중요한 기능의 일부만 시험해, 무언가 깨졌으면 바로 드러나게 함. 통과하면 더 엄격한 수동·자동 테스트로 이어감
    - 이름은 전자 공학에서 옴: 회로를 조립한 뒤 "꽂고, 켜고, 연기가 나는지 본다". 연기가 나면 설계나 조립이 잘못된 것이고, 어느 부품에서 연기가 났는지 보고 오류를 찾음
- **고친 버그마다 회귀 테스트를 씀**
  - 되풀이되는 버그는 악몽: 무섭고, 또 옴. 엔지니어링 자원 낭비
  - 테스트로 버그가 고쳐졌음을 증명하고, 버그가 돌아오면(변경이 되돌려지거나, 브랜치가 잘못 합쳐지는 등) 경보가 울림
  - 테스트에 원래 **버그 번호**를 적어 두면, 실패했을 때 처음에 어떻게 고쳤는지 바로 찾아 쉽게 고침

## 성공적인 테스트 요령

- **자동 테스트 시스템**을 설계하는 데 시간을 씀. 하루 내내 도는 시스템은 실패를 빨리 찾음. 실패하면 자동으로 이메일을 보내거나 방 한가운데서 소리를 내면 문제가 잘 보임
- **스트레스 테스트**를 잊지 않음. 단위 테스트를 다 통과한 데이터베이스 접근 클래스도 스레드 수십 개가 동시에 쓰면 쓰러질 수 있음. 실제로 만날 가장 극한 조건에서 시험
- **여러 플랫폼**에서, 또는 고객 시스템과 가까운 플랫폼에서 시험. 가상 머신으로 한 기계에서 여러 플랫폼을 돌릴 수 있음
- **결함 주입** (fault injection): 일부러 고장을 넣는 테스트. 예: 읽는 도중 파일을 지우기, 네트워크 작업 중 끊김 흉내
- 버그와 테스트는 붙어 다님. 버그 수정은 회귀 테스트로 증명하고, 테스트 주석에 원래 버그 번호를 적음
- **실패하는 테스트를 지우지 않음**. 동료가 그 버그와 씨름하다 테스트가 사라진 걸 알면 찾아옴

:::caution
가장 중요한 요령: 테스트는 소프트웨어 개발의 일부다. 코딩을 시작하기 전에 이것을 받아들이면, 기능을 다 만든 뒤에도 그것이 동작함을 증명할 일이 남아 있다는 사실에 놀라지 않는다.
:::

## 헷갈리기 쉬운 점

- 퍼징은 아무 바이트나 마구 넣는 것이다?
  - 그러면 대부분 입구에서 거부됨. 구조 규칙과 커버리지를 써서 깊이 들어가는 입력을 만듦
- 단위 테스트가 다 통과하면 통합은 문제없다?
  - 구성 요소 사이의 가정이 어긋날 수 있음. 만나는 곳을 따로 시험
- 회귀 테스트는 출시 직전에만 돌린다?
  - 자동으로 자주 돌려야 깨뜨린 변경을 바로 찾음
- 스모크 테스트를 통과하면 출시해도 된다?
  - 가장 중요한 기능이 "연기 나지 않음"을 볼 뿐. 그다음 더 엄격한 테스트
- 계속 실패하는 테스트는 지워서 결과를 깨끗하게 한다?
  - 실패는 알려진 문제의 표시. 고칠 때까지 남겨 둠

## 정리

| 테스트 | 범위 | 핵심 |
| --- | --- | --- |
| 퍼징 | 입력 | 무작위지만 그럴듯한 입력으로 처리 못 한 경계 조건 찾기. 시드 기록 |
| 통합 | 구성 요소의 경계 | JSON+파일, 공유 큐, 외부 라이브러리 래퍼 |
| 시스템 | 프로그램 전체 | 가상 사용자, 기능 조합, 실제 쓰임 |
| 회귀 | 이미 되던 기능 | 수동·자동·스모크. 고친 버그마다 테스트, 버그 번호 기록 |
| 요령 | — | 자동화, 스트레스, 여러 플랫폼, 결함 주입, 실패 테스트 지우지 않기 |

- 코드의 현재 결과를 기대값으로 삼았을 뿐, 옳음을 증명하지 않음. 실제 평균은 2.5이므로, 정수 나눗셈 버그를 테스트가 굳혀 버림
- 기대값은 코드와 독립적으로 구함: 손 계산, 원소 하나면 그 값, 모두 같으면 그 값, 순서를 바꿔도 같음 같은 성질

</details>

<summary>지난주에 고친 버그가 브랜치 병합 뒤 다시 나타났다. 무엇이 있었다면 바로 알 수 있었는가?</summary>

- 그 버그를 고칠 때 쓴 회귀 테스트. 자동 테스트 시스템이 병합된 빌드에서 돌리면 바로 실패해 알림이 가고, 테스트에 적힌 버그 번호로 지난 수정을 찾아 다시 적용할 수 있음

</details>
