- 다루는 것: 버그를 찾는 유일한 방법은 테스트. 개발자에게 가장 중요한 테스트 중 하나가 단위 테스트
- 이 글에서 배우는 것: 단위 테스트의 이점, 접근법, 과정, 좋은 테스트를 쓰는 지침, 직접 만든 작은 도구로 테스트하기

## 단위 테스트란

- **단위 테스트** (unit test): 클래스나 하위 시스템의 특정 기능을 실행해 보는 코드. 쓸 수 있는 가장 잘게 나눈 테스트
- 이상적으로는 코드가 하는 저수준 작업마다 단위 테스트가 하나 이상 있음
- 예: 덧셈과 곱셈을 하는 수학 라이브러리라면
  - 간단한 덧셈(1+2), 큰 수, 음수, 0 더하기, 교환 법칙
  - 간단한 곱셈, 큰 수, 음수, 0 곱하기, 교환 법칙

### 잘 쓴 단위 테스트가 주는 것

- 기능이 **실제로 동작함을 증명**함. 클래스를 실제로 써 보는 코드가 생기기 전까지 그 동작은 큰 미지수
- 최근 변경이 무언가를 망가뜨리면 **가장 먼저 경고**함. 이 쓰임을 회귀 테스트라 함(3편)
- 개발 과정에 넣으면 문제를 **처음부터** 고치게 됨. 단위 테스트가 실패하면 체크인할 수 없게 하면 바로 해결해야 함
- 다른 코드가 준비되기 전에 **따로 시험**할 수 있음. 처음 배울 때는 전체를 다 쓰고 실행했지만, 전문적인 프로그램은 너무 커서 구성 요소를 분리해 시험해야 함
- **사용 예**가 됨. 동료가 행렬 곱셈 쓰는 법을 물으면 해당 테스트를 보여 주면 됨

## 접근법

- 테스트를 안 쓰거나 엉성하게 쓰지 않는 한 잘못되기 어려움. 테스트가 많을수록 커버리지가 넓고, 버그가 틈으로 빠져나가 "그건 시험 안 해 봤어요"라고 말할 일이 줄어듦
- **테스트를 먼저**(XP, 28장)
  - 요구 사항을 굳히고, 코딩이 끝났는지 판단할 기준이 됨
  - 까다롭고 꾸준함이 필요함. 어떤 사람의 코딩 방식과는 맞지 않음
  - 덜 엄격한 방법: 코딩 전에 테스트를 **설계**만 하고 구현은 나중에. 요구 사항은 이해하되, 아직 없는 클래스를 쓰는 코드는 쓰지 않아도 됨
- **다른 사람이 테스트 쓰기**
  - 자기 코드의 테스트를 쓰면 알고 있는 문제를 무의식적으로 피하거나, 잘 처리하는 경우만 시험할 수 있음. 방금 쓴 코드에서 버그 찾기에 열의가 덜 나기도 함
  - 조율 비용이 크지만, 해내면 더 효과적인 테스트가 됨

### 코드 커버리지

- **코드 커버리지** (code coverage): 단위 테스트가 코드의 얼마만큼을 실행하는지 재는 지표
- 도구가 테스트로 불린 코드의 비율을 알려 줌. 예: [gcov](https://gcc.gnu.org/onlinedocs/gcc/Gcov.html)
- 가능한 모든 경로를 시험하면 100%에 이름
- 도구마다 정의가 다르므로 쓰기 전에 알아봄
  - 한 줄에 쓴 `if`의 본문이 실행되지 않아도 그 줄을 덮었다고 볼까?
  - 템플릿은 어떻게 셀까?
  - 분기의 모든 방향을 확인하는 **분기 커버리지** (branch coverage)를 지원할까?

## 단위 테스트 과정

- 코드를 쓰기 훨씬 전, 설계 단계부터 시작함. 테스트할 수 있는가를 염두에 두면 설계 결정에도 영향이 감
- 테스트를 먼저 쓰지 않더라도 어떤 테스트를 둘지는 설계 단계에서 생각해 둠
  - 일을 잘 정의된 조각으로 나누고, 조각마다 테스트로 확인할 기준을 둠
  - 예: 데이터베이스 접근 클래스라면 삽입을 먼저 만들어 충분히 시험하고, 그다음 수정, 삭제, 조회를 하나씩 시험하며 진행

### 입자 크기 정하기

- 단위 테스트에는 시간이 듦. 마감에 쫓기면 건너뛰고 싶지만 길게 보면 역효과
- **버그는 일찍 찾을수록 싸다**
  - 단위 테스트에서 찾으면 다른 사람이 만나기 전에 바로 고침
  - QA가 찾으면 버그 관리, 개발 팀으로 돌려보내 고치고, 다시 QA가 확인하는 추가 주기가 생김
  - 고객에게까지 가면 훨씬 비쌈
- **입자 크기** (granularity): 테스트의 범위. 데이터베이스 클래스라면

| 큰 입자 | 중간 입자 | 작은 입자 |
| --- | --- | --- |
| 연결, 삽입, 수정, 삭제, 조회 | 연결 끊김, 잘못된 데이터 삽입, 문자열·정수 삽입, 없는 행 삭제, 복잡한 조회 | HTTP로 연결, 서버 바쁨 오류, 넓은 문자 삽입, 큰 데이터 삽입, 권한 없는 삭제, 삭제 후 수정, 중첩 조회 |

- 잘게 갈수록 오류 조건, 다른 입력 집합, 다른 동작 방식을 고려하게 됨
- 처음 결정은 고정이 아님. 개념 증명용이라 몇 개면 충분할 수도, 나중에 쓰임이 바뀔 수도 있음. 예: 국제 문자를 지원하게 되면 그것을 겨냥한 테스트를 더함
- 단위 테스트는 기능 구현의 **일부**
  - 코드를 고치면 테스트가 통과하도록 고치기만 하지 말고, 새 테스트를 쓰고 기존 테스트를 다시 평가함
  - 버그를 찾아 고치면 그 수정을 겨냥한 테스트를 더함(회귀 테스트)

:::caution
단위 테스트는 시험하는 하위 시스템의 일부다. 하위 시스템을 다듬을 때 테스트도 함께 다듬는다.
:::

### 테스트 떠올리기

- 시간이 지나면 무엇을 테스트해야 할지 감이 생김. 시행착오와 동료의 테스트를 보며 얻음
- 그 전까지는 질문으로 아이디어를 냄
  - 이 코드는 무엇을 하려고 썼나?
  - 각 함수는 보통 어떻게 불리나?
  - 부르는 쪽이 어길 수 있는 사전 조건은?
  - 어떻게 잘못 쓰일 수 있나?
  - 어떤 입력을 기대하나? 기대하지 않는 입력은?
  - 경계 조건이나 예외적인 상황은?
- 떠올린 테스트를 **범주**로 묶음: 기본, 오류, 지역화, 잘못된 입력, 복잡한 경우
  - 찾고 보태기 쉽고, 어느 부분이 잘 시험되었고 어디가 모자란지 보임

:::caution
간단한 테스트를 잔뜩 쓰기는 쉽다. 복잡한 경우를 잊지 않는다.
:::

### 기대 결과를 먼저 정하기

- 가장 흔한 함정: 테스트로 코드를 **검증**하지 않고, 테스트를 코드의 **현재 동작에 맞추는** 것
  - 테스트가 실패했을 때 코드를 옳다고 가정하고 테스트를 고치기 쉬움. 대개 틀린 방법
- 예: 키로 텍스트를 암호화하는 코드
  - 모듈을 먼저 돌려 결과를 보고 그럴듯하면 그 값을 기대값으로 적고 싶어짐. 이것은 아무것도 증명하지 못함. 같은 값을 계속 돌려준다는 것만 보장할 뿐
  - 올바른 테스트는 모듈과 **독립적으로** 암호화한 결과가 필요함
  - 알고리즘을 모르면(외부 라이브러리 등) 최소한 성질을 시험함: `decrypt(encrypt(x)) == x`, `encrypt(a) != encrypt(b)`

:::caution
테스트를 처음 실행하기 전에 올바른 출력을 정한다.
:::

### 테스트 쓰기

- 테스트 하나에서 **한 가지만** 시험함. 실패하면 특정 기능을 가리킴
- **구체적으로**: 예외가 나서 실패했는지 값이 틀려서인지 구별되게
- 테스트 코드에 **로그**를 넉넉히. 언젠가 실패했을 때 무슨 일인지 단서가 됨
- 앞 테스트에 **의존하지 않게**. 가능한 한 독립적이고 원자적으로
- 다른 하위 시스템이 필요하면 **스텁** (stub)이나 **목** (mock)으로 흉내 냄
  - 흉내 내는 하위 시스템과 같은 인터페이스를 구현해 그 자리에 씀
  - 예: 데이터베이스가 시험 대상이 아니면 데이터베이스 인터페이스를 구현한 목을 씀. 실제 연결이 필요 없고, 실제 데이터베이스의 버그가 이 테스트에 영향을 주지 않음
  - 실제로는 재현하기 어려운 **오류 조건**도 목으로 흉내 낼 수 있음
- 코드 리뷰어는 코드뿐 아니라 단위 테스트도 리뷰하고, 테스트를 더할 곳을 알려 줌
- 단위 테스트는 대개 작고 단순해서 몇 분이면 씀. 시간 대비 가장 생산적인 일 중 하나

### 테스트 실행

- 쓰자마자 실행함. 통과로 가득한 화면은 코드가 쓸모 있고 (아는 한) 옳다는 정량적 증거
- 테스트를 먼저 쓴다면 쓴 직후 실행해 **처음엔 실패함을** 확인함
  - 코드가 없는데 통과하면 테스트에 문제가 있는 것
  - 코드를 다 썼는데 실패하면 코드가 틀렸거나 테스트가 틀렸거나
- 실행은 **자동화**해야 함
  - 전용 시스템이 지속적 통합 빌드마다, 또는 적어도 매일 밤 모든 테스트를 돌리고 실패하면 이메일로 알림
  - 또는 로컬에서 컴파일할 때마다 실행. 그러려면 테스트가 작고 빨라야 함. 오래 걸리는 테스트는 따로 떼어 전용 시스템에 맡김

## 테스트 프레임워크

- 실무에서는 테스트 등록, 단언(assertion), 결과 보고를 해 주는 프레임워크를 씀
  - [GoogleTest](https://github.com/google/googletest), [Catch2](https://github.com/catchorg/Catch2), [doctest](https://github.com/doctest/doctest), Boost.Test, Visual Studio의 Microsoft 단위 테스트 프레임워크
  - 보통 시험 대상과 테스트 코드는 별도 프로젝트로 나눔
- 공통 요소
  - 테스트를 이름 붙여 **자동으로 찾아** 실행
  - **단언**: 값이 같은지, 참인지, 특정 예외를 던지는지 확인
  - 테스트 묶음마다 **준비와 정리** (setup, teardown)
  - 실패한 단언의 위치와 값을 보고
- 이 사이트의 예제는 한 파일로 돌아가야 하므로, 이 요소들을 갖춘 아주 작은 도구를 직접 만들어 원리를 봄

### 테스트의 모양: AAA

- **AAA**: 준비(Arrange) → 실행(Act) → 확인(Assert). **IF-WHEN-THEN**이라고도 함
- 주석을 `IF`, `WHEN`, `THEN`으로 시작하면 세 단계가 눈에 잘 띔

```cpp
TEST(released_slot_is_reused)
{
    // IF 객체 하나를 받았다가 돌려준 풀에서
    // WHEN 다시 하나를 받으면
    // THEN 같은 칸을 다시 쓴다
}
```

### 부정 테스트

- **부정 테스트** (negative test): 실패해야 하는 일을 해 보는 테스트. 예: 특정 예외를 던지는지 확인
- 예외가 나지 않거나 다른 예외가 나면 실패로 봄

```cpp
check_throws<std::invalid_argument>([&] { pool.acquire(-1); },
                                    "acquire(-1)");
```

### 작은 도구의 구조

- `TEST(name)` 매크로: 함수를 선언하고, 전역 등록 객체로 이름과 함수를 목록에 넣고, 함수 본문을 이어 씀 <CppRef path="cpp/preprocessor/replace" />
- `CHECK(expr)`: 거짓이면 식의 글자와 줄 번호를 담은 예외를 던짐. 줄 번호는 `std::source_location`<Badge text="C++20" />으로 얻음 <CppRef path="cpp/utility/source_location" />
- `run_all()`: 모든 테스트를 돌리며 예외를 잡아 통과/실패/예상 못 한 오류를 구분해 출력하고, 실패가 있으면 0이 아닌 종료 코드를 돌려줌(자동화 도구가 이 값을 봄)

- 시험 대상: 29장 2편의 객체 풀. 도우미 `Probe`는 살아 있는 개수를 세고, 음수를 받으면 던짐
- 볼 것
  - 테스트마다 한 가지: 인수 전달, 주소가 겹치지 않음, 칸 재사용, 덩어리 단위로 자람, 반환 때 소멸자 호출, 생성자 예외 전달(부정 테스트)
  - 부정 테스트는 예외가 난 **뒤에도** 칸을 잃지 않았는지까지 확인함
  - 마지막 테스트는 일부러 틀린 기대값을 넣어, 실패가 어떻게 보고되는지 보여 줌. 종료 코드는 1
- 직접 해 볼 것
  - `acquire()`에서 `m_free.pop_back()`을 생성 **앞으로** 옮기고 실행. `constructor_exception_propagates`가 실패함(예외가 나면 칸을 잃음). 테스트가 버그를 잡는 모습
  - 실패하는 마지막 테스트를 고쳐 모두 통과시키기

## 헷갈리기 쉬운 점

- 테스트가 실패하면 테스트를 코드에 맞게 고친다?
  - 먼저 기대 결과가 옳은지 따짐. 대개 코드를 고쳐야 함
- 프로그램을 돌려 나온 값을 기대값으로 적으면 된다?
  - 지금 동작을 굳힐 뿐 옳음을 증명하지 못함. 독립적으로 구한 값이나 성질(왕복 등)로
- 테스트 하나에 여러 가지를 확인하면 효율적이다?
  - 실패했을 때 무엇이 깨졌는지 모름. 한 테스트에 한 가지
- 테스트끼리 순서에 기대도 된다?
  - 독립적이어야 함. 순서가 바뀌거나 하나만 돌려도 같은 결과
- 커버리지 100%면 버그가 없다?
  - 모든 줄을 실행했다는 뜻일 뿐. 입력 조합과 기대값이 옳아야 함
- 먼저 쓴 테스트가 처음부터 통과하면 좋은 것이다?
  - 아직 코드가 없는데 통과하면 테스트가 잘못된 것

## 정리

| 요소 | 핵심 |
| --- | --- |
| 단위 테스트 | 가장 잘게 나눈 테스트. 동작 증명, 회귀 경고, 분리 시험, 사용 예 |
| 접근법 | 먼저 쓰기(또는 먼저 설계), 다른 사람이 쓰기, 커버리지 측정 |
| 과정 | 입자 크기 → 떠올리기(질문, 범주) → 기대 결과 먼저 → 쓰기 → 실행·자동화 |
| 쓰기 지침 | 한 가지만, 구체적으로, 로그, 독립적으로, 스텁·목 |
| 모양 | AAA(IF-WHEN-THEN), 부정 테스트 |
| 프레임워크 | 자동 발견, 단언, 준비·정리, 실패 위치 보고 |
