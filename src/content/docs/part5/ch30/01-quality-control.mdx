- 다루는 것: 테스트는 개발 과정의 **일부**라는 사실
  - 버그는 가끔 생기는 일이 아님. 규모 있는 프로젝트라면 어디에나 있음
  - 좋은 품질 보증(QA) 팀은 귀하지만 테스트의 짐을 QA에만 지울 수 없음
  - 프로그래머의 책임: 동작하는 코드를 쓰고, 그것이 옳다는 것을 **증명하는 테스트**를 쓰는 것
- 이 글에서 배우는 것: 두 종류의 테스트, 테스트의 책임, 버그의 생명 주기, 버그 추적 도구
- 이 장의 순서: 품질 관리(1편) → 단위 테스트(2편) → 퍼징과 상위 수준 테스트, 성공적인 테스트 요령(3편)

## 화이트박스와 블랙박스

| 종류 | 뜻 | 특징 |
| --- | --- | --- |
| **블랙박스 테스트** (black-box testing) | 구현을 모르고 기능만 시험 | 사용자의 행동을 본뜸. 가장 기본. 예: 버튼을 눌렀는데 아무 일도 없으면 버그 |
| **화이트박스 테스트** (white-box testing) | 프로그램 내부를 알고 시험 | 특정 객체나 하위 시스템을 겨냥해, 코드의 모든 경로를 지나가게 하기 쉬움. 쓰기와 자동화가 대개 더 쉬움 |

- 블랙박스만으로는 다 덮을 수 없음. 요즘 프로그램은 너무 커서 모든 버튼, 모든 입력, 모든 명령 조합을 흉내 낼 수 없음
- 화이트박스는 **테스트 커버리지** (test coverage), 즉 테스트가 코드의 얼마나 많은 부분을 실행하는지를 높이는 데 도움이 됨
- 둘 다 전문적인 품질의 프로젝트에 중요함. 이 장은 프로그래머가 개발 중에 쓸 수 있는 화이트박스 기법에 집중

## 품질 관리

- 큰 프로젝트는 기능을 다 넣었다고 끝나지 않음. 주 개발 단계 중에도, 끝난 뒤에도 찾아 고칠 버그가 늘 있음
- 팀에서 잘 일하려면 품질 관리의 공동 책임과 버그의 생명 주기를 이해해야 함

### 테스트는 누구의 책임인가

- 조직마다 다름
  - 작은 스타트업: 테스트만 하는 사람이 없을 수 있음. 개발자 각자의 몫이거나, 출시 전에 전 직원이 제품을 망가뜨려 보라는 요청을 받기도 함
  - 큰 조직: 전담 QA 직원이 기준에 따라 출시본을 시험해 승인함. 그래도 일부 테스트는 개발자의 몫
- 개발자가 공식 테스트를 맡지 않는 조직이라도, 품질 보증이라는 큰 과정에서 **내 책임이 무엇인지** 알고 있어야 함

### 버그의 생명 주기

- 좋은 엔지니어링 팀은 출시 전후 모두 버그가 생긴다는 것을 인정함. 다루는 방법은 다양함
- 공식적인 과정의 예: 버그는 늘 QA 팀원이 등록함

- 덜 공식적인 과정의 예
  - **누구나** 버그를 등록하고 처음 우선순위와 모듈을 정함
  - 모듈 담당자가 받아들이거나 다른 엔지니어나 모듈로 다시 배정함
  - 고치면 "고침"으로 표시
  - 테스트 단계 끝 무렵 개발자와 QA가 고친 버그를 나눠 맡아 현재 빌드에서 정말 사라졌는지 확인함
  - 모든 버그가 "닫힘"이면 출시 준비 완료

### 버그 추적 도구

- 스프레드시트나 이메일로 하는 비공식 방식부터 비싼 상용 도구까지 다양함. 조직의 크기, 소프트웨어의 성격, 원하는 공식성의 정도에 따라 고름
- 무료 오픈 소스도 많음. 예: [Bugzilla](https://www.bugzilla.org/)(Mozilla 개발자들이 만듦). 요즘은 저장소 호스팅 서비스의 이슈 트래커(GitHub Issues, GitLab Issues)나 Jira도 흔히 씀
- 흔한 기능
  - 버그마다 우선순위, 관련 구성 요소, 상태 등을 설정
  - 새 보고나 변경을 이메일로 알림
  - 버그 사이의 의존 관계 추적, 중복 버그 정리
  - 보고서와 검색
  - 웹에서 등록하고 고치기
- 등록할 때 **심각도** (severity, 얼마나 큰 문제인가), 요약, 설명을 적어 검색하고 보고서로 모을 수 있게 함
- 지금 열린 버그 목록이자, 지난 버그와 그 해결의 **기록 보관소**
  - 예: 지원 엔지니어가 고객이 말한 문제와 비슷한 버그를 찾아, 어느 버전으로 업데이트하면 되는지나 우회 방법을 알려 줌

### 좋은 버그 보고서

- 가능한 한 많은 정보를 담음
  - 재현 단계, 기대한 결과, 실제 결과
  - 버전, 운영체제, 빌드 설정 같은 환경
- 오류 메시지는 스크린숏만 붙이지 말고 **텍스트로도** 그대로 넣음
  - 같은 오류를 만난 다른 사람이 검색으로 내 보고서를 찾을 수 있게

```text
제목: 빈 파일을 열면 편집기가 멈춤
버전: 2.4.1 (Release, Windows 11)
재현:
  1. 크기가 0바이트인 .txt 파일을 만든다
  2. 파일 > 열기로 그 파일을 연다
기대: 빈 문서가 열린다
실제: 응답 없음. 30초 뒤 다음 메시지와 함께 종료
  "fatal: buffer index out of range (0 >= 0)"
```

## 헷갈리기 쉬운 점

- QA 팀이 있으면 개발자는 테스트하지 않아도 된다?
  - 코드가 옳다는 것을 보이는 테스트는 프로그래머의 책임
- 블랙박스 테스트만 충분히 하면 된다?
  - 조합이 너무 많아 다 덮을 수 없음. 화이트박스로 코드 경로를 덮음
- "고침"이면 끝이다?
  - QA나 다른 사람이 현재 빌드에서 확인해 "닫힘"이 되어야 끝
- 오류는 스크린숏이면 충분하다?
  - 검색되도록 텍스트로도

## 정리

| 요소 | 핵심 |
| --- | --- |
| 테스트의 위치 | 개발 과정의 일부. 프로그래머의 책임 |
| 블랙박스 / 화이트박스 | 구현을 모르고 기능 시험 / 내부를 알고 경로를 덮음 |
| 버그 생명 주기 | 등록 → 우선순위·배정 → 수락 → 고침 → 확인 → 닫힘(또는 다시 엶) |
| 버그 추적 도구 | 중앙 목록 + 기록 보관소. 우선순위, 알림, 의존성, 검색 |
| 버그 보고서 | 재현 단계, 기대·실제, 환경, 오류 메시지는 텍스트로 |
