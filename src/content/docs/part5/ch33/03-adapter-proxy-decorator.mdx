- 다루는 것: 객체를 **감싸서** 인터페이스를 바꾸거나, 대신 서거나, 기능을 덧붙이는 패턴들. 그리고 구조와 알고리즘을 떼는 반복자
- 이 글에서 배우는 것: 어댑터, 프록시, 데코레이터, 반복자

## 어댑터

- 어떤 클래스가 주는 추상화가 지금 설계에 맞지 않는데 **고칠 수 없을** 때 **어댑터** (adapter) 클래스를 만듦
  - 나머지 코드가 쓰는 추상화를 제공하고, 원하는 추상화와 실제 코드를 이어 줌
- 주된 두 쓰임
  - 구현을 숨기고 원하는 인터페이스만 보여 줌. 어댑터가 뒤에서 구현 객체를 직접 만들어 가짐
  - 이미 있는 기능을 새 인터페이스로 쓰게 함. 어댑터가 생성자로 기존 객체를 받음
- 표준 라이브러리도 씀: `std::stack`, `std::queue`는 `std::deque`나 `std::list` 같은 컨테이너를 감싼 **컨테이너 어댑터**(18장)

### 예: 옛 온도계

- 고칠 수 없는 외부 라이브러리의 온도계가 "채널 번호를 받아 화씨의 10배를 정수로" 돌려줌
- 우리 코드는 "섭씨를 `double`로" 주는 `ITemperature`를 원함

```cpp
class ThermometerAdapter : public ITemperature {   // 원하는 인터페이스를 구현
public:
    ThermometerAdapter(const LegacyThermometer& t, int channel);
    double celsius() const override
    {
        double f{ m_device.read_fahrenheit_x10(m_channel) / 10.0 };
        return (f - 32.0) * 5.0 / 9.0;              // 호출 방식과 단위를 맞춤
    }
private:
    const LegacyThermometer& m_device;              // 감싼 기존 객체(합성)
    int m_channel;
};
```

- 어댑터는 원하는 인터페이스를 **구현**하고, 기존 객체를 **합성**으로 가짐
- 어댑터는 더 알맞은 인터페이스를 주려고 있는 것이므로 쓰는 법은 단순함. 사용하는 코드는 `ITemperature`만 앎

## 프록시

- **프록시** (proxy): 진짜 객체 **대신 서는** 객체. 클래스의 추상화를 아래 표현과 떼어 놓는 패턴 중 하나
- 진짜 객체를 쓰는 것이 오래 걸리거나 불가능할 때 씀
  - **가상 프록시**: 문서 편집기가 문서를 열 때 큰 그림들을 다 읽지 않고 프록시로 대신함. 사용자가 스크롤해 그림에 닿으면 그때 프록시가 진짜 그림 객체에 그리기를 맡기고, 그 객체가 그림을 읽음
  - **원격 프록시**: 네트워크 너머의 객체를 대신함. 연결이 끊기면 마지막으로 알던 상태를 보여 주는 등, 바탕 객체의 바람직하지 않은 동작(예외)을 숨김
  - **보호 프록시**: 일부 기능을 클라이언트로부터 막음. 프록시만 넘기면 캐스트로도 진짜 객체에 닿지 못함

```cpp
class LazyImage : public IImage {      // 진짜와 같은 인터페이스
public:
    std::string draw() const override
    {
        if (!m_real) {                 // 처음 그릴 때만 진짜를 만듦
            m_real = std::make_unique<DiskImage>(m_file);
        }
        return m_real->draw();         // 일을 진짜 객체에 넘김
    }
    std::string name() const override { return m_file; }   // 읽지 않고도 답함
private:
    std::string m_file;
    mutable std::unique_ptr<DiskImage> m_real;
};
```

- 잘 만든 프록시는 쓰는 쪽에서 진짜 객체와 구별되지 않음. 같은 인터페이스를 구현하기 때문
- `draw()`가 `const`인데 내부 상태(`m_real`)를 바꾸므로 `mutable`(9장). 겉보기 상태는 그대로

## 데코레이터

- **데코레이터** (decorator): 이름 그대로 클래스에 다는 "장식". 실행 중에 객체의 동작을 **보태거나 바꿈**
- 파생 클래스와 비슷하지만
  - 동적으로 바꿀 수 있고, 조합마다 파생 클래스를 만들지 않아도 **겹쳐** 쓸 수 있음
  - 바탕 클래스의 코드를 건드리지 않음(비침투적)
  - 대신 바꿀 수 있는 범위가 좁음. 예: 바탕 클래스의 도우미 멤버 함수를 재정의할 수 없음
- 예: 데이터 스트림을 파싱하다 그림 데이터를 만나면, 잠시 스트림을 그림 파서 데코레이터로 감싸 그림을 읽고, 끝나면 원래 스트림으로 계속

### 예: 글 꾸미기

- 글에 대문자, 느낌표, 따옴표를 원하는 조합으로 붙이고 싶음
  - 조합마다 파생 클래스(`UpperExclaimText`, `QuotedUpperText`, ...)를 만들면 꾸밈이 늘 때마다 **기하급수적**으로 늘어남
  - 꾸민 글을 "글의 종류"가 아니라 "꾸며진 글"로 봄: `Quote`가 `Upper`를, `Upper`가 `Exclaim`을, `Exclaim`이 `Plain`을 감쌈

		{ title: 'Exclaim', text: '안쪽 결과 뒤에 ! → "hello!"' },
		{ title: 'Upper', text: '안쪽 결과를 대문자로 → "HELLO!"' },

```cpp
class Decorator : public IText {                 // 데코레이터도 IText
public:
    explicit Decorator(std::unique_ptr<IText> inner);   // 감쌀 대상을 받음
protected:
    std::string inner() const { return m_inner->render(); }
private:
    std::unique_ptr<IText> m_inner;
};

class Exclaim : public Decorator {
public:
    using Decorator::Decorator;                  // 생성자 상속
    std::string render() const override { return inner() + "!"; }
};

std::unique_ptr<IText> t{ std::make_unique<Plain>("hello") };
t = std::make_unique<Exclaim>(std::move(t));
t = std::make_unique<Upper>(std::move(t));
```

- 데코레이터가 같은 인터페이스를 구현하므로 데코레이터를 다시 데코레이터로 감쌀 수 있음
- 감싼 대상을 **소유**할지(`unique_ptr`) **참조**만 할지(참조 멤버)는 설계 선택
  - 참조라면 감싼 대상이 바뀌면 데코레이터를 통해서도 바뀐 모습이 보임. 대신 수명을 바깥에서 보장해야 함
- 순서를 바꾸면 결과가 달라질 수 있음: `Exclaim(Quote(...))`는 `"hello"!`, `Quote(Exclaim(...))`는 `"hello!"`

## 반복자

- **반복자 패턴** (iterator pattern): 알고리즘·연산을 그것이 다루는 **자료 구조**에서 떼어 놓음. 반복자 덕분에 알고리즘이 실제 구조를 몰라도 자료를 따라갈 수 있음
- 데이터와 동작을 클래스로 묶는 객체 지향 원칙과 어긋나 보이지만, 기본 동작을 클래스에서 빼라는 것이 아님. 둘이 강하게 묶일 때 생기는 두 문제를 풂
  - **제네릭 알고리즘**을 쓸 수 없음: 여러 구조에서 돌려면 구조를 모른 채 내용을 따라가는 표준 수단이 필요함
  - **새 동작을 더하기 어려움**: 자료 클래스의 소스가 필요함. 고칠 수 없는 외부 라이브러리라면?
- 표준 라이브러리의 반복자가 이 패턴(17장)
  - 표준 반복자 인터페이스만 맞추면 어떤 컨테이너에서도 알고리즘이 돎
  - 한 구조에 여러 반복자를 둬서 다른 순서로 돌 수도 있음. 예: 트리를 위에서 아래로, 아래에서 위로
  - 연산은 반복자에 의존하고, 자료 객체는 반복자를 제공함. 반복자가 가운데에서 둘을 이어 줌
- 표준 라이브러리와 호환되는 반복자를 만드는 자세한 예는 25장
- 아래 예제의 `Countdown`은 아무것도 저장하지 않고 n, n-1, ..., 1을 내놓는 범위. 반복자만 갖추면 범위 기반 `for`와 `std::ranges::count_if`가 그대로 돎 <CppRef path="cpp/algorithm/ranges/count" />

## 헷갈리기 쉬운 점

- 어댑터와 데코레이터는 같다?
  - 어댑터는 인터페이스를 **바꿈**. 데코레이터는 같은 인터페이스로 **기능을 보탬**
- 프록시와 데코레이터는 같다?
  - 둘 다 같은 인터페이스로 감싸지만, 프록시는 접근을 **대신·통제**(미루기, 숨기기, 막기), 데코레이터는 **보태기**. 프록시는 보통 겹쳐 쓰지 않음
- 데코레이터 조합마다 파생 클래스가 필요하다?
  - 그것을 피하려는 패턴. 감싸서 조합함
- 반복자는 컨테이너에만 있다?
  - 저장하지 않는 범위(생성기, 스트림)도 반복자를 줄 수 있음

## 정리

| 패턴 | 하는 일 | 모양 |
| --- | --- | --- |
| 어댑터 | 인터페이스를 원하는 모양으로 | 새 인터페이스 구현 + 기존 객체 합성 |
| 프록시 | 대신 서서 미루기·숨기기·막기 | 같은 인터페이스 + 진짜 객체에 위임 |
| 데코레이터 | 실행 중에 기능을 겹쳐 보탬 | 같은 인터페이스 + 감싼 대상 호출 후 덧붙임 |
| 반복자 | 구조와 알고리즘 분리 | 구조가 반복자를 주고 알고리즘이 반복자를 씀 |
