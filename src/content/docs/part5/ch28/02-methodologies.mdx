- 다루는 것: 생명 주기 모델은 "다음에 무엇을 하나?"에 답하지만 "그것을 **어떻게** 하나?"에는 거의 답하지 못함. **방법론** (methodology)은 실무를 위한 구체적인 경험칙을 줌
- 이 글에서 배우는 것: 스크럼, 통합 프로세스(UP), RUP, 익스트림 프로그래밍(XP), 소프트웨어 트리아지

## 스크럼

- 애자일(1편)은 높은 수준의 바탕일 뿐 실제로 어떻게 할지는 정하지 않음. **스크럼** (Scrum)은 날마다 어떻게 쓰는지까지 정한 애자일 방법론. 업계에서 가장 많이 쓰이는 방법론 중 하나
- 반복 프로세스. 반복 하나가 **스프린트** (sprint). 스프린트가 스크럼의 중심
  - 길이는 프로젝트 시작 때 정하며 보통 **2주에서 4주**
  - 스프린트를 시작하기 전에 팀이 **스프린트 목표**를 정하고, 끝날 때 그것을 내놓기로 약속함
  - 스프린트가 끝날 때마다 고객 요구의 일부를 담은, 완전히 동작하고 테스트된 버전을 만드는 것이 목표
  - 고객은 개발 중에 마음을 자주 바꾸므로, 스프린트 결과를 고객에게 내놓을 수 있게 함. 고객은 반복되는 버전을 보며 피드백을 줌

### 역할

| 역할 | 하는 일 |
| --- | --- |
| **제품 책임자** (product owner) | 고객과 다른 사람들을 잇는 창구. 고객의 의견으로 높은 수준의 **사용자 스토리** (user story)를 쓰고 우선순위를 매겨 **제품 백로그** (product backlog)에 올림. 팀원 누구나 스토리를 쓸 수 있지만 무엇을 남기고 뺄지는 제품 책임자가 정함 |
| **스크럼 마스터** (Scrum master) | 프로세스가 잘 돌게 함. 팀의 리더는 아님(팀은 스스로 이끎). 팀의 연락 창구가 되어 다른 팀원이 일에 집중하게 하고, 일일 회의를 여는 등 스크럼을 제대로 따르게 함. 제품 책임자와 다른 사람이어야 함 |
| **팀** | 소프트웨어를 만듦. 작게, 되도록 10명 미만 |

### 진행

- **스프린트 계획 회의**: 새 스프린트에서 구현할 기능을 정해 **스프린트 백로그** (sprint backlog)로 만듦
  - 기능은 우선순위가 매겨진 사용자 스토리(새 기능의 높은 수준 요구 사항)를 담은 제품 백로그에서 고름
  - 사용자 스토리를 작업량을 추정한 작은 작업들로 나눠 스프린트 백로그에 올림
  - 시간은 스프린트 길이와 팀 크기에 따라 다르며, 대략 2주 스프린트마다 2~4시간
  - 보통 둘로 나눔: 제품 책임자와 팀이 제품 백로그 항목의 우선순위를 논의, 그다음 팀만 스프린트 백로그를 완성
- **스크럼 보드** (Scrum board, sprint board): 할 일, 진행 중, 끝남 세 칸
  - 작업마다 작은 종이에 써서 알맞은 칸에 붙임. 회의에서 사람에게 작업을 **배정하지 않음**. 팀원이 스스로 "할 일"에서 하나를 골라 "진행 중"으로 옮기고, 끝나면 "끝남"으로
  - 남은 일, 진행 중인 일, 끝난 일을 한눈에 봄. 소프트웨어로 만든 가상 보드도 씀
  - 칸은 팀에 맞게 더할 수 있음

| 칸 | 뜻 |
| --- | --- |
| 할 일 | 이번 스프린트에 계획했지만 아직 시작하지 않은 작업 |
| 진행 중 | 개발자가 개발 브랜치(3편)에서 작업 중 |
| 리뷰 중 | 구현을 끝내고 다른 팀원의 **코드 리뷰** (code review)를 기다림 |
| 테스트 중 | 리뷰를 마치고 품질 보증(QA) 팀의 승인 테스트를 기다림 |
| 통합 중 | 리뷰와 QA를 통과해 개발 브랜치를 주 코드에 합칠 수 있음. 그 브랜치의 모든 테스트가 성공할 때만 |
| 끝남 | 구현, 리뷰, 테스트, 통합을 모두 마침 |

- 작업은 **작게** 유지하기를 권함. 그러면 개발 브랜치도 짧게 삶
- **번다운 차트** (burn-down chart)를 날마다 그리기도 함: 가로축은 스프린트의 날, 세로축은 남은 개발 시간. 계획한 작업을 다 끝낼 수 있을지 빨리 봄
- **일일 스크럼** (daily Scrum, daily standup): 팀원 모두와 스크럼 마스터가 서서 하는 날마다의 회의
  - 같은 시간, 같은 장소에서, **15분 이내**. 스프린트 보드가 보이는 곳에서
  - 스프린트 목표까지의 진행을 보고, 막힌 점이나 늦어지는 점을 논의함. 필요하면 이번 스프린트에서 작업을 빼거나 더함
  - 보통 모두가 세 질문에 답함
    - 어제 스프린트 목표를 위해 무엇을 했나?
    - 오늘 무엇을 할 것인가?
    - 나나 팀이 목표에 닿는 것을 막는 장애물이 있나?
- 스프린트가 끝나면 회의 둘
  - **스프린트 리뷰**: 보통 2주 스프린트마다 2시간. 제품 관리자, 지원 엔지니어 같은 이해관계자에게 결과와 현재 소프트웨어를 **시연**함. 끝낸 작업, 못 끝낸 작업과 그 이유도 논의
  - **스프린트 회고** (retrospective): 보통 2주마다 1시간 반. 지난 스프린트를 어떻게 진행했는지 돌아봄. "무엇이 잘 됐나?", "무엇을 고칠 수 있나?", "무엇을 시작하고, 계속하고, 그만둘까?" 프로세스의 약점을 찾아 다음 스프린트에 반영. **지속적 개선** (continuous improvement)

### 장단점

- 장점
  - 개발 중 생기는 예상 밖의 문제에 강함. 문제가 생기면 다음 스프린트에서 다루면 됨
  - 팀이 모든 단계에 참여함: 제품 책임자와 사용자 스토리를 논의하고, 작업으로 나누고, 스스로 나눠 맡음. 보드와 일일 회의로 모두가 상황을 앎
  - 이해관계자는 스프린트마다 시연으로 진행을 빨리 보고 요구 사항을 바꿀 수 있음. 바뀐 요구는 대개 다음 스프린트에 넣음
- 단점
  - 누가 무엇을 할지 팀이 정한다는 것을 받아들이기 어려운 회사도 있음. 관리자나 팀장이 배정하지 않음
  - 스크럼 마스터가 핵심. 팀을 믿어야 하며, 팀원을 지나치게 통제하면 스크럼이 실패함
  - **기능 확장**: 개발 중 제품 백로그에 새 스토리를 더할 수 있으므로 관리자가 계속 기능을 더할 위험. 마지막 출시일이나 마지막 스프린트의 끝 날짜를 일찍 정해 막음

## 통합 프로세스

- **통합 프로세스** (Unified Process, UP): 반복적이고 점진적인 개발 프로세스. 고정된 것이 아니라 프로젝트에 맞게 고쳐 쓰는 **틀**
- 네 단계

| 단계 | 하는 일 |
| --- | --- |
| **도입** (inception) | 보통 아주 짧음. 타당성 검토, 사업 근거 작성, 직접 만들지 외부에서 살지 결정, 비용과 일정의 대략적 추정, 범위 정의 |
| **정련** (elaboration) | 요구 사항 대부분을 문서로 씀. 위험 요소를 다루고 시스템 아키텍처를 검증함. 검증하려고 아키텍처 핵심의 가장 중요한 부분을 실행 가능한 형태로 만들어, 그 아키텍처가 전체 시스템을 감당할 수 있음을 보임 |
| **구축** (construction) | 정련 단계의 실행 가능한 아키텍처 위에 모든 요구 사항을 구현 |
| **전환** (transition) | 제품을 고객에게 넘김. 고객 피드백은 이어지는 전환 반복에서 다룸 |

- 모든 단계가 **시간 상자** (time-boxed) 반복으로 나뉘고, 반복마다 눈에 보이는 결과가 있음
- 반복마다 여러 **분야** (discipline)를 동시에 진행함: 비즈니스 모델링, 요구 사항, 분석과 설계, 구현, 테스트, 배포. 분야별 작업량은 반복마다 달라짐
  - 예: 도입 1회, 정련 2회, 구축 4회, 전환 2회 반복. 초반에는 요구 사항과 설계가, 후반에는 테스트와 배포가 많음

## RUP

- **RUP** (Rational Unified Process): 통합 프로세스를 다듬은 것 중 가장 잘 알려진 것. 규율 있고 공식적인 방식
- 가장 큰 특징: 나선형이나 폭포수와 달리 이론적 모델에 그치지 않고, IBM의 Rational Software 부문이 파는 **소프트웨어 제품**이기도 함
- 프로세스 자체를 소프트웨어로 다루는 장점
  - 소프트웨어처럼 프로세스도 업데이트하고 다듬을 수 있음
  - 틀을 제안하는 데 그치지 않고 그 틀로 일할 도구를 함께 줌
  - 제품으로 팀 전체에 배포해, 모두가 똑같은 프로세스와 도구를 씀
  - 사용자의 필요에 맞게 고칠 수 있음

### 제품으로서

- 개발 과정을 안내하는 응용 프로그램 모음. 다른 Rational 제품(시각 모델링 도구 Rational Rose, 구성 관리 도구 Rational ClearCase)에 대한 안내도 있음. 지식을 나누는 협업 도구 포함
- 바탕 원칙: 개발 주기의 반복마다 **눈에 보이는 결과**가 있어야 함. 설계, 요구 사항 문서, 보고서, 계획 같은 산출물을 만들 시각화·개발 도구를 줌

### 프로세스로서

- 중심 원칙은 **정확한 모델**을 정의하는 것. 모델로 개발 과정의 복잡한 구조와 관계를 설명함. 주로 UML로 표현(부록 D)
- 과정의 각 부분을 **작업 흐름** (workflow)으로 정의함(UP의 "분야"): 누가 책임지는지, 무슨 작업을 하는지, 그 산출물, 작업을 이끄는 사건의 순서
- 기본으로 정의된 핵심 작업 흐름은 폭포수의 단계와 닮았지만 각각 반복적이고 더 구체적임

| 작업 흐름 | 다루는 것 |
| --- | --- |
| 비즈니스 모델링 | 사업 과정을 모델링해 소프트웨어 요구 사항을 이끎 |
| 요구 사항 | 시스템의 문제를 분석하고 가정을 반복해 요구 사항 정의를 만듦 |
| 분석과 설계 | 시스템 아키텍처와 하위 시스템 설계 |
| 구현 | 하위 시스템의 모델링, 코딩, 통합 |
| 테스트 | 품질 테스트의 계획, 구현, 평가 |
| 배포 | 계획, 출시, 지원, 테스트의 전체적인 모습 |
| 구성 관리 | 새 프로젝트 구상부터 반복, 제품 수명 끝까지 |
| 환경 | 개발 도구를 만들고 유지해 조직을 지원 |

### 실제로는

- 주로 **큰 조직**을 겨냥함. 소프트웨어 사용법을 익히고 나면 모두가 설계, 소통, 구현에 공통 플랫폼을 씀. 팀에 맞게 고칠 수 있고, 단계마다 개발을 기록한 산출물이 풍부하게 남음
- 어떤 조직에는 **너무 무거움**. 개발 환경이 다양하거나 예산이 빠듯한 팀은 소프트웨어 기반 개발 체계로 표준화하기 어려움
- 학습 곡선: 새 엔지니어는 제품과 기존 코드를 익히면서 동시에 프로세스 소프트웨어도 배워야 함

## 익스트림 프로그래밍

- **익스트림 프로그래밍** (Extreme Programming, XP): 1999년 켄트 벡(Kent Beck)이 널리 알림. 좋은 개발 관행들을 모으고, 그것을 **한 단계 더 극단으로** 밀어붙임
  - 예: 테스트가 좋다는 데는 누구나 동의함. XP에서는 테스트가 너무 좋아서 **코드보다 테스트를 먼저** 씀
- 12가지 원칙을 네 범주로 묶음. 개발 전 과정에 나타나며 엔지니어의 일상 업무에 직접 영향을 줌

### 범주 1: 잘게 자주 받는 피드백

- **짝 프로그래밍** (pair programming): 모든 제품 코드를 두 사람이 나란히 앉아 씀
  - 키보드는 한 사람만 잡음. 다른 사람은 짝이 쓰는 코드를 검토하며 테스트, 필요한 리팩터링, 프로젝트 전체 모델 같은 높은 수준을 생각함
  - 예: 어떤 기능의 UI를 맡았다면 그 기능의 원래 작성자와 함께 앉음. 올바른 쓰임과 함정을 알려 주고 높은 수준에서 지켜봐 줌. 원래 작성자가 아니어도 다른 팀원이면 도움이 됨
  - 지식을 함께 쌓고, 올바른 설계를 보장하며, 비공식적인 견제와 균형이 생김
- **계획 게임** (planning game): 계획을 한 번 하고 끝내지 않고 **끝없이** 함
  - 폭포수는 처음에 한 번, 나선형은 반복의 첫 단계. XP는 제품의 큰 줄기를 담은 대략적인 계획으로 시작해, 반복마다 계획 게임 회의를 열고 필요하면 계획을 다듬고 고침. 상황은 늘 바뀌고 새 정보가 계속 들어오기 때문
  - **출시 계획**: 개발자와 고객이 함께. 어떤 요구 사항을 어느 출시에 넣을지
  - **반복 계획**: 개발자만. 실제 작업을 계획
  - 기능의 추정은 늘 그 기능을 **구현할 사람**이 함. 비현실적인 일정을 강요받지 않게. 처음엔 몇 주 단위로 대략, 가까워질수록 세밀하게. 기능은 5일 이내의 작업으로 나눔
- **늘 테스트**: XP는 테스트에 열성적임. 자동화된 테스트가 없는 기능은 없는 것으로 봄
  - 코드와 함께 **단위 테스트** (unit test)를 쓰는 것이 XP 엔지니어의 책임. 단위 테스트: 기능 하나가 제대로 동작하는지 확인하는 작은 코드. 예: 파일 기반 객체 저장소라면 저장 테스트, 불러오기 테스트, 지우기 테스트
  - 한 걸음 더: 실제 코드보다 **테스트를 먼저** 씀. 처음엔 당연히 실패함. 이론상 테스트가 충분하면 모두 통과할 때 코드가 완성된 것. 다만 테스트가 충분한지 알기 어렵고, 좋은 테스트를 쓰는 것이 좋은 코드를 쓰는 것보다 훨씬 어려울 수 있음
  - 이것이 **테스트 주도 개발** (test-driven development, TDD)(30장)
- **고객이 현장에**: 계획을 계속 다듬고 지금 필요한 것만 만드므로 고객의 참여가 값짐. 고객이 늘 함께 있기는 어렵지만, 개발과 최종 사용자 사이의 소통은 분명 가치 있음. 기능 설계를 돕고, 필요를 알려 작업의 우선순위를 정하게 도움

### 범주 2: 끊임없는 과정

- **지속적 통합** (continuous integration): 하위 시스템을 자주 합쳐 어긋남을 일찍 찾음
  - 통합은 누구나 두려워하는 일. 내가 생각한 하위 시스템과 실제로 쓰인 것이 완전히 다를 때 악몽이 됨. 하위 시스템이 모일 때 문제가 드러나므로, 개발하는 동안 자주 프로젝트에 합침
  - 저장소에 넣기 전에 모든 테스트를 돌림. 또 전용 기계가 자동 테스트를 계속 돌리고, 실패하면 문제와 최근 변경 목록을 담은 이메일을 팀에 보냄
  - 개발 브랜치는 그 브랜치에서 모든 테스트가 성공했을 때만 주 코드에 합치도록 프로세스를 정하기를 권함
- **필요할 때 리팩터링**: **리팩터링** (refactoring)은 동작하는 코드를, 작성 후 알게 된 지식·새 API·다른 쓰임에 맞게 다시 설계하는 것
  - 새 기능처럼 결과가 눈에 보이지 않아 전통적인 일정에 넣기 어렵지만, 좋은 관리자는 장기 유지 보수에 중요함을 앎
  - XP 방식: 출시 초에 어디를 손볼지 정하지 않고, 개발 중 리팩터링할 때가 된 코드의 신호를 알아보고 그때 함. 계획에 없던 작업이 생기지만 앞으로의 개발이 쉬워짐
- **작게 출시**: 한 번에 너무 많은 것을 하려 하면 위험하고 다루기 어려워짐. 핵심을 바꾸는 거대한 출시 대신 18개월보다 2개월에 가까운 작은 출시. 짧은 주기에는 가장 중요한 기능만 들어가므로 개발과 마케팅이 무엇이 정말 중요한지 합의하게 됨

### 범주 3: 공유하는 이해

- **공통 코딩 표준**: 공동 소유와 짝 프로그래밍 때문에 사람마다 이름 짓기와 들여쓰기가 다르면 곤란함. XP는 특정 스타일을 권하지 않지만, 코드를 보고 작성자를 바로 알아볼 수 있다면 코딩 표준을 더 잘 정해야 한다고 봄(3장)
- **코드 공동 소유**: 많은 전통적 환경은 코드 소유를 엄격히 정함(다른 팀원 코드에 변경을 넣지 못하게 하는 관리자도 있음). XP는 정반대로 코드는 **모두가 함께** 소유한다고 선언함
  - 관리 면: 한 엔지니어가 갑자기 떠나도 그 코드를 아는 사람이 있어 타격이 적음. **버스 지수** (bus factor, bus number)가 커짐: 몇 명이 버스에 치여야 프로젝트가 멈추는가
  - 엔지니어 면: 시스템이 어떻게 동작하는지 공통 시각이 생겨 설계에 도움이 되고, 전체에 가치를 더하는 변경을 누구나 할 수 있음
  - 모두가 모든 줄을 알아야 한다는 뜻은 아님. 프로젝트는 팀의 일이고 누구도 지식을 쌓아 두고 혼자 가질 이유가 없다는 마음가짐
- **단순한 설계**: "추측성 일반화를 피하라", **KISS** (Keep It Simple, Stupid)
  - 많은 프로그래머의 본능과 반대임. 파일 기반 객체 저장소를 맡으면 모든 파일 저장 문제를 푸는 궁극의 해법을 만들고 싶어짐. 여러 언어, 모든 타입의 객체로 금세 커짐
  - XP는 일반성-구체성 사이에서 구체성 쪽으로 기울라고 함. 상을 받을 이상적인 저장소 대신, 일을 해내는 **가장 단순한** 저장소. 지금의 요구 사항을 이해하고 그에 맞게 써서 지나치게 복잡한 코드를 피함
  - 익숙해지기 어려울 수 있음. 코드가 몇 년 살아남아 상상도 못 한 곳에서 쓰일 수도 있음. 그러나 6장에서 본 대로, 미래에 쓸지 모를 기능을 넣는 문제는 그 가상의 쓰임을 모른다는 것. 순전히 추측으로 좋은 설계를 할 수 없음. 오지 않을 쓰임에 맞춘 설계가 정작 쓸모 있었을 다른 쓰임을 막기도 함
  - 오늘 쓸모 있는 것을 만들고, 나중에 고칠 여지를 남김
- **공통 은유** (metaphor): 고객과 관리자를 포함한 팀 전원이 시스템에 대해 같은 높은 수준의 그림을 공유함
  - 객체가 어떻게 소통하는지, 정확한 API가 무엇인지가 아니라 시스템 구성 요소에 대한 **머릿속 모델과 이름 체계**
  - 구성 요소마다 이름만 보고도 기능을 짐작할 수 있는 이름을 붙이고, 프로젝트를 논의할 때 그 이름으로 용어를 맞춤

### 범주 4: 프로그래머의 행복

- **건전한 근무 시간**: 잘 쉰 프로그래머가 행복하고 생산적임. 주 40시간 정도를 권하고, **2주 넘게 연속으로** 초과 근무하지 말라고 경고함
  - 필요한 휴식은 사람마다 다르지만, 머리가 맑지 않을 때 쓴 코드는 질이 나쁘고 XP 원칙도 많이 버리게 됨

### 실제로는

- XP 순수주의자는 12원칙이 서로 깊이 얽혀 있어 일부만 받아들이면 방법론이 망가진다고 주장함
  - 예: 짝 프로그래밍이 테스트에 중요함. 어떤 코드를 어떻게 테스트할지 모르면 짝이 도와줌. 피곤해서 테스트를 건너뛰려 할 때 짝이 있으면 죄책감이 듦
- 지키기 어려운 원칙도 있음
  - 테스트를 코드보다 먼저 쓰는 것이 너무 추상적인 엔지니어도 있음. 그러면 테스트를 설계만 해 두고 코드가 생긴 뒤에 써도 충분할 수 있음. 원칙의 바탕 이론을 이해하면 프로젝트에 맞게 바꿀 방법을 찾을 수 있음
- 협업도 어려울 수 있음
  - 짝 프로그래밍의 이점은 측정 가능하지만, 날마다 코드를 쓰는 사람이 절반이 되는 것을 관리자가 정당화하기 어려움
  - 남이 보는 앞에서 타이핑하기 불편한 사람도 있음. 내향적인 사람은 특히 싫어할 수 있음
  - 팀이 지리적으로 흩어져 있거나 원격 근무가 잦으면 어려움
- 공식 정책이 자리 잡은 큰 회사에는 너무 급진적일 수 있음. 회사가 XP를 받아들이지 않아도 그 이론을 이해하면 자기 생산성은 높일 수 있음

## 소프트웨어 트리아지

- 에드워드 요던(Edward Yourdon)은 일정이 밀리고, 인력이 모자라고, 예산을 넘기고, 설계가 엉성한 프로젝트가 흔하다고 말함. 이런 **죽음의 행군** (death march) 상태에서는 가장 좋은 현대 방법론도 통하지 않음
  - 많은 방법론이 공식 문서나 사용자 중심 설계를 바탕으로 하는데, 그럴 시간이 없음
- **소프트웨어 트리아지** (software triage): 프로젝트가 이미 나쁜 상태라 시간, 엔지니어, 돈이 모두 모자랄 때의 접근
  - 관리자와 개발자가 넘어야 할 가장 큰 마음의 장벽: 원래 요구 사항을 주어진 시간 안에 다 채우는 것은 **불가능하다**는 사실을 받아들이기
  - 남은 기능을 **꼭 있어야 함**, **있어야 함**, **있으면 좋음** 목록으로 나눔
- 어렵고 섬세한 과정이라, 어려운 결정을 내리려면 죽음의 행군을 겪어 본 외부의 노련한 사람이 이끄는 경우가 많음
- 엔지니어에게 중요한 점: 어떤 상황에서는 제때 끝내려고 익숙한 프로세스(어쩌면 기존 코드 일부도)를 버려야 할 수 있음

## 헷갈리기 쉬운 점

- 스크럼 마스터는 팀장이다?
  - 프로세스를 지키게 돕는 사람이지 팀을 이끄는 사람이 아님. 팀은 스스로 일을 고름
- 스크럼에서는 관리자가 작업을 배정한다?
  - 팀원이 보드에서 스스로 고름
- 짝 프로그래밍은 두 사람이 번갈아 같은 일을 하는 낭비다?
  - 한 사람은 쓰고, 다른 사람은 검토하며 높은 수준을 생각함. 지식 공유와 견제의 효과
- KISS는 앞날을 생각하지 말라는 뜻이다?
  - 추측으로 일반화하지 말고, 지금 필요한 것을 단순하게 만들되 나중에 고칠 여지를 남기라는 뜻
- 트리아지는 실패를 인정하고 포기하는 것이다?
  - 모든 것을 할 수 없다는 현실을 받아들이고, 꼭 필요한 것부터 확실히 끝내는 전략

## 정리

| 방법론 | 핵심 |
| --- | --- |
| 스크럼 | 2~4주 스프린트. 제품 책임자, 스크럼 마스터, 팀. 백로그, 스크럼 보드, 일일 회의, 리뷰, 회고 |
| 통합 프로세스 | 도입, 정련, 구축, 전환. 시간 상자 반복, 여러 분야를 동시에 |
| RUP | UP를 다듬은 제품이자 프로세스. 모델(UML)과 작업 흐름. 큰 조직용, 무거움 |
| XP | 12원칙: 짝 프로그래밍, 계획 게임, TDD, 고객 참여, 지속적 통합, 리팩터링, 작은 출시, 코딩 표준, 공동 소유, 단순한 설계, 공통 은유, 건전한 근무 시간 |
| 트리아지 | 죽음의 행군에서 기능을 꼭/있어야/있으면 좋음으로 나눠 꼭 필요한 것부터 |
