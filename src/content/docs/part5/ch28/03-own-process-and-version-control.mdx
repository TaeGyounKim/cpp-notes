## 나만의 프로세스와 방법론 만들기

- 어떤 책이나 공학 이론도 내 프로젝트나 조직에 꼭 맞기는 어려움. 여러 접근법에서 최대한 배워 **자기 프로세스를 설계**하기를 권함
- 여러 접근법의 개념을 섞는 것은 생각보다 쉬울 수 있음. 예: RUP는 선택적으로 XP 같은 방식을 지원함

### 새 아이디어에 열려 있기

- 처음엔 터무니없거나 안 될 것처럼 보이는 기법도 있음. 새 방법론을 지금 프로세스를 다듬을 기회로 봄
- 할 수 있으면 해 봄. XP가 흥미롭지만 우리 조직에 맞을지 모르겠다면, 원칙 몇 개씩 천천히 들여오거나 작은 **시범 프로젝트**로 시험해 봄

### 새 아이디어를 가져오기

- 팀원들의 배경은 다양함: 스타트업 경력자, 오랜 컨설턴트, 갓 졸업한 사람, 박사
- 저마다 다른 경험과 프로젝트 운영에 대한 생각이 있음. 가장 좋은 프로세스는 이런 서로 다른 환경의 방식을 섞은 것으로 판명되기도 함

### 잘 되는 것과 안 되는 것을 알아보기

- 프로젝트가 끝날 때, 더 좋게는 진행 중에(스크럼의 회고처럼) 팀이 모여 프로세스를 평가함
  - 팀 전체가 멈춰 생각해 보기 전까지 아무도 몰랐던 큰 문제가 있을 수 있음
  - 모두 알지만 아무도 말하지 않은 문제가 있을 수 있음
- 안 되는 것은 어떻게 고칠지 생각함
  - 예: 저장소에 넣기 전 공식 코드 리뷰가 필수인데, 너무 길고 지루해서 아무도 제대로 하지 않는다면 리뷰 방식을 팀이 함께 논의
- 잘 되는 것은 어떻게 넓힐지 생각함
  - 예: 함께 고치는 위키로 기능 작업을 관리하는 것이 잘 된다면 그 사이트를 더 낫게 만드는 데 시간을 씀

### 프로세스를 무시하지 않기

- 관리자가 정했든 팀이 만들었든 프로세스에는 이유가 있음
- 공식 설계 문서를 쓰기로 했다면 꼭 씀
- 프로세스가 고장 났거나 너무 복잡하다고 생각되면 관리자와 이야기함. 그냥 피해 가면 나중에 반드시 문제로 돌아옴

## 버전 관리

- 소스 코드 전체를 관리하는 일은 회사가 크든 작든, 혼자 하는 프로젝트에서도 중요함
  - 회사에서 모든 코드를 개발자 각자의 컴퓨터에만 두고 관리하지 않으면, 모두가 늘 최신 코드를 갖지 못해 **유지 보수의 악몽**이 됨
  - 모든 소스 코드는 **버전 관리 소프트웨어** (version control software)로 관리해야 함
- 혼자 하는 프로젝트에도 강력히 권함

### 방식 셋

| 방식 | 설명 |
| --- | --- |
| **로컬** (local) | 모든 파일과 이력을 내 컴퓨터에만 저장. 팀에는 맞지 않음. 1970~80년대 방식으로 이제는 쓰지 않음 |
| **클라이언트/서버** (client/server) | 서버 쪽과 클라이언트 쪽으로 나뉨. 개인이라면 둘을 한 컴퓨터에서 돌려도 되고, 필요하면 서버 쪽을 전용 서버로 옮기기 쉬움 |
| **분산** (distributed) | 중앙 저장소가 없음. 모든 개발자가 이력까지 포함한 모든 파일의 사본을 가짐. 동료끼리(peer-to-peer) **패치**를 주고받아 동기화 |

- 클라이언트/서버
  - 서버 소프트웨어: 중앙 서버에서 돌며 모든 파일과 그 이력을 관리함
  - 클라이언트 소프트웨어: 개발자마다 설치. 서버와 통신해 최신 버전이나 이전 버전을 가져오고, 로컬 변경을 서버에 올리고, 이전 버전으로 되돌리는 등의 일을 함
- 분산
  - 중앙 서버 없이 동료끼리 패치를 주고받음
  - 커밋, 되돌리기 같은 흔한 작업이 **빠름**: 중앙 서버에 네트워크로 접근하지 않으므로
  - 단점: 모든 파일과 전체 이력을 저장하므로 각 컴퓨터에 공간이 더 필요함

### 용어

- 시스템마다 고유한 용어가 있고 다 같지는 않음. 흔히 쓰는 것들

| 용어 | 뜻 |
| --- | --- |
| **브랜치** (branch) | 여러 버전을 나란히 개발함. 예: 출시한 버전마다 브랜치를 만들어 그 버전의 버그를 고치고, 새 기능은 주 브랜치(흔히 트렁크 trunk)에 넣음. 출시 브랜치의 버그 수정을 주 브랜치에 합치기도 함 |
| **체크아웃** (check out) | 중앙 서버나 동료에게서 개발자 컴퓨터에 로컬 사본을 만듦 |
| **체크인, 커밋, 머지, 푸시** (check in, commit, merge, push) | 로컬 사본을 고쳐 로컬에서 잘 동작하면, 그 변경을 중앙 서버(나 동료)로 올림 |
| **충돌과 해결** (conflict, resolve) | 여러 개발자가 같은 파일의 겹치는 곳을 고치면 커밋할 때 충돌이 날 수 있음. 도구가 자동으로 풀려 하고, 안 되면 사용자에게 직접 풀게 함 |
| **레이블, 태그** (label, tag) | 어느 시점의 모든 파일이나 특정 커밋에 사람이 읽을 이름을 붙임. 그 시점의 코드로 쉽게 돌아감 |
| **저장소** (repository) | 버전 관리가 관리하는 모든 파일과 이력. 커밋마다 언제, 누가, 왜(커밋 메시지) 했는지 같은 메타데이터도 포함 |
| **리비전, 버전** (revision, version) | 어느 시점의 파일 내용 스냅숏. 되돌리거나 비교하는 기준점 |
| **업데이트, 동기화** (update, sync) | 로컬 사본을 서버나 동료의 버전에 맞춤. 상류(upstream) 코드를 내 로컬 변경과 합쳐야 하므로 충돌이 날 수 있음 |
| **작업 사본** (working copy) | 개발자 개인 컴퓨터의 로컬 사본 |

### 도구

| 방식 | 무료/오픈 소스 | 상용 |
| --- | --- | --- |
| 로컬 | SCCS, RCS | PVCS |
| 클라이언트/서버 | CVS, Subversion | IBM Rational ClearCase, Azure DevOps Server, Perforce |
| 분산 | Git, Mercurial, Bazaar | TeamWare, BitKeeper, Plastic SCM |

- 빠짐없는 목록이 아니라 어떤 것이 있는지 감을 잡기 위한 예
- 특정 도구를 권하지는 않음. 요즘 대부분의 회사에는 이미 버전 관리 시스템이 있고 개발자는 그것을 써야 함
  - 없다면 시간을 들여 알맞은 것을 골라야 함. 버전 관리가 없으면 유지 보수의 악몽이 됨
- 개인 프로젝트에도 써 보기를 권함. 버전과 변경 이력을 자동으로 남겨, 변경이 잘못되면 이전 버전으로 쉽게 돌아감

:::note
이 사이트 자체도 Git으로 관리한다. 글 하나를 마칠 때마다 커밋하고, 원격 저장소에 푸시하면 자동으로 빌드되어 공개된다.
:::

## 헷갈리기 쉬운 점

- 남의 방법론을 그대로 들여와야 효과가 있다?
  - 팀에 맞게 섞고 고치는 것이 보통. 시범 적용으로 시험
- 프로세스가 비효율적이면 조용히 건너뛰어도 된다?
  - 이유가 있어 만든 것. 문제를 관리자와 팀에 꺼내 고침
- 혼자 하는 프로젝트에는 버전 관리가 필요 없다?
  - 이전 버전으로 돌아가고 변경 이력을 보는 것만으로도 큰 도움
- 분산 버전 관리에는 서버가 전혀 없다?
  - 꼭 필요한 중앙이 없다는 뜻. 실제로는 공유하려고 공용 원격 저장소를 두는 경우가 많음
- 충돌은 도구가 다 알아서 푼다?
  - 자동으로 풀 수 없는 겹침은 사람이 직접 풀어야 함

## 정리

| 요소 | 핵심 |
| --- | --- |
| 프로세스 만들기 | 새 아이디어에 열려 있기, 아이디어 가져오기, 잘 되는 것·안 되는 것 평가, 프로세스를 무시하지 않기 |
| 버전 관리 | 크든 작든, 혼자여도 필수 |
| 방식 | 로컬(쓰지 않음), 클라이언트/서버, 분산 |
| 용어 | 브랜치, 체크아웃, 커밋·푸시, 충돌과 해결, 태그, 저장소, 리비전, 동기화, 작업 사본 |

## 복습 질문

<details>
<summary>출시한 1.0의 버그를 고치면서 2.0 기능도 계속 개발하려면 브랜치를 어떻게 쓰는가?</summary>

- 1.0 출시 시점에 출시 브랜치를 만들어 그 브랜치에서 버그를 고침
- 새 기능은 주 브랜치에서 개발하고, 1.0 브랜치의 버그 수정은 주 브랜치에도 합침

</details>

<details>
<summary>분산 버전 관리에서 커밋이 빠른 이유와 그 대가는?</summary>

- 커밋과 되돌리기가 내 컴퓨터의 저장소에서 일어나 네트워크로 중앙 서버에 접근하지 않음
- 대신 모든 파일과 전체 이력을 각 컴퓨터에 저장하므로 저장 공간이 더 필요함

</details>

<details>
<summary>팀 회고에서 "코드 리뷰가 너무 오래 걸려 다들 대충 승인한다"는 문제가 나왔다. 무엇을 할 수 있는가?</summary>

- 리뷰를 없애기보다 방식을 함께 고침: 변경을 작게 나눠 리뷰를 짧게, 확인할 점 목록을 정하기, 자동 검사(포맷, 정적 분석, 테스트)를 먼저 돌려 사람은 설계와 논리에 집중하기 등

</details>

## 28장을 마치며

- 소프트웨어 개발 과정의 여러 모델과 방법론을 소개함. 공식적이든 비공식적이든 소프트웨어를 만드는 방법은 이 밖에도 많음
- 소프트웨어 개발의 단 하나의 올바른 방법은 없음. **우리 팀에 맞는 방법**이 있을 뿐
  - 찾는 법: 스스로 조사하고, 여러 방법에서 배우고, 동료의 경험을 듣고, 프로세스를 반복해서 다듬음
  - 프로세스를 평가할 때 중요한 기준은 단 하나: 팀이 코드를 쓰는 데 얼마나 도움이 되는가
- 버전 관리의 개념을 봄. 크든 작든 모든 소프트웨어 회사의 기본이며 개인 프로젝트에도 이로움. 무료·상용 도구가 많으니 몇 가지 써 보고 맞는 것을 고름
