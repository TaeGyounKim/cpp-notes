- 다루는 것: Part 5(소프트웨어 공학)의 시작. 이 Part는 공학 방법, 코드 효율, 테스트, 디버깅, 설계 기법, 디자인 패턴, 여러 플랫폼 대상 개발을 다룸
- 이 장(28장)은 여러 소프트웨어 공학 접근법을 **넓게** 훑어 서로 비교할 수 있게 함. 어느 하나를 권하거나 깎아내리지 않음. 장단점을 알고 팀에 맞는 프로세스를 만드는 것이 목적
- 이 글에서 배우는 것: 프로세스가 필요한 이유, 폭포수 모델, 사시미 모델, 나선형 모델, 애자일

## 왜 프로세스가 필요한가

- 처음 프로그래밍을 배울 때는 자기 일정대로 함. 마지막 순간에 몰아서 해도 되고, 구현하다 설계를 확 바꿔도 됨
- 실무에서는 그렇게 할 수 없음. 아무리 자유로운 관리자도 어느 정도의 **프로세스** (process)는 필요하다고 인정함. 요즘은 소프트웨어 공학 프로세스를 아는 것이 코딩만큼 중요함
- 소프트웨어 개발의 역사는 실패한 프로젝트로 가득함: 예산 초과, 팔리지 않은 제품, 거창하게 홍보했다 무너진 운영체제 등
  - 사용자에게 닿더라도 버그가 흔해 끝없이 업데이트와 패치를 받아야 함
  - 해야 할 일을 못 하거나 사용자가 기대한 대로 동작하지 않기도 함
  - 결론: 소프트웨어를 만드는 일은 **어렵다**

### 소프트웨어 공학은 무엇이 다른가

- 자동차가 버퍼 오버플로로 갑자기 멈춰 재부팅을 요구하는 일은 드물고, TV 채널을 보려고 2.3 버전으로 업그레이드할 필요도 없음. 왜 소프트웨어만 이렇게 자주 실패할까?

| 원인 | 설명 |
| --- | --- |
| 빠른 기술 변화 | 컴퓨터 기술이 빨리 바뀌어 개발 과정이 불확실함. 경쟁이 치열해 빨리 만들어야 함 |
| 예측하기 어려운 일정 | 까다로운 버그 하나를 고치는 데 며칠, 몇 주가 걸릴 수 있음 |
| 범위 확장 | 제품 정의가 계속 바뀌는 **기능 확장** (feature creep, scope creep). 내버려 두면 결국 **소프트웨어 비대화** (software bloat) |
| 복잡함 | 프로그램에 버그가 없음을 쉽고 정확하게 증명할 방법이 없음 |
| 유지 보수의 짐 | 지저분한 코드는 여러 버전에 걸쳐 오래 영향을 줌. 사람이 바뀌면 아무도 레거시 코드에 다가가려 하지 않아 땜질과 우회가 끝없이 이어짐 |
| 일반 사업 위험 | 마케팅 압박, 소통 실패, 개발 조직과 제품·마케팅 조직 사이의 갈등 |

- 그래서 크고 복잡하고 빠르게 움직이는 소프트웨어 프로젝트를 다스릴 **체계**가 필요함
- 깔끔하고 유지 보수하기 좋은 코드로 잘 설계된 소프트웨어를 만드는 것은 가능함. 다만 팀원 모두의 꾸준한 노력과 알맞은 개발 프로세스·관행을 따르는 것이 필요함

## 소프트웨어 생명 주기 모델

- **생명 주기 모델** (life cycle model): 처음 아이디어부터 최종 제품까지의 과정을 단계로 정의해 개발의 혼란에 질서를 주려는 시도
- 수십 년에 걸쳐 다듬어져 오늘날 개발의 많은 부분을 이끎

### 폭포수 모델

- **폭포수 모델** (waterfall model): 고전적인 생명 주기 모델. 요리법을 따라 하듯 정해진 단계를 제대로 밟으면 제품이 나온다는 생각
  - 한 단계를 **끝내야** 다음 단계를 시작함. 폭포처럼 아래로만 내려감

	steps={[
		{ title: '계획', text: '요구 사항을 빠짐없이 모음. 기능의 완성 기준' },
		{ title: '설계', text: '모든 설계 결정을 내리고 하위 시스템과 그 상호 작용을 정함' },
		{ title: '구현', text: '설계를 그대로 코드로' },
		{ title: '테스트', text: '단위, 하위 시스템, 통합 테스트' },
		{ title: '평가', text: '완성된 제품을 평가' },
	]}
/>

- 요구 사항과 설계는 **최대한 구체적일수록** 성공할 가능성이 큼
  - 설계 단계에서 의사 코드, 하위 시스템 정의까지 함. 하위 시스템 담당자들이 코드끼리 어떻게 맞물릴지 정하고, 팀이 아키텍처의 세부에 합의함
- 구현은 완전히 정해진 설계를 꼭 따라야 함. 그러지 않으면 조각들이 맞지 않음
- 마지막 네 단계: 단위 테스트, 하위 시스템 테스트, 통합 테스트, 평가
- 변형: 공식 요구 사항을 모으기 전에 실험을 해 보는 "타당성 검토" 단계를 넣기도 함

#### 장점

- **단순함**. 이름을 몰라도 이미 이렇게 해 본 사람이 많음
- 바탕 가정: 각 단계를 최대한 완전하고 정확하게 끝내면 다음 단계가 순조로움
  - 요구 사항을 모두 꼼꼼히 정하고 설계 결정과 문제를 다 풀어 두면, 구현은 설계를 코드로 옮기기만 하면 됨
- 계획이 체계적이고 관리하기 쉬움
  - 예: 설계 단계가 끝날 때 하위 시스템 담당자마다 공식 설계 문서나 기능 명세를 내게 할 수 있음. 관리자 입장에서는 위험이 (이론상) 줄어듦
- 엔지니어 입장: 큰 문제를 먼저 풀게 강제함. 코드를 많이 쓰기 전에 프로젝트를 이해하고 하위 시스템을 설계하므로, 조각이 맞지 않아 땜질하거나 다시 쓸 일이 줄어듦
- 요구 사항이 아주 명확한 **작은** 프로젝트에 잘 맞음. 특히 외주 계약에서는 처음부터 성공 기준이 분명해, 고객이 원하는 것을 정확히 만들고 고객도 목표를 구체적으로 정하게 됨

#### 단점

- 많은 조직과 거의 모든 현대 소프트웨어 공학 교재에서 인기를 잃음
  - 핵심 전제인 "개발 작업은 따로 떨어진 직선 단계로 일어난다"가 비판받음
  - 보통 **뒤로 돌아가기**를 허용하지 않음. 그런데 요즘은 개발 도중 새 요구 사항이 계속 들어옴(판매에 꼭 필요한 기능을 고객이 요구하거나, 경쟁 제품에 생긴 기능을 따라가야 함)
- 실제로는 다음 단계를 조금이라도 살펴보지 않고 한 단계를 끝낼 수 없음
  - 코드를 조금이라도 써 보지 않고 설계를 확정할 수 없음
  - 테스트에서 버그가 나오면 모델이 허용하든 말든 "폭포를 거슬러" 다시 코딩해야 함
- 결정을 최대한 공식적으로, 일찍 내려 위험을 줄이려다 오히려 **위험을 숨길** 수 있음
  - 큰 설계 문제가 설계 단계에서 발견되지 않거나, 대충 넘어가거나, 잊히거나, 일부러 피해짐. 통합 테스트에서야 드러나면 폭포를 거슬러 올라가야 함
  - 어디서든 실수하면 끝에 가서 일정이 늦어짐. 일찍 발견하기 어렵고 드묾
- 폭포수 모델을 쓴다면 다른 접근법에서 아이디어를 빌려 유연하게 만드는 경우가 많음

:::note
모든 요구 사항을 처음에 정해야 하는 점 때문에, 변화에 빠르게 대응해야 하는 많은 조직에서는 폭포수 모델을 쓰기 어렵다.
:::

### 사시미 모델

- 폭포수 모델을 다듬은 것 중 하나. **단계가 겹치는** 개념을 들여옴
  - 이름은 생선 조각을 겹쳐 담는 일본 요리 사시미에서 옴
- 계획, 설계, 코딩, 테스트의 엄격한 과정은 그대로지만, 이어지는 단계가 **일부 겹칠** 수 있음
- 두 단계의 활동을 동시에 할 수 있음. 다음 단계를 어느 정도 살펴보지 않고는 한 단계를 끝낼 수 없다는 현실을 인정함

| 시간 → | 초반 | 중반 | 후반 |
| --- | --- | --- | --- |
| 계획 | ■■■ | ■ | |
| 설계 | ■ | ■■■ | |
| 구현 | | ■■■ | ■ |
| 테스트·평가 | | ■ | ■■■ |

### 나선형 모델

- **나선형 모델** (spiral model): 1986년 배리 보엠(Barry W. Boehm)이 제안한 **위험 중심** 개발 프로세스. 여러 변형이 있어 **나선형 계열 모델** (spiral-like models)이라고 부름
- **반복 프로세스** (iterative process) 계열. 기본 생각: 무언가 잘못되어도 괜찮음. 다음 반복에서 고치면 되므로
- 한 바퀴의 네 단계(폭포수의 단계와 비슷함)

	steps={[
		{ title: '발견', text: '요구 사항, 목표, 대안(설계 대안, 재사용, 외부 라이브러리 구입 등), 제약을 찾음' },
		{ title: '평가', text: '구현 대안을 평가하고 위험을 분석함. 시제품도 고려. 위험을 평가하고 해결하는 데 특히 신경 씀' },
		{ title: '개발', text: '평가에서 찾은 위험으로 할 일을 정함. 가장 위험한 작업을 이번 바퀴에 구현' },
		{ title: '분석', text: '이번 바퀴의 결과로 다음 바퀴의 계획을 세움' },
	]}
/>

- 예: 운영체제를 만든다면
  1. 첫 바퀴: 주요 요구 사항을 담은 계획
  2. 둘째 바퀴: 사용자 경험을 보여 주는 시제품
  3. 셋째 바퀴: 위험이 크다고 판단된 기능 A를 만듦

#### 장점

- 폭포수 모델의 좋은 점에 **반복**을 더한 것으로 볼 수 있음. 반복하는 폭포수
- 폭포수의 두 약점인 숨은 위험과 직선 진행이 반복 주기로 풀림
- **가장 위험한 일을 먼저** 함. 위험을 앞에 꺼내 놓고 새 상황이 언제든 생길 수 있음을 인정하므로, 폭포수의 숨은 시한폭탄을 피함. 예상 밖의 문제도 같은 네 단계로 다룸
- 테스터의 피드백을 반영할 수 있음. 이른 버전을 내부나 외부에 내놓고 "이 기능이 없다", "이 기능이 기대대로 동작하지 않는다" 같은 의견을 받으면 다음 바퀴에서 대응함
- 바퀴마다 분석하고 새로 설계하므로 "설계한 뒤 구현" 방식의 현실적 어려움이 거의 사라짐. 바퀴를 돌수록 시스템에 대한 지식이 쌓여 설계에 반영됨

#### 단점

- 각 반복을 **충분히 작게** 정하기 어려움. 최악이면 반복이 너무 길어져 폭포수 모델로 돌아감
  - 모델은 생명 주기만 설명할 뿐, 프로젝트를 한 바퀴짜리로 나누는 방법은 정해 주지 않음(프로젝트마다 다르므로)
- 바퀴마다 네 단계를 모두 반복하는 부담
- 바퀴를 맞추기 어려움
  - 설계 논의에 모든 사람을 알맞은 때에 모으기 어려움
  - 여러 팀이 제품의 다른 부분을 동시에 만들면 바퀴가 어긋남. 예: UI 팀은 창 관리자 바퀴의 발견 단계를 시작하려는데, 핵심 OS 팀은 아직 메모리 하위 시스템의 개발 단계에 있음
- 전체 일정 계획: 네 단계를 계속 반복한다면 언제 멈추나? 보통 관리자가 끝낼 조건을 정하고 그 근거를 대야 함

## 애자일

- 폭포수 모델의 단점을 해결하려고 2001년 **애자일 선언** (Agile Manifesto)과 함께 등장
- 선언의 요지(원문은 agilemanifesto.org): 직접 개발하고 다른 사람을 도우며 더 나은 개발 방법을 찾아 왔고, 그 결과 다음을 더 중요하게 여기게 되었다

| 더 중요하게 | 보다 |
| --- | --- |
| 개인과 상호 작용 | 프로세스와 도구 |
| 동작하는 소프트웨어 | 포괄적인 문서 |
| 고객과의 협력 | 계약 협상 |
| 변화에 대응하기 | 계획 따르기 |

- 오른쪽에도 가치가 있지만 왼쪽을 더 중시한다는 뜻
- "애자일"은 높은 수준의 설명일 뿐: 개발 도중 고객의 변경을 쉽게 반영하도록 프로세스를 유연하게 만들라는 것
- 가장 널리 쓰이는 애자일 방법론 중 하나가 **스크럼**(2편)

## 헷갈리기 쉬운 점

- 폭포수 모델은 아무 데도 쓸모가 없다?
  - 요구 사항이 아주 명확한 작은 프로젝트, 성공 기준을 먼저 정해야 하는 계약에서는 잘 맞음
- 사시미 모델은 단계를 없앤 것이다?
  - 단계는 그대로이고, 이어지는 단계가 일부 겹치게 허용한 것
- 나선형 모델은 쉬운 일부터 끝낸다?
  - 위험이 가장 큰 일을 먼저 함
- 반복만 하면 저절로 나선형의 이점을 얻는다?
  - 반복을 충분히 작게 나눠야 함. 너무 길면 폭포수와 같아짐
- 애자일은 계획과 문서를 버리라는 뜻이다?
  - 그것들에도 가치가 있지만, 사람·동작하는 소프트웨어·협력·변화 대응을 **더** 중시한다는 뜻

## 정리

| 모델 | 핵심 | 장점 | 단점 |
| --- | --- | --- | --- |
| 폭포수 | 단계를 끝내야 다음으로. 뒤로 가지 않음 | 단순, 관리 쉬움, 큰 문제를 먼저 풂 | 변화에 약함, 위험을 숨김, 늦게 발견 |
| 사시미 | 폭포수 + 단계 겹침 | 현실에 더 맞음 | 여전히 직선적 |
| 나선형 | 발견·평가·개발·분석을 반복. 위험 먼저 | 위험을 드러냄, 피드백 반영 | 반복 크기 정하기, 바퀴 맞추기, 끝내기 |
| 애자일 | 유연한 프로세스. 변화를 반영 | 고객 변경에 대응 | 높은 수준의 가치일 뿐. 구체적 방법론이 필요 |

## 복습 질문

<details>
<summary>고객이 개발 중에 요구 사항을 자주 바꾸는 사내 도구 프로젝트에 폭포수 모델이 맞지 않는 이유는?</summary>

- 폭포수는 처음에 요구 사항을 모두 정하고 뒤로 돌아가지 않는다는 전제라, 바뀐 요구 사항을 반영하려면 설계·구현 단계를 다시 거슬러 올라가야 함
- 반복하는 모델(나선형, 애자일 방법론)이 변경을 다음 반복에 자연스럽게 넣을 수 있음

</details>

<details>
<summary>나선형 모델에서 "새 압축 알고리즘이 정말 목표 속도를 낼 수 있을지 모름"이라는 위험은 어떻게 다루는가?</summary>

- 평가 단계에서 가장 큰 위험으로 꼽고, 이번 바퀴의 개발 단계에서 그 알고리즘을 먼저 모델링·구현·테스트함. 결과에 따라 분석 단계에서 다음 바퀴 계획(대안 알고리즘 등)을 세움

</details>

<details>
<summary>"기능 확장"(feature creep)이 프로젝트에 해로운 이유는?</summary>

- 제품 정의가 계속 늘어나 일정을 예측할 수 없게 만들고, 내버려 두면 쓰지 않는 기능으로 가득한 비대한 소프트웨어가 됨

</details>
